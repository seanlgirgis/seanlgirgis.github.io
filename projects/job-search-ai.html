Why It Was Built

Searching for a senior data engineering role means tailoring every resume, every cover letter, and researching every company before applying. Done manually across dozens of applications, that's a full-time job stacked on top of the actual job search. The goal was to build a system that handles the repetitive, mechanical work — so judgment and attention can go to the parts that actually need them: the interview, the conversation, the preparation.

The design principle is not "automate the application" in a spray-and-pray sense. It's "automate the craft" — produce tailored, high-quality, grounded documents for each role with the same care a senior engineer would apply manually, just at a fraction of the time cost. Every output is reviewed before submission. The pipeline removes the friction, not the judgment.

The pipeline is not a bot that fires off applications automatically. It produces a production-ready folder — resume, cover letter, company research — and the human decides whether to submit.

Pipeline Mental Model

The right mental model is a data pipeline where the input is a raw job posting and the output is a tailored, production-ready application package tracked in a structured system. Ten stages run in sequence, orchestrated by a single Python script. Drop in a job posting URL or text, run one command, and get back a folder with everything needed to apply.

StageNameWhat It Does
00Duplicate GateFAISS semantic similarity check against all previously processed jobs
01Job ScoringRAG-based match score, skill gap analysis, and recommendation via Grok
02Intake DecisionAccept or reject based on score threshold; rejected jobs are logged but not processed
03Job TailoringExtract structured YAML: skills, qualifications, seniority signals, culture indicators
04Resume IntermediateGenerate tailored JSON resume — select and rewrite bullets to match role keywords
05Resume RenderRender JSON to production-ready DOCX + Markdown preview

08Cover RenderRender cover letter to DOCX; classify employer type (agency vs direct) and adjust tone

The orchestrator is scripts/10_auto_pipeline.py — a single script that runs each stage as a subprocess, passes the job UUID as context, and halts immediately on any stage failure.

Stage 00 — Duplicate Detection

Before any LLM call is made, the pipeline runs a semantic duplicate check. Companies repost the same role continuously across LinkedIn, Indeed, and their own careers page. Without a gate, the pipeline would consume API credits and processing time on jobs already in the tracker. Stage 00 uses FAISS with locally running sentence-transformer embeddings to compare the incoming job description against every job already in the index.

The embedding model is all-MiniLM-L6-v2 from the sentence-transformers library, running entirely on-device with no cloud API call. The FAISS index is persisted to disk and rebuilt in seconds whenever a new job is accepted into the pipeline. If the cosine similarity between the new posting and any existing job exceeds the configured threshold, the pipeline blocks at stage 00 and logs the potential duplicate for review.

# Stage 00 — semantic duplicate check (simplified)
from sentence_transformers import SentenceTransformer
import faiss, numpy as np

model = SentenceTransformer("all-MiniLM-L6-v2")
index = faiss.read_index("data/faiss/jobs.index")

embedding = model.encode([new_job_text])
D, I = index.search(np.array(embedding, dtype="float32"), k=1)
similarity = 1 - D[0][0]   # cosine similarity

if similarity > DUPLICATE_THRESHOLD:
    raise DuplicateJobError(f"Similarity {similarity:.2f} — possible duplicate")
Running embeddings locally is a deliberate choice: every job description contains sensitive company and role details. Keeping the embedding step local means no job text is sent to any external API at this stage.

Stage 01 — Job Scoring with RAG

Stage 01 is where the RAG pattern is applied. The pipeline retrieves the master career profile — a structured YAML file containing all skills, roles, experience summaries, and competency indicators — and injects it alongside the full job description into a structured prompt. Grok analyzes the pair and returns a structured response containing a match score (0–100), a skill gap analysis listing missing or weak areas, and an accept/reject recommendation.

The first live run scored an 85% match on a Collective Health Senior Data Engineer role. That score is not fabricated — it's the output of the RAG scoring chain against the actual job description. The score drives whether the pipeline continues: below the threshold, the job is logged as "passed" and no further API calls are made.

Output FieldTypeExample
match_scoreinteger 0–10085
skill_gapslist[str]["dbt", "Terraform IaC"]
recommendationACCEPT / PASSACCEPT
reasoningstringSummary of fit vs. gaps
The master career profile is the single source of truth. All downstream stages — resume bullets, cover letter content, skill highlights — are grounded in this profile. The LLM cannot invent experience that isn't in the profile YAML.

Two-Tier Model Strategy

The pipeline uses two different Grok models depending on the task. The split is intentional: not every stage needs the same reasoning depth, and routing lighter tasks to a smaller model reduces cost without sacrificing quality where quality matters.

ModelUsed ForReason
grok-3-miniScoring, parsing, classification, company researchSufficient reasoning at lower cost; these are structured extraction tasks
grok-3Resume tailoring, cover letter generationFull model reasoning for generation work that goes in front of a hiring manager

The model is a configuration parameter, not a hard-coded string in each script. Every stage reads its model from a central config, which means switching the entire pipeline to a different model (or falling back to OpenAI) is a single environment variable change.

Over-using the full model on lightweight tasks is a common cost trap in LLM pipelines. Scoring a job posting doesn't require the same reasoning capacity as generating a tailored executive summary. The tier split cut per-job cost significantly without degrading output quality.

OpenAI-Compatible Grok Client

xAI's Grok exposes an OpenAI-compatible REST API. The client in this pipeline is the standard openai Python library, pointed at https://api.x.ai/v1 instead of OpenAI's endpoint. No custom HTTP client was required. Every LangChain chain, every prompt template, and every tool built for OpenAI works with Grok without code changes.

# src/ai/grok_client.py (simplified)
from openai import OpenAI

class GrokClient:
    def __init__(self):
        self.client = OpenAI(
            api_key=os.environ["XAI_API_KEY"],
            base_url="https://api.x.ai/v1",
        )
        self.mini_model  = "grok-3-mini"
        self.heavy_model = "grok-3"

    def complete(self, messages, heavy=False):
        model = self.heavy_model if heavy else self.mini_model
        return self.client.chat.completions.create(
            model=model,
            messages=messages,
        )
The OpenAI-compatible interface means the entire pipeline could switch to GPT-4o or any other OpenAI-compatible provider by changing base_url and api_key. The model layer is fully decoupled from the business logic.

Stages 03–05 — Tailoring and Resume Generation

Stage 03 extracts structured information from the job posting: required skills, preferred qualifications, seniority signals, and company culture indicators. The output is a structured YAML file that all downstream stages consume as their primary input — rather than re-parsing the raw job text repeatedly.

Stage 04 generates the resume intermediate — a tailored JSON resume that selects the most relevant bullet points from the master profile and rewrites them to match the role's keyword signals. The rewriting is grounded: Grok is instructed to select and sharpen existing experience, not to invent achievements. The master profile YAML is the hard boundary for what can appear in the output.

Stage 05 renders the JSON resume into two formats: an ATS-safe DOCX file ready to attach and submit, and a Markdown preview for quick human review before submission. The DOCX uses python-docx with templated section ordering and consistent font/spacing — no custom formatting that might confuse ATS parsers.

│   └── cover_{uuid}.docx       # stage 08 render

Stages 06–08 — Company Research and Cover Letter

Stage 06 runs company research: Grok fetches and summarises publicly available information about the employer — size, funding stage, recent news, engineering culture signals, tech stack indicators from job postings, and leadership context. This research is saved as a Markdown summary that feeds directly into stage 07. The goal is to give the cover letter generator enough context to reference specific, real things about the company rather than producing generic filler.

Stage 07 generates a cover letter intermediate in JSON format. The structure separates the opening hook, the experience alignment section, the company-specific section (which references the stage 06 research), and the closing. Separating these into structured fields makes it easier to regenerate individual sections without rerunning the full cover letter generation.

Stage 08 classifies the target employer as either an agency or a direct employer, then renders the cover letter to DOCX with tone adjusted accordingly. Agency letters are more concise and skills-forward. Direct employer letters are more narrative and culture-aligned. The classification is automatic — Grok determines the employer type from the job posting content.

The agency vs. direct employer classification is one of the highest-signal design decisions. Sending a narrative culture-alignment letter to a staffing agency wastes their time. Sending a bullet-list skills sheet to a direct employer misses the relationship-building opportunity. The classifier handles this automatically.

Stage 09 — Quality Gate and Status Tracking

The final stage is a blocking quality gate before any application is marked as submitted. It confirms that all required output files exist in the job folder, meet minimum size thresholds (ruling out truncated or empty outputs), and pass basic content checks (ruling out malformed documents). Only after all checks pass does the pipeline write the application record to the job's metadata_{uuid}.yaml with date, method, status, and score.

If any check fails, the pipeline raises an error and the job status remains in-progress. Nothing is marked as applied. The human must investigate, fix, and rerun. This is the same quality gate principle from production data pipelines: a pipeline that completes silently but produces wrong output is more dangerous than one that fails loudly.

# Stage 09 quality checks (simplified)
REQUIRED_FILES = ["resume_{uuid}.docx", "cover_{uuid}.docx", "research_{uuid}.md"]
MIN_SIZES      = {"resume": 8_000, "cover": 3_000, "research": 1_000}  # bytes

for f in REQUIRED_FILES:
    path = job_dir / "generated" / f.format(uuid=uuid)
    if not path.exists():
        raise QualityGateError(f"Missing: {path.name}")
    if path.stat().st_size < MIN_SIZES[f.split("_")[0]]:
        raise QualityGateError(f"Too small ({path.stat().st_size}B): {path.name}")

# All checks passed — write status
metadata["status"]       = "applied"
metadata["applied_date"] = datetime.utcnow().isoformat()
write_yaml(metadata_path, metadata)
Marking a job as "applied" when documents aren't ready means you might not realize the application didn't go through. The quality gate forces review before the status is written — there's no silent success state.

UUID-Based Data Model

Each job processed by the pipeline gets a UUID at intake. All data, intermediates, and outputs for that job live under data/jobs/{uuid}/ — a self-contained folder that can be inspected, regenerated, or archived independently of every other job. The UUID also serves as the foreign key for the FAISS index entry and the status registry.

The status registry is a lightweight YAML file (data/registry.yaml) that maps UUIDs to top-level metadata: company, role title, date processed, score, and status. This is what the pipeline queries for reporting — "how many jobs accepted this week," "which jobs are pending submission" — without scanning individual job folders.

StudyBook — The Interview Prep Extension

Once the application pipeline was running, the other half of the problem became clear: getting the application is only useful if you can win the interview. Building a parallel pipeline for interview preparation followed the same logic. StudyBook is that pipeline — it generates structured audio learning scripts for technical topics, converts them to MP3 using GPT-4o text-to-speech, hosts the audio on Cloudflare R2, and generates complete HTML reference pages that go live on GitHub Pages.

The learning pages cover 21+ technical topics: AWS services, data engineering patterns, system design, pipeline design, and project deep-dives like this one. Each page has audio, code examples, tables, interview Q&A, and a cheat sheet. Claude Code orchestrates quality review, gap analysis, and HTML regeneration. ChatGPT Project 1 generates audio scripts. ChatGPT Project 2 generates HTML pages. The result is a living, self-updating interview preparation library maintained entirely through automation.

6. Save to seanlgirgis.github.io/learning/{slug}.html

Engineering Challenges

Structured Output Reliability

Language models don't always return the YAML or JSON structure the prompt asks for. Sometimes the model returns well-formed JSON. Sometimes it wraps the JSON in markdown code fences. Sometimes it returns free-form prose with the structured data buried inside. Each variation breaks a naive json.loads() call. The fix was a two-layer approach: prompt templates that include concrete output format examples, and a regex-based extraction fallback that attempts to recover structured data from improperly formatted responses before raising an error.

# Structured output extraction with fallback
import re, json

def extract_json(raw: str) -> dict:
    # Try direct parse first
    try:
        return json.loads(raw)
    except json.JSONDecodeError:
        pass
    # Fallback: extract from markdown code fence
    match = re.search(r"```(?:json)?\s*(\{.*?\})\s*```", raw, re.DOTALL)
    if match:
        return json.loads(match.group(1))
    # Last resort: find first {...} block
    match = re.search(r"\{.*\}", raw, re.DOTALL)
    if match:
        return json.loads(match.group(0))
    raise ValueError("No extractable JSON found in model response")

Windows Encoding in Subprocess Pipelines

The auto-pipeline script runs each stage as a Python subprocess to keep stages isolated and independently restartable. On Windows, when a job description or a status message contains Unicode — which they do, because the scripts use emoji for status output — the default encoding for subprocess stdout/stderr is not UTF-8. This causes encoding errors that silently truncate subprocess output or crash the stage entirely, with error messages that don't make the root cause obvious.

The fix was two-part: enforce PYTHONUTF8=1 in the environment dictionary passed to every subprocess.run() call, and add explicit encoding="utf-8" on every file open. Once both were in place, all Unicode handling became consistent across the pipeline regardless of Windows system locale.

# Subprocess call with UTF-8 enforcement
import subprocess, os

env = os.environ.copy()
env["PYTHONUTF8"] = "1"

result = subprocess.run(
    ["python", stage_script, "--uuid", job_uuid],
    capture_output=True,
    text=True,
    encoding="utf-8",
    env=env,
)
if result.returncode != 0:
    raise StageError(f"Stage failed:\n{result.stderr}")

Lessons Learned

Local JSON and YAML storage works fine for an MVP — it's zero infrastructure, zero cost, and immediately inspectable. But it starts to show friction when you want to query across jobs. "Show me all roles where I scored above 80%" requires scanning every metadata YAML file rather than running a single query. The fix is SQLite from the start: it's still a local file, still zero infra, but you get full SQL query capability without changing the deployment model.

Building the Streamlit UI earlier would have paid off. The CLI is great for automation but reviewing outputs before submission is awkward without a proper interface. A simple Streamlit app that shows each job's score, status, and generated documents side by side would cut review time significantly and reduce the chance of missing a quality issue in the generated content.

Defining the data contract between pipeline stages more formally from day one would have prevented several rounds of refactoring. The YAML structures evolved organically as new stages were added — field names changed, optional fields became required, and new stages expected keys that earlier stages didn't always produce. A shared schema file (Pydantic models or a JSON Schema) for each stage's input and output would have caught contract violations at stage boundaries rather than buried inside downstream parsing errors.

The most satisfying moment was the first live run: feeding in the Collective Health job description, watching all ten stages complete, and getting back a folder with an 85% match score, a tailored resume, company research, and a cover letter that referenced specific things about the company. That was when it stopped being a project and became a tool.

Interview Q&A

Walk me through the architecture of this pipeline end to end.
The pipeline is a ten-stage sequential data pipeline where the input is a raw job posting and the output is a production-ready application package. Stage zero runs a semantic duplicate check using FAISS and local embeddings — no API call, no cost, no processing time wasted on reposted roles. Stage one uses RAG to score the job against my career profile and returns a match score, skill gap analysis, and an accept/reject recommendation. If accepted, stages three through five extract structured job data, generate a tailored JSON resume, and render it to a DOCX. Stages six through eight run company research and generate a tailored cover letter with automatic agency vs. direct employer tone adjustment. Stage nine is a blocking quality gate that validates all outputs before writing the "applied" status to the job record. The whole pipeline runs from a single orchestrator script — drop in a posting, run one command, get back a folder ready to review and submit.
Why did you choose Grok over OpenAI for the primary LLM?
The decision came down to two things: API compatibility and the two-tier model economics. Grok exposes an OpenAI-compatible endpoint, which means the entire pipeline uses the standard OpenAI Python library pointed at x.ai instead of OpenAI. No custom client, no LangChain adapter changes, and no lock-in — switching to GPT-4o is one environment variable change. On the economics side, grok-3-mini handles all the light tasks — scoring, parsing, classification, research — at significantly lower cost per call. grok-3, the full model, is reserved for the generation work that ends up in front of a hiring manager. That tier split means you get the reasoning quality you need where you need it without paying full-model rates for every API call in the pipeline.
How does the FAISS duplicate detection work and why run it locally?
Stage zero embeds the incoming job description using the all-MiniLM-L6-v2 sentence transformer model, running entirely on-device with no API call. It then searches the FAISS index — a flat index of all previously processed job embeddings — for the nearest neighbor using cosine similarity. If similarity exceeds the threshold, the pipeline blocks and logs the potential duplicate. Running this step locally was the right call for three reasons: it's fast (milliseconds, not seconds), it's free (no API cost on every single intake), and it's private (job descriptions contain sensitive company and role details that don't need to leave the machine for an embedding operation). The index rebuilds in seconds whenever a new job is accepted, so it stays current without maintenance overhead.
How did you handle structured output reliability from the LLM?
The problem is that language models don't always return the exact JSON or YAML structure the prompt requests — you might get well-formed JSON, or JSON wrapped in markdown code fences, or free-form prose with the data buried inside it. A naive json.loads() call fails on all but the first case. The solution was a layered extraction approach: prompt templates include concrete output format examples with actual field names, which reduces off-format responses significantly. For the cases that still slip through, a regex-based extraction fallback attempts to recover structured data from the raw response before raising an error — it tries direct parse, then code fence extraction, then raw JSON block extraction. Combined, these two layers dropped the structured output failure rate to near zero in production.
What is the quality gate and why is it a blocking step?
The quality gate at stage nine is a validation check that confirms all required output files exist in the job folder, meet minimum byte-size thresholds ruling out truncated or empty outputs, and pass basic content checks. Only after all checks pass does the pipeline write "applied" to the job's metadata. If any check fails, the job status stays in-progress and the human must investigate and rerun. It's blocking by design — the same principle that applies in production data pipelines: a pipeline that completes silently but produces wrong output is more dangerous than one that fails loudly. In this context, marking a job as applied when the resume or cover letter isn't actually ready means you might not realize the application didn't go through correctly, and you lose the window to fix it.
What would you build differently if you started over?
Three things. First, SQLite from day one instead of YAML files for the job registry. Local YAML is fine for an MVP but cross-job queries — show me all roles above 80% this month, show me pending submissions — require scanning files rather than running a SQL query. SQLite is still a single local file with zero infrastructure overhead, but you get full query capability. Second, I'd build the Streamlit review interface earlier. The CLI is great for automation but reviewing generated documents before submission is awkward without a proper interface. Third, I'd define the data contracts between pipeline stages formally — Pydantic models or JSON Schema for each stage's input and output — from the start. The YAML structures evolved organically as the pipeline grew, which caused several rounds of refactoring when downstream stages expected fields that upstream stages didn't consistently produce.
