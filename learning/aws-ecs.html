1. What ECS & Docker Actually Are

Docker is a container runtime — a technology for packaging an application and all its dependencies (libraries, runtime, OS packages, config) into a portable, reproducible unit called a container image. A container image runs identically on any host that has a Docker-compatible runtime, eliminating the "works on my machine" class of environment inconsistencies. Containers share the host OS kernel (unlike virtual machines which emulate full hardware), making them lightweight and fast to start.

Amazon ECS (Elastic Container Service) is AWS's fully managed container orchestration platform. It handles scheduling containers across a cluster of compute, maintaining desired container counts, integrating with load balancers, managing rolling deployments, and wiring containers into the VPC networking model. ECS answers the question: "I have container images — how do I run them reliably at scale in AWS?" You define what to run (task definitions), ECS decides where and handles the how.

ECS competes with Kubernetes (EKS on AWS) in the container orchestration space. ECS is simpler to operate — it has less surface area, fewer abstractions, and integrates more naturally with native AWS services (IAM, ALB, CloudWatch, Secrets Manager) without custom operators or controllers. EKS offers more flexibility, a larger ecosystem, and portability across clouds. For teams building entirely on AWS without Kubernetes expertise, ECS is typically the right starting point. For organizations with existing Kubernetes knowledge or multi-cloud requirements, EKS makes more sense.

For data engineering, containers solve a critical problem: reproducible execution environments. A Python ETL job that runs in a Docker container carries its exact Python version, library versions, and system dependencies with it — no dependency drift between dev, staging, and production, and no "the Glue runtime doesn't have my library version" problem.

2. Docker Core Concepts

Understanding Docker's core primitives is prerequisite to working effectively with ECS. The concepts are simple but the implications for security, performance, and reproducibility run deep.

Image vs Container

An image is an immutable, layered snapshot of a filesystem — the blueprint. A container is a running instance of an image — the process. You can run many containers from the same image simultaneously. Images are built from Dockerfiles and stored in registries (ECR, Docker Hub). Containers are ephemeral by default — when a container stops, any filesystem changes within it are lost unless written to a mounted volume.

Image Layers

Docker images are composed of layers, each corresponding to a Dockerfile instruction (FROM, RUN, COPY, etc.). Layers are cached by content hash. When rebuilding an image, Docker reuses cached layers up to the first changed instruction and only rebuilds from that point forward. Layer ordering in a Dockerfile directly impacts build speed — instructions that change frequently (copying application code) should come last; instructions that change rarely (OS package installs, pip installs) should come first.

Volumes and Bind Mounts

Containers are ephemeral — data written to the container filesystem is lost when the container exits. For persistence, Docker provides volumes (managed by Docker, stored on the host filesystem) and bind mounts (a host directory mounted into the container). In ECS/Fargate, bind mounts work differently — Fargate tasks don't have a persistent host, so ephemeral storage (configurable up to 200 GB on Fargate) or EFS mounts are used for data that must outlive the task.

Docker Networking Basics

Containers can communicate via Docker networks. By default, each container gets a network namespace with its own IP. Containers on the same Docker network can reach each other by container name (DNS resolution). In ECS, the awsvpc network mode replaces Docker networking with VPC-native ENIs — each task gets its own VPC IP and communicates via standard VPC routing.

# Essential Docker commands
docker build -t my-etl-job:1.0.0 .          # Build image from Dockerfile
docker run --rm my-etl-job:1.0.0            # Run container, remove on exit
docker run -it my-etl-job:1.0.0 /bin/bash  # Interactive shell into container
docker ps                                    # List running containers
docker images                               # List local images
docker logs                   # Tail container stdout/stderr
docker exec -it  /bin/bash   # Shell into running container
docker stop                   # Graceful stop (SIGTERM)
docker rm                     # Remove stopped container
docker rmi my-etl-job:1.0.0               # Remove image

3. Writing Effective Dockerfiles

A Dockerfile is a sequence of instructions that build a container image. Writing good Dockerfiles means: small final image size, fast rebuild times via layer caching, security (minimal attack surface, no root), and reproducibility (pinned versions).

Multi-Stage Builds

Multi-stage builds use multiple FROM statements in a single Dockerfile. An early stage performs heavy build steps (compiling code, installing build tools, pip install with all dev dependencies). A final stage starts from a clean base image and copies only the build artifacts. The final image contains no build tools, no source code, no test dependencies — only what's needed to run. This is the most impactful technique for reducing image size.

# Multi-stage Dockerfile for a Python ETL job
# ─────────────────────────────────────────────

# Stage 1: Build — install all dependencies including build tools
FROM python:3.12-slim AS builder

WORKDIR /build

# Copy requirements first — cached until requirements change
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# Stage 2: Runtime — clean minimal image
FROM python:3.12-slim AS runtime

# Non-root user for security
RUN useradd --create-home --shell /bin/bash appuser

# Copy installed packages from builder stage
COPY --from=builder /install /usr/local

# Copy application code
WORKDIR /app
COPY --chown=appuser:appuser src/ ./src/
COPY --chown=appuser:appuser entrypoint.sh .
RUN chmod +x entrypoint.sh

USER appuser

ENTRYPOINT ["./entrypoint.sh"]

Layer Caching Strategy

Order Dockerfile instructions from least-frequently-changing to most-frequently-changing. Package installs (RUN pip install) should come before application code copies (COPY src/ ./) because code changes on every commit but requirements change rarely. A COPY . . at the top of a Dockerfile busts the cache on every build, forcing full reinstallation of dependencies every time.

# BAD — cache busts on every code change
FROM python:3.12-slim
COPY . .                          # Busts cache for everything below
RUN pip install -r requirements.txt

# GOOD — pip install cached until requirements.txt changes
FROM python:3.12-slim
COPY requirements.txt .           # Only changes when deps change
RUN pip install -r requirements.txt
COPY src/ ./src/                  # Code changes don't bust pip cache

Security Hardening

  • Never run as root: Add a non-root user with RUN useradd and switch with USER. Containers running as root that escape their namespace have host-root access.
  • Pin base image versions: FROM python:3.12-slim not FROM python:latest. Unpinned base images change silently and break reproducibility.
  • No secrets in image layers: Every layer is permanently in the image history. A secret in a RUN command (even if deleted in a later layer) is extractable. Use Docker BuildKit secrets or pass secrets at runtime via environment variables.
  • Minimize installed packages: Fewer packages = smaller attack surface. Use -slim or -alpine base images. Don't install curl, wget, or SSH unless genuinely required.
Never COPY .env or credentials files into an image: A COPY . . instruction will include any .env, ~/.aws/credentials, or other sensitive files in the current directory unless explicitly excluded in .dockerignore. Always maintain a thorough .dockerignore that excludes .env, *.pem, .git/, __pycache__/, and test fixtures.

4. ECR — Elastic Container Registry

Amazon ECR is AWS's managed Docker container registry. It stores, versions, and serves container images to ECS tasks, Lambda container functions, and EC2 instances. ECR integrates natively with IAM for access control, with KMS for image encryption at rest, and with CloudWatch for pull metrics and lifecycle policies.

Pushing Images to ECR

# Authenticate Docker to ECR (token valid 12 hours)
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS \
    --password-stdin 123456789.dkr.ecr.us-east-1.amazonaws.com

# Tag local image for ECR
docker tag my-etl-job:1.0.0 \
  123456789.dkr.ecr.us-east-1.amazonaws.com/my-etl-job:1.0.0

# Push to ECR
docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/my-etl-job:1.0.0

# In CI/CD (GitHub Actions, CodeBuild) — use IRSA or CodeBuild role,
# never hardcode AWS credentials

Image Tagging Strategy

Tag images with both a specific version tag and latest. Version tags should be immutable — once pushed, never overwrite a tagged version. Use semantic versioning (1.2.3) or Git commit SHA tags (abc1234) for production deployments. latest is useful for development but should never be what ECS task definitions reference in production — a new latest push would immediately affect any task definition using it on next deployment.

Reference container images in ECS task definitions by their full URI including the digest (@sha256:...) for maximum reproducibility, or by a specific immutable tag. Never use :latest in production task definitions — it makes deployments non-deterministic.

Lifecycle Policies

ECR repositories accumulate images over time. Without lifecycle policies, storage costs grow unboundedly and repositories become cluttered. Configure policies to: keep the last N tagged images per repository, expire untagged images after N days, and retain release-tagged images indefinitely. Lifecycle policies run daily and are evaluated per-repository.

# ECR lifecycle policy — keep last 10 tagged images, expire untagged after 1 day
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Expire untagged images after 1 day",
      "selection": {
        "tagStatus": "untagged",
        "countType": "sinceImagePushed",
        "countUnit": "days",
        "countNumber": 1
      },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 2,
      "description": "Keep only last 10 tagged images",
      "selection": {
        "tagStatus": "tagged",
        "tagPrefixList": ["v"],
        "countType": "imageCountMoreThan",
        "countNumber": 10
      },
      "action": { "type": "expire" }
    }
  ]
}

5. ECS Architecture — Clusters, Services, Tasks

ECS has a clear three-level hierarchy: Clusters contain Services (or standalone Tasks), and Services manage Tasks (running container instances defined by Task Definitions).

Cluster

An ECS Cluster is a logical grouping of compute capacity. For Fargate, the cluster is purely logical — AWS manages the underlying compute. For EC2 launch type, the cluster contains a fleet of EC2 instances running the ECS agent. One cluster can contain both Fargate and EC2 capacity simultaneously. Clusters are typically environment-scoped (one cluster per environment: dev, staging, prod) or workload-scoped for larger organizations.

Task Definition

A Task Definition is the blueprint for a task — analogous to a Docker Compose file or a pod spec in Kubernetes. It specifies: container image(s), CPU and memory allocation, network mode, IAM roles, environment variables, secrets, log configuration, volumes, and health checks. Task Definitions are versioned; each update creates a new revision. ECS services reference a specific revision.

Task

A Task is a running instance of a Task Definition — one or more containers executing together on the same compute. Tasks can be launched standalone (run-task, for batch jobs) or managed by a Service (for long-running workloads). Tasks in the same task definition share the same network namespace (in awsvpc mode, they share the task's ENI and IP address).

Service

An ECS Service ensures a desired number of tasks are always running. If a task exits or fails a health check, the service scheduler replaces it. Services integrate with ALB/NLB target groups for load-balanced traffic distribution, support rolling and blue/green deployments, and can be auto-scaled based on CloudWatch metrics.

──────────────────────────────────────────────────────

  ECS Cluster (prod-cluster)
  │
  ├── Service: api-service (desired: 3 tasks)
  │   ├── Task (running) ── Container: api:1.2.0

6. Task Definitions Deep-Dive

The Task Definition is where most ECS configuration lives. Understanding its structure is essential for correctly deploying containerized workloads.

# Task Definition JSON structure (key fields)
{
  "family": "my-etl-job",
  "taskRoleArn": "arn:aws:iam::123456789:role/ETLTaskRole",
  "executionRoleArn": "arn:aws:iam::123456789:role/ECSExecutionRole",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "1024",        # 1 vCPU (in units: 256=0.25, 512=0.5, 1024=1, 2048=2, 4096=4)
  "memory": "4096",     # MB (must be compatible with cpu value)
  "containerDefinitions": [
    {
      "name": "etl-worker",
      "image": "123456789.dkr.ecr.us-east-1.amazonaws.com/my-etl-job:1.0.0",
      "essential": true,
      "environment": [
        {"name": "ENV",        "value": "production"},
        {"name": "S3_BUCKET",  "value": "my-processed-bucket"}
      ],
      "secrets": [
        {
          "name": "DB_PASSWORD",
          "valueFrom": "arn:aws:secretsmanager:us-east-1:123456789:secret:prod/db-password"
        }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group":         "/ecs/my-etl-job",
          "awslogs-region":        "us-east-1",
          "awslogs-stream-prefix": "etl"
        }
      },
      "healthCheck": {
        "command":     ["CMD-SHELL", "python -c 'import sys; sys.exit(0)' || exit 1"],
        "interval":    30,
        "timeout":     5,
        "retries":     3,
        "startPeriod": 60
      }
    }
  ]
}

CPU and Memory Sizing (Fargate)

Fargate CPU and memory must be a valid combination. CPU is specified in vCPU units (256 = 0.25 vCPU) and memory in MB. Common valid combinations: 256 CPU / 512–2048 MB; 512 CPU / 1024–4096 MB; 1024 CPU / 2048–8192 MB; 2048 CPU / 4096–16384 MB; 4096 CPU / 8192–30720 MB. Fargate bills per vCPU-second and per GB-second — right-sizing matters. Over-allocating 4 GB for a job that uses 512 MB wastes 3.5 GB of billing with no benefit.

Essential containers: If a container is marked "essential": true and it exits (for any reason — success or failure), ECS stops all other containers in the task. For single-container tasks this is always correct. For multi-container tasks (sidecar patterns), only mark the primary application container as essential; sidecars (log forwarders, proxies) should be non-essential unless the task genuinely cannot function without them.

7. Fargate vs EC2 Launch Type

ECS supports two launch types that determine where tasks run: Fargate (serverless, AWS-managed compute) and EC2 (your own EC2 fleet managed by the ECS agent). The choice is one of the most consequential architectural decisions when adopting ECS.

Fargate

With Fargate, you never provision or manage EC2 instances. AWS allocates compute for each task on demand, handles OS patching, and charges per vCPU-second and GB-second consumed. Tasks start in seconds. There is no cluster capacity to manage — if you need to run 100 tasks simultaneously, Fargate handles it without pre-provisioning 100 instances. Fargate is the right choice for: teams that want minimal operational overhead, variable or bursty workloads, batch jobs with unpredictable concurrency, and organizations where patching EC2 instances is a compliance burden.

EC2 Launch Type

With EC2 launch type, you manage a fleet of EC2 instances in the cluster. The ECS agent on each instance reports available CPU/memory to ECS, and the scheduler places tasks onto instances with sufficient capacity. EC2 launch type gives you: access to GPU instances, access to instance store (local NVMe for high-I/O workloads), more control over instance placement (placement groups, dedicated hosts), and potentially lower cost at sustained high utilization (Reserved Instances or Savings Plans apply). The trade-off: you manage the EC2 fleet, patches, and capacity planning.

DimensionFargateEC2 Launch Type
Infrastructure managementNone — fully managedYou manage EC2 fleet, patches, capacity
Cost modelPer vCPU-second + GB-secondEC2 instance hours (RI/SP applicable)

Start with Fargate. The operational simplicity dividend — no EC2 fleet to manage, no capacity planning, no AMI patching — is worth the cost premium for most data engineering workloads. Move to EC2 launch type only when you have a concrete, measured reason: GPU requirements, instance store I/O, or validated cost savings from Reserved Instances at sustained high utilization.

8. IAM — Task Roles vs Execution Roles

ECS uses two distinct IAM roles per task, and confusing them is one of the most common ECS misconfiguration problems. They serve entirely different purposes.

Task Execution Role

The execution role is used by the ECS agent and Fargate infrastructure — not your application code. It grants ECS permission to: pull the container image from ECR, write container logs to CloudWatch Logs, and fetch secrets from Secrets Manager or SSM Parameter Store to inject as environment variables at task startup. Your application never directly uses the execution role.

# Execution Role — used by ECS agent, not your code
# Minimum required permissions:
{
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ecr:GetAuthorizationToken",
        "ecr:BatchCheckLayerAvailability",
        "ecr:GetDownloadUrlForLayer",
        "ecr:BatchGetImage"
      ],
      "Resource": "*"   # ECR auth is account-wide
    },
    {
      "Effect": "Allow",
      "Action": ["logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": "arn:aws:logs:us-east-1:123456789:log-group:/ecs/*"
    },
    {
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue"],
      "Resource": "arn:aws:secretsmanager:us-east-1:123456789:secret:prod/*"
    }
  ]
}

Task Role

The task role is the IAM identity assumed by your application code running inside the container. When your Python code calls boto3.client('s3'), it uses credentials from the task role — fetched from the ECS task metadata endpoint (not IMDS, which is EC2-specific). The task role should follow least privilege: only the permissions the application actually needs.

# Task Role — used by your application code
# Example: ETL job that reads S3, writes to Redshift
{
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::my-raw-bucket",
        "arn:aws:s3:::my-raw-bucket/raw/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject"],
      "Resource": "arn:aws:s3:::my-processed-bucket/processed/*"
    },
    {
      "Effect": "Allow",
      "Action": ["glue:StartJobRun", "glue:GetJobRun"],
      "Resource": "arn:aws:glue:us-east-1:123456789:job/my-job"
    }
  ]
}
Missing task role ≠ no AWS access: If no task role is specified, the container may still be able to reach the EC2 IMDS on EC2 launch type hosts and inherit the EC2 instance's IAM role — which is typically far more permissive than intended. Always explicitly specify a scoped task role, and on EC2 launch type, set HttpPutResponseHopLimit=1 on the host instances to prevent container escape to the host IMDS.

9. Networking — awsvpc, ALB, Service Discovery

awsvpc Network Mode

The awsvpc network mode is required for Fargate and strongly recommended for EC2 launch type. In awsvpc mode, each ECS task gets its own Elastic Network Interface (ENI) with a dedicated VPC IP address. This means tasks are first-class VPC citizens — they can have security groups applied directly to them, they participate in VPC routing, and they can be targets in ALB target groups. Network traffic to/from a task is governed by the task's security group, not the host instance's security group.

# Run a Fargate task programmatically (boto3)
import boto3

ecs = boto3.client('ecs', region_name='us-east-1')

response = ecs.run_task(
    cluster='prod-cluster',
    taskDefinition='my-etl-job:5',
    launchType='FARGATE',
    networkConfiguration={
        'awsvpcConfiguration': {
            'subnets': ['subnet-0a1b2c3d', 'subnet-0e5f6g7h'],
            'securityGroups': ['sg-0123456789abcdef0'],
            'assignPublicIp': 'DISABLED'   # private subnet — no public IP
        }
    },
    overrides={
        'containerOverrides': [{
            'name': 'etl-worker',
            'environment': [
                {'name': 'PROCESSING_DATE', 'value': '2026-04-13'},
                {'name': 'INPUT_PREFIX',    'value': 'raw/events/year=2026/month=04/day=13/'}
            ]
        }]
    }
)

task_arn = response['tasks'][0]['taskArn']
print(f"Task started: {task_arn}")

ALB Integration

ECS Services integrate with Application Load Balancers via target groups. The service scheduler automatically registers new task ENI IPs into the target group when tasks start, and deregisters them when tasks stop or fail health checks. ALB health checks run against each task's IP directly, providing per-task health visibility. For rolling deployments, the service waits until new tasks are registered and healthy in the target group before deregistering old tasks.

Service Discovery

ECS Service Discovery (backed by Route 53 Auto Naming) automatically creates DNS records for each task in a service. Each task gets a DNS A record in a private hosted zone (my-service.my-namespace.local). Other services can reach it by name without going through an ALB. Service Discovery is useful for: internal microservice communication, gRPC services where ALB doesn't fit, and background workers that need to be reachable by name from other containers.

10. ECS for Data Pipelines

ECS is well-suited for containerized data pipelines that outgrow Lambda's constraints but don't warrant the Glue/EMR abstraction. The key pattern is: trigger an ECS task run-task call from Lambda, EventBridge, or Step Functions, passing job parameters as container environment variable overrides.

Run-Task Pattern for Batch ETL

Rather than running a long-lived ECS Service, batch ETL jobs run as standalone tasks launched on demand. A Lambda function or Step Functions state machine calls ecs:RunTask with the task definition, cluster, network config, and parameter overrides. The task runs to completion (success or failure) and ECS reports the exit code. The orchestrator waits for task completion by polling ecs:DescribeTasks or by listening for the ECS Task State Change EventBridge event.

# Step Functions ECS RunTask state (ASL)
{
  "Type": "Task",
  "Resource": "arn:aws:states:::ecs:runTask.sync:2",
  "Parameters": {
    "Cluster": "prod-cluster",
    "TaskDefinition": "my-etl-job:5",
    "LaunchType": "FARGATE",
    "NetworkConfiguration": {
      "AwsvpcConfiguration": {
        "Subnets":         ["subnet-0a1b2c3d"],
        "SecurityGroups":  ["sg-0123456789abcdef0"],
        "AssignPublicIp":  "DISABLED"
      }
    },
    "Overrides": {
      "ContainerOverrides": [{
        "Name": "etl-worker",
        "Environment": [
          {"Name": "PROCESSING_DATE", "Value.$": "$.processing_date"},
          {"Name": "INPUT_S3_PREFIX", "Value.$": "$.input_prefix"}
        ]
      }]
    }
  },
  "Next": "RegisterPartitions"
}

Advantages Over Glue for Containerized ETL

ECS/Fargate gives you complete control over the runtime environment — any Python version, any library, any system package, compiled binaries, custom C extensions. Glue's Python Shell and PySpark runtimes are managed environments with version lag and library constraints. If your ETL needs a library not available in Glue, requires a specific Python version, or uses compiled native extensions that don't work in Glue's environment, ECS/Fargate is the right compute layer.

The ECS + Step Functions combination is a powerful pattern for complex multi-step data pipelines: Step Functions handles orchestration, retries, error handling, and branching logic; ECS provides the containerized compute for each step. This gives you the operational simplicity of managed containers with the orchestration power of a proper workflow engine.

11. Auto Scaling ECS Services

ECS Application Auto Scaling adjusts the desired task count for a service based on CloudWatch metrics. It uses the same Auto Scaling policies as EC2 ASGs: target tracking, step scaling, and scheduled scaling.

Target Tracking

The simplest policy: set a target value for a metric and let Auto Scaling adjust task count to maintain it. Common targets: ECSServiceAverageCPUUtilization (target 70%), ECSServiceAverageMemoryUtilization (target 80%), or ALB request count per target (for request-driven services). ECS will add tasks when the metric rises above the target and remove tasks (down to the minimum) when it falls below.

# Register ECS service as scalable target
import boto3

aas = boto3.client('application-autoscaling')

aas.register_scalable_target(
    ServiceNamespace='ecs',
    ResourceId='service/prod-cluster/api-service',
    ScalableDimension='ecs:service:DesiredCount',
    MinCapacity=2,
    MaxCapacity=20
)

# Target tracking — keep CPU at 70%
aas.put_scaling_policy(
    PolicyName='cpu-target-tracking',
    ServiceNamespace='ecs',
    ResourceId='service/prod-cluster/api-service',
    ScalableDimension='ecs:service:DesiredCount',
    PolicyType='TargetTrackingScaling',
    TargetTrackingScalingPolicyConfiguration={
        'PredefinedMetricSpecification': {
            'PredefinedMetricType': 'ECSServiceAverageCPUUtilization'
        },
        'TargetValue': 70.0,
        'ScaleInCooldown':  60,
        'ScaleOutCooldown': 30
    }
)

SQS-Driven Scaling for Worker Services

For ECS services consuming messages from SQS, scale on a custom metric: the ratio of ApproximateNumberOfMessagesVisible to the number of running tasks (messages per task). Target tracking on this ratio maintains a target number of messages per worker, scaling out when the queue grows and scaling in when it drains. This is more responsive than CPU-based scaling for queue-driven workloads where workers may be idle between messages.

Scale-in protection for long-running tasks: Auto Scaling scale-in can terminate tasks mid-processing. Enable scale-in protection for tasks that are actively processing jobs, and remove the protection when the task completes its current unit of work. ECS supports task-level scale-in protection via ecs:UpdateTaskProtection, callable from within the running container via the task metadata endpoint.

12. Logging & Observability

awslogs Log Driver

The standard logging mechanism for ECS is the awslogs log driver, which streams container stdout/stderr directly to CloudWatch Logs. Configure it in the task definition's logConfiguration block. Each container gets a log stream within the configured log group. The stream name follows the pattern {prefix}/{container-name}/{task-id}, making it easy to find logs for a specific task.

# awslogs configuration in task definition
"logConfiguration": {
    "logDriver": "awslogs",
    "options": {

ECS Task Metadata Endpoint

Every ECS task has a metadata endpoint accessible from within the container (no credentials required). It provides: task ARN, cluster, task definition family/revision, container resource limits, and crucially — temporary IAM credentials for the task role. The endpoint URL is available via the ECS_CONTAINER_METADATA_URI_V4 environment variable injected by ECS automatically.

import os, requests

metadata_uri = os.environ.get('ECS_CONTAINER_METADATA_URI_V4')
task_metadata = requests.get(f"{metadata_uri}/task").json()

task_arn = task_metadata['TaskARN']
cluster   = task_metadata['Cluster']
print(f"Running in task: {task_arn} on cluster: {cluster}")

13. Secrets & Configuration Management

Injecting secrets into containers is a critical security concern. The wrong approach (hardcoding in images or passing as plain environment variables visible in task definition JSON) exposes secrets in multiple places. ECS provides a native mechanism for secure secret injection from Secrets Manager and SSM Parameter Store.

Secrets Manager Integration

In the task definition's secrets block, reference a Secrets Manager ARN. ECS fetches the secret value at task launch time using the execution role's permissions and injects it as an environment variable inside the container. The secret value never appears in task definition JSON, CloudFormation templates, or CloudWatch logs. It is only present as a decrypted environment variable inside the running container's process space.

# Task definition — secrets block
"secrets": [
    {
        "name": "DB_PASSWORD",
        "valueFrom": "arn:aws:secretsmanager:us-east-1:123456789:secret:prod/rds/password-AbCd12"
    },
    {
        "name": "API_KEY",
        "valueFrom": "arn:aws:ssm:us-east-1:123456789:parameter/prod/api-key"
    },
    {
        "name": "DB_HOST",
        # Reference a specific JSON key within a Secrets Manager secret
        "valueFrom": "arn:aws:secretsmanager:us-east-1:123456789:secret:prod/rds-AbCd12::host::"
    }
]
Secrets are fetched at task launch only: ECS injects secrets as environment variables when the task starts. If the secret is rotated in Secrets Manager after the task is running, the running task still has the old value. For services that need to pick up rotated secrets, you must restart the tasks (rolling deployment) after each rotation. Design your database and API connections to handle rotation gracefully.

Non-Secret Configuration

Non-sensitive configuration (environment names, S3 bucket names, feature flags, timeouts) should use plain environment variables in the task definition, or be retrieved from SSM Parameter Store at application startup. Keep task definitions as environment-agnostic as possible — pass the environment name as an env var and have the application construct resource names from it, rather than hardcoding prod-specific resource names in the task definition.

14. Common Gotchas and Anti-Patterns

1. Confusing task role and execution role: The execution role is for ECS infrastructure (pull image, write logs, fetch secrets). The task role is for your application code (call S3, DynamoDB, etc.). Attaching application permissions to the execution role works but is incorrect — it grants the ECS agent unnecessarily broad permissions. Always use separate, scoped roles for each purpose.
2. Using :latest tag in task definitions: Referencing :latest in a task definition makes deployments non-deterministic — a new push to ECR with the :latest tag changes what the next task launch runs without any deployment action. Always use specific version tags or image digests in production task definitions.
3. Running containers as root: Unless a specific capability requires root, containers should run as a non-root user. Root containers that escape their namespace have host-level access. Add RUN useradd and USER to your Dockerfile. Set "readonlyRootFilesystem": true in the task definition to further restrict filesystem access.
4. Not setting CPU and memory limits per container: If a task definition has multiple containers and only sets task-level CPU/memory without container-level limits, one container can consume all task resources, starving others. Set per-container cpu and memory/memoryReservation limits, especially for sidecar containers (log forwarders, proxies) that should be resource-constrained.
5. Ignoring container health checks: Without a health check, ECS considers a container healthy as soon as it starts — even if the application inside hasn't finished initializing. A task that starts but serves errors will not be replaced because ECS sees it as healthy. Always define a meaningful health check that validates the application is actually ready to handle requests.
6. Not handling SIGTERM for graceful shutdown: When ECS stops a task (scale-in, deployment, spot interruption), it sends SIGTERM to the main process and waits up to 30 seconds (configurable) before sending SIGKILL. Applications that don't handle SIGTERM are killed mid-operation — mid-write, mid-transaction, mid-message-processing. Catch SIGTERM, finish the current unit of work, flush buffers, and exit cleanly.
7. Storing state in the container filesystem: Containers are ephemeral. Any data written to the container's local filesystem is lost when the task exits. For data that must persist, write to S3, a database, or an EFS mount. A common pattern where developers write intermediate files to /tmp inside the container works fine for within-task scratch space, but breaks if the intent is for another task to read those files.

15. 10 Key Engineering Questions

Q1. What is the difference between a Docker image and a container?
An image is an immutable, layered snapshot of a filesystem — the blueprint. It is built from a Dockerfile and stored in a registry. A container is a running instance of an image — a process with its own isolated filesystem, network namespace, and process space, created from the image. Multiple containers can run simultaneously from the same image. Container filesystem changes are ephemeral unless written to a mounted volume. Images are the artifact; containers are the runtime.
Q2. What is the difference between the ECS task role and the execution role?
The execution role is used by the ECS agent and Fargate infrastructure at task launch time — to pull the image from ECR, stream logs to CloudWatch, and fetch secrets from Secrets Manager. Your application code never uses it directly. The task role is the IAM identity assumed by your application code running inside the container — it's what boto3 uses when calling S3, DynamoDB, or other AWS services. Both roles must be specified separately in the task definition; confusing them leads to either broken infrastructure operations or over-privileged agents.
Q3. How do Docker layer caches work and how do you optimize a Dockerfile for fast builds?
Docker caches each layer by its content hash. When rebuilding, it reuses cached layers up to the first instruction whose inputs have changed, then rebuilds all subsequent layers. To optimize: order instructions from least-frequently-changing to most-frequently-changing — OS packages first, then pip/npm installs (triggered by requirements file changes), then application code (changes on every commit). A COPY . . at the top busts the cache on every code change, forcing full reinstallation. Use multi-stage builds to separate build-time dependencies from the runtime image.
Q4. When would you choose Fargate over EC2 launch type for ECS?
Fargate is the right default for most workloads — no EC2 fleet to manage, no capacity planning, no AMI patching, and tasks scale independently of instance availability. Choose EC2 launch type when: you need GPU instances (Fargate has no GPU support), you need access to instance store for high-I/O ephemeral workloads, you have validated cost savings from Reserved Instances at high sustained utilization, or you have workloads requiring specific instance placement (dedicated hosts, placement groups). The operational simplicity of Fargate outweighs its cost premium for variable or moderate workloads.
Q5. How does awsvpc network mode change ECS networking compared to bridge mode?
In bridge mode, containers share the EC2 host's network namespace and communicate via Docker's virtual bridge network with port mapping. Multiple containers on the same host share an IP and are distinguished by port. In awsvpc mode, each task gets its own ENI with a dedicated VPC IP address — tasks are first-class VPC citizens with their own security groups, routing table entries, and VPC-native reachability. Security groups apply per-task rather than per-host, enabling fine-grained network control. awsvpc is required for Fargate and strongly recommended for EC2 launch type.
Q6. How do you pass secrets securely into an ECS container?
Use the task definition's secrets block to reference Secrets Manager ARNs or SSM Parameter Store paths. ECS fetches the secret at task launch time using the execution role's permissions and injects the decrypted value as an environment variable inside the container. The secret never appears in task definition JSON, CloudFormation/CDK templates, CloudWatch logs, or the ECS console. Never pass secrets as plain environment variables in the task definition — they appear in plaintext in the console, API responses, and CloudTrail logs.
Q7. What happens when an ECS service task fails a health check?
ECS marks the task as unhealthy after the configured number of consecutive health check failures. It deregisters the task from the ALB target group (stopping new traffic from reaching it), stops the task, and launches a replacement task. The replacement goes through health checks before being registered in the target group. If tasks repeatedly fail health checks (a crash loop), ECS will continue launching replacements but the service enters a degraded state — monitor the service:task:failed metric and set alarms on repeated task launch failures.
Q8. How does an ECS rolling deployment work and what controls prevent bad deployments?
A rolling deployment launches new tasks (with the updated task definition) while keeping old tasks running. The minimumHealthyPercent setting controls the minimum percentage of desired tasks that must remain healthy during deployment — at 100%, ECS can only replace tasks as capacity allows without reducing below desired count. The maximumPercent controls how far above desired count ECS can go to launch new tasks. Once new tasks pass ALB health checks, old tasks are deregistered and stopped. Setting both to 100/200 gives zero-downtime rolling deployments.
Q9. What is a multi-stage Docker build and when is it essential?
A multi-stage build uses multiple FROM instructions in one Dockerfile. An early stage installs build tools and compiles or installs all dependencies; a final stage starts from a clean minimal base image and copies only the runtime artifacts. The final image contains no build tools, compilers, or dev dependencies — dramatically reducing image size and attack surface. It is essential when: build tools (gcc, make, rust compiler) are needed to build native extensions but not to run the application, when dev/test dependencies must not appear in production images, or when image size is a concern (cold start time, ECR storage, pull latency).
Q10. How would you design a containerized ETL pipeline using ECS and Step Functions?
Define a task definition for each ETL step (or one generic task definition with parameter overrides for different job types). Store step parameters (date ranges, input paths, job types) as Step Functions execution input. Each Step Function state calls ecs:runTask.sync to launch a Fargate task with environment variable overrides, waits for completion, and branches on success or failure. Retries are configured at the Step Functions state level with exponential backoff. On terminal failure, an EventBridge rule captures the execution failure event and routes it to SNS for alerting. The orchestration logic lives in Step Functions; the execution logic lives in containers — cleanly separated.

16. Production Story Angles

At a large financial institution, containerized ETL jobs running on ECS/Fargate replaced a mix of cron-driven EC2 scripts and Lambda functions that had accumulated over several years. The Lambda functions were hitting the 15-minute ceiling on complex transformation jobs; the EC2 cron jobs had environment drift between instances that caused intermittent failures impossible to reproduce locally. Containerization solved both: each job had an exact, reproducible runtime environment, and Fargate removed any ceiling on job duration.

The migration pattern was incremental. New jobs were written as containerized Fargate tasks from the start. Existing Lambda jobs approaching the timeout limit were refactored into containers. The Dockerfile for each job used a multi-stage build: a builder stage ran pip install with all dependencies including large data libraries (pandas, pyarrow, a proprietary risk library with compiled C extensions), and a slim runtime stage carried only the installed packages and application code. Images averaged 280 MB — smaller than many Lambda layers, and built in under 2 minutes in the CI pipeline with layer caching.

All secrets were injected via the task definition's secrets block referencing Secrets Manager ARNs. The task role was scoped per-job: an ingestion job got S3 GetObject on the raw prefix and KMS Decrypt for the input bucket's CMK. A load job got S3 GetObject on the processed prefix and Redshift GetClusterCredentials. No job had cross-job access. This least-privilege posture was enforced through a CDK construct that generated task definitions — developers provided a job manifest specifying required resources, and the construct generated the appropriately scoped IAM policies automatically.

Step Functions orchestrated multi-step pipelines. A typical pipeline ran: validate schema (Fargate task) → transform and partition (Fargate task) → load to Redshift (Fargate task) → register Athena partitions (Lambda, fast and simple) → notify downstream consumers (SNS). Each Fargate step had a 3-retry policy in Step Functions with exponential backoff. Failed executions triggered a CloudWatch alarm which posted a structured alert including the failed step name, input parameters, and a link to the ECS task logs. Mean time to diagnose a failed job dropped significantly compared to the previous cron-based system, where the only signal was a missing output file.
