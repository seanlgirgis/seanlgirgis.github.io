Architecture Overview

Airflow is an orchestration platform, not a compute engine. Its job is to schedule, coordinate, retry, and observe work across systems such as S3, Glue, EMR, ECS, dbt, Snowflake, Redshift, Kubernetes, and APIs. The actual heavy processing should live outside Airflow workers unless the workload is very small.

The core pieces are the scheduler, metadata database, webserver, executor, and workers. The scheduler parses DAG files, creates task instances, and decides what should run. The executor decides how those task instances become running work, while the metadata database stores DAG runs, task state, retries, variables, connections, and history.

Key insight: Airflow scales best when it orchestrates distributed systems instead of becoming the distributed system.
Production gotcha: a slow metadata database, overloaded scheduler, or expensive DAG parsing loop can make the whole platform look broken even when the downstream systems are healthy.

DAGs & Scheduling

A DAG is a Python-defined dependency graph of tasks. It should describe what runs, when it runs, what depends on what, and how failures are handled. Senior teams keep DAG code deterministic: no network calls, no database scans, and no runtime discovery at parse time.

Scheduling is based on data intervals, not just wall-clock triggers. A daily DAG scheduled for midnight usually processes the prior completed interval, which matters for backfills, SLAs, and partition naming. Cron expressions are common, but newer timetable concepts are better when business calendars or custom interval logic matter.

from airflow import DAG
from airflow.operators.empty import EmptyOperator
from datetime import datetime

with DAG(
    dag_id="daily_curated_load",
    start_date=datetime(2026, 4, 1),
    schedule="0 2 * * *",
    catchup=False,
    max_active_runs=1,
    tags=["s3", "curated", "daily"],
) as dag:
    extract = EmptyOperator(task_id="extract")
    validate = EmptyOperator(task_id="validate")
    publish = EmptyOperator(task_id="publish")

    extract >> validate >> publish
Key insight: design DAGs around data readiness and idempotent partitions, not just around a clock.
Gotcha: setting an old start_date with catchup=True can launch a large historical backlog if the DAG is enabled without guardrails.

Operators & Sensors

Operators are task templates. Common examples include PythonOperator, BashOperator, AWS operators for Glue, EMR, ECS, Redshift, and S3, plus provider-specific operators for dbt, Snowflake, Databricks, and Kubernetes. Good Airflow design chooses operators that delegate work rather than embedding large application logic in DAG files.

Sensors wait for external conditions such as an S3 object, a partition, an API state, or another DAG. In older patterns, sensors could occupy worker slots while waiting. Deferrable sensors and reschedule mode reduce wasted capacity by moving long waits out of worker execution.

ToolBest useRisk
PythonOperatorSmall control logicTurns into hidden application code
BashOperatorSimple shell commandHarder observability and quoting bugs
GlueJobOperatorStart AWS Glue ETLAirflow success may only mean job submitted unless configured to wait
S3 sensorWait for filesCan waste slots if not deferrable or rescheduled
Key insight: operators should represent boundaries between systems; do not bury a whole data platform inside one Python task.
Gotcha: sensors are deceptively expensive at scale. Hundreds of blocking sensors can starve the executor before any real ETL starts.

XComs & Task Dependencies

XComs pass small task outputs through Airflow metadata. They are useful for IDs, row counts, partition names, status flags, or lightweight JSON values. They are not a data transport layer and should not carry DataFrames, large payloads, files, or result sets.

Task dependencies define execution order. The bitshift operators >> and << are the clearest style for most DAGs; set_upstream and set_downstream are useful when generating tasks programmatically. Branching and trigger rules let a DAG handle conditional paths, partial failures, and fan-in behavior.

Key insight: use XComs for control-plane metadata; use S3, databases, queues, or object stores for data-plane payloads.
Gotcha: large XComs bloat the metadata database, slow the UI, and create painful cleanup problems.

Dynamic DAGs & Backfill

Dynamic DAGs let teams generate similar tasks from configuration, such as one task per source table, region, vendor, or data product. The key is to generate stable task IDs in a deterministic way. If task IDs change between parses, Airflow history becomes noisy and retries become hard to reason about.

Backfill runs historical intervals. This is powerful for rebuilding partitions, replaying corrected logic, or recovering missed schedules, but it can overwhelm warehouses, APIs, queues, and object storage. Use max_active_runs, pools, concurrency limits, and idempotent writes to keep replay safe.

Key insight: backfill is a production feature, not a panic button. Design every partitioned pipeline so yesterday, last month, or last year can be rerun safely.
Gotcha: dynamic DAG generation from a live database or API during parse can destabilize the scheduler and create inconsistent DAG definitions.

Executors

The executor determines where task instances run. LocalExecutor is simple and useful for small deployments, but all work is tied to one machine. CeleryExecutor distributes work across worker nodes and is common in traditional Airflow clusters. KubernetesExecutor launches isolated pods per task, which improves isolation but adds cluster complexity.

Executor choice affects cost, isolation, scaling behavior, operational burden, and failure modes. For senior data engineering, the real question is less "which executor is best" and more "where should compute happen?" If Airflow launches Glue, EMR, ECS, or Databricks jobs, the executor mostly needs to handle orchestration load, not transformation horsepower.

ExecutorStrengthTradeoff
LocalExecutorSimple deploymentLimited scale and machine-level blast radius
CeleryExecutorDistributed workersRequires broker, worker fleet, and tuning
KubernetesExecutorTask isolationKubernetes overhead and pod startup latency
Key insight: executor capacity should match orchestration pressure, while ETL compute should usually run in purpose-built services.
Gotcha: increasing worker count does not fix poor pools, overloaded downstream systems, slow DAG parsing, or database bottlenecks.

MWAA on AWS

Amazon Managed Workflows for Apache Airflow runs managed Airflow environments on AWS. DAGs, plugins, and requirements are stored in S3 and synced into the environment. AWS manages much of the webserver, scheduler, worker, and environment lifecycle, but the user still owns DAG design, dependency hygiene, IAM, networking, logging, and cost discipline.

MWAA fits teams that want Airflow without operating the full control plane. It integrates naturally with S3, CloudWatch, IAM, Secrets Manager, Glue, EMR, ECS, Lambda, Redshift, and Athena. The tradeoff is reduced infrastructure control compared with self-managed Airflow, plus AWS-specific constraints around supported versions, environment classes, package installation, and upgrade paths.

Key insight: MWAA removes much of the platform babysitting, but it does not remove Airflow design responsibility.
Gotcha: dependency conflicts in requirements.txt, private networking issues, and IAM permission gaps are among the fastest ways to break an MWAA deployment.

Airflow for Data Engineering

Airflow is strongest as the control plane for multi-step data pipelines: landing files in S3, validating inputs, launching Glue or EMR jobs, loading Redshift, running dbt models, refreshing materialized views, publishing data quality checks, and notifying downstream consumers. It gives teams dependency visibility and operational recovery that ad hoc cron jobs cannot provide.

For AWS-heavy data stacks, Airflow often coordinates S3 events, Glue Catalog updates, Athena checks, Redshift loads, ECS batch tasks, and EMR Spark steps. The best pipelines are idempotent, partition-aware, observable, and safe to retry. A failed task should tell the operator whether the problem is input readiness, transformation logic, infrastructure capacity, or downstream availability.

Key insight: Airflow becomes valuable when the pipeline spans systems and teams; single-system scheduling is often better handled by the system itself.
Gotcha: using Airflow as a streaming processor, message queue, or long-running service usually creates brittle architecture.

Common Mistakes & Comparisons

The most common Airflow mistakes are putting heavy transformation code inside DAG files, doing expensive work at parse time, abusing XComs, creating blocking sensors everywhere, ignoring idempotency, and letting every DAG hit downstream systems without pools. These issues rarely appear in a tiny dev environment but become obvious once hundreds of DAGs and thousands of task instances compete for scheduler and worker resources.

Airflow competes with tools such as Step Functions, EventBridge Scheduler, Glue Workflows, Dagster, Prefect, and dbt Cloud jobs. Airflow wins when dependency graphs are complex, operators need strong visibility, and many external systems must be coordinated. It is weaker when the problem is simple event routing, high-frequency streaming, or application-level workflow state.

ChoiceUse whenAvoid when
AirflowComplex batch orchestrationYou need millisecond event processing
Step FunctionsAWS-native service workflowYou need rich DAG authoring by data teams
Glue WorkflowsGlue-centered ETLThe pipeline spans many non-Glue systems
dbt CloudAnalytics model orchestrationYou need broad infrastructure orchestration
Key insight: Airflow is a coordinator. Pick it when coordination complexity is the problem.
Gotcha: Airflow can make a bad pipeline more visible, but visibility is not the same as reliability.

Interview Q&A

Q: What are the main components of Airflow architecture?
A: The scheduler parses DAGs and creates task instances, the metadata database stores state, the webserver exposes the UI, and the executor decides how tasks run. Workers execute the tasks when using distributed executors. In production, the scheduler and metadata database are often the bottlenecks before raw worker CPU is.
Q: Why should Airflow tasks be idempotent?
A: Airflow retries failed tasks and can backfill historical intervals. If a task writes duplicate records, overwrites the wrong partition, or sends repeated side effects, retry becomes dangerous. Idempotent tasks make recovery boring, which is exactly what production pipelines need.
Q: When is XCom the wrong tool?
A: XCom is wrong for large payloads, DataFrames, files, or query result sets. It stores values through Airflow metadata, so large XComs hurt database performance and UI responsiveness. Store real data in S3, a database, or a queue, and pass only the reference through XCom.
Q: How do you prevent a backfill from overwhelming downstream systems?
A: Limit parallelism with max_active_runs, task concurrency, and pools. Make writes partition-scoped and idempotent, and verify that downstream systems can tolerate replay volume. For large historical rebuilds, use separate queues or dedicated infrastructure to avoid starving daily production runs.
Q: What does MWAA manage, and what does the team still own?
A: MWAA manages much of the Airflow environment lifecycle, including managed infrastructure around the scheduler, webserver, workers, logs, and S3-based DAG sync. The team still owns DAG quality, IAM, networking, dependencies, environment sizing, observability, and cost. Managed Airflow reduces operations, but it does not fix weak orchestration design.
Q: How would you compare Airflow with AWS Step Functions?
A: Airflow is better for data-team-authored batch DAGs with many operators, retries, backfills, and cross-platform integrations. Step Functions is better for AWS-native application workflows with explicit state machines and service integrations. For data engineering, the choice often depends on whether the workflow is pipeline-centric or application-state-centric.

Quick Reference

DAG
Python-defined dependency graph that describes tasks, order, schedule, retries, and metadata.
Scheduler
Parses DAGs, creates task instances, and decides what should run next.
Metadata DB
Stores DAG runs, task state, XComs, variables, connections, and history.
Executor
Determines how task instances are dispatched to local processes, workers, or pods.
Operator
Reusable task template such as Python, Bash, Glue, EMR, ECS, S3, or dbt execution.
Sensor
Task that waits for an external condition such as file arrival, partition readiness, or external DAG completion.
XCom
Small metadata exchange between tasks; not for datasets or large payloads.
catchup
Controls whether Airflow creates historical runs between start date and now.
Backfill
Runs historical data intervals to rebuild or recover prior pipeline outputs.
Pools
Limit concurrency against scarce downstream systems such as warehouses, APIs, or clusters.
MWAA
AWS managed Airflow service with S3 DAG sync, CloudWatch logging, IAM integration, and managed environment operations.
Deferrable
Pattern that lets waiting tasks release worker slots while external conditions are pending.
Idempotency
Task design property that makes retries and reruns safe without duplicate side effects.
Data interval
The logical time window a DAG run processes, often different from the wall-clock trigger time.
