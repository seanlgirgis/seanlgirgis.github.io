Core vs ORM — what data engineers actually use

SQLAlchemy has two major layers: Core and ORM. Core is the SQL expression and database connectivity layer: engines, connections, transactions, SQL text, metadata, and result handling. ORM maps database rows to Python objects and is more common in application backends than batch pipelines.

Data engineers usually reach for Core because ETL work is set-oriented, SQL-heavy, and often crosses multiple systems. You typically need reliable connection management, parameterized execution, transaction control, and compatibility with pandas rather than object graphs with lazy-loaded relationships.

Use SQLAlchemy Core as the database access spine for pipeline code; use ORM only when the problem is truly object-centric.
The ORM can hide expensive queries behind attribute access. In data pipelines, hidden database reads are exactly how small code turns into slow production jobs.

Engine, Connection Strings & Native Drivers

The create_engine() call is the entry point. It does not immediately connect to the database; it builds an Engine object that knows how to create connections, manage the pool, and speak through the selected native driver.

The connection string follows the shape dialect+driver://user:password@host:port/dbname. SQLAlchemy wraps native drivers such as psycopg2 or psycopg for PostgreSQL, cx_Oracle or oracledb for Oracle, and pyodbc for SQL Server, but those drivers must still be installed and configured separately.

from sqlalchemy import create_engine

engine = create_engine(
    "postgresql+psycopg2://etl_user:secret@db01:5432/warehouse",
    pool_pre_ping=True,
    pool_recycle=1800,
)

with engine.connect() as conn:
    version = conn.exec_driver_sql("select version()").scalar_one()
The Engine is lazy, reusable, and thread-safe as a factory. Connections are the short-lived objects you open, use, and close.
A working SQLAlchemy URL does not mean the environment is complete. Native client libraries, ODBC DSNs, wallets, SSL certificates, and firewall rules can still break runtime connectivity.

Connection Pooling — sizing for pipelines

SQLAlchemy pools connections by default. pool_size controls persistent connections, max_overflow allows temporary burst connections, and pool_recycle helps prevent stale connections in environments where load balancers or databases close idle sessions.

For pipelines, pool sizing should match concurrency, not wishful thinking. A batch job with 20 worker threads and pool_size=5 may bottleneck on the pool; the same job with pool_size=50 may exhaust database sessions or overwhelm an operational system.

SettingMeaningPipeline use
pool_sizePersistent open connectionsMatch steady concurrent query load
max_overflowTemporary connections above pool sizeAbsorb short bursts without overcommitting
pool_timeoutSeconds to wait for a connectionFail loudly instead of hanging forever
pool_recycleMaximum connection ageAvoid stale network sessions
pool_pre_pingTest connection before useUseful for long-running workers
Pool size is a production contract between your pipeline and the database. Treat it like capacity planning, not decoration.
Creating an Engine inside every function call defeats pooling and can flood the database with connection churn.

Executing SQL Safely — text() & parameterized queries

Use text() for explicit SQL and bind parameters for values. This keeps SQL readable while letting the driver handle escaping, typing, and query parameters correctly.

Never build SQL by formatting user input, job parameters, filenames, dates, or IDs into a string. Even internal pipelines can ingest hostile or malformed data, and string-built SQL also breaks on quotes, dates, decimals, and driver-specific syntax.

from sqlalchemy import text

sql = text("""
    select endpoint_id, metric_name, value
    from telemetry.metrics
    where metric_name = :metric
      and timestamp >= :start_ts
""")

with engine.connect() as conn:
    rows = conn.execute(sql, {
        "metric": "cpu_pct",
        "start_ts": "2026-04-01",
    }).fetchmany(1000)
Parameterized SQL is both a security control and a correctness control. It lets the driver bind values using database-native rules.
Parameters bind values, not SQL identifiers. Table names, column names, and schema names need explicit whitelisting if they must be dynamic.

Reading Results & pandas read_sql

SQLAlchemy returns a CursorResult. Use fetchone() for one row, fetchmany(n) for controlled batches, and fetchall() only when the result is safely small. Rows can be accessed positionally or through mappings depending on how you consume the result.

For DataFrame pipelines, pd.read_sql_query() is often the cleanest bridge. It accepts a SQL string or SQLAlchemy text object plus an Engine or Connection, and it can stream chunks with chunksize to avoid loading a huge result into memory.

import pandas as pd
from sqlalchemy import text

query = text("""
    select endpoint_id, avg(value) as avg_cpu
    from telemetry.metrics
    where metric_name = :metric
    group by endpoint_id
""")

with engine.connect() as conn:
    df = pd.read_sql_query(query, conn, params={"metric": "cpu_pct"})
Use SQL to reduce data before pandas sees it. Push filters, joins, and aggregations into the database when the database is built for that workload.
fetchall() plus pd.DataFrame() is a common memory trap. It materializes everything before pandas even starts building the frame.

pandas to_sql — writing DataFrames to databases

DataFrame.to_sql() is convenient for landing small to medium DataFrames, staging tables, prototypes, and controlled internal loads. It can append, replace, or fail when a table exists, and method="multi" can reduce round trips for inserts.

For large production loads, to_sql() may not be enough. Native bulk loaders, database-specific COPY commands, external tables, S3 staging, or vendor bulk APIs are often faster and more controllable for millions of rows.

df.to_sql(
    name="stg_metric_summary",
    con=engine,
    schema="etl",
    if_exists="append",
    index=False,
    chunksize=5000,
    method="multi",
)
A strong pattern is: write to a staging table, validate counts and constraints, then merge into the target table inside a controlled transaction.
if_exists="replace" can drop and recreate a table. That may destroy indexes, grants, constraints, and downstream assumptions.

Transactions & Context Managers

Transactions define what becomes permanent and what rolls back together. SQLAlchemy context managers make this explicit: engine.connect() manages connection lifetime, while engine.begin() manages both connection lifetime and transaction commit or rollback.

For pipeline stages, transaction boundaries should align with business recovery points. Commit after a validated stage, not after every row; rollback when a stage fails; design idempotent writes so a rerun does not duplicate or corrupt data.

from sqlalchemy import text

with engine.begin() as conn:
    conn.execute(text("delete from etl.metric_summary where run_id = :run_id"),
                 {"run_id": run_id})
    conn.execute(text("""
        insert into etl.metric_summary(run_id, endpoint_id, avg_cpu)
        select :run_id, endpoint_id, avg(value)
        from telemetry.metrics
        where metric_name = 'cpu_pct'
        group by endpoint_id
    """), {"run_id": run_id})
engine.begin() is the clean default for write stages: success commits, exceptions roll back.
Long transactions can hold locks, bloat undo/redo logs, and block operational workloads. Batch carefully when writing large volumes.

Upsert Patterns (PostgreSQL / Oracle / SQL Server)

Upsert means insert new rows and update existing rows according to a key. SQLAlchemy can execute the vendor SQL directly, which is often the most practical path for data engineering because each database has different syntax and locking behavior.

PostgreSQL commonly uses INSERT ... ON CONFLICT. Oracle and SQL Server commonly use MERGE, but production teams often stage data first, deduplicate it, validate keys, and then merge from staging to target.

DatabasePatternProduction note
PostgreSQLON CONFLICTRequires a unique index or constraint on the conflict target
OracleMERGE INTOStage first; validate source uniqueness before merge
SQL ServerMERGE or update plus insertMany teams prefer explicit update/insert patterns for predictability
Any DBStaging tableBest place for validation, dedupe, and audit columns
stmt = text("""
    insert into etl.endpoint_status(endpoint_id, status, updated_at)
    values (:endpoint_id, :status, now())
    on conflict (endpoint_id)
    do update set
        status = excluded.status,
        updated_at = excluded.updated_at
""")

with engine.begin() as conn:
    conn.execute(stmt, records)
The most reliable upsert is usually a two-phase pipeline: land raw rows into staging, then perform one database-native merge into the curated table.
Upserts are not magic idempotency. If the match key is wrong, duplicated, nullable, or not enforced, the pipeline can silently produce bad history.

Secrets, Credentials & Large Result Sets

Connection strings contain sensitive material and should not be hardcoded. Pull credentials from environment variables, a secrets manager, container runtime injection, or cloud-native identity where possible. Logging the full engine URL is a real leak risk.

Large result sets need streaming discipline. Use server-side filtering, chunked reads, pagination keys, and database-native export mechanisms. In AWS-style pipelines, it is often better to unload from the database to S3 and process Parquet than to drag billions of rows through a Python process.

import os
from sqlalchemy import URL, create_engine

url = URL.create(
    "postgresql+psycopg2",
    username=os.environ["DB_USER"],
    password=os.environ["DB_PASSWORD"],
    host=os.environ["DB_HOST"],
    port=5432,
    database="warehouse",
)

engine = create_engine(url, pool_pre_ping=True)
Treat SQLAlchemy as the control plane for database access. For massive movement, prefer database unload, object storage, and columnar formats.
Never print raw connection URLs, exception objects with embedded DSNs, or environment dumps in CI logs. Secrets tend to leak through debug convenience.

Interview Q&A

Q: Why would a data engineer use SQLAlchemy Core instead of the ORM?
A: Core keeps the work close to SQL, which fits ETL and analytical pipelines. It gives you engines, connection pooling, transactions, parameterized execution, and result handling without object-mapping overhead. The ORM is useful for domain objects, but pipelines usually move sets of rows through database-native operations.
Q: What does create_engine() actually create?
A: It creates an Engine, which is a reusable database connectivity object and connection factory. It usually does not open a database connection immediately. The actual connection is checked out when you call connect(), use begin(), or execute through an API that needs one.
Q: How would you size a SQLAlchemy pool for a pipeline?
A: Start from actual concurrency: number of worker threads, processes, or parallel tasks that can hit the database at once. Then cap it below database session limits and operational tolerance. Use pool_timeout, monitoring, and database-side connection metrics to verify the setting under load.
Q: Why is string formatting SQL dangerous even in internal ETL?
A: Internal ETL still consumes external files, job parameters, API payloads, and unpredictable values. String formatting can create injection risk and also breaks correctness for quotes, dates, decimals, and special characters. Bind parameters let the driver handle values safely and consistently.
Q: When is pandas.to_sql() not the right loading strategy?
A: It is often too slow or too opaque for very large production loads. For millions or billions of rows, native bulk loaders, staged files, COPY-style commands, or cloud object storage patterns are usually better. to_sql() is strongest for staging, prototypes, and moderate append workloads.
Q: How do you make SQLAlchemy write stages recoverable?
A: Use explicit transaction scopes with engine.begin(), write to staging tables, validate counts and keys, then merge into targets. Include run IDs or batch IDs so reruns can cleanly replace or skip prior work. The goal is idempotency: a failed run can be retried without duplicate or partial data.

Quick Reference

Core
SQLAlchemy layer most useful for data engineers: engines, SQL expressions, connections, transactions, and results.
ORM
Object-relational mapper; useful for application models, less common for batch ETL.
create_engine()
Creates a lazy, reusable Engine that manages connectivity and pooling.
dialect+driver
Connection URL prefix such as postgresql+psycopg2, oracle+oracledb, or mssql+pyodbc.
pool_size
Number of persistent connections kept open for steady workload.
max_overflow
Temporary extra connections allowed during bursts above pool_size.
pool_pre_ping
Checks whether a pooled connection is alive before handing it to the caller.
text()
Wraps SQL text so bind parameters and SQLAlchemy execution APIs work cleanly.
:param
Named bind parameter style used inside SQLAlchemy text statements.
engine.begin()
Context manager that opens a connection and commits or rolls back a transaction automatically.
fetchmany(n)
Reads controlled batches from a result instead of materializing the full result set.
read_sql_query
pandas bridge for loading SQL query results into a DataFrame, with params and chunksize support.
to_sql
Convenient DataFrame writer; good for staging and moderate loads, not always ideal for bulk ingestion.
ON CONFLICT
PostgreSQL upsert pattern requiring a unique constraint or index on the conflict target.
MERGE
Oracle and SQL Server style upsert pattern, usually safest when fed from a validated staging table.
