What IAM Is

AWS Identity and Access Management is the authorization and authentication layer that guards every AWS API call. When any principal — a human user, a Lambda function, a Glue job, or an ECS task — makes an API request, IAM intercepts that request, identifies who is calling, and decides whether the action is permitted on the target resource. There is no trusted session that bypasses this check. Every request is evaluated from first principles every time.

IAM is a global service scoped to the AWS account rather than to a region. A role you create is visible everywhere. A policy you attach takes effect everywhere. This means weak IAM design creates broad risk across all regions and workloads in the account simultaneously. It also means mistakes are account-wide, not contained.

The authorization model defaults to deny. Nothing is allowed unless a matching allow exists in an applicable policy, and any explicit deny in any layer wins regardless of other allows. This deny-first behavior is non-negotiable and governs every decision IAM makes.

IAM evaluates every API request. A "trusted" session, once established, does not skip policy evaluation — the attached role's policies are still checked on each call.
The root account has unrestricted, irreversible power over the entire account. Enable MFA immediately, create no root access keys, and never use root for daily work. Create an admin IAM user or use IAM Identity Center instead.

Core Primitives

IAM has four building blocks: users, groups, roles, and policies. Policies contain the permission logic. Users, groups, and roles are attachment points — they carry policies into authorization decisions.

Users

An IAM user represents a long-lived identity with persistent credentials: a password for console access and optionally access keys for programmatic access. The problem with users is that their credentials are static. Leaked access keys remain valid until someone manually rotates or deletes them. For this reason, IAM users should be limited to human console access with MFA enforced. Workloads should never use IAM user access keys.

Groups

A group is a container for users, used for policy management at scale. Policies attached to the group apply to every member. Groups cannot be nested and cannot be used as principals in trust policies. They exist purely to simplify bulk permission assignment for teams.

Roles

A role is a temporary assumable identity. Unlike a user, a role has no permanent credentials. When a principal assumes a role, STS issues short-lived credentials — an access key, a secret key, and a session token — that expire automatically. This is the correct identity mechanism for all non-human workloads: EC2 instances, Lambda functions, ECS tasks, Glue jobs, CI/CD pipelines, and cross-account access patterns all use roles.

Policies

A policy is a JSON document that defines what actions are allowed or denied on what resources under what conditions. Policies are versioned, reusable, and can be attached to multiple identities. AWS provides hundreds of managed policies, but for production workloads you should author custom policies scoped precisely to the actions and resources your workload actually needs.

For all non-human identities, the answer is always a role. Roles automatically rotate credentials through STS, so there is nothing to leak that stays valid long enough to matter.
Service accounts with static access keys are one of the most common AWS security findings. Every time you see a workload using an IAM user key, that is a role waiting to replace it.

Policy Document Anatomy

An IAM policy is a JSON document with a Version field and a Statement array. Each statement specifies the permission logic for one rule. The four core fields in a statement are Effect, Action, Resource, and optionally Condition.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowRawS3ReadWithMFA",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-data-lake-raw",
        "arn:aws:s3:::my-data-lake-raw/*"
      ],
      "Condition": {
        "Bool": { "aws:MultiFactorAuthPresent": "true" },
        "StringEquals": { "aws:RequestedRegion": "us-east-1" }
      }
    }
  ]
}
FieldValuesPurpose
EffectAllow or DenyGrant or block the matched actions
ActionService:Operation stringsWhich API calls are in scope, e.g. s3:GetObject, glue:StartJobRun
ResourceARNs or *Which specific resources the statement applies to
PrincipalAWS account, role, serviceUsed in resource-based policies to identify the allowed caller
ConditionCondition operators and keysAdd context constraints: MFA, source IP, VPC endpoint, tag values
SidString identifierOptional label for the statement, useful for auditing and automation

Action and Resource together define the blast radius of any statement. The narrower both are, the closer you are to least privilege. Conditions add a second enforcement layer — for example, requiring that the request arrive via a specific VPC endpoint, or that MFA was used in the calling session.

"Action": "*" combined with "Resource": "*" and "Effect": "Allow" is equivalent to full administrator access. Never ship that on a production role. AWS managed policy AdministratorAccess does exactly this, which is why it should only be attached to break-glass or ops roles.
Wildcards inside action strings are legal but dangerous: s3:* grants all S3 operations including delete and ACL changes. Prefer explicit action lists so every permission is intentional and reviewable.

Policy Types

There are five categories of IAM policy, and they interact. Understanding each one is essential for diagnosing access failures and designing a secure permission model.

Identity-Based Policies

Attached directly to users, groups, or roles. These are the most common policy type. They define what the principal is allowed or denied across any resource. AWS provides managed policies (read-only, admin, service-specific) and you can author inline or customer-managed policies.

Resource-Based Policies

Attached to the resource itself rather than the caller. S3 buckets, SQS queues, SNS topics, KMS keys, Lambda functions, and ECR repositories all support resource-based policies. They identify the allowed principals explicitly using a Principal field. Critical for cross-account access without assuming a role.

Permission Boundaries

An advanced guardrail attached to a user or role that caps the maximum permissions it can ever have. Even if the identity policy grants broad access, only actions within the permission boundary are effective. The boundary does not grant anything by itself — it only constrains. Used to safely delegate role creation to dev teams without risking privilege escalation.

Service Control Policies (SCPs)

Organization-level controls applied to accounts or OUs in AWS Organizations. SCPs define the maximum permissions available to all identities in the account, including admins. They do not grant permissions — they restrict what identity policies can grant. Extremely useful for enforcing compliance guardrails (no public S3 buckets, no root key creation, region lockdown) across an entire organization.

Session Policies

Passed inline during an AssumeRole call to further restrict the role's permissions for that specific session. Effective permissions are the intersection of the role policy and the session policy. Useful for granting a scoped-down version of a shared role to a specific workflow or caller.

How IAM Evaluates a Request

IAM evaluates all applicable policies in a specific order every time a request arrives. The first matching explicit deny stops evaluation immediately. If no deny is found, IAM looks for an allow. If no allow is found, the default implicit deny applies. Understanding this order is what lets you reason about why access is granted or refused.

Evaluation order for each API request:

1. Explicit Deny in any policy layer?         --> DENY (final, no override)
2. SCP allows the action?                     --> Continue (if in an Organization)
3. Resource-based policy allows the caller?   --> ALLOW (cross-account) or continue (same account)
4. Permission boundary allows the action?     --> Continue or DENY
5. Session policy allows the action?          --> Continue or DENY
6. Identity-based policy allows the action?  --> ALLOW
7. None of the above matched?                 --> Implicit DENY
An explicit Deny in an SCP cannot be overridden even by an account administrator. This is intentional — SCPs are the organization's hard ceiling.
For cross-account access, both the identity-based policy on the caller and the resource-based policy on the target must independently allow the access. In same-account access, either is sufficient.

Roles vs Users: The Critical Distinction

The most important mental shift in AWS security is understanding why roles are almost always the right choice over users for anything that is not a human logging into the console. A user carries static credentials that can be extracted from environment files, leaked in logs, committed to source code, or left behind in containers. An IAM role issues credentials through STS that expire automatically, usually in one hour by default. If those credentials are exposed, the attacker has a shrinking window before they become worthless.

Beyond the credential lifetime advantage, roles are more operationally flexible. You can modify what a role can do at the policy level without touching the workload. You can attach the same role to many resources. You can implement cross-account access through role assumption without creating users in every account. You can rotate behavior by simply updating the policy, and the change takes effect on the next STS call.

Leaked STS credentials expire on their own. Leaked access keys stay valid until manually revoked. This single difference makes roles the correct default for every non-human identity in AWS.
If you find an IAM user access key in a codebase, treat it like a live security incident. Rotate it immediately, audit CloudTrail for recent usage, and replace the user with a role or IAM Identity Center.

How Services Get Permissions

Each AWS compute service has its own mechanism for attaching IAM credentials to a workload at runtime. The pattern is always the same: an IAM role is associated with the resource, and the service uses that role's temporary credentials when calling other AWS APIs. The workload code never sees long-term keys.

EC2 Instance Profiles

An instance profile is a container that holds an IAM role and attaches it to an EC2 instance. The EC2 metadata service (IMDS) at 169.254.169.254 exposes temporary credentials from that role. The AWS SDK automatically fetches and refreshes these credentials. You never configure keys in userdata or environment files. The instance profile is attached at launch time or can be swapped on a running instance.

# SDK auto-retrieves credentials from instance metadata:
import boto3
s3 = boto3.client('s3')          # no keys needed
s3.get_object(Bucket='my-data-lake', Key='raw/data.parquet')

Lambda Execution Role

Lambda functions assume an execution role on every invocation. The role must grant permissions to the services your function calls, as well as write access to CloudWatch Logs for the function's own log group. The SDK inside the function inherits these credentials automatically from the Lambda runtime environment.

# Minimal Lambda execution role policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": "arn:aws:logs:us-east-1:123456789012:log-group:/aws/lambda/my-function:*"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::my-data-lake/processed/*"
    }
  ]
}

ECS Task Role vs Task Execution Role

ECS uses two distinct roles that are often confused. The task execution role is used by the ECS agent to pull the container image from ECR, write logs to CloudWatch, and fetch secrets from Secrets Manager during task startup. This is infrastructure-level work. The task role is used by your application code running inside the container to call AWS services like S3, SQS, or DynamoDB at runtime. These must be separate roles with separate policies.

RoleUsed ByNeeds Access To
Task execution roleECS agent (before container starts)ECR pull, CloudWatch Logs, Secrets Manager, SSM Parameter Store
Task roleApplication code inside the containerS3, SQS, DynamoDB, Bedrock, Glue — whatever the app calls
Confusing the task role and task execution role is one of the most common ECS access failures. If your container starts but your app gets AccessDenied, you almost certainly set the permissions on the wrong role.

Glue Service Role

A Glue job assumes a service role that grants access to S3, the Glue Data Catalog, CloudWatch Logs, and any other services the ETL script touches. The trust policy on the role must allow glue.amazonaws.com to assume it. For jobs accessing encrypted S3 data, the role also needs KMS decrypt permissions on the relevant key.

# Glue service role trust policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "glue.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}

AssumeRole and STS

The AWS Security Token Service issues temporary credentials. The core operation is sts:AssumeRole: a caller presents their current identity, requests a specific role, and STS returns a fresh set of credentials scoped to that role. The returned credentials include an access key ID, a secret access key, and a session token, all of which expire at a configurable time between 15 minutes and 12 hours.

import boto3

sts = boto3.client('sts')
response = sts.assume_role(
    RoleArn='arn:aws:iam::987654321098:role/data-reader-role',
    RoleSessionName='glue-etl-session',
    DurationSeconds=3600,
    ExternalId='my-vendor-external-id'   # optional, for third-party trust
)

creds = response['Credentials']
# Use creds['AccessKeyId'], creds['SecretAccessKey'], creds['SessionToken']

The session name is recorded in CloudTrail for every API call made with those credentials — this is how you trace a specific pipeline run through access logs. The external ID is an additional secret that prevents confused deputy attacks when a third party assumes your role.

Common AssumeRole Patterns

PatternWho AssumesWhy

The session name you pass to AssumeRole appears in every CloudTrail log entry made during that session. Use meaningful names like glue-daily-etl-2026-04-25 to make audit trails readable.
The caller must have sts:AssumeRole permission on the target role ARN in their own identity policy, and the target role's trust policy must list the caller as an allowed principal. Both sides must agree.

Cross-Account Access

Cross-account access is one of the most common patterns in mature AWS organizations. The design separates workload accounts from data accounts, or dev/staging/prod into distinct accounts, and uses role assumption to let services in one account operate on resources in another.

The pattern requires two cooperating configurations. In Account B (the target), create a role with a trust policy that explicitly names the principal in Account A. In Account A, give the calling identity a policy that grants sts:AssumeRole on the Account B role's ARN. Both must be correct or the assumption fails.


{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/glue-etl-role"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "sts:ExternalId": "data-platform-x9f2" }
      }
    }
  ]
}


{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::account-b-datalake",
        "arn:aws:s3:::account-b-datalake/*"
      ]
    }
  ]
}
Trust policy controls who can assume the role. Permission policy controls what the role can do after assumption. These are two separate JSON documents and both must be correct. A common mistake is granting the right actions in the permission policy but forgetting to add the caller principal to the trust policy.
The external ID prevents the confused deputy problem: a third-party SaaS should not be able to assume your role just because they know its ARN. The external ID acts as a shared secret that both sides must agree on.

Cross-Account S3 via Resource Policy (No Role Assumption)

For simpler patterns where a single bucket needs to be accessed by a role in another account, a bucket policy can grant access directly without role assumption. This works only if both the bucket policy and the caller's identity policy allow the operation.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCrossAccountRead",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/glue-etl-role"
      },
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::account-b-datalake",
        "arn:aws:s3:::account-b-datalake/*"
      ]
    }
  ]
}

S3 Bucket Policies

S3 bucket policies are resource-based IAM policies attached directly to a bucket. They evaluate alongside identity-based policies and are the primary mechanism for enforcing access controls on data lake buckets: encryption requirements, VPC endpoint restrictions, cross-account sharing, and explicit denial of public access or non-secure transport.

Deny Non-TLS Access

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::my-data-lake",
        "arn:aws:s3:::my-data-lake/*"
      ],
      "Condition": {
        "Bool": { "aws:SecureTransport": "false" }
      }
    }
  ]
}

Restrict to VPC Endpoint Only

{
  "Sid": "DenyNonVPCEndpoint",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::my-private-datalake",
    "arn:aws:s3:::my-private-datalake/*"
  ],
  "Condition": {
    "StringNotEquals": {
      "aws:sourceVpce": "vpce-0a1b2c3d4e5f67890"
    }
  }
}

Enforce SSE-KMS Encryption on Put

{
  "Sid": "DenyUnencryptedPut",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::my-data-lake/*",
  "Condition": {
    "StringNotEquals": {
      "s3:x-amz-server-side-encryption": "aws:kms"
    }
  }
}
For access to succeed on a cross-account request, the bucket policy must explicitly allow the external principal. An identity policy alone is not sufficient. Both sides must permit the path independently.
Stack multiple statements in one bucket policy. Deny non-TLS, deny unencrypted puts, and restrict to VPC endpoint can all coexist as separate statements in the same policy document.

Permission Boundaries

A permission boundary is an advanced IAM feature that sets a hard ceiling on what an identity can do, regardless of what its attached policies say. It is attached to a user or role just like a managed policy, but instead of granting permissions, it constrains them. The effective permissions for any identity subject to a boundary are the intersection of the identity-based policy and the boundary — both must allow the action for it to succeed.

The most important use case is delegated role creation. If you allow a development team to create IAM roles for their services, they could escalate privileges by creating a role with administrator access and then assuming it. A permission boundary on all roles they create prevents this by capping the maximum permissions those roles can ever have, even if the team writes a broad policy document.

# Attach a boundary when creating a role via CLI
aws iam create-role \
  --role-name dev-team-service-role \
  --assume-role-policy-document file://trust.json \
  --permissions-boundary arn:aws:iam::123456789012:policy/dev-boundary-policy

# Boundary policy: caps what the role can ever reach
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:*", "dynamodb:*", "logs:*", "sqs:*"],
      "Resource": "*"
    }
  ]
}
The boundary alone grants nothing. If the identity policy allows S3 but the boundary does not, access is denied. If the boundary allows S3 but the identity policy does not, access is also denied. Both must independently allow an action.
Permission boundaries do not apply to the root account and are not the same as SCPs. SCPs restrict accounts; boundaries restrict individual users and roles. You often need both in a well-governed organization.

Service Control Policies

Service Control Policies live in AWS Organizations and apply to every principal in an account or organizational unit, including administrators. They do not grant permissions — they define the outer boundary of what any policy in the account can grant. Think of them as the organization's non-negotiable rules that individual accounts cannot override.

SCPs are invaluable for enforcing compliance requirements across a large AWS estate. You can deny specific high-risk actions (deleting CloudTrail, creating root access keys, disabling GuardDuty), restrict which regions accounts can use, or prevent specific instance types from being launched. These controls apply uniformly even if a workload account's admin tries to override them.

# SCP: Deny actions outside approved regions
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyNonApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "organizations:*",
        "support:*",
        "sts:*",
        "cloudfront:*",
        "route53:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["us-east-1", "us-west-2"]
        }
      }
    }
  ]
}
SCP Use CaseEffect
Deny root key creationNo one in the account can create root access keys
Region lockdownResources only in approved regions
Deny CloudTrail disableAudit trail cannot be turned off by anyone
Require MFA for sensitive actionsCertain operations require an MFA-authenticated session
Deny public S3 bucket ACLsBlock accidental data exposure at org level
An explicit Deny in an SCP overrides everything, including the account's own admin user. This is by design. Use this power carefully — a badly written SCP can lock an account out of critical services.

IAM for Data Engineering

Data engineering workloads tend to touch many AWS services simultaneously: S3 for storage, Glue for ETL, Athena for queries, Redshift for warehousing, SQS or Kinesis for streaming, Secrets Manager for database credentials, and CloudWatch for monitoring. The risk is natural sprawl — every job wants access to everything because it is easier to grant broad permissions than to carefully scope them per workload.

The correct architecture is role-per-workload. Each pipeline stage gets its own IAM role scoped to exactly the buckets, queues, tables, and secrets it touches. A Glue crawler role is different from an ETL job role. An ECS scheduler role is different from the task role of the job it triggers. Separation means a compromised role or a runaway script has limited blast radius.

Auditing Tools

IAM Access Analyzer scans your policies and resource configurations to find over-permissive access — public S3 buckets, roles accessible from outside your organization, and policy statements that grant more than intended. Enable it in every account and review its findings regularly.

IAM Access Advisor shows the last-accessed date for each service on any user or role. If a Glue role has not touched DynamoDB in six months, it probably does not need that permission. Use Access Advisor data to drive removal of unused permissions and prove least-privilege compliance to auditors.

CloudTrail records every IAM and API action. Use CloudTrail Lake or Athena queries over CloudTrail S3 logs to answer: who assumed this role, what did they call, when, and from where. This is your forensics foundation.

Access Analyzer plus Access Advisor together give you a continuous least-privilege feedback loop: find what is over-permissive today and find what has not been used and can be removed safely.

Common Mistakes

Hardcoded credentials in application code

Access keys committed to source control, baked into Docker images, or written into environment files are the most common cause of AWS credential exposure. Replace every static key with a role and remove the key immediately when found.

Using AdministratorAccess on workload roles

AdministratorAccess grants Action: * on Resource: *. It is appropriate only for break-glass or initial setup roles under strict controls. Using it on a Glue ETL role or an ECS task means a single exploit can do anything to your account.

Confusing ECS task role with task execution role

These are two separate IAM roles that serve different phases of the ECS lifecycle. Putting S3 and DynamoDB permissions on the execution role instead of the task role is a silent failure — the container starts fine, but application code gets AccessDenied at runtime.

Forgetting the KMS key policy

If a bucket uses SSE-KMS encryption, the calling role needs both S3 permissions and kms:Decrypt and kms:GenerateDataKey on the specific key. The KMS key policy must also allow the caller. Forgetting one of these layers is a very common cause of "S3 access denied" when IAM policies look correct.

Over-relying on managed policies

AWS managed policies like AmazonS3FullAccess grant permissions across all buckets and all actions. They are convenient during development but should be replaced with scoped customer-managed policies before production. Managed policies can also be updated by AWS, which may silently broaden permissions.

Not versioning IAM policies as code

Define all IAM roles and policies in Terraform or CloudFormation. This makes every permission change reviewable in a pull request, auditable in git history, and reproducible across environments. Ad-hoc console changes are invisible to code review and cannot be rolled back easily.

Interview Q&A

What is the difference between an IAM role and an IAM user, and when do you use each?
An IAM user is a long-lived identity with persistent credentials — a password and optionally static access keys. A role is a temporary assumable identity that issues short-lived STS credentials on each assumption, typically expiring in one hour. The key security difference is that leaked role credentials expire automatically, while leaked user access keys remain valid until someone manually rotates or deletes them. In practice, users should be limited to human console access with MFA enforced. Every non-human workload — EC2 instances, Lambda functions, ECS tasks, Glue jobs, GitHub Actions pipelines — should use a role. The only exception is legacy programmatic access that cannot be refactored, which should be treated as a known risk and tracked for eventual remediation.
Both an explicit Allow and an explicit Deny match a request. What happens, and why does this matter?
The explicit Deny wins unconditionally, regardless of where the Allow comes from or how many Allows exist. IAM's evaluation engine checks for explicit denies first and stops immediately if one is found. This matters enormously in multi-layer policy stacks. An SCP can deny an action even if the account admin's identity policy allows it. A bucket policy can deny access even if the calling role's identity policy permits it. Understanding this order is what lets you write preventive controls — a Deny in an SCP is a true hard stop that no policy within the account can override, which is exactly how organizations enforce compliance guardrails.
A Glue job is getting AccessDenied on S3. The Glue service role clearly has s3:GetObject. What do you check?
AccessDenied with a seemingly correct identity policy usually means another policy layer is blocking the request. Start by checking the S3 bucket policy — it may have a Deny statement for requests not coming through a VPC endpoint, or it may not explicitly allow the Glue role for cross-account access. Next check whether the bucket uses SSE-KMS encryption: the Glue role also needs kms:Decrypt and kms:GenerateDataKey on the key, and the KMS key policy must allow the Glue role as a caller. Then check whether an SCP in the organization denies the action in this account. Finally, use the IAM Policy Simulator to test the exact call path and look at the CloudTrail event for the denied request — the error message often identifies which policy layer caused the denial.
What is the difference between the ECS task execution role and the ECS task role?
The task execution role is used by the ECS agent before your container ever starts. It handles pulling the container image from ECR, writing logs to CloudWatch, and retrieving secrets from Secrets Manager or SSM Parameter Store that are injected as environment variables at startup. The task role is used by your application code running inside the container at runtime when it calls other AWS services like S3, DynamoDB, or SQS. Confusing these two is one of the most common ECS permission mistakes. If you put your application's S3 and DynamoDB permissions on the execution role, the container will start successfully, but your application will get AccessDenied when it tries to make those API calls because application code draws credentials from the task role, not the execution role.
How do you securely give GitHub Actions permission to deploy to AWS, without storing AWS keys in GitHub Secrets?
Use OIDC federation. GitHub Actions supports OpenID Connect, which allows a workflow to request a short-lived token from GitHub's OIDC provider and exchange it for temporary AWS credentials by assuming an IAM role. On the AWS side, you configure an IAM OIDC identity provider for token.actions.githubusercontent.com and create an IAM role whose trust policy allows sts:AssumeRoleWithWebIdentity from that provider. Critically, you add conditions to the trust policy scoping which repository, branch, and workflow can assume the role — for example, StringLike: token.actions.githubusercontent.com:sub: repo:seanlgirgis/data-platform:ref:refs/heads/main. This means there are no long-term keys to leak, the credentials expire after the workflow run, and only the specific branch you trust can deploy to production.
When would you use a permission boundary, and how is it different from an SCP?
Permission boundaries and SCPs both cap what permissions an identity can exercise, but they operate at different scopes. An SCP is an organization-level control that applies to every principal in an AWS account or OU — you use it to enforce org-wide policies like region restrictions, mandatory encryption, or preventing deletion of audit infrastructure. A permission boundary is attached to a specific IAM user or role and caps what that individual identity can do, regardless of what its identity policies say. The most important use case for permission boundaries is safe delegation: if you want to let a development team create IAM roles for their own services, you attach a permission boundary to every role they create, which prevents them from escalating privileges by creating a role with more permissions than they themselves have. Unlike an SCP, a permission boundary affects only the role it is attached to and has no effect on other identities in the account.
