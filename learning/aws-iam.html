What IAM Is

AWS IAM is the central authorization layer for AWS. Every API request from a user, role, or service is evaluated against IAM and related policy controls before access is allowed. IAM answers who is calling, how they are authenticated, and whether they are authorized for the requested action.

IAM is global at account scope, not region-specific. That means weak IAM design can create broad risk across all workloads in the account.

IAM is evaluated on every request. There is no permanent "trusted" session that bypasses policy checks.
Root credentials have full, irreversible account power. Enable MFA on root, create no root access keys, and never use root for daily operations.

Core Primitives: Users, Groups, Roles, Policies

IAM has four building blocks: users, groups, roles, and policies. Policies define permission logic. The others are attachment points and identity types.

Policy Document Anatomy

An IAM policy is JSON containing one or more statements. Each statement uses Effect, Action, Resource, and optional Condition.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": ["arn:aws:s3:::my-data-bucket/raw/*"],
      "Condition": {
        "Bool": {"aws:MultiFactorAuthPresent": "true"}
      }
    }
  ]
}

Action and Resource scope determine blast radius. Conditions add context-aware limits such as source network, MFA, or region.

`Action: *` plus `Resource: *` with Allow is effectively admin access. Never ship that in production roles.

Policy Types and Evaluation Logic

Identity-based policies attach to users, groups, and roles. Resource-based policies attach directly to resources like S3 buckets or SQS queues. Permission boundaries cap maximum rights for identities. SCPs apply organization-wide limits.

Effective access is the intersection of these layers. Explicit deny in any applicable layer overrides all allows.

Think of IAM as a deny-first engine: default deny, explicit deny precedence, and narrow allow paths.

Roles vs Users: The Critical Distinction

Users are long-lived identities with potential static credentials. Roles are temporary identities assumed by trusted principals and issued short-lived credentials through STS.

For services, role attachment is mandatory best practice: EC2 instance profile, Lambda execution role, ECS task role, Glue service role.

Leaked STS credentials expire. Leaked access keys persist until manually rotated.
Service accounts with access keys are a high-risk anti-pattern. Replace with roles.

How Services Get Permissions

EC2 obtains credentials from attached instance profiles via instance metadata. Lambda assumes its execution role on invocation. ECS separates task execution role from task role. Glue uses a dedicated service role for data plane actions.

These are runtime identity mechanisms, not hardcoded credential flows.

In ECS, execution role and task role are different. Mixing them causes access failures and confusing diagnostics.

AssumeRole and STS

AssumeRole calls STS to exchange current credentials for temporary credentials of a target role. Returned keys include an access key, secret, and session token with bounded session duration.

This is core to secure automation and federation. CI/CD, admin elevation, and workload identity switching rely on this path.

AssumeRole is the standard for temporary privileged access and federated identity in AWS.

Cross-Account Access

Cross-account design uses a role in Account B trusted by Account A principal(s). Trust policy controls who may assume. Permission policy controls what the role can do after assumption.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::111122223333:role/data-pipeline-role"},
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {"sts:ExternalId": "vendor-shared-id"}
      }
    }
  ]
}
Trust policy and permission policy are separate controls. Both must be correct.

IAM in a Data Engineering Stack

Data platforms should isolate permissions per workload: crawler role, ETL role, trigger role, analytics role. Each role should target specific resources and actions only.

Use Access Analyzer for over-permission findings and CloudTrail for immutable IAM change auditing.

Defense in depth means narrowing IAM role scope and also constraining resource policies like S3 bucket policy.

S3 Bucket Policies

S3 bucket policies are resource-based and evaluated with identity policies. They are essential for encryption enforcement, source network controls, and cross-account sharing.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyNonVPCEndpoint",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::my-secure-bucket",
        "arn:aws:s3:::my-secure-bucket/*"
      ],
      "Condition": {
        "StringNotEquals": {"aws:sourceVpce": "vpce-0123456789abcdef0"}
      }
    }
  ]
}
For access to succeed, policy layers must align. For cross-account, both sides must permit the path.

Permission Boundaries

Permission boundaries cap what an identity can ever do. They do not grant permissions by themselves, but they constrain granted permissions from attached identity policies.

Use boundaries when delegating role creation to engineering teams to prevent privilege escalation.

Effective permissions are bounded intersection, not union.

Common Mistakes

Hardcoding credentials in code or env files instead of using roles.
Using wildcard admin policies for convenience in production.
Confusing ECS task role with task execution role during incident response.
Using root account for daily administrative work.
Failing to rotate and remove unused access keys.

Least Privilege in Practice

Start broad only in controlled development, then reduce permissions based on real CloudTrail evidence. Use policy simulator for change validation before deployment.

Version IAM policy definitions in infrastructure as code to make changes reviewable and auditable.

Access Analyzer and Access Advisor together provide a practical loop to remove unused permissions safely.

Interview Q&A

What is the difference between an IAM role and an IAM user?
A user is typically long-lived identity; a role is temporary identity assumed through STS and preferred for workloads.
If explicit Deny and explicit Allow both match, what happens?
Explicit deny wins immediately, regardless of where allow appears.
A Glue job has S3 access denied. What do you check first?
Validate the runtime-assumed role, then evaluate identity policy, bucket policy, and KMS key policy together.
What is the difference between ECS task role and task execution role?
Task role is what application code can call; execution role is what ECS agent uses for image pull and logs.
How do you securely grant GitHub Actions AWS deploy permissions?
Use OIDC federation with AssumeRole and tightly scoped trust and permission conditions.
When would you use a permission boundary?
When delegating role creation to teams while preventing them from granting permissions outside allowed guardrails.
