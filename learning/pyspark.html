Where PySpark Fits in Data Engineering

PySpark is the Python API for Apache Spark, a distributed compute engine designed for large-scale batch processing, SQL analytics, machine learning feature preparation, and streaming workloads. For a senior data engineer, PySpark is less about writing Python loops and more about expressing data transformations that Spark can optimize and execute across many machines.

The practical value is that PySpark lets you process data too large or too slow for a single-node Pandas job while keeping the development experience close to Python. The tradeoff is that you must think in distributed systems terms: partitions, shuffles, executor memory, serialization, file layout, and cluster-level failure behavior.

PySpark is best treated as a distributed SQL and DataFrame engine with a Python control plane, not as normal Python running faster.
A common production failure is porting Pandas-style row-by-row thinking into Spark. If the code depends on Python loops, repeated collects, or custom UDFs for basic logic, Spark loses most of its advantage.
Use PySpark WhenPrefer Something Else When
Data is hundreds of GBs to TBs and needs distributed compute.The job is a few MBs or simple enough for SQL, Pandas, DuckDB, or Athena.
You need joins, aggregations, feature prep, deduplication, or file compaction at scale.You need low-latency request-response serving.
You need repeatable pipelines on S3, HDFS, Delta, Iceberg, or Hive tables.You need millisecond operational transactions.
You need to integrate with EMR, Glue, Databricks, Airflow, or lakehouse tables.You only need ad-hoc reporting over already optimized data.

Spark Architecture: Driver, Executors, Cluster Manager

A Spark application has a driver process and a set of executor processes. The driver runs the main application, builds the logical plan, requests resources, coordinates tasks, and tracks job progress. Executors run tasks against partitions of data and keep cached data in memory or disk. The cluster manager, such as YARN, Kubernetes, standalone Spark, EMR, Glue, or Databricks infrastructure, allocates resources.

The driver does not process every row. It plans and coordinates. Executors do the distributed work. When engineers accidentally pull data back to the driver using collect(), toPandas(), or oversized broadcast variables, the driver becomes the bottleneck and can crash even when the cluster has plenty of executor capacity.

The driver is the brain; executors are the workers. Good Spark code sends computation to the data instead of dragging data back to the driver.
Driver OOM is often caused by control-plane mistakes: collecting large datasets, creating huge task graphs, listing millions of files, or broadcasting a dimension table that is not actually small.
ComponentRoleFailure Impact
DriverBuilds plans, schedules jobs, manages metadata, receives action results.Application fails if the driver dies.
ExecutorRuns tasks, stores shuffle data, caches partitions.Tasks can retry; cached or shuffle data may be recomputed.
Cluster managerAllocates CPU, memory, and containers or pods.Resource shortage causes pending jobs, executor loss, or preemption.
DAG schedulerSplits logical work into stages separated by shuffle boundaries.Poor plans produce many stages and high shuffle cost.

RDDs vs DataFrames vs Datasets

Spark started with RDDs, which are distributed collections of objects. RDDs give low-level control, but the optimizer sees them as opaque code. DataFrames represent structured data with schema, columns, expressions, and relational operations. That structure lets Spark use Catalyst optimization and Tungsten execution improvements.

For data engineering, DataFrames usually win. They are easier to optimize, easier to explain, easier to push down into data sources, and better aligned with SQL, Parquet, Glue Catalog, Hive Metastore, Delta, and Iceberg. Datasets are strongly typed in Scala and Java, but PySpark users mostly work with DataFrames because Python does not get the same compile-time type benefits.

Senior PySpark code should look more like relational algebra than Python object manipulation: select, filter, join, groupBy, window, write.
RDDs still exist, but reaching for them in a modern data pipeline is usually a smell unless you need a very specific low-level operation that DataFrames cannot express.
APIBest ForTradeoff
RDDLow-level distributed transformations over arbitrary objects.Limited optimizer visibility; more manual tuning.
DataFrameStructured ETL, SQL-like transformations, lakehouse pipelines.Requires thinking in columns and expressions.
DatasetTyped JVM workloads in Scala or Java.Not the main ergonomic path in PySpark.
from pyspark.sql import functions as F

curated = (
    spark.read.parquet("s3://lake/raw/orders/dt=2026-04-25/")
    .filter(F.col("status") == "COMPLETE")
    .groupBy("customer_id")
    .agg(
        F.count("*").alias("order_count"),
        F.sum("order_total").alias("gross_revenue")
    )
)

Lazy Evaluation, Transformations, and Actions

Spark is lazy. Transformations such as select, filter, withColumn, join, and groupBy build a logical plan but do not execute immediately. Actions such as count, show, collect, write, and foreachBatch trigger execution.

This matters because Spark can optimize the full plan before running it. It can push filters down, remove unused columns, combine operations, reorder some work, and choose physical strategies. But lazy evaluation can also surprise engineers during debugging because an error may appear many lines after the transformation that caused it.

A PySpark pipeline is a recipe until an action runs. Optimization happens because Spark can inspect the whole recipe before cooking.
Do not sprinkle count(), show(), or cache() everywhere for debugging in production code. Each action can trigger a full job and multiply cost.
Operation TypeExamplesRuns Immediately?
Narrow transformationselect, filter, withColumnNo
Wide transformationgroupBy, distinct, many joinsNo, but creates shuffle boundary
Actionwrite, count, collect, showYes
# Builds a plan only
bad_orders = orders.filter("order_total < 0").select("order_id", "order_total")

# Triggers execution
bad_orders.write.mode("overwrite").parquet("s3://lake/quality/bad_orders/dt=2026-04-25/")

Partitions, Parallelism, Repartition, and Coalesce

Partitions are Spark's unit of parallelism. Each task usually processes one partition. Too few partitions underuse the cluster. Too many partitions create scheduling overhead, tiny files, and excessive task metadata. The right number depends on data size, file layout, executor cores, and the cost of the transformation.

repartition() performs a full shuffle to increase or rebalance partitions. coalesce() usually reduces partitions without a full shuffle, making it cheaper but less able to fix skew. Use repartition before large joins or writes when distribution matters. Use coalesce to reduce output files after the heavy work is done.

Partition count is not a cosmetic setting. It controls parallelism, memory pressure, shuffle behavior, and the number of output files.
A frequent lakehouse problem is the small files trap: a job succeeds but writes thousands of tiny Parquet files, making Athena, Glue, Spark, and Redshift Spectrum slower and more expensive later.
MethodUse CaseCost
repartition(n)Increase partitions or rebalance data before expensive work.Full shuffle.
repartition("key")Cluster same keys together before joins or writes.Full shuffle.
coalesce(n)Reduce partitions before final output.Usually avoids full shuffle.
partitionBy()Write Hive-style directory partitions.Affects physical file layout.
daily = spark.read.parquet("s3://lake/processed/events/dt=2026-04-25/")

# Rebalance before a large aggregation
agg = daily.repartition(400, "customer_id").groupBy("customer_id").count()

# Reduce file count for the final write
agg.coalesce(64).write.mode("overwrite").parquet("s3://lake/curated/customer_event_counts/dt=2026-04-25/")

Shuffles: The Expensive Boundary

A shuffle moves data across executors so records with the same key land together. Shuffles are triggered by operations such as groupBy, distinct, orderBy, many joins, window functions, and repartitioning. They are expensive because they use network, disk spill, serialization, and many intermediate files.

Most Spark performance tuning starts with reducing shuffle volume. Filter early, project only needed columns, avoid unnecessary distincts, pre-aggregate before joins when possible, and use broadcast joins for genuinely small dimensions. In the Spark UI, shuffle read/write size, spill metrics, and stage duration are the first clues.

A shuffle is the moment Spark stops doing local partition work and starts redistributing data across the cluster.
A job can look fine in development and collapse in production when a shuffle grows from GBs to TBs. The failure mode is often executor OOM, disk spill storms, or a few slow straggler tasks.
OperationShuffle RiskMitigation
groupByHigh for high-cardinality keys.Filter/project first; aggregate in stages.
joinHigh unless broadcast applies.Broadcast small side; align partitioning; handle skew.
distinctHigh because duplicates must meet.Deduplicate only required columns.
orderByHigh global sort.Avoid unless business output truly needs ordering.
# Avoid carrying unused columns into a shuffle
small_projection = events.select("customer_id", "event_type", "event_ts")

counts = (
    small_projection
    .filter("event_ts >= timestamp'2026-04-25 00:00:00'")
    .groupBy("customer_id", "event_type")
    .count()
)

Joins: Broadcast, Sort-Merge, and Strategy Control

Join strategy has a huge effect on PySpark performance. A broadcast hash join sends a small table to every executor so the large table can be scanned locally. A sort-merge join shuffles and sorts both sides by the join key. Sort-merge is scalable for large tables but expensive. Broadcast is fast when the dimension table is truly small, but dangerous when it exceeds memory expectations.

Spark can choose a strategy automatically using statistics and configuration such as spark.sql.autoBroadcastJoinThreshold. In production, statistics can be missing, stale, or misleading. Senior engineers inspect the physical plan and use hints only when they understand the data size and failure mode.

Broadcast joins remove the large-table shuffle by replicating the small side. Sort-merge joins scale to large joins but pay the shuffle-and-sort bill.
Forcing broadcast on a table that is not small can crash executors. Forcing sort-merge on a tiny dimension can waste minutes shuffling data that could have stayed local.
Join StrategyBest WhenRisk
Broadcast hash joinOne side is small enough to fit safely in executor memory.Executor OOM if underestimated.
Sort-merge joinBoth sides are large and join keys are sortable.Large shuffle and sort cost.
Shuffle hash joinOne side per partition is small after shuffle.Memory pressure by partition.
Bucketed joinTables are pre-bucketed compatibly.Operational complexity and strict layout requirements.
from pyspark.sql import functions as F

customers = spark.read.parquet("s3://lake/dim/customers/")
orders = spark.read.parquet("s3://lake/fact/orders/dt=2026-04-25/")

joined = orders.join(F.broadcast(customers), "customer_id", "left")
joined.explain("formatted")

Data Skew and Salting

Data skew happens when a few keys contain far more records than other keys. Spark may create hundreds of normal tasks and a few monster tasks that run forever. In the Spark UI, skew appears as long-tail tasks, huge shuffle read for a small number of tasks, and stages where most tasks finish quickly but a few stragglers dominate runtime.

Salting is one remedy. You add a synthetic random bucket to spread a hot key across multiple partitions, then join or aggregate with the salted key. This is powerful but should be targeted. Salting every key blindly can increase data volume and complexity without solving the actual hotspot.

Skew is not a cluster-size problem first. It is a data distribution problem. Adding more executors may not help if one key creates one huge task.
Salting changes the shape of the computation. If you salt an aggregation, you often need a second aggregation to combine salted partial results back to the true key.
from pyspark.sql import functions as F

salt_buckets = 16

# Salt the large fact side for known hot customer IDs
orders_salted = orders.withColumn(
    "salt",
    F.when(F.col("customer_id").isin("UNKNOWN", "GUEST"),
           (F.rand() * salt_buckets).cast("int"))
     .otherwise(F.lit(0))
)

# Expand the small dimension side for those hot keys
salts = spark.range(salt_buckets).withColumnRenamed("id", "salt")
customers_salted = customers.crossJoin(salts)

fixed_join = orders_salted.join(customers_salted, ["customer_id", "salt"], "left")
Skew SignalWhat It MeansResponse
One task runs much longerA partition has too much data.Identify hot keys and repartition or salt.
Huge shuffle read in few tasksSome keys dominate shuffle output.Enable AQE skew join handling; consider salting.
Executor OOM on specific stageLarge partition or broadcast pressure.Reduce partition size or change join strategy.

Adaptive Query Execution

Adaptive Query Execution, or AQE, lets Spark adjust the physical plan at runtime using actual shuffle statistics. It can coalesce small shuffle partitions, convert sort-merge joins to broadcast joins when runtime size is small enough, and split skewed partitions for certain joins. In Spark 3, AQE is one of the biggest practical improvements for production SQL and DataFrame jobs.

AQE is not magic. It cannot fix poor file layout, broken business logic, Python UDF overhead, or massive data expansion. It works best when the query is expressed with DataFrame or SQL operations that Spark understands.

AQE helps Spark correct bad guesses after it sees real runtime data sizes.
Do not use AQE as an excuse to ignore data modeling. A badly partitioned lake, missing statistics, and explosive joins can still overwhelm the cluster.
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.autoBroadcastJoinThreshold", "64MB")
AQE FeatureBenefitWatch For
Coalesce shuffle partitionsReduces tiny post-shuffle tasks.Too much coalescing can reduce parallelism.
Dynamic join conversionCan switch to broadcast at runtime.Broadcast still needs memory headroom.
Skew join handlingSplits large skewed shuffle partitions.Only applies to supported patterns.

UDFs, Built-In Functions, and Python Overhead

PySpark has a Python API, but Spark's execution engine is JVM-based. Built-in SQL functions are optimized, code-generated, and visible to Catalyst. Standard Python UDFs force data to cross the Python-JVM boundary and often prevent important optimizations. Pandas UDFs can improve throughput through Arrow vectorization, but they still add serialization and operational complexity.

The senior rule is simple: use built-in functions first, SQL expressions second, Pandas UDFs only when needed, and normal Python UDFs as a last resort. Many UDFs exist only because the engineer did not know the matching Spark function.

The fastest PySpark code is often the code that lets Spark stay inside its optimized expression engine.
A Python UDF can silently disable predicate pushdown, column pruning, code generation, and other optimizations. It may pass tests and then become the slowest part of the production job.
ApproachPerformanceOptimizer Visibility
Built-in functionsBestHigh
SQL expressionsBestHigh
Pandas UDFMedium to goodLimited
Python UDFOften poorLow
from pyspark.sql import functions as F

# Prefer this
clean = raw.withColumn("email_domain", F.lower(F.regexp_extract("email", "@(.+)$", 1)))

# Avoid this for simple parsing
# clean = raw.withColumn("email_domain", my_python_udf("email"))

Parquet on S3: Pruning, Pushdown, and Schema Evolution

Most AWS data engineering PySpark work eventually lands on S3 in Parquet, often registered in Glue Data Catalog and queried by Athena, EMR, Glue, Databricks, or Redshift Spectrum. Parquet is columnar, compressed, splittable, and stores metadata that helps engines skip data. This is why Parquet is usually a better lake format than CSV for analytics.

Partition pruning skips entire directory partitions such as dt=2026-04-25. Predicate pushdown skips row groups inside files when Parquet statistics prove they cannot match a filter. Column pruning reads only needed columns. Together, these reduce scan cost and runtime.

Good S3 data layout is a performance feature. Spark tuning cannot fully compensate for bad file sizes, bad partition keys, and inconsistent schemas.
Partitioning by a high-cardinality field such as user ID can create millions of directories and tiny files. Partition by common filter dimensions such as date, region, tenant, or source only when they match query patterns.
Design ChoiceGood PatternBad Pattern
FormatParquet for analytics and ETL outputs.CSV for large recurring analytical scans.
PartitioningDate or low/medium-cardinality query filters.High-cardinality keys with tiny partitions.
File sizeUsually hundreds of MBs per file for large tables.Thousands of 1 MB files.
Schema evolutionAdd nullable columns carefully and test readers.Change types in place without migration.
curated.write \
    .mode("overwrite") \
    .format("parquet") \
    .partitionBy("dt", "region") \
    .option("compression", "snappy") \
    .save("s3://lake/curated/orders/")

filtered = (
    spark.read.parquet("s3://lake/curated/orders/")
    .where("dt = '2026-04-25' and region = 'us-east-1'")

)

EMR vs Glue vs Databricks

PySpark can run on several managed platforms. AWS EMR gives strong control over cluster configuration, Spark versions, bootstrap actions, networking, and cost model. AWS Glue gives a serverless job abstraction with Glue Catalog integration, job bookmarks, crawlers, and managed workers. Databricks gives an integrated lakehouse platform with strong notebooks, Delta Lake, job orchestration, governance, and runtime optimizations.

The right platform depends on team maturity, operational needs, governance, workload shape, and cost control. For heavy custom Spark engineering, EMR or Databricks often gives more control. For scheduled AWS-native ETL with minimal infrastructure management, Glue is attractive. For collaborative analytics and lakehouse operations, Databricks is often the most productive.

The PySpark code may look similar across platforms, but the operational model is very different: cluster ownership, startup time, debugging, dependency packaging, permissions, and cost visibility all change.
Platform migration is rarely just a runtime change. Job bookmarks, cluster libraries, metastore behavior, IAM permissions, secrets, logging, and table formats can all differ.
PlatformStrengthWatch For
EMRFlexible AWS-managed Spark clusters; strong control.More cluster operations and tuning responsibility.
GlueServerless ETL, Catalog integration, simple scheduling.Runtime constraints, startup latency, worker sizing quirks.
DatabricksProductive lakehouse platform, Delta ecosystem, collaborative workflows.Vendor cost model and platform-specific features.

Performance Tuning and OOM Failures

Performance tuning starts with evidence: Spark UI stages, task time distribution, shuffle read/write, spill, input size, executor logs, and physical plans. Randomly increasing memory may hide symptoms while raising cost. A better sequence is to identify whether the bottleneck is input scan, shuffle, skew, join strategy, serialization, output file layout, or Python execution.

Common memory failures split into driver OOM and executor OOM. Driver OOM usually means too much metadata or result data returned to the driver. Executor OOM usually means partitions are too large, joins are too heavy, broadcast is oversized, skew is severe, or UDFs create excessive memory pressure.

Tune the shape of the work before tuning the size of the cluster. Better plans usually beat bigger clusters.
Increasing spark.sql.shuffle.partitions can reduce per-task memory pressure but create overhead. Decreasing it can reduce overhead but create huge partitions. There is no universal magic number.
SymptomLikely CauseFix Direction
Driver OOMcollect(), toPandas(), huge file listing, huge plan.Limit driver data; write results; reduce metadata explosion.
Executor OOMLarge partitions, bad join, skew, oversized broadcast.Repartition, reduce shuffle volume, handle skew, change join strategy.
Disk spill highInsufficient memory for shuffle or sort.Reduce data before shuffle; adjust partitions and memory overhead.
Many tiny output filesToo many partitions at write time.Coalesce or optimize file compaction strategy.
spark.conf.set("spark.sql.shuffle.partitions", "400")
spark.conf.set("spark.sql.files.maxPartitionBytes", "134217728")
spark.conf.set("spark.executor.memoryOverhead", "2048")

Production Patterns for Reliable Spark Pipelines

Production PySpark is about repeatable outputs, observable failures, and safe reruns. Use immutable raw zones, deterministic run dates, explicit input paths, schema validation, row-count checks, data-quality checks, and idempotent writes. Avoid jobs that depend on hidden global state or the accidental current contents of a directory.

On AWS, PySpark commonly sits in a broader stack: S3 for storage, Glue Catalog for metadata, Athena for validation, EMR or Glue for execution, Airflow or Step Functions for orchestration, CloudWatch for logs, and IAM/KMS for security. The pipeline is only as reliable as the weakest boundary between these services.

A Spark job should be restartable. If rerunning the same run date produces different or duplicated output, the pipeline is not production-safe yet.
Writing directly into a final S3 prefix without a staging or commit pattern can expose partial data to downstream readers if the job fails midway.
# Safer pattern: write to a run-specific staging path, validate, then promote
run_date = "2026-04-25"
staging = f"s3://lake/_staging/orders_curated/run_date={run_date}/"
final = f"s3://lake/curated/orders/dt={run_date}/"

curated.write.mode("overwrite").parquet(staging)

# After validation, promote using table format commit semantics,
# object copy, or a controlled metadata update depending on platform.
Production ConcernRecommended Pattern
RerunsParameterize by run date and write idempotently.
Schema driftValidate schema before writing curated data.
Partial outputUse staging paths or table formats with commit semantics.
ObservabilityEmit counts, input paths, output paths, duration, and quality metrics.
SecurityUse least-privilege IAM, encrypted buckets, and KMS-aware roles.

Interview Q&A

Q: How would you explain the difference between a transformation and an action in Spark?
A: A transformation builds the logical plan and is lazy; an action triggers execution. For example, filter and join only describe work, while count or write starts a Spark job. This matters because Spark optimizes the whole lineage before execution.
Q: A PySpark job is slow and the Spark UI shows one task running much longer than all others. What do you check?
A: I suspect skew. I check task duration distribution, shuffle read size by task, partition sizes, and hot keys. Remedies include filtering early, changing partition strategy, enabling AQE skew handling, or salting specific hot keys.
Q: When would you use a broadcast join, and when would you avoid it?
A: I use broadcast when one side is small enough to fit in executor memory and avoids shuffling the large side. I avoid it when table size is uncertain, stats are stale, the dimension can grow, or executor memory is already tight.
Q: Why are Python UDFs often discouraged in PySpark pipelines?
A: Python UDFs force data across the JVM-Python boundary and reduce Catalyst optimizer visibility. Built-in functions usually perform better because Spark can optimize, code-generate, prune columns, and push predicates more effectively.
Q: How do you design Parquet data on S3 for efficient Spark and Athena reads?
A: I use columnar Parquet with compression, choose partitions based on common filters such as date or region, avoid high-cardinality partitions, target healthy file sizes, and validate schema evolution. The goal is partition pruning, predicate pushdown, and fewer small files.
Q: How do you distinguish driver OOM from executor OOM?
A: Driver OOM usually comes from collecting data, converting to Pandas, huge metadata listing, or massive plans. Executor OOM usually comes from large partitions, shuffles, joins, skew, oversized broadcasts, or UDF memory pressure. The fix depends on where memory is being consumed.
