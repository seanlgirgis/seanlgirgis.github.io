Architecture & Execution Model

PySpark is the Python API for Apache Spark, but the engine doing the heavy lifting is still Spark on the JVM. The driver builds the logical plan, coordinates jobs, and requests resources from a cluster manager. Executors run tasks against partitions, cache data, perform shuffles, and return results or metadata back to the driver.

For data engineers, the important split is control plane versus data plane. Python code defines the work, but distributed execution happens across executor JVMs. The fastest PySpark jobs keep data inside Spark SQL expressions and avoid pulling large data back into Python or the driver.

Key insight: the driver is the brain, executors are the workers, and partitions are the units of parallel work. Most production failures come from confusing those boundaries.
Gotcha: collect(), large toPandas(), or driver-side loops over data can turn a distributed job into a single-machine memory problem.

Lazy Evaluation & DAG

Spark transformations are lazy. A chain of select, filter, join, and withColumn calls builds a plan but does not execute until an action such as count, write, show, or collect is called. This lets Catalyst optimize the full query instead of executing line by line.

The DAG scheduler breaks the optimized plan into stages. Narrow dependencies, such as filters and projections, can run in the same stage. Wide dependencies, such as joins and aggregations, usually create shuffle boundaries and new stages.

df = (
    spark.read.parquet("s3://lake/raw/events/")
    .filter("event_date >= '2026-04-01'")
    .select("user_id", "event_type", "event_ts")
    .groupBy("event_type")
    .count()
)

df.explain("formatted")   # plan inspection, still no data movement
df.write.mode("overwrite").parquet("s3://lake/curated/event_counts/")
Key insight: read the plan before tuning. explain("formatted") often reveals unnecessary scans, shuffles, broadcasts, and Python execution.
Gotcha: adding many debug actions during development can run the same expensive lineage repeatedly unless the intermediate data is cached or checkpointed intentionally.

Partitioning & Coalesce

Partitions determine parallelism. Too few partitions underuse the cluster; too many small partitions create task scheduling overhead and tiny output files. Spark reads from file splits, shuffle settings, and explicit repartitioning to decide how work is divided.

repartition(n) performs a full shuffle and can increase or decrease partition count. coalesce(n) avoids a full shuffle and is usually used to reduce partitions before writing, especially after heavy filtering. The tradeoff is that coalesce can create uneven partitions if the upstream data is already imbalanced.

OperationBest useTradeoff
repartitionRedistribute data evenly by count or keyFull shuffle cost
coalesceReduce partition count before outputMay preserve skew
File partitioningPrune reads by date, region, tenantBad keys create small files
Key insight: partitioning is both a compute decision and a storage decision. The output layout affects every Athena, Glue, EMR, and downstream Spark read after it.
Gotcha: forcing a single output file with coalesce(1) is convenient for demos and painful in production. It serializes the write path and often creates a bottleneck.

Shuffles

A shuffle moves data across the network so records with the same key can land together. Joins, groupBy, distinct, orderBy, window operations, and repartitioning commonly trigger shuffles. Shuffles are expensive because they involve serialization, disk spill, network transfer, and new stage boundaries.

The goal is not to eliminate every shuffle; analytical workloads need them. The goal is to make shuffles intentional, reduce the data volume before they happen, and avoid repeated shuffles on the same keys.

Key insight: filter early, project only needed columns, and aggregate before joining when the business logic allows it. Less data entering the shuffle is the cleanest optimization.
Gotcha: orderBy on a large dataset can create a global sort. Use partition-aware sorting or avoid global ordering unless the final consumer truly needs it.

Joins & Broadcast

Spark commonly uses sort-merge joins for large tables and broadcast hash joins when one side is small enough to ship to every executor. Broadcast joins avoid shuffling the large table and can be a huge win for dimension lookups, reference data, and small mapping tables.

The risk is memory. A table that looks small by row count may be large after deserialization, wide columns, or poor statistics. Use broadcast hints when you know the data shape, but do not treat them as magic.

Join strategyUse whenWatch for
Broadcast hashOne side is genuinely smallExecutor memory pressure
Sort-mergeBoth sides are largeShuffle and sort cost
Bucketed joinStable large tables share join keysOperational complexity
Key insight: joins are where data modeling meets compute cost. A better dimension table, fewer columns, or earlier aggregation can beat cluster resizing.
Gotcha: stale table statistics can make Spark choose the wrong join. Refresh stats or inspect the physical plan when a join suddenly slows down.

Data Skew

Data skew happens when a few keys contain far more records than the rest. Spark may launch hundreds of tasks, but one or two giant tasks keep running while everything else finishes. In the Spark UI, skew usually shows up as a long tail of task durations, large shuffle reads, or repeated spill on specific tasks.

Common fixes include salting hot keys, pre-aggregating before joins, splitting hot keys into a separate path, or enabling Adaptive Query Execution where available. The right fix depends on whether skew is predictable, temporary, or part of the business domain.

Key insight: skew is not just a Spark setting problem. It is usually a data distribution problem, and the durable fix often lives in keys, layout, or pipeline design.
Gotcha: increasing executors rarely fixes a single hot key. More workers do not help if one partition owns most of the data.

UDFs vs Built-ins

Built-in Spark SQL functions run inside Catalyst and Tungsten optimization paths. They benefit from predicate pushdown, column pruning, whole-stage code generation, and better planning. Python UDFs often force data to cross the JVM-Python boundary, which adds serialization cost and blocks many optimizer tricks.

Use built-ins first, SQL expressions second, pandas UDFs when vectorization is a clear fit, and plain Python UDFs as the last resort. If a rule is business-critical and reused often, consider expressing it as Spark SQL, a tested library function, or a platform-native transformation rather than scattering UDFs through pipelines.

Key insight: a readable built-in expression is usually faster, more portable, and easier for Spark to optimize than a Python UDF.
Gotcha: UDFs can hide expensive logic from the optimizer. They also complicate debugging because the plan says little about what the Python function really does.

Platform Choice (Glue / EMR / Databricks)

Glue is attractive for serverless ETL, AWS-native catalogs, job bookmarks, and pipelines that live close to S3. EMR gives more control over cluster shape, Spark versions, bootstrap actions, and long-running or specialized workloads. Databricks adds a managed lakehouse experience, strong notebooks, Delta Lake integration, collaborative workflows, and higher-level performance features.

The best platform is the one that matches operating model, not just runtime. Teams that need minimal infrastructure often start with Glue. Teams that need deep control or cost tuning may prefer EMR. Teams that value collaboration, lakehouse conventions, and managed Spark productivity often justify Databricks.

PlatformStrengthTypical concern
GlueServerless AWS ETL and catalog integrationLess runtime control
EMRConfigurable Spark clusters on AWSMore operational ownership
DatabricksManaged lakehouse and productivity layerCost governance
Key insight: platform choice should follow workload shape, team skill, governance needs, and cost visibility. Spark code portability helps, but operational behavior still differs.
Gotcha: do not assume the same job cost profile across Glue, EMR, and Databricks. Startup time, autoscaling, storage layout, and idle clusters can dominate the bill.

Performance Tuning

Start with the physical plan and Spark UI before changing random settings. Look at scan volume, shuffle read and write, spill, task skew, executor memory, file counts, and stage boundaries. Most wins come from data reduction, better joins, sane partitioning, and avoiding Python execution in the hot path.

Key settings such as spark.sql.shuffle.partitions, broadcast thresholds, executor memory, and Adaptive Query Execution matter, but they should follow evidence. Tuning without understanding the bottleneck creates brittle jobs that pass small tests and fail at month-end scale.

SymptomLikely causeFirst check
Long final taskSkew or single outputStage task timeline
High spillMemory pressure or wide shuffleShuffle read and spill metrics
Slow S3 readToo many files or no pruningInput file count and partitions
Driver OOMCollecting data to driverActions and result size
Key insight: optimize the pipeline shape before resizing the cluster. Better plans usually beat bigger machines.
Gotcha: small files are a performance tax across Spark, Glue, Athena, and lakehouse tables. Compact intentionally and choose partition keys carefully.

Interview Q&A

Q: Explain the difference between driver memory problems and executor memory problems.
A: Driver memory problems usually come from collecting too much data, building huge query plans, or managing too many tasks and metadata objects. Executor memory problems happen while processing partitions, joins, aggregations, caching, or shuffle spill. The fix depends on where the data is accumulating, so I would inspect logs and Spark UI metrics before increasing memory.
Q: When would you use repartition versus coalesce?
A: I use repartition when I need a true redistribution, especially before key-based joins, aggregations, or output partitioning. I use coalesce when reducing partition count after filtering or before writing. The tradeoff is that repartition costs a shuffle, while coalesce can preserve uneven data distribution.
Q: How do you diagnose a slow Spark join?
A: I start with the physical plan to see whether Spark chose broadcast, sort-merge, or another strategy. Then I check shuffle size, skew, spilled bytes, and whether table statistics are current. If one side is small, a broadcast may help; if both sides are large, I look at filtering, projection, partitioning, and key distribution.
Q: Why are Python UDFs often discouraged in PySpark pipelines?
A: Python UDFs usually require data to cross between the JVM and Python runtimes, adding serialization overhead. They also hide logic from Catalyst, which limits optimization opportunities. Built-in functions, SQL expressions, and vectorized pandas UDFs are usually better choices when they fit the problem.
Q: What is data skew, and why does it hurt distributed processing?
A: Data skew means work is unevenly distributed across partitions, often because a few keys dominate the dataset. Most tasks finish quickly, but one or two huge tasks hold the stage open. Fixes include salting hot keys, pre-aggregation, isolating hot keys, or using Adaptive Query Execution where available.
Q: How would you choose between Glue, EMR, and Databricks for a PySpark workload?
A: Glue fits AWS-native serverless ETL with lower infrastructure ownership. EMR fits teams needing more cluster control, custom libraries, or specialized runtime tuning. Databricks fits collaborative lakehouse work, Delta-centric pipelines, and productivity-heavy environments, but it needs strong cost governance.

Quick Reference

Driver
Coordinates the application, builds plans, schedules work, and holds driver-side results.
Executor
Worker JVM process that runs tasks, stores cache blocks, and handles shuffle data.
Action
Triggers execution; examples include count, show, collect, write, and foreach.
Transformation
Builds lineage lazily; examples include select, filter, join, withColumn, and groupBy.
DAG
Directed graph of stages and dependencies created from the optimized Spark plan.
Narrow dep
Each output partition depends on limited input partitions; usually no shuffle.
Wide dep
Data must move across partitions; joins, aggregations, and distinct often create this.
Shuffle
Network and disk-heavy redistribution of data across executors.
Broadcast join
Ships a small table to each executor to avoid shuffling the large side.
Sort-merge join
Default large-table join pattern that sorts and shuffles both sides by join key.
AQE
Adaptive Query Execution can adjust joins, partitions, and skew handling at runtime.
coalesce
Reduces partitions with minimal movement; useful before writes but may preserve skew.
repartition
Full redistribution used to change parallelism or partition by a key.
explain
Shows logical and physical plans; use formatted mode for practical plan review.
Small files
Too many tiny outputs increase metadata, planning, and read overhead across the lake.
