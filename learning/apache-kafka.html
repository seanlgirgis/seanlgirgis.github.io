Kafka Mental Model

Apache Kafka is a distributed commit log used as the backbone for event-driven systems, streaming ETL, change data capture, observability pipelines, and real-time data products. The key shift is this: Kafka is not a queue first. It is an append-only log that many independent consumers can read at their own pace.

In a traditional queue, messages are usually removed once consumed. In Kafka, records remain for a configured retention period or compacted lifecycle. Consumers track their own position through offsets. This allows one pipeline to feed many workloads: operational consumers, lake ingestion, feature generation, fraud scoring, metrics aggregation, and replay-based recovery.

Kafka becomes powerful when you treat it as a durable event history, not just a pipe between two applications.
A common design mistake is using Kafka as a magic buffer for bad downstream systems. Kafka can absorb bursts, but it will not fix broken consumer logic, unbounded lag, poor partitioning, or missing schema discipline.

Topics, Partitions, Offsets, and Brokers

A Kafka topic is a named stream of records. A topic is split into partitions. Each partition is an ordered append-only log. Records inside a partition receive monotonically increasing offsets. Brokers are Kafka servers that store partitions, serve reads and writes, and coordinate cluster metadata.

Ordering is guaranteed only within a partition, not across the whole topic. If records for the same business entity must be processed in order, the producer should use a stable message key, such as account_id, device_id, order_id, or endpoint_id. Kafka hashes the key to choose a partition, keeping same-key events ordered.

Partitioning is both a scalability decision and a correctness decision. It controls parallelism, ordering boundaries, hotspot risk, and consumer group behavior.
Adding partitions later can change key-to-partition mapping for future records. That may surprise systems that assumed a key always lands on the same partition forever.

The Log-Based Storage Model

Kafka stores records sequentially in partition logs. Each partition is broken into segment files on disk. Kafka appends new records to the active segment, indexes offsets, and deletes or compacts old segments according to topic policy. Sequential disk IO is the reason Kafka can handle high throughput even on commodity infrastructure.

Retention can be time-based, size-based, or compaction-based. Time and size retention are common for telemetry and stream ingestion. Log compaction keeps the latest value for each key and is useful for changelog topics, state stores, and slowly changing reference data.

Kafka retention is an architecture decision. Longer retention enables replay and recovery, but increases storage, replication traffic, and operational blast radius.
Compaction is not the same as deduplication for all events. It preserves the latest record per key eventually, but old key versions can remain until the cleaner runs.

Producers: Batching, Compression, Acks, and Idempotency

Kafka producer performance comes from batching and asynchronous IO. Producers collect records into batches per partition, optionally compress the batch, and send it to the partition leader. Larger batches improve throughput and compression ratio, but add latency. Smaller batches reduce latency but increase request overhead.

Compression is usually worth enabling. lz4 and snappy are common low-latency options. gzip compresses better but costs more CPU and latency. For data engineering workloads that write to S3 or lakehouse storage downstream, compression also reduces broker network and storage pressure.

The producer tuning triangle is latency, throughput, and durability. You rarely maximize all three at once.
Setting acks=0 may look fast in a benchmark, but it removes broker acknowledgement. For business events, it is usually an unacceptable data-loss tradeoff.
SettingEffectTypical production guidance
acks=0Do not wait for brokerOnly for disposable telemetry
acks=1Leader acknowledgesModerate durability, possible loss on leader failure
acks=allWait for in-sync replicasPreferred for critical data
enable.idempotence=truePrevents duplicate writes from producer retriesUse by default for serious pipelines

Consumers: Poll Loop, Commits, and Crash Behavior

Kafka consumers read records through a poll loop. A consumer calls poll(), receives batches, processes them, and commits offsets. The committed offset says, in effect, "this consumer group has processed records up to this point." Commit strategy controls whether a crash causes duplicates, loss, or replay.

Auto-commit is simple, but dangerous when processing has side effects. Manual commit after successful processing gives better control. For data engineering sinks such as S3, JDBC, Elasticsearch, or Snowflake staging, the safest pattern is to make the sink idempotent and commit offsets only after the sink write is confirmed.

Kafka does not know whether your business processing succeeded. It only knows what offset your consumer committed.
If a consumer commits before writing to the destination and then crashes, data can be lost from the destination even though Kafka thinks the group advanced.
Commit styleBehaviorRisk
Auto commitClient periodically commits offsetsCan commit records before processing finishes
Manual syncCommit blocks until acknowledgedSafer but slower
Manual asyncCommit returns immediatelyFaster but callback/error handling matters
External offset storeOffsets stored with sink transactionMore engineering, stronger recovery story
while running:
    records = consumer.poll(timeout_ms=1000)
    for record in records:
        write_idempotently(record)
    consumer.commit()  # commit only after successful processing

Consumer Groups and Rebalancing

A consumer group is a set of consumers sharing work for one or more topics. Within a group, each partition is assigned to only one consumer at a time. This gives horizontal scale while preserving partition-level ordering. If a topic has 24 partitions, one consumer group can use up to 24 active consumers for that topic. Extra consumers sit idle.

Rebalancing occurs when consumers join, leave, fail heartbeats, or when subscribed topics change. The group coordinator manages membership and partition assignment. Rebalances can pause consumption and create duplicate processing if records were processed but not committed before partition revocation.

Consumer group design should start from partition count, expected lag tolerance, processing cost per record, and failure behavior.
Long processing inside the poll loop can trigger max.poll.interval.ms violations. The broker may consider the consumer dead and rebalance the group while the process is still working.

Replication, ISR, Leader Election, and Durability

Kafka replicates partition data across brokers. Each partition has one leader replica and zero or more follower replicas. Producers and consumers talk to the leader. Followers copy from the leader. The in-sync replica set, or ISR, contains replicas caught up enough to be eligible for durable acknowledgement and leader election.

The durability-availability tradeoff is controlled by replication factor, acks, and min.insync.replicas. For critical pipelines, a common baseline is replication factor 3, acks=all, and min.insync.replicas=2. That means a write succeeds only if the leader and at least one follower are in sync.

Durability in Kafka is a contract between producer settings and broker/topic settings. Looking at only one side is incomplete.
If min.insync.replicas is too high during broker failures, producers may fail writes. If it is too low, acknowledged records may be lost during leader failure.
ConfigurationHigher value improvesHigher value can hurt
Replication factorFault toleranceStorage and network cost
min.insync.replicasWrite durabilityAvailability during replica loss
acksProducer certaintyLatency and failure sensitivity
ISR strictnessClean leader election safetyMore unavailable partitions if cluster unhealthy

kafka-topics.sh --bootstrap-server localhost:9092 \
  --create \
  --topic orders.events \
  --partitions 24 \
  --replication-factor 3 \
  --config min.insync.replicas=2

Delivery Semantics in Practice

Delivery semantics describe what can happen when producers, brokers, consumers, or sinks fail. At-most-once means records may be lost but should not be processed twice. At-least-once means records should not be lost but may be processed more than once. Exactly-once means the combined read-process-write result appears once within a supported transactional boundary.

Kafka's exactly-once semantics are real, but not free. They require idempotent producers, transactions, compatible consumers, careful isolation settings, and sink support. Exactly-once inside Kafka does not automatically make an external database, REST API, or S3 write exactly-once. For many data engineering systems, at-least-once plus idempotent sink writes is the practical sweet spot.

The senior answer is rarely "use exactly-once everywhere." The better answer is to define the failure boundary and make the sink idempotent.
A pipeline can be exactly-once from Kafka topic A to Kafka topic B, then still duplicate records when writing from topic B to a non-transactional external system.
SemanticCommit patternTypical use
At-most-onceCommit before processingLow-value metrics where loss is acceptable
At-least-onceProcess, then commitMost ETL and analytics ingestion
Exactly-onceTransactions across consume and produceFinancial/event transformations within Kafka

Schema Registry and Contract Evolution

Kafka topics live longer than most producer implementations. Without schema discipline, downstream consumers break when fields are renamed, removed, retyped, or semantically changed. Schema Registry adds a contract layer around records. Producers register schemas and consumers validate or deserialize using schema IDs.

Avro is common because it is compact and designed for schema evolution. JSON Schema is easier for human readability and web teams. Protobuf is strong for typed service ecosystems. Compatibility modes decide which schema changes are allowed relative to existing producers and consumers.

Schemas are not bureaucracy. They are how you keep independent teams from silently breaking each other's pipelines.
Backward-compatible syntax does not guarantee semantic compatibility. Changing status from "ACTIVE" to "A" may pass a schema check and still break business logic.

Kafka Connect and S3 Sink Patterns

Kafka Connect is the integration framework for moving data into and out of Kafka. Source connectors ingest from databases, files, SaaS systems, or CDC tools. Sink connectors write Kafka data to destinations such as S3, JDBC databases, OpenSearch, Snowflake, and data lakes. Single Message Transforms, or SMTs, perform lightweight record-level changes such as routing topics, extracting fields, adding metadata, or masking values.

For data engineering, the S3 sink connector pattern is especially important. Kafka topics are written to S3 in partitioned paths, usually with time-based partitioning and columnar formats such as Parquet. This gives a durable lake landing zone for Athena, Glue, Spark, EMR, Snowflake external tables, or Iceberg ingestion.

Kafka Connect is best for standardized movement, not complex business logic. Heavy enrichment belongs in stream processors or ETL jobs.
Small files are the classic S3 sink problem. Low-volume topics, short flush intervals, or too many partitions can produce thousands of tiny files and punish query engines.

Kafka Streams and Stateful Processing

Kafka Streams is a Java library for building stream processing applications directly on Kafka. It supports stateless maps and filters, stateful aggregations, joins, windows, and local state stores backed by Kafka changelog topics. Unlike a separate cluster engine, Kafka Streams apps run as normal applications that join consumer groups and scale by partitions.

Stateful processing is where design gets serious. Windowed aggregations require event-time thinking, grace periods, late-arriving events, changelog topics, and state store sizing. Joins require co-partitioning and compatible keys. The local RocksDB state store can become a performance bottleneck if disks, memory, or changelog restore time are ignored.

Kafka Streams is attractive when the processing logic belongs close to Kafka and the team wants application-style deployment instead of a separate Spark or Flink cluster.
State restore after a rebalance or restart can be painful for large state stores. Changelog topic retention, standby replicas, and disk sizing are not optional details.
OperationWhat it enablesDesign concern
WindowingCounts, rates, rolling metricsEvent time, late data, grace period
JoinsEnrichment and correlationKey alignment and co-partitioning
State storesLocal fast lookup and aggregation stateRestore time and disk pressure
Changelog topicsFault-tolerant state recoveryRetention and compaction correctness

KStream<String, MetricEvent> metrics = builder.stream("telemetry.events");

  .groupByKey()

ksqlDB and Streaming SQL

ksqlDB provides SQL-like stream processing over Kafka topics. It is useful for quick transformations, filtering, aggregations, joins, and creating derived streams without writing a full application. Push queries continuously emit results as new events arrive. Pull queries look up current materialized state from tables.

For a data platform, ksqlDB can speed up prototyping and operational stream transformations. The tradeoff is that complex engineering still requires clear ownership, version control, deployment automation, and observability. SQL does not remove the need to understand partitioning, keys, schemas, and state stores.

ksqlDB is strongest for simple to medium streaming transformations where SQL readability helps more than custom application control.
Do not let ad hoc streaming SQL become untracked production infrastructure. Treat persistent queries like deployable code.
Query typeBehaviorExample use
Push queryContinuous stream of resultsLive alerts or filtered event stream
Pull queryPoint lookup against materialized tableCurrent device status by ID
Persistent queryWrites derived stream/tableReusable transformation pipeline
CREATE STREAM telemetry_events (
  endpoint_id VARCHAR KEY,
  metric_name VARCHAR,
  value DOUBLE,
  event_time BIGINT
) WITH (
  KAFKA_TOPIC='telemetry.events',
  VALUE_FORMAT='AVRO'
);

CREATE TABLE endpoint_error_counts AS
SELECT endpoint_id, COUNT(*) AS error_count
FROM telemetry_events
WHERE metric_name = 'error'
GROUP BY endpoint_id

Kafka vs Kinesis

Kafka and Amazon Kinesis both serve streaming workloads, but their operating models are different. Kafka gives broad ecosystem control, open-source portability, topic compaction, rich client behavior, and mature connector/stream processing patterns. Kinesis is AWS-native, managed, shard-based, and simpler to operate when the workload fits AWS service boundaries.

In AWS, the decision is often Kafka on MSK versus Kinesis Data Streams or Firehose. Kafka may win when teams need open Kafka APIs, Connect, existing Kafka applications, exactly-once Kafka transactions, or portability. Kinesis may win when the team wants a managed AWS-native ingestion stream with tight integration to Lambda, Firehose, and IAM.

The real comparison is not just technology. It is operational ownership, ecosystem fit, portability, cost shape, and team experience.
Do not compare Kafka partitions to Kinesis shards as if they are identical. Ordering, scaling mechanics, throughput limits, and consumer models differ.

Production Operations and Data Platform Patterns

Operating Kafka well requires monitoring both cluster health and data pipeline health. Broker CPU, disk, network, request latency, under-replicated partitions, offline partitions, controller events, ISR shrinkage, and leader imbalance matter. For data pipelines, consumer lag, end-to-end latency, dead-letter rate, schema failures, sink write failures, and duplicate handling matter more than broker metrics alone.

A mature Kafka data platform usually includes topic naming standards, schema governance, retention tiers, ACLs, secrets management, connector deployment patterns, disaster recovery planning, and a clear path from raw topics to curated lake tables. In AWS, Kafka often connects with MSK, IAM authentication, Glue Schema Registry, S3, Glue Catalog, Athena, EMR, Flink, Lambda, OpenSearch, Redshift, and Snowflake.

Kafka operations should be measured from producer to broker to consumer to final sink. A green cluster can still hide a broken data product.
Consumer lag alone is not enough. A consumer can have low lag while writing corrupt records, skipping poison messages, or silently failing downstream idempotency.

Interview Q&A

Q: How would you explain Kafka to a senior data platform stakeholder?
A: Kafka is a distributed event log that decouples producers from consumers. Producers append events to partitioned topics, Kafka stores them durably for a retention period, and multiple consumer groups can independently process or replay those events. The value is not only low latency; it is fan-out, replayability, and a stable event backbone for operational and analytical systems.
Q: How do you choose the number of partitions for a topic?
A: I start with required consumer parallelism, target throughput, ordering boundaries, key distribution, and future growth. More partitions increase parallelism, but they add broker overhead, file handles, replication work, recovery time, and operational complexity. I also check whether key-based ordering is required and whether hot keys could overload a single partition.
Q: What happens if a Kafka consumer crashes after processing records but before committing offsets?
A: The next consumer assigned to that partition will resume from the last committed offset, so some records may be processed again. That is at-least-once behavior. The correct mitigation is idempotent processing, deduplication keys, transactional sink patterns where possible, and committing offsets only after successful downstream writes.
Q: What is the relationship between acks=all, replication factor, and min.insync.replicas?
A: Replication factor defines how many copies of a partition exist. acks=all tells the producer to wait for acknowledgement from the in-sync replica requirement. min.insync.replicas defines how many replicas must be in sync for writes to succeed. Together they define the real durability and availability tradeoff.
Q: When would you use Kafka Connect instead of writing a custom consumer?
A: I use Kafka Connect when the job is standardized movement between Kafka and a supported source or sink, such as CDC to Kafka or Kafka to S3. I write a custom consumer when I need complex business logic, custom error handling, advanced enrichment, unusual transaction boundaries, or application-specific observability.
Q: What does exactly-once mean in Kafka, and what does it not mean?
A: In Kafka, exactly-once usually means transactional consume-process-produce semantics within Kafka, using idempotent producers and transactions. It does not automatically guarantee exactly-once effects in external systems like S3, REST APIs, or databases unless the sink participates in the same transactional or idempotent design.
