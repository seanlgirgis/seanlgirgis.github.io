1. What Kafka Actually Is

Apache Kafka is a distributed, durable, high-throughput event streaming platform. At its core it is a commit log: producers append records to topics, and consumers read from those topics at their own pace by tracking their position (offset) in the log. Unlike traditional message queues (RabbitMQ, SQS) where a message is consumed and deleted, Kafka retains messages for a configurable duration (hours, days, indefinitely), allowing multiple independent consumers to read the same data at different speeds and starting points.

Kafka's defining characteristics — durability, ordering within a partition, high throughput, and multi-consumer replay — make it the backbone of event-driven data architectures. It decouples producers from consumers both temporally (consumers can lag behind producers and catch up) and operationally (a consumer can be restarted, redeployed, or replaced without affecting the producer or other consumers). These properties are what make Kafka the right fit for high-volume data ingestion pipelines, change data capture (CDC), microservice event buses, and real-time analytics feeds.

Positioning Kafka against alternatives: compared to AWS SQS, Kafka offers ordered delivery within partitions, message replay, multi-consumer fan-out from the same topic, and much higher throughput at scale. SQS is simpler to operate but loses messages once consumed and can't replay. Compared to AWS Kinesis, Kafka has a richer ecosystem (Kafka Connect, Kafka Streams, ksqlDB), more flexible deployment options, and more tuning knobs — but Kinesis is fully managed with no cluster to operate. Compared to RabbitMQ, Kafka is not a traditional broker with routing logic — it's a log storage system optimized for throughput and durability over complex routing.

Kafka's killer property is not throughput — it's the commit log model. Messages are retained and replayable. A new consumer can start from the beginning of a topic and replay all historical events. This fundamentally changes how systems integrate: producers don't need to know who will consume their data, and consumers can be added, fixed, or replayed without any producer-side changes.

2. Core Architecture — Brokers, Topics, Partitions

Brokers

A Kafka cluster is a group of brokers — server processes that store and serve topic data. Each broker holds a subset of the partitions for each topic. One broker is elected as the controller (formerly managed by ZooKeeper, now by KRaft — Kafka's built-in Raft consensus since Kafka 3.x) and is responsible for partition leadership elections and cluster metadata. Brokers are identified by integer IDs and communicate with each other for replication and coordination.

Topics

A topic is a named, ordered, durable log of records. Topics are the primary organizational unit — analogous to a database table or an S3 prefix. Topics have configurable retention (by time: retention.ms, or by size: retention.bytes). Retention is independent of consumption — messages are deleted when the retention period expires, not when consumed. A topic with indefinite retention (retention.ms=-1) acts as a permanent event store.

Partitions

Every topic is divided into one or more partitions. A partition is an ordered, append-only sequence of records. Records within a partition have a monotonically increasing offset — the position of the record in the partition log. Partitions are the unit of parallelism: producers write to partitions in parallel, consumers in the same group each read from a subset of partitions in parallel. More partitions = more parallelism, but also more overhead (more files, more leaders to manage, more replication traffic).

Topic: "order-events" — 4 partitions, replication factor 3
──────────────────────────────────────────────────────────

Partition 0:  [offset 0] [offset 1] [offset 2] [offset 3] ...  → Leader: Broker 1
Partition 1:  [offset 0] [offset 1] [offset 2] ...             → Leader: Broker 2
Partition 2:  [offset 0] [offset 1] ...                        → Leader: Broker 3
Partition 3:  [offset 0] [offset 1] [offset 2] [offset 3] ...  → Leader: Broker 1

Each partition is replicated across 3 brokers.
Producers write to the leader partition.
Consumers read from the leader partition (or followers with KIP-392).
Partition count is the most consequential topic configuration decision and cannot be easily changed after the fact (reducing partitions requires topic recreation). Set partition count at topic creation based on your expected peak consumer parallelism and throughput needs. A common starting point: number of partitions = desired consumer group size × 2–3 for headroom.

3. Producers — Publishing Messages

The Kafka producer is the client library used to publish records to topics. It handles serialization, partitioning, batching, compression, and retry logic. Understanding producer configuration is critical for both throughput optimization and delivery guarantee control.

from confluent_kafka import Producer
import json

conf = {
    'bootstrap.servers': 'broker1:9092,broker2:9092,broker3:9092',
    'acks':               'all',       # Wait for all in-sync replicas to acknowledge
    'retries':            5,
    'retry.backoff.ms':   300,
    'linger.ms':          10,          # Wait up to 10ms to batch more records
    'batch.size':         65536,       # 64KB batch size
    'compression.type':   'snappy',
    'enable.idempotence': True,        # Exactly-once producer semantics
}

producer = Producer(conf)

def delivery_report(err, msg):
    if err:
        print(f"Delivery failed: {err}")
    else:
        print(f"Delivered to {msg.topic()} [{msg.partition()}] @ offset {msg.offset()}")

# Produce with a key (determines partition)
record = {'order_id': 12345, 'status': 'placed', 'amount': 99.99}
producer.produce(
    topic='order-events',
    key=str(record['order_id']).encode(),   # same order_id → same partition
    value=json.dumps(record).encode(),
    callback=delivery_report
)

producer.flush()  # Wait for all in-flight messages to be delivered

4. Consumers & Consumer Groups

The Kafka consumer reads records from topic partitions. Consumers track their position in each partition via offsets. A consumer group is a logical grouping of consumers that collectively consume a topic — each partition is assigned to exactly one consumer in the group at any time. This is the fundamental parallelism model: a topic with 12 partitions and a consumer group with 6 consumers gives each consumer 2 partitions to process in parallel.

Consumer Group Mechanics

When consumers in a group join or leave (crash, redeploy, scale), Kafka triggers a rebalance — it reassigns partitions across the current group members. During a rebalance, all consumers in the group pause consumption (stop-the-world in the default eager rebalance protocol). Cooperative rebalancing (available since Kafka 2.4) allows incremental rebalances where only the partitions that need to move are reassigned, minimizing pause duration.

from confluent_kafka import Consumer, KafkaException
import json

conf = {
    'bootstrap.servers':        'broker1:9092,broker2:9092',
    'group.id':                 'order-processor-v1',
    'auto.offset.reset':        'earliest',   # start from beginning if no committed offset
    'enable.auto.commit':       False,        # manual commit for at-least-once control
    'max.poll.interval.ms':     300000,       # 5 min max between polls before rebalance
    'session.timeout.ms':       30000,        # 30s heartbeat timeout
    'partition.assignment.strategy': 'cooperative-sticky',  # minimize rebalance disruption
}

consumer = Consumer(conf)
consumer.subscribe(['order-events'])

try:
    while True:
        msg = consumer.poll(timeout=1.0)
        if msg is None:
            continue
        if msg.error():
            raise KafkaException(msg.error())

        record = json.loads(msg.value().decode('utf-8'))
        process_order(record)

        # Commit only after successful processing
        consumer.commit(message=msg, asynchronous=False)

except KeyboardInterrupt:
    pass
finally:
    consumer.close()   # triggers rebalance to redistribute partitions
Consumer group parallelism ceiling: Adding more consumers than partitions to a group leaves the extra consumers idle — they have no partition to read from. If you need more than N consumers, increase the partition count first. Conversely, a topic with 100 partitions and a consumer group of 10 means each consumer handles 10 partitions — valid, but each consumer is doing 10x the work of a 100-consumer group.

5. Offsets & Offset Management

An offset is a monotonically increasing integer that identifies the position of a record within a partition. Offset 0 is the first record, offset 1 the second, and so on. Consumers track their read position by committing offsets — recording "I have processed up to offset N in partition P" to an internal Kafka topic (__consumer_offsets). On restart or rebalance, the consumer resumes from the last committed offset.

Auto vs Manual Commit

With enable.auto.commit=true (the default), the consumer periodically commits the current offset automatically. This is convenient but can lead to data loss (commit before processing completes — crash loses the message) or duplicates (processing completes but crash before commit — message reprocessed on restart). For production pipelines, always use manual commit: commit only after successful processing of a record or batch.

# Manual offset commit patterns

# Option 1: commit per message (safest, lowest throughput)
msg = consumer.poll(1.0)
process(msg)
consumer.commit(message=msg, asynchronous=False)

# Option 2: commit per batch (higher throughput)
batch = []
for _ in range(100):
    msg = consumer.poll(0.1)
    if msg: batch.append(msg)

process_batch(batch)
consumer.commit(asynchronous=False)  # commits all polled offsets

# Option 3: seek to specific offset (for replay or skip)
from confluent_kafka import TopicPartition

tp = TopicPartition('order-events', partition=0, offset=5000)
consumer.seek(tp)   # resume from offset 5000 on partition 0

Offset Reset Policy

auto.offset.reset controls what happens when a consumer group has no committed offset for a partition (new group, or retained offsets expired):

  • earliest: Start from the beginning of the partition — replay all available records
  • latest: Start from the end — consume only records produced after the consumer starts
  • none: Throw an exception if no committed offset exists — forces explicit handling
Offset retention: Kafka retains committed offsets for offsets.retention.minutes (default 7 days). A consumer group that is inactive for longer than this period loses its committed offsets. On restart, auto.offset.reset determines whether it replays from the beginning or skips to latest — which may not be what you want. Monitor consumer group lag and set alerts for groups that have been inactive unexpectedly long.

6. Replication & Fault Tolerance

Kafka replicates each partition across multiple brokers for fault tolerance. The replication factor of a topic determines how many broker copies exist for each partition. A replication factor of 3 means each partition has one leader and two followers. Producers and consumers interact with the leader; followers passively replicate from the leader.

In-Sync Replicas (ISR)

The ISR (In-Sync Replicas) set is the subset of replicas that are fully caught up with the leader — within a configurable lag threshold. When a producer sends with acks=all, the broker waits for all ISR members to acknowledge the write before returning success. If a follower falls behind (network issue, slow disk), it is removed from the ISR. A message is considered committed (safe to consume) only when written to all ISR members.

# Topic configuration for production durability
kafka-topics.sh --create \
  --topic order-events \
  --partitions 12 \
  --replication-factor 3 \
  --config min.insync.replicas=2 \    # require at least 2 ISR to accept writes
  --config retention.ms=604800000 \   # 7 days retention
  --config compression.type=snappy \
  --bootstrap-server broker1:9092

min.insync.replicas

min.insync.replicas (broker or topic config) sets the minimum number of replicas that must be in-sync for a write with acks=all to succeed. With replication factor 3 and min.insync.replicas=2, Kafka can tolerate one broker failure without losing write availability. If two brokers fail, writes are rejected (the producer receives a NotEnoughReplicasException) rather than risking data loss. This is the standard production setting.

Leader Election

When a leader broker fails, the controller elects a new leader from the ISR. Only ISR members are eligible — this guarantees the new leader has all committed messages. The election is fast (milliseconds) but during election, the partition is temporarily unavailable for reads and writes. Producers with retry configured will retry during the leadership transition without losing messages.

The golden durability configuration for production: replication.factor=3 + min.insync.replicas=2 + acks=all + enable.idempotence=true. This combination tolerates one broker failure with no data loss and no duplicate delivery on producer retry.

7. Delivery Semantics — At-Most, At-Least, Exactly-Once

One of Kafka's most discussed topics is delivery semantics — the guarantees around whether a message is delivered zero, one, or more times end-to-end. There are three levels, each with different configuration requirements and performance implications.

At-Most-Once

A message is delivered zero or one times — never duplicated, but may be lost. Achieved with: acks=0 or acks=1 (producer may not retry on failure), and auto-commit before processing (consumer commits offset then crashes before processing). Appropriate for: metrics, log aggregation, and any pipeline where occasional loss is acceptable and deduplication logic is absent.

At-Least-Once

A message is delivered one or more times — never lost, but may be duplicated. Achieved with: acks=all + producer retries (retries can produce duplicates on network timeout — the broker may have written the record but the ack was lost), and manual commit after processing (consumer may reprocess on restart). Appropriate for: most data pipelines where the processing logic is idempotent (writing to S3 with a deterministic key, upserts to a database).

Exactly-Once

A message is delivered exactly once — no loss, no duplicates. This requires coordination across producer, broker, and consumer. The Kafka implementation uses two mechanisms:

  • Idempotent producer: enable.idempotence=true. The broker assigns each producer a PID (producer ID) and a sequence number per partition. Duplicate produces from retries are detected and discarded by the broker.
  • Transactions: A producer opens a transaction, produces to multiple partitions, and commits the transaction atomically. Consumers configured with isolation.level=read_committed see only committed transactional records.
# Exactly-once producer with transactions
producer_conf = {
    'bootstrap.servers':  'broker1:9092',
    'transactional.id':   'etl-producer-instance-1',  # unique per producer instance
    'enable.idempotence': True,
    'acks':               'all'
}
producer = Producer(producer_conf)
producer.init_transactions()

try:
    producer.begin_transaction()
    for record in batch:
        producer.produce('processed-events', value=json.dumps(record).encode())
    producer.commit_transaction()
except Exception as e:
    producer.abort_transaction()
    raise
Exactly-once is end-to-end, not just Kafka-internal: Exactly-once delivery within Kafka (producer → broker → consumer read_committed) does not automatically extend to your downstream sink (database, S3). If your consumer reads a message exactly once but the write to the database fails and retries, you may still write duplicates to the database. True end-to-end exactly-once requires idempotent writes at the sink: upserts keyed on message ID, or transactional database writes that include offset commits in the same transaction.

8. Partitioning Strategies

The partition a record is assigned to determines which consumer in the group processes it, and whether ordering is maintained relative to other records. Choosing the right partitioning strategy is critical for correctness (ordering guarantees), load balance (even distribution), and parallelism.

Key-Based Partitioning

When a record has a key, Kafka's default partitioner hashes the key and assigns it to a partition deterministically: partition = hash(key) % num_partitions. All records with the same key always land on the same partition, guaranteeing ordering within that key. This is essential for: event sourcing (all events for the same entity in order), CDC (all changes to the same database row in order), and any use case where per-entity ordering matters.

# Key-based partitioning — all records for the same order_id go to same partition
producer.produce(
    topic='order-events',
    key=str(order_id).encode(),    # hash(key) % partitions → consistent partition
    value=json.dumps(event).encode()
)

Round-Robin (No Key)

Records produced without a key are distributed round-robin across all partitions (with sticky partitioning for batching efficiency). This maximizes load balance across partitions but provides no ordering guarantees — two records produced sequentially may land on different partitions and be consumed in any order. Use for: independent events where order doesn't matter (log lines, metrics, independent transactions).

Custom Partitioner

When hash-based key partitioning creates skew (some keys have vastly more records than others), a custom partitioner allows routing based on any logic: range-based, modulo of a numeric field, geography-based. Implement by subclassing the partitioner and registering it in the producer config.

Partition skew from hot keys: If a small number of keys account for the majority of traffic (e.g., a user_id that's a system account generating 90% of events), hash-based partitioning concentrates those records on one partition, creating a hot partition that one consumer handles while others are idle. Mitigate with: salting the key (append a random suffix), using a custom partitioner that routes hot keys differently, or redesigning the key to be more granular.

9. Schema Registry & Avro

Kafka messages are raw bytes — the broker doesn't know or care about schema. Without schema enforcement, producers and consumers must coordinate schema evolution out of band, which leads to silent compatibility breaks. The Schema Registry (Confluent's open-source component) solves this by: storing versioned schemas, enforcing compatibility rules on new schema versions, and enabling producers and consumers to serialize/deserialize records with minimal payload overhead.

Avro Serialization

Avro is the most common schema format used with Kafka and the Schema Registry. An Avro schema defines the record structure as JSON. The producer registers the schema, and messages are serialized as: a magic byte + 4-byte schema ID + Avro binary data. The schema ID tells the consumer which schema to use for deserialization — the schema itself is not embedded in every message, keeping payload size minimal.

# Avro schema for an order event
order_schema = """
{
  "type": "record",
  "name": "OrderEvent",
  "namespace": "com.example.events",
  "fields": [
    {"name": "order_id",    "type": "long"},
    {"name": "user_id",     "type": "long"},
    {"name": "event_type",  "type": "string"},
    {"name": "amount",      "type": ["null", "double"], "default": null},
    {"name": "event_time",  "type": {"type": "long", "logicalType": "timestamp-millis"}}
  ]
}
"""

# Producer with Schema Registry
from confluent_kafka.schema_registry import SchemaRegistryClient
from confluent_kafka.schema_registry.avro import AvroSerializer
from confluent_kafka.serialization import SerializationContext, MessageField

schema_registry_conf = {'url': 'http://schema-registry:8081'}
schema_registry_client = SchemaRegistryClient(schema_registry_conf)

avro_serializer = AvroSerializer(
    schema_registry_client,
    order_schema,
    lambda obj, ctx: obj   # dict → dict (no transformation needed)
)

# Serialize and produce
record = {'order_id': 12345, 'user_id': 67890, 'event_type': 'placed',
          'amount': 99.99, 'event_time': 1744574400000}

serialized = avro_serializer(record, SerializationContext('order-events', MessageField.VALUE))
producer.produce(topic='order-events', value=serialized)

Schema Compatibility Modes

ModeAllowsUse When
BACKWARDNew schema reads data written with old schemaConsumers upgrade first — new consumers must read old data
FORWARDOld schema reads data written with new schemaProducers upgrade first — old consumers must read new data
FULLBoth directionsMaximum safety; most restrictive
NONENo compatibility checkDev/test only — never production
BACKWARD compatibility is the most useful production setting. New consumers that understand the new schema can still read old data from the topic's history. Safe changes under BACKWARD: adding optional fields with defaults, removing fields that consumers don't use. Breaking changes: removing required fields, changing field types incompatibly, renaming fields without aliases.

10. Kafka Streams & ksqlDB

Kafka Streams is a Java library (embedded in your application) for building stateful stream processing applications on top of Kafka. ksqlDB is a SQL-based stream processing engine built on Kafka Streams that lets you express transformations and aggregations in SQL without writing Java. Both process data directly from Kafka topics and write results back to Kafka topics.

Kafka Streams Key Concepts

A Kafka Streams application defines a topology — a directed graph of stream processing nodes (sources, processors, sinks). Streams are infinite sequences of records keyed by a field; tables are a changelog view of a stream (the latest value per key, materialized in a local RocksDB store). Stream-table joins, aggregations, windowed operations, and repartitioning are all first-class operations in the Streams API.

# ksqlDB — SQL stream processing on Kafka topics
-- Create a stream from a topic
CREATE STREAM order_events (
    order_id   BIGINT,
    user_id    BIGINT,
    event_type VARCHAR,
    amount     DOUBLE,
    event_time TIMESTAMP
) WITH (
    KAFKA_TOPIC  = 'order-events',
    VALUE_FORMAT = 'AVRO',
    TIMESTAMP    = 'event_time'
);

-- Aggregate: revenue per user per hour (tumbling window)
CREATE TABLE hourly_user_revenue AS
SELECT
    user_id,
    WINDOWSTART AS window_start,
    WINDOWEND   AS window_end,
    SUM(amount) AS total_revenue,
    COUNT(*)    AS order_count
FROM order_events
WHERE event_type = 'placed'
WINDOW TUMBLING (SIZE 1 HOUR)
GROUP BY user_id
EMIT CHANGES;

-- Join stream with a table (enrich orders with user data)
CREATE STREAM enriched_orders AS
SELECT
    o.order_id,
    o.amount,
    u.user_name,
    u.tier
FROM order_events o
JOIN users_table u ON o.user_id = u.user_id
EMIT CHANGES;
Kafka Streams state stores require local disk: Stateful operations (aggregations, joins with tables) store state in local RocksDB instances on the application host. If the application crashes or is redeployed, the state is rebuilt from the changelog topic (a Kafka-backed replica of the state store). Rebuild time scales with state size — a large aggregation state can take minutes to rebuild on restart. Design for this by sizing standby replicas (num.standby.replicas) so a warm copy of the state is available on failover.

11. AWS MSK — Managed Kafka

Amazon MSK (Managed Streaming for Apache Kafka) is AWS's fully managed Kafka service. It handles broker provisioning, OS patching, Kafka upgrades (with some caveats), ZooKeeper/KRaft management, and CloudWatch metrics integration. You choose the broker instance type, storage per broker, and number of brokers — MSK handles the rest.

MSK vs Self-Managed Kafka on EC2

MSK eliminates significant operational burden: no broker OS management, no ZooKeeper cluster to run, no manual leader rebalancing, built-in CloudWatch integration, and IAM-based authentication (MSK IAM auth) as an alternative to mTLS or SASL/SCRAM. The trade-offs: MSK lags behind Kafka releases (typically 1–2 major versions behind latest), some advanced broker configurations are not exposed, and MSK is more expensive per broker-hour than equivalent EC2 instances. For teams without deep Kafka operations expertise, MSK is the right starting point.

# Connect to MSK with IAM authentication (python)
from confluent_kafka import Producer
import boto3

# MSK IAM auth uses AWS SigV4 — confluent-kafka with aws-msk-iam-sasl-signer
from aws_msk_iam_sasl_signer import MSKAuthTokenProvider

def oauth_cb(oauth_config):
    auth_token, expiry_ms = MSKAuthTokenProvider.generate_auth_token('us-east-1')
    return auth_token, expiry_ms / 1000

conf = {
    'bootstrap.servers':                  'broker1.msk.us-east-1.amazonaws.com:9098',
    'security.protocol':                  'SASL_SSL',
    'sasl.mechanism':                     'OAUTHBEARER',
    'oauth_cb':                            oauth_cb,
}
producer = Producer(conf)

MSK Serverless

MSK Serverless removes broker sizing entirely — capacity scales automatically and you pay per partition-hour and GB-in/out. It's appropriate for variable or unpredictable workloads. Constraints: MSK Serverless only supports IAM auth, has a maximum throughput per topic partition of 5 MB/s ingress, and does not support all Kafka configurations available on provisioned MSK. For predictable high-throughput pipelines, provisioned MSK with right-sized brokers is more cost-effective.

12. Kafka in Data Lake Pipelines

Kafka serves as the real-time ingestion layer for data lake architectures. The standard pattern: operational systems produce events to Kafka topics; a streaming consumer (Kafka Connect S3 Sink, Spark Structured Streaming, Flink, or a custom consumer) reads from Kafka and writes to S3 in partitioned Parquet files; downstream systems (Athena, Redshift Spectrum, Glue) query the S3 data.

Kafka Connect S3 Sink

Kafka Connect is a framework for scalable, fault-tolerant connectors between Kafka and external systems. The Confluent S3 Sink Connector reads records from Kafka topics and writes them to S3 in configurable formats (Parquet, Avro, JSON) with configurable partitioning (by time, by field value). It handles offset commits, file rotation, and S3 upload atomically — a file is written to S3 only when it is complete (by record count or time flush).

# S3 Sink Connector configuration
{
  "name": "s3-sink-order-events",
  "config": {
    "connector.class":           "io.confluent.connect.s3.S3SinkConnector",
    "tasks.max":                 "6",
    "topics":                    "order-events",
    "s3.region":                 "us-east-1",
    "s3.bucket.name":            "my-data-lake-raw",
    "s3.part.size":              "67108864",
    "flush.size":                "10000",
    "rotate.interval.ms":        "300000",
    "storage.class":             "io.confluent.connect.s3.storage.S3Storage",
    "format.class":              "io.confluent.connect.s3.format.parquet.ParquetFormat",
    "parquet.codec":             "snappy",
    "schema.compatibility":      "FULL",
    "locale":                    "en-US",
    "timezone":                  "UTC",
    "timestamp.extractor":       "RecordField",
    "timestamp.field":           "event_time",
    "path.format":               "'year'=YYYY/'month'=MM/'day'=dd/'hour'=HH",
    "partition.duration.ms":     "3600000",
    "value.converter":           "io.confluent.connect.avro.AvroConverter",
    "value.converter.schema.registry.url": "http://schema-registry:8081"
  }
}
The Kafka → S3 Sink → Athena/Glue pattern gives you a real-time ingestion pipeline with sub-minute latency from event production to queryable data in S3, at a fraction of the cost and complexity of a real-time database. Tune flush.size and rotate.interval.ms to balance file size (larger = better Athena performance) against latency (smaller = lower query lag).

13. Performance Tuning

Kafka performance tuning operates at three levels: broker configuration, producer configuration, and consumer configuration. Understanding the levers and their tradeoffs is essential for achieving target throughput and latency.

Broker Tuning

# Key broker configurations for throughput
num.network.threads=8           # threads for network I/O
num.io.threads=16               # threads for disk I/O
socket.send.buffer.bytes=102400
socket.receive.buffer.bytes=102400
socket.request.max.bytes=104857600

# Log segment and flush settings
log.segment.bytes=1073741824    # 1 GB segments (fewer files to manage)

Producer Throughput Tuning

For maximum throughput: increase batch.size (more records per request), increase linger.ms (wait longer to fill batches), enable compression.type=snappy or lz4 (fewer bytes over the wire), and increase buffer.memory (more in-memory buffer before backpressure). For minimum latency: set linger.ms=0 and batch.size=1 at the cost of throughput.

Consumer Throughput Tuning

Scale horizontally by adding consumers to the group (up to partition count). Increase fetch.min.bytes (consumer waits until this many bytes are available before fetching — larger batches, fewer requests). Increase max.poll.records (more records per poll call — process in larger batches). For CPU-bound consumers, enable parallel processing within each consumer using threading or async I/O for the downstream write.

14. Common Gotchas and Anti-Patterns

1. Too few partitions at topic creation: Partition count determines maximum consumer parallelism and is very difficult to increase later (it requires careful handling of key-based ordering guarantees — records for the same key may land on different partitions after repartitioning). Plan partition count for your expected peak consumer scale, not current scale.
2. Auto-committing before processing: With enable.auto.commit=true (the default), the consumer commits the fetched offset on a timer regardless of whether processing succeeded. A crash between commit and successful processing silently loses messages. Always set enable.auto.commit=false and commit manually after successful processing for any pipeline where data loss is unacceptable.
3. Not handling rebalances gracefully: During a rebalance, partitions are reassigned. If your consumer has in-flight processing for records from a partition it's about to lose, those records may be processed again by the consumer that takes over the partition. Use cooperative rebalancing and a ConsumerRebalanceListener to commit offsets for in-flight work before partitions are revoked.
4. Assuming exactly-once at the sink: Kafka's exactly-once semantics apply within the Kafka ecosystem (producer → broker → read_committed consumer). If your consumer writes to a database or S3 without idempotent write logic, you can still produce duplicates at the sink. Always design sink writes to be idempotent: upserts keyed on event ID, S3 writes to deterministic key paths, or transactional database writes that include offset commits.
5. Hot partition from high-cardinality or skewed keys: Hash-based key partitioning can produce severe imbalance if one key or a small set of keys accounts for most traffic. One consumer handles all records for those keys while others are idle. Monitor per-partition message rates and consumer lag per partition, not just aggregate lag.
6. max.poll.interval.ms too short for slow processing: If processing one poll batch takes longer than max.poll.interval.ms (default 5 minutes), the broker considers the consumer dead and triggers a rebalance. The consumer is removed from the group, its partitions are reassigned, and the batch it was processing may be re-delivered. Either reduce batch size (max.poll.records), increase the timeout, or move slow processing off the poll thread.
7. Using Kafka as a database: Kafka is optimized for write-once, read-sequentially access patterns. It does not support random reads by key (you can't efficiently query "give me the latest record for order_id=12345" without reading all records). For current-state lookups, project your Kafka stream into a proper key-value store (Redis, DynamoDB) or use Kafka Streams' KTable materialized views.

15. 10 Key Engineering Questions

Q1. What is a Kafka partition and why does partition count matter?
A partition is an ordered, append-only log segment of a topic. Each partition is assigned to exactly one consumer in a consumer group at a time — partitions are the unit of parallelism. The number of partitions caps the maximum consumer group size: a topic with 6 partitions can have at most 6 active consumers in one group; additional consumers are idle. Partition count should be set at topic creation for expected peak parallelism and is difficult to change retroactively because it breaks key-based ordering guarantees.
Q2. How does a consumer group achieve parallel consumption?
Kafka assigns each partition to exactly one consumer in the group. With 12 partitions and 4 consumers, each consumer reads 3 partitions in parallel. Adding more consumers (up to 12) reduces per-consumer partition count; beyond 12, extra consumers are idle. When a consumer joins or leaves, Kafka triggers a rebalance — redistributing partitions across the current group members. Cooperative rebalancing (partition.assignment.strategy=cooperative-sticky) minimizes disruption by only moving the partitions that need reassignment rather than stopping all consumers.
Q3. What is the difference between at-least-once and exactly-once delivery in Kafka?
At-least-once: messages are never lost but may be duplicated — achieved with acks=all, producer retries, and manual commit after processing. Idempotent retries can produce duplicates without idempotent producer enabled. Exactly-once: no loss and no duplicates — requires enable.idempotence=true on the producer (deduplicates retried produces by sequence number), transactions for atomic multi-partition writes, and isolation.level=read_committed on consumers. Importantly, exactly-once within Kafka does not extend to external sinks — idempotent writes at the sink are still required.
Q4. What is the ISR (In-Sync Replicas) set and how does it affect durability?
The ISR is the set of replicas that are fully caught up with the leader within a lag threshold. With acks=all, a write is only acknowledged when all ISR members have replicated the record. min.insync.replicas sets the minimum ISR size required for writes to succeed — with replication factor 3 and min.insync.replicas=2, one broker can fail and writes continue; two failures reject writes (returning NotEnoughReplicasException) rather than risking data loss. A message is only exposed to consumers after it is committed to all ISR members.
Q5. How does key-based partitioning guarantee ordering and what are its risks?
Records with the same key always hash to the same partition (hash(key) % num_partitions), and within a partition records are strictly ordered by offset. This guarantees all records for the same entity (same order_id, same user_id) are processed in order by the same consumer. The risk: if a small number of keys generate the majority of records (hot keys), their partition receives disproportionate load while other partitions are underutilized. Monitor per-partition message rates and use key salting or custom partitioners to redistribute hot-key traffic.
Q6. What happens to consumer offsets during a rebalance?
During a rebalance (default eager protocol), all consumers in the group stop, partition assignments are revoked, and new assignments are distributed. Offsets committed before the rebalance are preserved — the new consumer assigned to a partition resumes from the last committed offset. Uncommitted in-flight work is reprocessed by whichever consumer takes the partition. Cooperative rebalancing improves this by only revoking partitions that need to move — consumers retaining their partitions continue processing without interruption.
Q7. What is the Schema Registry and why is it important for Kafka in production?
The Schema Registry is a centralized service that stores versioned Avro (or JSON Schema, Protobuf) schemas and enforces compatibility rules. It prevents schema changes that would break consumers: a producer cannot register a schema that is incompatible with the current version (under BACKWARD/FORWARD/FULL compatibility modes). Without Schema Registry, schema evolution is coordinated out of band, leading to silent deserialization failures when producers update fields consumers depend on. It also reduces per-message payload size by replacing the full schema with a 4-byte schema ID.
Q8. What is max.poll.interval.ms and what happens when it is exceeded?
max.poll.interval.ms is the maximum time between consecutive poll() calls before the broker considers the consumer dead and triggers a rebalance. If processing a single batch takes longer than this value (default 5 minutes), the consumer is removed from the group, its partitions are reassigned to other consumers, and the batch it was processing is redelivered. Fix by: reducing max.poll.records (smaller batches take less time to process), increasing the timeout if processing is legitimately long, or offloading slow processing to a thread pool and polling on the main thread to maintain heartbeats.
Q9. How does Kafka Connect simplify building Kafka pipelines?
Kafka Connect is a scalable, fault-tolerant framework for connecting Kafka to external systems without writing consumer/producer boilerplate. Source connectors pull data from external systems (databases via CDC, S3, APIs) into Kafka topics. Sink connectors push data from Kafka topics to external systems (S3, Redshift, Elasticsearch, databases). Connect handles offset management, fault tolerance, parallel task execution, and schema conversion. For common integrations (S3 sink, JDBC source, Debezium CDC), pre-built connectors eliminate the need to write and maintain custom consumer code.
Q10. How would you design a Kafka-to-data-lake pipeline with low latency and high reliability?
Deploy Kafka Connect S3 Sink with Parquet format and Avro Schema Registry integration. Set flush.size and rotate.interval.ms to control file size vs latency tradeoff (e.g., 10,000 records or 5 minutes — whichever comes first). Use timestamp.extractor=RecordField with an event_time field for Hive-style time partitioning (year/month/day/hour) so Athena can prune partitions. Set acks=all and min.insync.replicas=2 on the source topics. After each file is written, trigger an Athena partition registration (ALTER TABLE ADD PARTITION or MSCK REPAIR) via Lambda reacting to the S3 PutObject event. Monitor connector consumer group lag as the primary health metric — rising lag means the connector is falling behind the topic.

16. Production Story Angles

At a large financial institution, Kafka served as the central event bus for a real-time data platform processing millions of events per hour. Operational systems — transaction processors, risk engines, user activity trackers — published to a set of well-defined Kafka topics. The topics were owned by the producing team, versioned with Avro schemas in the Schema Registry, and governed by BACKWARD compatibility policies. Schema changes required a pull request against the schema registry configuration, with automated compatibility validation in CI before merging — this eliminated the class of production incidents where a producer schema change silently broke consumer deserialization.

The pipeline from Kafka to the data lake used Kafka Connect S3 Sink deployed on ECS/Fargate (one connector instance per topic family). Parquet files were written with Snappy compression, time-partitioned by event hour derived from the event timestamp field (not wall-clock time, which would misassign late-arriving events). File rotation was set to 50,000 records or 10 minutes, whichever came first, balancing Athena query performance against pipeline latency. A Lambda function triggered on S3 object creation events registered new partitions in the Glue Data Catalog, making them queryable by Athena within seconds of the file landing.

Consumer group management required deliberate design. Each downstream team (analytics, risk, ML features) ran their own consumer group against the same topics, consuming at their own pace without affecting each other. Consumer group lag was monitored per partition using a custom CloudWatch metric published by a small lag-monitoring Lambda that ran every 60 seconds. Alarms on sustained lag above 100,000 records triggered an on-call notification — the team had defined SLAs for maximum acceptable lag per topic and used this monitoring to meet them.

The most operationally challenging aspect was partition rebalancing during deployments. Consumer groups with 12–20 consumers, processing events that took 200–500ms each, experienced multi-second disruption during the default eager rebalance triggered by rolling deployments. Migrating to cooperative-sticky rebalancing reduced deployment disruption from ~30 seconds (full group stop) to under 3 seconds (only moved partitions paused). Combined with graceful shutdown logic that committed in-flight offsets before closing the consumer, this eliminated the duplicate-processing spikes that had appeared in the metrics after every deployment.
