EC2 Mental Model

Amazon EC2 is raw, configurable compute capacity in AWS. You choose the instance family, CPU architecture, memory, network profile, storage layout, operating system, placement, IAM role, lifecycle behavior, and scaling model. Managed services such as Lambda, Glue, EMR Serverless, and Fargate hide those details. EC2 exposes them because sometimes performance, dependency control, local disk, daemon processes, GPU scheduling, or long-running workload behavior matters more than convenience.

For a senior data engineer, EC2 is not just a virtual machine. It is the fallback layer when a workload does not fit cleanly into a serverless box: custom Spark workers, Kafka clients, Airflow workers, long-running feature generation, GPU inference endpoints, file conversion pipelines, legacy ETL binaries, or high-throughput collectors that need stable network and disk behavior.

Key insight: EC2 gives maximum control over compute shape, OS dependencies, disk layout, networking, and lifecycle. That control is valuable only when the workload needs it.
Production gotcha: EC2 is easy to start and easy to forget. Idle instances, unattached EBS volumes, oversized disks, stale AMIs, and orphaned Elastic IPs can quietly become a large bill.
# Basic launch example
aws ec2 run-instances \
  --image-id ami-xxxxxxxxxxxxxxxxx \
  --instance-type m7i.large \
  --subnet-id subnet-xxxxxxxx \
  --security-group-ids sg-xxxxxxxx \
  --iam-instance-profile Name=ec2-data-engineering-role \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=etl-worker}]'

Instance Families

Instance selection is a workload-shaping decision. The wrong instance type can waste money, throttle jobs, or create misleading performance conclusions. Start from the bottleneck: CPU, memory, disk throughput, network throughput, GPU, or per-core licensing cost.

FamilyExamplesBest fitData engineering angle
General purposem7i, m7g, t4gBalanced CPU and memoryAirflow workers, API services, light ETL, metadata jobs
Compute optimizedc7i, c7gHigh CPU-to-memory ratioCompression, parsing, stateless transforms, CPU-heavy batch
Memory optimizedr7i, x2idnLarge memory footprintSpark executors, joins, caching, graph workloads, large Pandas jobs
Storage optimizedi4i, i8g, d3Local NVMe or dense storageShuffle-heavy jobs, temporary sort, Kafka brokers, search indexing
Accelerated/GPUg6, p5, trn1, inf2GPU, Trainium, InferentiaML training, batch inference, embedding generation, model serving
Key insight: choose instance families by bottleneck, then tune size. Do not start by asking for the biggest machine; start by asking what resource saturates first.
Production gotcha: burstable t instances can look cheap but fail under sustained CPU. For steady ETL workers, CPU credits can turn a simple job into a mystery slowdown.

Architecture choice: x86 vs Arm

Graviton instances can be excellent for cost/performance, especially for Linux workloads using Python, Java, Go, Spark, or containers with Arm-compatible images. The migration risk is native dependencies: compiled wheels, vendor binaries, old ODBC/JDBC drivers, monitoring agents, and proprietary software.

Pricing Models

EC2 has several buying models. The practical question is not which one is cheapest on a pricing page. The question is how predictable the workload is and how much interruption or commitment risk the team can tolerate.

ModelCommitmentDiscount patternUse when
On-DemandNoneHighest flexibility, highest unit costExperiments, unpredictable jobs, production baseline before sizing
Reserved Instances1 or 3 yearsDiscount tied to attributes; Standard less flexible, Convertible more flexibleStable instance families and steady state capacity
Savings Plans1 or 3 years hourly spendCommit to dollars per hour, often more flexible than classic RIsPredictable baseline spend across evolving instance types
SpotInterruptibleDeep discount using spare capacityBatch, stateless workers, retryable data jobs, distributed compute
Key insight: the clean pattern is On-Demand for discovery, Savings Plans or RIs for the stable baseline, and Spot for elastic fault-tolerant overflow.
Production gotcha: commitment math should be based on actual utilization, not wishful capacity. A 40% discount on a machine used 30% of the time can still lose to On-Demand.
# Simple break-even thinking
monthly_on_demand = hourly_rate * hours_used
monthly_commitment = committed_hourly_rate * 730

# - runs most hours
# - stable family/region/OS
# - right-sized from real CloudWatch data
# - unlikely to be replaced by Glue, Fargate, or serverless in the term

EBS vs Instance Store

EC2 storage has two major personalities. EBS is network-attached block storage that persists independently of the instance lifecycle. Instance store is physically attached local storage that is fast and temporary. The choice affects durability, restart behavior, backup strategy, throughput, and operational risk.

StoragePersists after stop?Performance shapeBest use
EBSYesProvisioned or baseline IOPS and throughputRoot volumes, databases, durable state, application data
Instance storeNoVery high local NVMe performance on supported familiesScratch space, shuffle, cache, temporary staging
Key insight: use EBS for data you must keep; use instance store for data you can rebuild.
Production gotcha: instance store data does not survive stop, hibernate, or termination. Treat it like a local cache, not a database backup plan.

Data engineering examples

For Spark shuffle, local NVMe can be excellent because failed partitions can be recomputed. For Kafka brokers, storage optimized instances can work, but the operational design must account for replication, broker replacement, partition rebalancing, and AZ failure. For a single-node Postgres lab, EBS is usually the safer default because snapshots and stop/start behavior matter more than raw local speed.

EBS Volume Types

EBS volume type selection is a cost/performance contract. Modern general-purpose workloads usually start with gp3 because performance can be provisioned independently from size. High-end transactional workloads move to io2. Throughput-heavy sequential workloads may use st1, but not for latency-sensitive databases.

VolumePerformance profileUse whenAvoid when
gp3General-purpose SSD, configurable IOPS and throughputMost EC2 roots, app disks, moderate databases, ETL stagingYou need extreme durability or very high sustained IOPS
io2Provisioned IOPS SSDCritical databases, latency-sensitive write-heavy systemsThe workload is mostly sequential scan or cheap scratch
st1Throughput optimized HDDLarge sequential workloads, logs, big file processingBoot volumes, random I/O, OLTP databases
Key insight: gp3 is usually the default. Move to io2 only when measured latency and IOPS requirements justify the price.
Production gotcha: increasing instance size does not automatically fix EBS bottlenecks. You can be limited by volume IOPS, volume throughput, instance EBS bandwidth, file system settings, or application queue depth.
# Create a gp3 data volume
aws ec2 create-volume \
  --availability-zone us-east-1a \
  --volume-type gp3 \
  --size 500 \
  --iops 6000 \
  --throughput 500 \
  --tag-specifications 'ResourceType=volume,Tags=[{Key=Name,Value=etl-data}]'

VPC Networking on EC2

Every EC2 instance sits inside a VPC subnet and communicates through elastic network interfaces, route tables, security groups, network ACLs, and optional endpoints or gateways. For data platforms, networking is often where good designs fail quietly: blocked S3 access, wrong subnet, no NAT path, public IP exposure, asymmetric routes, or over-permissive security groups.

ComponentRoleData engineering concern
SubnetPlaces instance in an AZ and routing boundaryPrivate subnets are preferred for workers that do not need public ingress
ENIVirtual network cardCan attach secondary IPs; useful for appliances or stable network identity
Security groupStateful instance firewallUse least-privilege ingress; allow egress intentionally
Route tableControls network pathsS3 endpoint routes can avoid NAT cost for data-heavy jobs
VPC endpointPrivate AWS service accessImportant for S3, STS, ECR, CloudWatch Logs, Secrets Manager
Key insight: data-heavy EC2 jobs should usually read S3 through private networking paths, not through public internet paths or expensive NAT bottlenecks.
Production gotcha: a private subnet without NAT or required VPC endpoints may launch fine but fail during bootstrap when it cannot reach package repositories, ECR, S3, STS, or CloudWatch Logs.
# Security group idea: inbound only from ALB or bastion, not the world
aws ec2 authorize-security-group-ingress \
  --group-id sg-worker \
  --protocol tcp \
  --port 22 \
  --source-group sg-bastion

IAM Instance Profiles and Metadata Service

An EC2 instance should not store long-lived AWS keys on disk. Instead, attach an IAM role through an instance profile. The AWS SDK automatically obtains temporary credentials from the Instance Metadata Service. This is how a Python process on EC2 can read S3, write CloudWatch metrics, call Secrets Manager, or publish to SNS without hardcoded secrets.

Key insight: instance profiles turn EC2 into an AWS-native workload identity. The application asks the SDK for credentials; the SDK retrieves short-lived credentials from metadata.
Production gotcha: require IMDSv2 where possible. Metadata credential exposure through SSRF, proxies, or unsafe local services can turn an application bug into AWS account access.
# Inspect role credentials from inside the instance for troubleshooting only
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/
# Force IMDSv2 on an instance
aws ec2 modify-instance-metadata-options \
  --instance-id i-xxxxxxxxxxxxxxxxx \
  --http-tokens required \
  --http-endpoint enabled

Auto Scaling Groups

Auto Scaling Groups manage a fleet of EC2 instances from a launch template. They replace unhealthy instances, scale capacity, spread across Availability Zones, and provide hooks for controlled lifecycle actions. In data engineering, ASGs are useful for worker fleets, collectors, self-managed processing nodes, and batch clusters that need predictable EC2 control without manually launching machines.

FeaturePurposeSenior-level concern
Launch templateDefines AMI, instance type, IAM role, security groups, user dataVersion it. Pin known-good versions for production rollouts.
Scaling policyChanges capacity based on metrics or schedulesScale on queue depth, lag, or job backlog, not only CPU.
Cooldown/warmupPrevents rapid oscillationLong bootstrap jobs need realistic warmup values.
Lifecycle hookRun custom logic before launch or terminate completesDrain workers, flush logs, deregister consumers, checkpoint progress.
Key insight: for worker fleets, the best scaling metric is often backlog per worker, not CPU percentage.
Production gotcha: terminating a worker without lifecycle draining can duplicate work, lose partial files, break Kafka consumer groups, or leave jobs half-committed.

Load Balancers: ALB vs NLB

Load balancers matter when EC2 instances expose APIs, ingestion endpoints, dashboards, model endpoints, or internal services. The main choice is between Application Load Balancer and Network Load Balancer.

BalancerLayerBest forData engineering examples
ALBLayer 7 HTTP/HTTPSPath routing, host routing, TLS termination, web APIsFastAPI data service, Airflow webserver, internal metadata API
NLBLayer 4 TCP/UDP/TLSHigh throughput, static IPs, non-HTTP protocols, low latencyKafka bootstrap endpoints, custom collectors, TCP ingestion
Key insight: use ALB when the protocol is HTTP-aware; use NLB when the protocol is TCP-native or latency/throughput behavior matters more.
Production gotcha: health checks must match application readiness, not just process liveness. A server can accept TCP while its DB pool, model, or downstream dependency is broken.

Placement Groups

Placement groups influence how EC2 instances are placed on AWS infrastructure. They are not everyday settings, but they matter for distributed systems where network latency, failure isolation, or partitioned topology changes performance and resilience.

TypeGoalUse whenTradeoff
ClusterLow-latency, high-bandwidth placementHPC, tightly coupled Spark or MPI-style workloadsLess fault isolation; capacity can be harder to obtain
SpreadEach instance on distinct hardwareSmall critical fleets, quorum systemsLimited number of instances per AZ
PartitionGroups instances into hardware partitionsLarge distributed systems like Hadoop, Cassandra, KafkaApplication must understand partition-aware placement
Key insight: placement groups are architecture tools. They do not replace replication, multi-AZ design, backups, or application-level fault handling.
Production gotcha: changing placement strategy later can require instance replacement. Decide early for clusters where topology is part of the reliability model.

EC2 in Data Engineering

EC2 beats Lambda, Fargate, and Glue when the workload needs long runtimes, custom system packages, local disk, stable daemons, specialized hardware, unusual networking, or precise performance tuning. It loses when the workload is short, event-driven, simple, and better served by managed scaling.

Choose EC2 whenPrefer managed/serverless when
Jobs run for hours or need local scratch spaceJobs are short and event-driven
You need OS-level agents, custom drivers, or legacy binariesDependencies fit cleanly into container or Glue runtime
You need GPU or instance-store optimized shapesCompute can be abstracted behind Lambda, Fargate, or Glue
You operate persistent services like collectors or brokersYou want AWS to own patching, scaling, and worker lifecycle
Key insight: EC2 is often the right answer for hard workloads, not because it is simpler, but because it gives you the knobs managed services intentionally remove.
Production gotcha: when teams choose EC2 only because it feels familiar, they often rebuild weaker versions of ECS, Glue, EMR, or managed Kafka.

Common EC2 data workloads

Examples include Kafka connector workers, custom CDC collectors, batch file converters, high-throughput API ingestion, Spark executors, ML inference nodes, Airflow workers with native drivers, and isolated vendor tools that cannot run inside managed runtimes.

AMIs, Golden Images, User Data, and Cloud-Init

An AMI is the machine image used to launch EC2 instances. User data and cloud-init bootstrap the instance at first boot. The design tradeoff is baking versus bootstrapping. Baking dependencies into a golden image makes launches faster and more repeatable. Bootstrapping at launch is more flexible but slower and more failure-prone.

ApproachStrengthWeakness
Golden AMIFast, repeatable, less external dependency at launchRequires image pipeline and patch discipline
User data bootstrapFlexible, easy to changeCan fail due to package repos, network, secrets, or slow installs
HybridBase dependencies baked; environment config at bootRequires clear boundary between image and runtime config
Key insight: bake slow, stable dependencies; bootstrap fast, environment-specific configuration.
Production gotcha: user data runs only during initial launch by default. Teams often edit user data and expect stopped instances to rerun bootstrap magically.
#!/bin/bash
set -euo pipefail

# cloud-init user data example
hostnamectl set-hostname etl-worker
aws s3 cp s3://company-bootstrap/ec2/worker.env /etc/worker.env
systemctl enable amazon-cloudwatch-agent
systemctl start amazon-cloudwatch-agent
systemctl enable etl-worker
systemctl start etl-worker

Cost Optimization

EC2 cost optimization is a system, not a one-time resize. The main levers are rightsizing, commitment coverage, Spot adoption, schedule-based shutdown, storage cleanup, data transfer reduction, and architecture replacement where managed services are cheaper overall.

LeverHow it savesRisk
RightsizingMatch CPU, memory, network, and EBS to real usageUndersizing creates slow jobs and missed SLAs
Spot for batchUses spare capacity at large discountInterruptions require checkpoint/retry design
Savings PlansDiscounts steady hourly spendOvercommitment wastes money
EBS cleanupDeletes orphaned volumes and stale snapshotsBad tagging can delete needed recovery points
S3/VPC endpointsCan reduce NAT and data path costsEndpoint policies and routes must be maintained
Key insight: optimize the fleet, not just the instance. The real bill includes compute, EBS, snapshots, NAT, data transfer, load balancers, CloudWatch logs, and idle capacity.
Production gotcha: Spot is not free money. Without idempotent jobs, durable checkpoints, and interruption handling, savings can be eaten by reruns and operational pain.
# Spot interruption notice from instance metadata
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \

curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/spot/instance-action

Interview Q&A

Q: When would you choose EC2 over Lambda, Fargate, or Glue for a data workload?
A: I choose EC2 when I need long-running compute, local disk, GPU, custom OS dependencies, specialized networking, persistent daemons, or precise tuning. I prefer Lambda, Fargate, or Glue when the workload fits their runtime, scaling, and dependency model because they reduce operational ownership.
Q: How do you decide between compute optimized, memory optimized, and storage optimized instances?
A: I profile the bottleneck. CPU-heavy parsing and compression lean toward compute optimized. Large joins, caches, and Spark executors often need memory optimized. Shuffle-heavy, indexing, Kafka, and temporary high-I/O workloads may need storage optimized local NVMe.
Q: Explain EBS versus instance store in production terms.
A: EBS is persistent network-attached block storage with snapshots and independent lifecycle. Instance store is fast local ephemeral storage. I use EBS for durable data and root volumes; I use instance store for scratch, cache, shuffle, and data that can be recomputed.
Q: What is the safest way for an EC2 process to access S3?
A: Attach an IAM role through an instance profile, grant least-privilege S3 permissions, require IMDSv2, and use the AWS SDK default credential chain. For private subnets, add the required VPC endpoints or NAT path so the instance can reach S3 and STS reliably.
Q: How would you design an Auto Scaling Group for retryable ETL workers?
A: I would use a launch template with a versioned AMI, scale on queue backlog per instance, add lifecycle hooks to drain work on termination, make jobs idempotent, emit custom metrics, and use mixed On-Demand plus Spot capacity if interruption is acceptable.
Q: What are common EC2 cost surprises?
A: Oversized always-on instances, orphaned EBS volumes, excessive snapshots, NAT charges from private subnet downloads, data transfer, forgotten Elastic IPs, verbose CloudWatch logs, and unused commitment coverage. The compute hourly rate is only part of the bill.

Quick Reference

EC2
Elastic virtual machine capacity with control over instance type, OS, networking, storage, and lifecycle.
AMI
Machine image used to launch instances; bake stable dependencies into golden images.
User data
Bootstrap script passed at launch, commonly executed by cloud-init on first boot.
Instance profile
Container that attaches an IAM role to EC2 so SDKs can get temporary credentials.
IMDSv2
Token-based Instance Metadata Service mode; prefer required tokens for better credential protection.
gp3
Default general-purpose EBS choice; configurable IOPS and throughput independent of size.
io2
Provisioned IOPS EBS for critical, latency-sensitive, high-I/O workloads.
st1
Throughput-optimized HDD EBS for large sequential workloads, not low-latency databases.
Instance store
Fast local ephemeral disk; data does not survive stop or termination.
Security group
Stateful firewall attached to ENIs; use least-privilege ingress and intentional egress.
ASG
Auto Scaling Group manages fleet size, health replacement, AZ spread, and scaling policies.
Launch template
Versioned EC2 launch configuration for AMI, instance type, IAM role, security groups, and user data.
ALB
Layer 7 load balancer for HTTP/HTTPS routing, APIs, dashboards, and TLS termination.
NLB
Layer 4 load balancer for TCP/UDP/TLS, static IPs, high throughput, and non-HTTP protocols.
Spot
Discounted spare EC2 capacity that can be interrupted; best for retryable batch and elastic workers.
Savings Plans
Commit to hourly spend for discounted compute; useful for stable baseline usage.
