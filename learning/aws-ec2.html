1. What EC2 Actually Is

Amazon EC2 (Elastic Compute Cloud) is AWS's core Infrastructure-as-a-Service virtual machine offering. You provision virtual servers - called instances - that run on AWS's physical hardware, choosing the operating system, CPU, memory, storage, and network configuration. Unlike serverless services (Lambda, Glue) where you never touch the underlying compute, EC2 gives you full control over the machine: you SSH in, install software, configure the OS, and manage the runtime environment yourself.

EC2's importance in data engineering extends beyond running application code. It underpins nearly every managed AWS service: EMR clusters run on EC2 instances, Redshift nodes are EC2 under the hood, RDS databases run on EC2, and ECS containers execute on EC2 hosts. Understanding EC2 - particularly its networking model, IAM integration, storage types, and Auto Scaling behavior - makes every other AWS service more comprehensible because the same primitives appear everywhere.

Positioning EC2 against modern alternatives: compared to Lambda, EC2 has no time limits, no cold starts, and full OS control - appropriate for long-running workloads, stateful processes, and anything requiring persistent network connections or custom system software. Compared to ECS/Fargate, EC2 provides the underlying compute that ECS can run on (ECS EC2 launch type), or Fargate abstracts it away entirely. For data engineering, EC2 commonly appears as: self-managed Kafka brokers, EMR cluster nodes, custom ETL workers that outgrow Lambda's constraints, and jump hosts or bastion servers for accessing private-network resources.

EC2 is not obsolete in the serverless era. It remains the right tool for workloads requiring persistent processes, high-throughput I/O, custom runtimes, or state that doesn't fit the 15-minute Lambda ceiling or the container abstraction of ECS/Fargate.

2. Instance Types & Families

EC2 instance types encode the hardware profile of the virtual machine. The naming convention is: family + generation + attributes + . + size. For example, r7g.2xlarge means: memory-optimized family (r), 7th generation, Graviton3 processor (g), 2xlarge size (8 vCPU, 64 GB RAM).

Instance Families

FamilyOptimized ForData Engineering Use Cases
m (General Purpose)Balanced CPU/memoryApplication servers, dev/test, moderate ETL workloads
c (Compute Optimized)High CPU, lower memory ratioCPU-bound transformations, batch processing, Kafka brokers
r (Memory Optimized)High memory, large RAMIn-memory processing, Spark executors, Redis, large joins
i (Storage Optimized)High local NVMe I/OHigh-throughput I/O, local Hadoop HDFS nodes, Cassandra
p / g (GPU)GPU acceleratorsML training, inference, GPU-accelerated data processing
t (Burstable)Baseline CPU + burst creditsDev/test, light workloads, jump hosts, cron runners
x (Extra Memory)Largest RAM (up to 24 TB)In-memory databases, SAP HANA, massive dataset caching

Graviton (ARM) Instances

AWS Graviton processors (Graviton2 = 6th gen suffix g, Graviton3 = 7th gen suffix g) are ARM-based chips designed by AWS. Graviton instances typically offer 20-40% better price/performance than equivalent x86 instances for the same workload. For data engineering workloads running Python, Java (JVM runs natively on ARM), or containerized applications, Graviton is worth evaluating. The constraint: binaries compiled for x86 don't run on Graviton - validate all dependencies support ARM64 before migrating.

t3.micro       # General purpose burstable, 3rd gen, 2 vCPU, 1 GB
m6i.xlarge     # General purpose, 6th gen Intel, 4 vCPU, 16 GB
r7g.2xlarge    # Memory optimized, 7th gen Graviton, 8 vCPU, 64 GB
c6i.4xlarge    # Compute optimized, 6th gen Intel, 16 vCPU, 32 GB

For Spark executor nodes (EMR, self-managed), the r family is typically optimal - Spark is memory-bound and needs high RAM-to-CPU ratios. For Kafka brokers, the c or m family with gp3 EBS volumes delivers the right balance of network throughput and cost. For jump hosts and cron runners, t3.micro or t3.small is sufficient and cheap.

3. Purchasing Options - On-Demand, Reserved, Spot

EC2 offers three primary purchasing models that trade flexibility for cost. Choosing the right model for each workload is one of the most impactful cost optimization decisions in an AWS environment.

On-Demand

Pay for compute capacity by the second (minimum 60 seconds) with no upfront commitment. The highest per-hour rate of all options. Use On-Demand for: workloads with unpredictable duration, short-lived dev/test environments, new workloads being profiled before committing, and capacity that must always be available without interruption risk.

Reserved Instances (RIs) and Savings Plans

Commit to a specific instance type (Standard RI) or a family/region (Convertible RI or Savings Plan) for 1 or 3 years in exchange for 40-72% discounts versus On-Demand. Standard RIs offer the highest discount but lock you to a specific instance type and AZ. Convertible RIs allow changing instance family/OS mid-term but at a lower discount. Compute Savings Plans (the modern replacement for RIs) apply the discount to any EC2 instance in a region regardless of family or size, offering the most flexibility at a slightly lower discount.

For stable, predictable workloads (production Kafka brokers, always-on Redshift nodes, persistent application servers), 1-year Savings Plans or Convertible RIs typically cut the compute bill by 40-50% with minimal risk. The break-even for a 1-year commitment is roughly 7-8 months of On-Demand usage.

Spot Instances

Bid for unused EC2 capacity at discounts of 60-90% off On-Demand. The catch: AWS can reclaim Spot instances with a 2-minute warning when demand for the capacity increases. Spot is appropriate for: fault-tolerant batch workloads, EMR transient clusters, stateless worker pools behind SQS, and any workload that can checkpoint progress and resume after interruption. Spot is inappropriate for: stateful single-node databases, primary application servers, or any workload that cannot tolerate sudden termination.

# Request a Spot instance via boto3
ec2 = boto3.client('ec2')

response = ec2.run_instances(
    ImageId='ami-0abcdef1234567890',
    InstanceType='r6i.xlarge',
    MinCount=1,
    MaxCount=1,
    InstanceMarketOptions={
        'MarketType': 'spot',
        'SpotOptions': {
            'SpotInstanceType': 'one-time',
            'InstanceInterruptionBehavior': 'terminate'
        }
    },
    IamInstanceProfile={'Name': 'MyEC2InstanceProfile'},
    SubnetId='subnet-0a1b2c3d',
    SecurityGroupIds=['sg-0123456789abcdef0']
)

4. AMIs - Amazon Machine Images

An AMI is a snapshot of a complete machine configuration: the operating system, pre-installed software, filesystem layout, and boot instructions. Every EC2 instance is launched from an AMI. AMIs are region-specific - an AMI in us-east-1 cannot directly launch instances in eu-west-1 (you must copy the AMI to the target region first).

AMI Components

An AMI consists of: one or more EBS snapshots (or an instance store template for instance-store-backed AMIs), a block device mapping (which snapshots attach as which device, root volume size), launch permissions (public, private, or shared with specific accounts), and virtualization type (HVM - the current standard - vs paravirtual, which is legacy).

Custom AMIs - The Golden Image Pattern

Rather than relying on user data scripts to configure instances at launch (which is slow, error-prone, and requires internet access at boot), mature pipelines bake a golden AMI - a pre-configured AMI with all dependencies, monitoring agents, security hardening, and application code already installed. New instances launched from the golden AMI are ready in seconds rather than minutes of bootstrapping. Rebuilding the golden AMI is part of the CI/CD pipeline whenever dependencies change.

# Create an AMI from a running instance (boto3)
ec2 = boto3.client('ec2')

response = ec2.create_image(
    InstanceId='i-0abcdef1234567890',
    Name='my-etl-worker-golden-ami-2026-04-13',
    Description='Pre-baked ETL worker: Python 3.12, pandas, pyarrow, CloudWatch agent',
    NoReboot=False,   # Reboot for a consistent filesystem state
    BlockDeviceMappings=[
        {
            'DeviceName': '/dev/xvda',
            'Ebs': {
                'VolumeSize': 30,
                'VolumeType': 'gp3',
                'DeleteOnTermination': True,
                'Encrypted': True
            }
        }
    ]
)
ami_id = response['ImageId']
print(f"AMI creation started: {ami_id}")
AMI region lock-in: AMIs are regional. If your infrastructure spans multiple regions for DR or multi-region active-active, you must copy the AMI to each region and maintain region-specific AMI IDs in your IaC (Terraform, CDK). A common mistake is hardcoding a us-east-1 AMI ID into a CloudFormation template and then trying to deploy it in eu-west-1.

5. Storage - EBS, Instance Store, EFS

EC2 instances have access to three distinct storage models with fundamentally different performance, persistence, and cost profiles. Choosing the right storage type for each use case is critical for both performance and reliability.

EBS (Elastic Block Store)

EBS volumes are network-attached block storage that persist independently of the instance. Data on EBS survives instance stops, restarts, and terminations (unless DeleteOnTermination is set). EBS volumes are AZ-scoped - they can only attach to instances in the same AZ. EBS is the right choice for: root volumes, database storage, any data that must persist across instance restarts.

# Create and attach a gp3 EBS volume
ec2 = boto3.client('ec2')

vol = ec2.create_volume(
    AvailabilityZone='us-east-1a',
    VolumeType='gp3',
    Size=500,           # GB
    Iops=6000,          # gp3: independently configurable up to 16,000
    Throughput=500,     # MB/s, up to 1,000
    Encrypted=True,
    KmsKeyId='arn:aws:kms:us-east-1:123456789:key/my-key-id'
)

ec2.attach_volume(
    VolumeId=vol['VolumeId'],
    InstanceId='i-0abcdef1234567890',
    Device='/dev/sdf'
)

Instance Store

Instance store volumes are physically attached NVMe SSDs on the host hardware. They deliver the highest possible IOPS and throughput (up to millions of IOPS on i3en instances) with sub-millisecond latency, because there is no network hop. The critical constraint: instance store data is lost when the instance is stopped or terminated. It survives reboots only. Use instance store for: Spark shuffle data, temporary sort buffers, HDFS DataNode local storage, and any ephemeral high-I/O scratch space that can be regenerated.

Instance store is ephemeral - no exceptions: A stopped instance loses all instance store data. An EC2 retirement (host hardware maintenance) forces a stop/start, not a reboot - instance store is wiped. If you use instance store for Spark local directories or shuffle, ensure Spark can recover from missing shuffle data (it will re-compute) rather than storing anything irreplaceable there.

EFS (Elastic File System)

EFS is a managed NFS file system that can be mounted on multiple EC2 instances simultaneously across multiple AZs. Unlike EBS (one-to-one instance-to-volume) and instance store (local only), EFS is a shared, multi-attach file system. Use EFS for: shared configuration or code that multiple instances need to read, shared scratch space for a distributed job where all workers need read/write access to common files, and ML training data that needs to be accessible from multiple training instances in parallel.

6. Networking - VPC, ENI, Security Groups

Every EC2 instance lives inside a VPC (Virtual Private Cloud), in a specific subnet within a specific Availability Zone. The subnet determines the instance's IP address range, routing rules, and network ACL. Understanding EC2 networking is essential for designing secure, correctly-routable architectures.

ENI - Elastic Network Interface

Every instance has at least one primary ENI (eth0) created at launch. An ENI has a primary private IPv4 address (from the subnet's CIDR range), optionally one or more secondary private IPs, an optional public IP (if the subnet has auto-assign public IP or an Elastic IP is attached), one or more security groups, and a MAC address. Additional ENIs can be attached to an instance for use cases like dual-homed instances (connecting to two different subnets), or for high-availability failover by detaching an ENI from a failed instance and attaching it to a replacement.

Security Groups

Security groups are stateful, instance-level virtual firewalls. Rules specify allowed traffic by protocol, port range, and source/destination (CIDR block or another security group ID). Security groups are stateful - if you allow inbound TCP 443, the return traffic is automatically allowed outbound without an explicit outbound rule. The default outbound rule allows all traffic; restrict it for defense-in-depth.

# Create a security group for an ETL worker
ec2 = boto3.client('ec2')

sg = ec2.create_security_group(
    GroupName='etl-worker-sg',
    Description='ETL worker: outbound to S3 (via endpoint), RDS, Redshift',
    VpcId='vpc-0a1b2c3d4e5f67890'
)

# Allow SSH from bastion only (not the world)
ec2.authorize_security_group_ingress(
    GroupId=sg['GroupId'],
    IpPermissions=[
        {
            'IpProtocol': 'tcp',
            'FromPort': 22,
            'ToPort': 22,
            'UserIdGroupPairs': [{'GroupId': 'sg-bastion-id'}]  # bastion SG only
        }
    ]
)

# Allow outbound HTTPS (S3 via VPC endpoint, SSM, Secrets Manager)
ec2.authorize_security_group_egress(
    GroupId=sg['GroupId'],
    IpPermissions=[
        {'IpProtocol': 'tcp', 'FromPort': 443, 'ToPort': 443, 'IpRanges': [{'CidrIp': '0.0.0.0/0'}]},
        {'IpProtocol': 'tcp', 'FromPort': 5439, 'ToPort': 5439, 'IpRanges': [{'CidrIp': '10.0.0.0/8'}]},  # Redshift
        {'IpProtocol': 'tcp', 'FromPort': 5432, 'ToPort': 5432, 'IpRanges': [{'CidrIp': '10.0.0.0/8'}]},  # RDS
    ]
)

Public vs Private Subnets

A public subnet has a route to an Internet Gateway - instances in it can have public IPs and reach the internet directly. A private subnet has no IGW route - instances cannot be reached from the internet and can only reach the internet via a NAT Gateway in a public subnet. Production EC2 instances should almost always be in private subnets. Public subnets are for load balancers and NAT Gateways only. SSH access to private instances goes through a bastion host (jump server) in the public subnet, or preferably via AWS Systems Manager Session Manager (no inbound SSH required).

Prefer SSM Session Manager over bastion hosts for instance access. Session Manager requires no open inbound SSH port, no key pair management, logs all session activity to CloudWatch/S3, and integrates with IAM for access control. It eliminates the most common EC2 attack surface - exposed SSH on port 22.

7. IAM Roles & Instance Profiles

EC2 instances interact with other AWS services using an IAM role attached via an instance profile. When your application code on the instance calls boto3.client('s3'), the SDK automatically retrieves temporary credentials from the EC2 instance metadata service (IMDS) - credentials issued by AWS STS for the attached IAM role. No hardcoded access keys are needed or appropriate.

Instance Metadata Service (IMDS)

IMDS is an HTTP endpoint accessible only from within an EC2 instance at 169.254.169.254. It serves instance metadata (instance ID, region, AZ, security groups) and temporary IAM credentials. IMDSv2 (the current version) requires a session token obtained via a PUT request before metadata can be read, preventing SSRF attacks that could steal credentials via IMDSv1's unauthenticated GET interface.

# boto3 retrieves credentials from IMDS automatically - no key config needed
import boto3

# This works on any EC2 instance with an attached IAM role
s3 = boto3.client('s3', region_name='us-east-1')
response = s3.list_objects_v2(Bucket='my-data-bucket', Prefix='raw/')

# Manually query IMDSv2 for instance metadata
import requests

# Step 1: get session token
token_response = requests.put(
    'http://169.254.169.254/latest/api/token',
    headers={'X-aws-ec2-metadata-token-ttl-seconds': '21600'}
)
token = token_response.text

# Step 2: use token to query metadata
metadata = requests.get(
    'http://169.254.169.254/latest/meta-data/instance-id',
    headers={'X-aws-ec2-metadata-token': token}
)
print(metadata.text)  # e.g. i-0abcdef1234567890
Enforce IMDSv2 on all instances: IMDSv1 allows unauthenticated GET requests to the metadata endpoint. An SSRF vulnerability in any application on the instance (a web app that fetches user-supplied URLs, for example) can be exploited to retrieve IAM credentials via IMDSv1. Always set HttpTokens=required (IMDSv2 only) at instance launch or in the account-level default settings. Enforce it with an SCP or IAM condition key.
# Launch instance with IMDSv2 enforced
ec2.run_instances(
    ...
    MetadataOptions={
        'HttpTokens': 'required',      # IMDSv2 only
        'HttpEndpoint': 'enabled',
        'HttpPutResponseHopLimit': 1   # Prevents container escape to host IMDS
    }
)

8. User Data & Instance Initialization

User data is a script (bash, PowerShell, or cloud-init YAML) that runs once at instance first boot. It is the standard mechanism for configuring instances at launch: installing packages, writing config files, pulling application code, registering the instance with a configuration management system, or starting services.

#!/bin/bash
# User data script - runs as root at first boot

set -e  # Exit on any error

# Update OS and install dependencies
yum update -y
yum install -y python3.12 python3.12-pip git amazon-cloudwatch-agent

# Install Python dependencies
pip3.12 install pandas==2.2.0 pyarrow==15.0.0 boto3

# Pull application code from S3
aws s3 cp s3://my-config-bucket/etl-worker/app.tar.gz /opt/app.tar.gz
tar -xzf /opt/app.tar.gz -C /opt/

# Configure and start CloudWatch agent
aws s3 cp s3://my-config-bucket/cloudwatch-agent-config.json /opt/aws/amazon-cloudwatch-agent/etc/
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
    -a fetch-config -m ec2 \
    -c file:/opt/aws/amazon-cloudwatch-agent/etc/cloudwatch-agent-config.json -s

# Signal CloudFormation/ASG that init is complete
/opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackName} --resource MyASG --region us-east-1

User Data Limitations

User data has a 16 KB size limit. For complex initialization, store the full script in S3 and have a minimal user data script download and execute it. User data runs at boot with root privileges and no interactive terminal - capture stdout/stderr to a log file (/var/log/user-data.log) for debugging failed initializations. User data only runs on first boot by default; to run on every boot, use cloud-init's runcmd module with the appropriate frequency setting.

Don't put secrets in user data: User data is visible to anyone with ec2:DescribeInstanceAttribute permission and is stored in plaintext in the EC2 service. Never pass passwords, API keys, or credentials via user data. Retrieve secrets at runtime from Secrets Manager or SSM Parameter Store using the instance's IAM role.

9. Auto Scaling Groups

An Auto Scaling Group (ASG) manages a fleet of EC2 instances as a logical unit. The ASG maintains a desired capacity, scales out (adds instances) when demand increases, and scales in (removes instances) when demand decreases. ASGs integrate with load balancers to automatically register and deregister instances as they join and leave the group.

Launch Templates

A Launch Template specifies the configuration for instances the ASG creates: AMI ID, instance type, key pair, security groups, IAM instance profile, user data, EBS volumes, network interfaces, and purchasing options (On-Demand vs Spot mix). Launch Templates replaced the older Launch Configurations - they support versioning, mixed instance policies (multiple instance types in one ASG), and Spot + On-Demand mixing.

# Create a launch template
ec2.create_launch_template(
    LaunchTemplateName='etl-worker-template',
    VersionDescription='Initial version',
    LaunchTemplateData={
        'ImageId': 'ami-0abcdef1234567890',
        'InstanceType': 'r6i.xlarge',
        'IamInstanceProfile': {'Name': 'ETLWorkerInstanceProfile'},
        'SecurityGroupIds': ['sg-0123456789abcdef0'],
        'UserData': base64.b64encode(user_data_script.encode()).decode(),
        'BlockDeviceMappings': [{
            'DeviceName': '/dev/xvda',
            'Ebs': {'VolumeSize': 50, 'VolumeType': 'gp3', 'Encrypted': True}
        }],
        'MetadataOptions': {'HttpTokens': 'required', 'HttpEndpoint': 'enabled'}
    }
)

Scaling Policies

  • Target Tracking: Maintain a target metric value (e.g., keep average CPU at 60%). ASG adds/removes instances automatically to maintain the target. Simplest to configure.
  • Step Scaling: Define thresholds with specific scaling adjustments (e.g., +2 instances if CPU > 70%, +4 if CPU > 90%). More control than target tracking, useful for workloads with known burst patterns.
  • Scheduled Scaling: Pre-scale to a known capacity at a specific time (e.g., increase to 20 instances before a daily 9am batch run). Useful when load patterns are predictable.
  • Predictive Scaling: Uses ML to forecast load and scale proactively. Useful for recurring cyclical patterns.

Instance Refresh

When you update a Launch Template (new AMI, new instance type), existing instances in the ASG continue running the old configuration. Instance Refresh replaces running instances with new ones based on the updated template, rolling through the fleet while maintaining a configurable minimum healthy percentage. This is the standard zero-downtime deployment mechanism for EC2-backed services.

For data pipeline worker pools backed by SQS, the pattern is: ASG scales based on SQS ApproximateNumberOfMessagesVisible via a Step Scaling policy. When the queue is empty, scale to zero (or minimum 0). When messages arrive, scale out proportionally. Workers dequeue, process, and delete messages. The ASG + SQS combination provides elastic, fault-tolerant batch processing without managing a job scheduler.

10. Load Balancers - ALB, NLB, CLB

Elastic Load Balancing distributes incoming traffic across multiple EC2 instances (or containers, or Lambda functions) to improve availability and scalability. There are three load balancer types with distinct use cases.

Application Load Balancer (ALB)

Layer 7 (HTTP/HTTPS) load balancer. Routes requests based on URL path, hostname, HTTP headers, or query string parameters. Supports host-based and path-based routing to different target groups, WebSocket connections, HTTP/2, and native authentication via Cognito or OIDC. ALB is the right choice for: web applications, REST APIs, microservices with path-based routing, and any HTTP/HTTPS workload where you need content-based routing.

Network Load Balancer (NLB)

Layer 4 (TCP/UDP/TLS) load balancer. Operates at the connection level without inspecting HTTP content. Handles millions of requests per second with ultra-low latency (~100 microseconds). Preserves the client's source IP address. NLB is the right choice for: TCP-based protocols (Kafka clients, database connections, gRPC), latency-critical applications, and workloads needing static IP addresses (NLB provides one Elastic IP per AZ).

Classic Load Balancer (CLB)

The original AWS load balancer - operates at both Layer 4 and Layer 7 but with limited features compared to ALB and NLB. CLB is legacy; AWS recommends migrating to ALB or NLB. New architectures should not use CLB.

11. EC2 in Data Pipelines

While Lambda and Glue handle most serverless ETL in modern AWS architectures, EC2 remains essential in several data engineering contexts where managed services hit their limits.

EMR on EC2

Amazon EMR (Elastic MapReduce) provisions EC2 instances as Spark/Hadoop cluster nodes. The master node, core nodes, and task nodes are all EC2 instances - understanding EC2 instance types, Spot purchasing, EBS vs instance store, and Auto Scaling is directly applicable to EMR cluster design. Task nodes (no HDFS, compute-only) are ideal Spot candidates; core nodes (hold HDFS data) should be On-Demand or Reserved.

Self-Managed Kafka on EC2

Amazon MSK (Managed Kafka) is the AWS-managed option, but some teams run self-managed Kafka on EC2 for greater version control, custom plugin support, or cost reasons at scale. Kafka brokers benefit from: compute-optimized (c family) or storage-optimized (i family) instances, dedicated EBS gp3 volumes with high IOPS configured independently of size, and placement groups (cluster placement) for low-latency broker-to-broker replication traffic.

# Kafka broker recommended EC2 config (IaC reference)
Instance type:  r6i.2xlarge or c6i.2xlarge
EBS:            gp3, 2 TB, 6000 IOPS, 500 MB/s throughput
Placement:      Partition placement group (AZ-resilient)
Spot:           No - brokers hold state; use On-Demand or Reserved
Security:       Private subnet, no public IP, SG restricts 9092 to app SGs

Long-Running ETL Workers

For ETL workloads that exceed Lambda's 15-minute limit, process large local files, or require persistent network connections (streaming consumers, long-running DB transactions), EC2 worker instances in an ASG backed by SQS provide a robust pattern. Workers poll SQS, process jobs, and report completion. The ASG scales to zero when the queue is empty, minimizing cost during idle periods.

The key design decision for EC2-based ETL workers: make each worker stateless and idempotent. The SQS message contains the job description; the worker fetches input from S3, processes it, writes output to S3 or a database, and deletes the SQS message only on success. If the instance is terminated mid-job (Spot interruption, AZ failure), the SQS message becomes visible again after the visibility timeout and another worker picks it up.

12. Monitoring - CloudWatch, SSM, Status Checks

CloudWatch Metrics

EC2 publishes basic metrics to CloudWatch every 5 minutes (free) or every 1 minute with detailed monitoring enabled (paid). Basic metrics: CPUUtilization, NetworkIn/NetworkOut, DiskReadOps/DiskWriteOps (instance store only - EBS metrics are separate), StatusCheckFailed. Notably absent from default metrics: memory utilization and disk usage for EBS volumes. These require the CloudWatch agent installed on the instance.

# CloudWatch agent config - collect memory + disk metrics
# /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
{
  "metrics": {
    "namespace": "MyApp/EC2",
    "metrics_collected": {
      "mem": {
        "measurement": ["mem_used_percent"],
        "metrics_collection_interval": 60
      },
      "disk": {
        "measurement": ["used_percent"],
        "metrics_collection_interval": 60,
        "resources": ["/", "/data"]
      }
    }
  }
}

EC2 Status Checks

EC2 runs two automatic status checks per instance:

  • System Status Check: Tests the underlying AWS hardware and hypervisor. A failure means the physical host has a problem. Resolution is usually a stop/start (which migrates to new hardware), not a reboot.
  • Instance Status Check: Tests the operating system and network configuration of the instance itself. A failure means the OS is unresponsive or the network is misconfigured. May require a reboot or OS-level investigation.

Configure CloudWatch alarms on StatusCheckFailed_System and StatusCheckFailed_Instance for production instances. You can configure automatic recovery actions (stop/start for system failures) via CloudWatch alarm actions.

AWS Systems Manager (SSM)

SSM provides fleet-wide instance management without SSH. Key features for data engineering: Session Manager for secure shell-less access, Run Command for executing scripts across multiple instances simultaneously, Patch Manager for automated OS patching, and Parameter Store for centralized configuration storage accessed by instances at runtime.

13. Security Best Practices

Principle of Least Privilege for IAM Roles

Instance profiles should grant only the permissions the application actually uses. An ETL worker that reads from S3 and writes to a specific Redshift table needs S3 GetObject on the input prefix, S3 PutObject on the output prefix, and Redshift credentials access - nothing more. Avoid attaching AmazonS3FullAccess or broad managed policies to instance profiles.

No SSH Keys in Production

Launch production instances with no key pair. Use SSM Session Manager for access instead. Key pairs stored on developer laptops or in shared credential stores are a persistent security liability. SSM access is controlled by IAM, audited in CloudTrail, and requires no inbound port 22.

Patch Management

EC2 instances run OS software that accumulates CVEs over time. Use SSM Patch Manager to automate OS patching on a defined schedule. For immutable infrastructure patterns (golden AMI), rebuild and replace instances rather than patching in place - rotating AMIs ensures all instances start from a known-good, fully patched baseline.

VPC Endpoints for AWS Service Access

Instances in private subnets accessing S3, DynamoDB, SSM, Secrets Manager, or other AWS services can use VPC Endpoints to route traffic within the AWS network rather than through a NAT Gateway. Gateway endpoints (S3, DynamoDB) are free and automatically route traffic within AWS. Interface endpoints (SSM, Secrets Manager, ECR, etc.) have an hourly charge but eliminate NAT Gateway data processing fees for high-volume traffic, often resulting in net cost savings.

Security group drift: Security groups accumulate rules over time as developers add temporary access for debugging and forget to remove it. Periodically audit security groups with AWS Config rules (restricted-ssh, vpc-sg-open-only-to-authorized-ports) or AWS Trusted Advisor. A single overly permissive inbound rule can expose an entire fleet.

14. Common Gotchas and Anti-Patterns

1. Using IMDSv1 in production: IMDSv1 allows unauthenticated access to instance metadata, including IAM credentials, via a simple HTTP GET. An SSRF vulnerability in any application on the instance can steal credentials. Always enforce IMDSv2 (HttpTokens=required) at account level via a default setting or SCP.
2. Hardcoding IAM credentials in application code or environment variables: EC2 applications should always use the instance profile via IMDS - boto3 does this automatically. Hardcoded access keys in code, config files, or environment variables are a critical security risk, create key rotation pain, and are regularly discovered by automated secret scanners.
3. Putting production instances in public subnets: Instances in public subnets with public IPs are directly reachable from the internet. Even with a restrictive security group, this is unnecessary exposure. Use private subnets for all production EC2 instances. Put load balancers and NAT Gateways in public subnets only.
4. Using instance store for data that must persist: Instance store is ephemeral - data is lost on stop, termination, or host hardware failure. Using instance store for application databases, logs that need to be retained, or any data that isn't regenerable from a source of truth will cause data loss at the first instance interruption.
5. gp2 vs gp3 - not migrating to gp3: gp2 EBS volumes scale IOPS with size (3 IOPS/GB, max 16,000), forcing you to over-provision size to get IOPS. gp3 decouples IOPS and throughput from size - you can get 16,000 IOPS on a 20 GB volume. gp3 is also 20% cheaper than gp2 for the same size. There is no reason to use gp2 for new volumes; existing gp2 volumes can be modified to gp3 in place with zero downtime.
6. Not setting DeleteOnTermination for EBS root volumes in ASGs: By default, the root EBS volume of an instance has DeleteOnTermination=true. Non-root volumes added via Launch Template may default to false depending on how they are configured. An ASG that terminates and replaces instances will accumulate orphaned EBS volumes if DeleteOnTermination is not set, generating storage cost with no attached instance.
7. Scaling based on CPU alone for queue-backed workers: An ASG scaling on CPU utilization doesn't react to SQS queue depth directly - if workers are idle waiting for messages, CPU stays low even if the queue has 50,000 messages. Scale queue-backed worker ASGs on ApproximateNumberOfMessagesVisible in SQS rather than (or in addition to) CPU, to ensure workers spin up as work arrives.

15. 10 Key Engineering Questions

Q1. What is the difference between stopping and terminating an EC2 instance?
Stopping an instance shuts down the OS and deallocates the underlying hardware, but the EBS root volume and attached EBS volumes are preserved. A stopped instance can be started again, resuming from the same EBS state. Instance store data is lost on stop. Terminating permanently deletes the instance - EBS volumes with DeleteOnTermination=true are deleted, others are detached and retained. A terminated instance cannot be recovered. The distinction matters for cost (stopped instances don't bill for compute, only for EBS storage) and data recovery.
Q2. What is an instance profile and how does it differ from an IAM role?
An IAM role is the identity and permission set. An instance profile is the container that associates an IAM role with an EC2 instance - it's the mechanism by which the instance can assume the role. When you launch an EC2 instance and specify an IAM role in the console, AWS automatically creates an instance profile with the same name. In CloudFormation/CDK, you must create the instance profile resource explicitly. The instance profile is what you reference in the launch template; the role is what you attach policies to.
Q3. What is the difference between EBS-backed and instance store-backed instances?
EBS-backed instances use an EBS volume as their root device - data persists across stop/start cycles, instances can be stopped and restarted, and snapshots can be taken. Instance store-backed instances use a local ephemeral disk as the root device - all data is lost on stop, termination, or host failure; they can only be rebooted (not stopped). Most modern instance types are EBS-backed. Instance store is available as additional volumes (not root) on storage-optimized instances (i3, i3en, d2) for high-I/O ephemeral scratch space.
Q4. When would you choose a Spot instance and what safeguards are required?
Spot instances are appropriate for fault-tolerant, stateless, or checkpointing workloads where a 2-minute interruption warning allows graceful shutdown: EMR task nodes, batch processing workers behind SQS, distributed training jobs that checkpoint to S3. Required safeguards: handle the SIGTERM signal sent 2 minutes before termination (complete current work, checkpoint state, delete in-flight SQS messages back to queue), use Spot with multiple instance types (mixed instance ASG) to reduce interruption probability, and never use Spot for stateful single-node databases or primary application servers.
Q5. How do Auto Scaling Groups maintain high availability across Availability Zones?
An ASG is configured with multiple subnets across multiple AZs. When an instance in one AZ fails its health check, the ASG terminates it and launches a replacement - ideally in the AZ with the fewest instances to maintain balance. The ASG's load balancer integration automatically deregisters unhealthy instances and registers new ones. For true AZ-resilient availability, distribute instances across at least 3 AZs, ensure the load balancer spans all AZs, and test AZ failure scenarios by manually terminating all instances in one AZ.
Q6. What is IMDSv2 and why is it important?
IMDSv2 (Instance Metadata Service version 2) requires a session token obtained via a PUT request before metadata can be read, unlike IMDSv1 which accepts unauthenticated GET requests. This prevents Server-Side Request Forgery (SSRF) attacks where an attacker tricks the instance's application into fetching the metadata URL and leaking IAM credentials. IMDSv2 should be enforced (HttpTokens=required) on all instances. The hop limit should be set to 1 to prevent container workloads from accessing the host instance's metadata.
Q7. What is the difference between gp2 and gp3 EBS volumes?
gp2 ties IOPS to volume size (3 IOPS per GB, max 16,000 at 5,333 GB) - you must over-provision size to get IOPS. gp3 decouples IOPS and throughput from size: baseline 3,000 IOPS and 125 MB/s, configurable up to 16,000 IOPS and 1,000 MB/s independently of size. gp3 is also approximately 20% cheaper per GB than gp2. There is no use case where gp2 is preferable to gp3 for new volumes. Existing gp2 volumes can be modified to gp3 in place with no downtime or data movement.
Q8. How does an ALB differ from an NLB and when would you choose each?
ALB operates at Layer 7 (HTTP/HTTPS) and can route based on URL path, hostname, and headers - appropriate for web applications, REST APIs, and microservices. NLB operates at Layer 4 (TCP/UDP) and passes connections through without HTTP inspection - appropriate for non-HTTP protocols (Kafka, databases, gRPC), latency-critical workloads (NLB adds ~100탎 vs ALB's ~1ms), and workloads needing static Elastic IPs per AZ. NLB preserves client source IP; ALB uses X-Forwarded-For headers.
Q9. What is a Launch Template and how does it improve on Launch Configurations?
Launch Templates support versioning (multiple versions with a default), mixed instance policies (combine multiple instance types in one ASG for Spot diversity), Spot + On-Demand mixing in a single ASG, and all the latest EC2 features (T3 unlimited, Nitro, IMDSv2 settings). Launch Configurations are immutable - any change requires creating a new one. They also don't support mixed instance policies or some newer EC2 features. AWS recommends Launch Templates for all new Auto Scaling Groups; Launch Configurations are a legacy feature.
Q10. How would you design an EC2-based worker fleet to process messages from SQS reliably?
Launch an ASG using a Launch Template pointing to a golden AMI with the worker software pre-baked. Scale the ASG based on SQS ApproximateNumberOfMessagesVisible via a Step Scaling policy (scale to 0 when queue empty, scale out proportionally when messages arrive). Workers: long-poll SQS for messages, set an appropriate visibility timeout (longer than the maximum expected processing time), process the message idempotently, delete the message only on success, and handle the SIGTERM signal (Spot interruption, ASG scale-in) by not deleting the message - it will become visible again after the visibility timeout for another worker to pick up.

16. Production Story Angles

At a large financial institution, EC2 served as the compute layer for a custom ETL worker fleet that processed jobs exceeding Lambda's 15-minute ceiling. Jobs involved reading multi-gigabyte encrypted files from S3, decrypting them using customer-managed KMS keys, applying complex validation and transformation rules, and loading the results into a PostgreSQL-compatible database. Each job took 20-45 minutes - clearly outside Lambda's scope. The fleet ran as an ASG scaling on SQS queue depth, allowing it to idle at 0 instances overnight and scale to 30+ workers during peak morning processing windows.

Instance selection required careful trade-off analysis. The workload was memory-bound (large in-memory DataFrames during transformation) but also needed reasonable I/O for the decryption and write phases. The r6i.2xlarge (8 vCPU, 64 GB RAM) was chosen after benchmarking - it provided sufficient memory to process the largest expected input files without spilling to disk, and the 6th-gen Intel processor delivered acceptable throughput on the CPU-bound decryption step. Graviton3 (r7g) was evaluated and showed a 25% cost reduction for the same performance profile, driving a subsequent migration.

All instances launched with IMDSv2 enforced, no key pair, and no public IP. Access for debugging and operational tasks went exclusively through SSM Session Manager - no bastion hosts, no open port 22. The IAM instance profile was scoped tightly: S3 GetObject on the input prefix, KMS Decrypt for the specific key, and Secrets Manager GetSecretValue for the database password. CloudWatch Logs received all application logs via the CloudWatch agent, with structured JSON output that made querying with CloudWatch Insights practical.

Spot instances were used for the task nodes, not the workers in this case - job state was not easily checkpointed mid-transform, making Spot interruption too disruptive for the 20-45 minute jobs. However, a second fleet of shorter validation-only workers (under 5 minutes per job, easily restarted) did use Spot with significant cost savings. The two fleets used separate SQS queues and separate ASGs with different scaling and purchasing strategies.

EBS gp3 volumes were sized conservatively at 50 GB for the OS and application layer, with IOPS and throughput configured to the minimum needed. The key insight discovered during load testing: default gp3 baseline (3,000 IOPS) was the bottleneck during the write phase, not CPU or memory. Increasing the configured IOPS to 6,000 on the same volume (no size increase, modest cost increase) eliminated the bottleneck entirely - something that would have required doubling the volume size on gp2 to achieve.
