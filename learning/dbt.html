What dbt Is — and what it is not

dbt is a SQL transformation framework. It takes SQL model files, compiles Jinja templates, resolves dependencies, and executes the resulting SQL inside the target warehouse. The compute happens in Snowflake, BigQuery, Redshift, Databricks, Postgres, or another adapter-backed engine — not inside dbt itself.

That boundary matters. dbt is not a loader, not a message bus, and not a full orchestrator. It shines after raw data has landed and been cataloged, when the work becomes modeling, testing, documenting, and deploying transformation logic safely.

Key insight: dbt turns warehouse SQL into a software engineering workflow: modular code, dependency graphs, environments, tests, documentation, review, and repeatable deployment.
Production gotcha: do not make dbt responsible for file arrival, CDC extraction, API ingestion, or long-running operational retries. Pair it with Airflow, Dagster, Prefect, cloud schedulers, or managed ELT tools.

Models & ref() — dependency graph basics

A dbt model is usually a SQL SELECT statement stored in a .sql file. Depending on its materialization, dbt builds that model as a view, table, incremental table, or CTE-only fragment. The file name becomes the model name, and the model becomes a node in dbt's DAG.

The ref() function is the center of dbt's dependency system. It resolves the correct relation name for the target environment and tells dbt that one model depends on another. That dependency graph controls run order, lineage, documentation, and selective builds.

{{ config(materialized='table') }}

select
    customer_id,
    min(order_date) as first_order_date,
    count(*) as lifetime_orders
from {{ ref('stg_orders') }}
group by customer_id
Key insight: ref() is not just string substitution. It is dependency declaration, environment-aware naming, and lineage metadata in one small function.
Production gotcha: hardcoding database.schema.table names bypasses dbt's graph. It makes lineage incomplete and breaks promotion across dev, staging, and production targets.

Materializations — view, table, incremental, ephemeral

Materialization controls what dbt creates in the warehouse. The choice is not cosmetic; it affects cost, freshness, downstream performance, rebuild behavior, storage footprint, and debugging. A senior data engineer should pick materialization based on workload shape, not habit.

MaterializationBest useTradeoff
viewLight logic, small data, always-fresh readsPushes compute to every downstream query
tableExpensive joins, stable dimensions, BI speedFull rebuild can be costly
incrementalLarge facts where only new or changed rows arriveNeeds careful keys, filters, and backfill design
ephemeralSmall reusable logic blocksNo physical object for debugging or reuse outside compiled SQL
Key insight: views optimize storage and freshness; tables optimize read performance; incremental models optimize large-scale repeated builds.
Production gotcha: too many stacked views can create monster SQL at query time. If BI dashboards crawl, inspect the compiled query chain before blaming the warehouse.

Incremental Models — strategies and unique_key

Incremental models let dbt process only new or changed data after the first build. The common pattern uses is_incremental() to filter source rows during incremental runs while still allowing a full refresh when needed. For append-only event streams this is straightforward; for mutable business records it requires more care.

unique_key is what makes many incremental models idempotent. With a merge-capable adapter, dbt can update existing keys and insert new ones. Without the right key, reruns can duplicate records or leave stale values behind.

{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge'
) }}

select *
from {{ ref('stg_orders') }}
{% if is_incremental() %}
where updated_at >= (
  select coalesce(max(updated_at), '1900-01-01') from {{ this }}
)
{% endif %}
Production gotcha: a pure max timestamp filter can miss late-arriving updates. Use a lookback window, source change tracking, or periodic full refresh for critical facts.

Sources, Seeds & Built-in Tests

Sources declare upstream raw tables that dbt does not own. They give raw data a formal contract: database, schema, table name, freshness expectations, and documentation. This is how dbt connects transformation lineage back to ingestion outputs from Fivetran, Airbyte, Glue, Kafka sinks, or custom pipelines.

Seeds are small static CSV files loaded by dbt, usually for controlled lookup tables: country codes, mapping tables, test fixtures, or business categories. They are not a replacement for large reference datasets or operational master data systems.

version: 2

sources:
  - name: raw_sales
    freshness:
      warn_after: {count: 2, period: hour}
    tables:
      - name: orders
        loaded_at_field: ingested_at
        columns:
          - name: order_id
            tests: [not_null, unique]
Key insight: built-in tests are SQL assertions. not_null, unique, accepted_values, and relationships turn data assumptions into repeatable gates.
Production gotcha: dbt tests prove specific assumptions, not total correctness. A table can pass all tests and still be semantically wrong if the wrong business rules were encoded.

Custom Tests & Macros

Custom tests handle rules that built-ins cannot express cleanly: valid date ranges, mutually exclusive flags, revenue reconciliation, duplicate natural keys within active records, or source-specific quality checks. Singular tests are standalone SQL files that return failing rows; generic tests are reusable Jinja macros parameterized across models and columns.

Macros are reusable Jinja SQL blocks. They reduce duplication, hide warehouse-specific syntax, and let teams standardize logic like surrogate key generation, safe casting, date spine generation, or audit columns. Packages from dbt Hub extend this pattern, but each dependency becomes part of your production surface area.

{% macro cents_to_dollars(column_name) %}
    round({{ column_name }} / 100.0, 2)
{% endmacro %}

select
    order_id,
    {{ cents_to_dollars('amount_cents') }} as amount_usd
from {{ ref('stg_payments') }}
Production gotcha: macro cleverness can hide expensive SQL. Always inspect compiled SQL when a macro touches large tables, joins, window functions, or adapter-specific behavior.

dbt Docs & Lineage DAG

dbt docs generate a browsable catalog of models, sources, columns, descriptions, tests, exposures, and lineage. For a senior data team, this is not just documentation polish; it is an operational map showing how raw inputs become trusted marts and dashboard-facing assets.

The lineage DAG is especially useful during impact analysis. Before changing a staging column, you can see downstream marts, tests, and exposures that may break. Combined with CI selection syntax, the DAG lets teams test only the impacted slice instead of rebuilding everything on every pull request.

Key insight: dbt docs become valuable when descriptions, tests, owners, and exposures are maintained. Auto-generated empty docs are just a prettier version of technical debt.
Production gotcha: lineage only sees what dbt owns or what you declare. External BI tools, notebooks, ad hoc warehouse jobs, and hardcoded table references may sit outside the graph.

SCD Type 2 Snapshots

dbt snapshots track changes to mutable source records over time. They create history rows with validity windows, commonly using dbt_valid_from and dbt_valid_to. This is a natural fit for slowly changing dimensions where analysts need to know what a customer, account, product, or policy looked like at a point in time.

The two common strategies are timestamp and check. Timestamp is cleaner when the source has a reliable updated_at. Check compares selected columns and is useful when the source lacks trustworthy change timestamps, but it can be more expensive and sensitive to noisy fields.

{% snapshot snap_customer_status %}
{{ config(
  target_schema='snapshots',
  unique_key='customer_id',
  strategy='timestamp',
  updated_at='updated_at'
) }}

select customer_id, status, tier, updated_at
from {{ source('raw_crm', 'customers') }}
{% endsnapshot %}
Production gotcha: snapshots are not magic CDC. If the source overwrites a row multiple times between snapshot runs, dbt only sees the state at run time and misses intermediate changes.

dbt + Airflow & CI/CD

Airflow and dbt solve different layers. Airflow coordinates workflows: file arrival, ingestion jobs, warehouse loads, dbt runs, notifications, and retries. dbt owns transformation logic, model dependency order, tests, and documentation. The clean design is orchestration outside, transformation graph inside.

CI/CD is where dbt starts feeling like professional software delivery. Pull requests can run dbt parse, compile checks, unit-sized model builds, state-based selection, and tests against a dev schema. Production jobs should publish artifacts such as manifest.json and run_results.json for observability and debugging.

dbt deps
 dbt build \
  --select state:modified+ \
  --defer \
  --state ./prod_artifacts \
  --target ci
Key insight: dbt build is usually the safest production primitive because it runs models, tests, snapshots, and seeds in graph order.
Production gotcha: avoid one giant Airflow task that runs the entire dbt project blindly. It hides failure blast radius and makes retry behavior expensive.

Interview Q&A

Q: What is dbt, and where does it fit in a modern data platform?
A: dbt is a SQL transformation framework that runs inside the warehouse. It fits after ingestion and before BI, ML features, data products, and analytical marts. It gives SQL projects dependency management, testing, documentation, environments, and deployment discipline.
Q: How do you decide between view, table, and incremental materializations?
A: Use views for light logic and freshness, tables for expensive reusable outputs, and incremental models for large datasets where only a slice changes each run. The decision balances compute cost, storage, query latency, and rebuild complexity. At scale, incremental models need extra attention around late-arriving data and idempotency.
Q: Why is ref() important beyond convenience?
A: ref() declares dependency edges in the dbt graph. That graph controls build order, lineage, selection syntax, documentation, and impact analysis. Hardcoded table names bypass that system and make production changes riskier.
Q: What can go wrong with incremental models?
A: They can duplicate rows, miss late-arriving updates, fail to delete records that disappeared upstream, or drift from a full-refresh equivalent. The usual controls are a reliable unique_key, merge strategy, lookback window, source audit columns, and periodic reconciliation. The design depends heavily on whether the upstream data is append-only or mutable.
Q: How would you use dbt tests in production?
A: I would gate critical assumptions such as primary keys, non-null foreign keys, accepted domain values, relationship integrity, and source freshness. Severity should be deliberate: some failures should block deployment, while others should warn and create operational follow-up. Tests should focus on business risk, not just easy-to-write checks.
Q: How should dbt be orchestrated with Airflow?
A: Airflow should coordinate upstream ingestion, dbt execution, downstream publication, and alerting. dbt should own the transformation graph and model-level dependencies. In mature setups, Airflow tasks call targeted dbt commands and preserve dbt artifacts for debugging.

Quick Reference

model
A SQL SELECT file that dbt builds into a warehouse object or inlines as a CTE.
ref()
Resolves model relation names and declares DAG dependencies.
source()
References upstream raw tables that dbt does not own but can document and freshness-check.
view
Default lightweight materialization; no stored data, but compute repeats at query time.
table
Physical rebuild each run; good for expensive logic and fast downstream reads.
incremental
Processes only changed slices after initial build; needs careful filters and keys.
unique_key
Model key used by merge/delete+insert strategies to make reruns idempotent.
is_incremental()
Jinja condition used to apply filters only during incremental runs.
seed
Small CSV-managed lookup table loaded by dbt; not for large reference data.
snapshot
SCD Type 2 history capture for mutable source records.
macro
Reusable Jinja SQL block for shared logic or adapter-specific abstraction.
generic test
Reusable parameterized test macro applied to models or columns.
dbt build
Runs seeds, models, snapshots, and tests in dependency order.
manifest.json
dbt artifact containing parsed graph metadata used for docs, selection, and CI state comparison.
state:modified+
Selection pattern for changed nodes and downstream dependents, useful in pull-request CI.
