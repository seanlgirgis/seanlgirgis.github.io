What Kafka Solves

Apache Kafka is a distributed commit log used to move events between producers and consumers with durable storage, ordered reads within partitions, replay capability, and horizontal scale. In a data engineering platform, Kafka is the buffer between operational systems and analytical consumers. It prevents tight coupling between source applications, transformation jobs, storage sinks, alerting systems, and machine learning features.

AWS Managed Streaming for Apache Kafka, or MSK, runs Kafka as a managed AWS service. It keeps the Kafka programming model while shifting broker operations, patching, monitoring integrations, encryption, and AWS networking into a managed platform.

Kafka is not just a queue. It is a durable event log. The key architectural advantage is replay: a new consumer can read old events without asking the source system to resend them.
Do not introduce Kafka only because a system needs async behavior. If nobody needs replay, ordering, multiple subscribers, or high-throughput ingestion, SQS or EventBridge may be simpler and cheaper.
Pattern Kafka Fit Reason
Clickstream ingestion Strong High volume, append-only events, multiple downstream consumers.
Database change data capture Strong CDC streams need ordering, replay, and sink fan-out.
One-off batch transfer Weak S3 batch loading is usually simpler.
Human workflow commands Mixed SQS/EventBridge may be better unless event history matters.

Core Kafka Concepts

A Kafka cluster contains brokers. Producers write records to topics. Topics are split into partitions. Each partition is an ordered append-only log. Consumers read from partitions and track their position using offsets. Consumer groups allow multiple consumers to share the work for one logical application.

Key building blocks

Concept Meaning Senior-Level Detail
Broker Kafka server node Stores partitions, serves reads/writes, participates in replication.
Topic Named event stream Retention, partitions, compaction, and replication are topic-level design decisions.
Partition Ordered shard of a topic Ordering is guaranteed only within one partition, not across the topic.
Offset Position in a partition Committed offsets represent what a consumer group has acknowledged.
Consumer group Logical subscriber application Each partition is assigned to only one active consumer in the group. 
# Inspect topics
kafka-topics.sh --bootstrap-server b-1.example:9098 --list

# Describe partition count, leaders, replicas, and ISR
kafka-topics.sh --bootstrap-server b-1.example:9098 \
  --describe --topic telemetry.events

# Check consumer group offsets and lag
kafka-consumer-groups.sh --bootstrap-server b-1.example:9098 \
  --describe --group warehouse-loader
Partition count controls maximum parallelism for a consumer group. If a topic has 12 partitions, one group can have up to 12 active consumers reading in parallel.
Adding more consumers than partitions does not increase throughput. Extra consumers sit idle because Kafka assigns each partition to only one consumer per group.

AWS MSK Architecture

MSK runs Kafka brokers inside your VPC subnets and exposes bootstrap endpoints for clients. In provisioned MSK, you choose broker instance types, broker count, storage, Kafka version, networking, authentication, and scaling approach. In MSK Serverless, AWS abstracts broker capacity and scales ingestion and storage behind a serverless cluster interface.

Most production MSK clusters span multiple Availability Zones. Replication protects data when a broker or AZ fails. Clients connect through VPC networking, typically with TLS and IAM authentication, SASL/SCRAM, or mutual TLS depending on the security model.

MSK is still Kafka. You keep Kafka client libraries, consumer group behavior, offsets, topic semantics, and producer/consumer tuning. The main difference is who operates the brokers.
A managed cluster does not eliminate data modeling mistakes. Poor partition keys, huge messages, unbounded lag, or broken offset commits will still hurt you on MSK.
Layer MSK Handles You Still Own
Infrastructure Broker provisioning, replacements, monitoring hooks Subnet design, client connectivity, quotas, capacity choices
Kafka runtime Version support, patch workflows Topic design, retention, partitions, app configs
Security TLS, auth integrations, encryption options IAM policy boundaries, secret rotation, least privilege
Operations CloudWatch metrics, broker health Lag alerting, consumer recovery, cost governance

MSK Serverless vs Provisioned

MSK Serverless is best when traffic is variable, teams want low operations overhead, and workload limits fit the serverless model. Provisioned MSK is better when you need predictable high throughput, broker-level control, specific instance sizing, custom capacity planning, or mature Kafka tuning knobs.

Dimension MSK Serverless MSK Provisioned
Capacity model Managed scaling You size brokers, storage, and partitions
Operational effort Lower Medium; still easier than EC2 self-managed
Cost profile Good for bursty or moderate workloads Good for steady, high utilization workloads
Control Less broker-level control More control over instance/storage/network tuning
Best use case New streaming apps, unpredictable demand Large established data platforms
The simplest decision rule: choose Serverless when you want Kafka semantics without Kafka capacity planning; choose Provisioned when throughput and cost efficiency require explicit engineering control.
Serverless can still surprise you on cost if producers flood the cluster, consumers fall behind, or retention is longer than expected. Serverless removes broker sizing, not architecture discipline.

MSK vs Self-Managed Kafka on EC2

Self-managed Kafka on EC2 gives maximum control but also maximum operational responsibility. You manage broker fleets, operating system patches, disk pressure, ZooKeeper or KRaft operations depending on version, rolling upgrades, metrics, certificates, restart procedures, broker replacement, and incident response.

MSK is usually the better enterprise default unless the team has a strong Kafka platform engineering function or requires custom configurations that MSK does not expose.

Choice Strength Risk
MSK Managed operations, AWS integrations, less undifferentiated work Less low-level control, service quotas, AWS-specific constraints
Kafka on EC2 Full control over binaries, configs, plugins, disk layout High operational burden and higher outage responsibility
Confluent Cloud Rich Kafka ecosystem and managed connectors Vendor cost, networking, and governance considerations
For most data engineering teams, operating Kafka well is not the business differentiator. Event modeling, data contracts, stream processing, and downstream reliability are where the value is.
Self-managed Kafka often starts cheap on paper and becomes expensive during the first disk-full incident, failed broker replacement, bad rolling upgrade, or cross-AZ latency problem.

Topic, Partition, and Key Design

Topic design is data architecture. A good topic represents a stable business event stream such as orders.created, payments.authorized, or telemetry.metric_samples. Partitions provide parallelism, but the partition key controls ordering and distribution. Choose keys based on the unit of ordering and expected cardinality.

Partition key examples

Use Case Candidate Key Tradeoff
Order lifecycle order_id Preserves order-level sequence; high cardinality is usually good.
Customer activity customer_id Preserves customer sequence but can create hot partitions for huge customers.
IoT telemetry device_id Good ordering per device; watch for noisy devices.
Unkeyed logs Null key Good distribution, no business ordering guarantee. 
# Create a topic for telemetry ingestion
kafka-topics.sh --bootstrap-server b-1.example:9098 \
  --create \
  --topic telemetry.metric_samples \
  --partitions 24 \
  --replication-factor 3 \
  --config retention.ms=604800000
Partition keys are a contract. Changing the key later can break ordering assumptions and repartition downstream state stores.
Too few partitions cap consumer parallelism. Too many partitions increase metadata, file handles, recovery time, and rebalance overhead. Do not create thousands casually.

Producer Configuration Tuning

Producer tuning balances durability, latency, throughput, and duplicate risk. The most important settings are acks, enable.idempotence, linger.ms, batch.size, compression.type, retries, and delivery.timeout.ms.

Setting Typical Production Value Why It Matters
acks all Waits for in-sync replicas before acknowledging writes.
enable.idempotence true Prevents duplicate writes during retries for a single producer session.
compression.type snappy or lz4 Reduces network and storage cost; CPU tradeoff applies.
linger.ms 5 to 50 Allows batching; improves throughput at small latency cost.
batch.size Workload dependent Larger batches improve throughput when events are small. 
# Example producer properties
bootstrap.servers=b-1.example:9098,b-2.example:9098
security.protocol=SASL_SSL
acks=all
enable.idempotence=true
retries=2147483647
delivery.timeout.ms=120000
linger.ms=20
batch.size=65536
compression.type=lz4
max.in.flight.requests.per.connection=5
For high-volume data pipelines, batching and compression often matter as much as broker size. Small uncompressed writes are a tax on brokers, network, and storage.
Setting acks=1 may look faster but can lose acknowledged data if the leader fails before replicas catch up. Do not use it blindly for critical events.

Consumer Configuration Tuning

Consumer tuning controls how quickly records are fetched, processed, committed, and recovered after failures. Important settings include fetch.min.bytes, fetch.max.wait.ms, max.poll.records, max.poll.interval.ms, session.timeout.ms, heartbeat.interval.ms, and offset commit strategy.

Concern Setting Design Guidance
Throughput fetch.min.bytes, max.poll.records Increase for batch-oriented sinks like S3 or warehouses.
Long processing max.poll.interval.ms Raise if processing batches can exceed default poll interval.
Failure detection session.timeout.ms Lower detects dead consumers faster but can cause false rebalances.
Commit behavior enable.auto.commit Use manual commits for reliable sinks and controlled retries. 
# Example consumer properties
bootstrap.servers=b-1.example:9098,b-2.example:9098
group.id=s3-raw-loader
enable.auto.commit=false
auto.offset.reset=earliest
max.poll.records=1000
max.poll.interval.ms=900000
fetch.min.bytes=1048576
fetch.max.wait.ms=500
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
Manual commits let a consumer write to a sink first, then commit offsets. This is the foundation of practical at-least-once processing.
If processing takes longer than max.poll.interval.ms, Kafka considers the consumer unhealthy and triggers a rebalance. The result can look like random duplicate processing.

Rebalancing and Consumer Lag

A rebalance happens when partitions are reassigned among consumers in a group. It can be triggered by consumer joins, consumer exits, missed heartbeats, topic partition changes, deployment restarts, or slow polling. Rebalances are normal, but frequent or long rebalances disrupt throughput and increase lag.

Consumer lag is the distance between the latest partition offset and the consumer group's committed offset. Lag is not always bad. A batch sink may intentionally process in waves. The real question is whether lag is bounded, predictable, and recovering.

Ways to reduce rebalance disruption

  • Use cooperative rebalancing where supported.
  • Avoid rolling all consumers at the same time.
  • Keep processing time below max.poll.interval.ms.
  • Use static group membership for stable long-running consumers.
  • Scale partitions and consumers based on measured throughput, not hope.
Lag alerting should combine lag size and lag age. A million records of lag may be fine for tiny events but dangerous if the oldest event is two hours late in a real-time pipeline.
A rebalance storm can be caused by slow processing, network instability, bad deployments, or too many partitions. Treat it as a platform reliability incident, not just an application bug.

Delivery Semantics and Exactly-Once

Kafka delivery semantics are usually described as at-most-once, at-least-once, and exactly-once. In real systems, the end-to-end guarantee depends on Kafka, the consumer code, the sink, idempotency, transactions, and failure recovery. Kafka can support exactly-once semantics for Kafka-to-Kafka workflows using idempotent producers and transactions. Once data leaves Kafka for S3, JDBC, OpenSearch, or an API, the sink must also support idempotent or transactional writes.

Semantic Meaning Typical Use
At-most-once May lose records, no duplicates Low-value metrics where loss is acceptable.
At-least-once No loss if designed correctly, duplicates possible Most data engineering pipelines.
Exactly-once Each logical event affects final state once Financial ledgers, stateful stream processing, compacted tables.
Most production pipelines do not need pure exactly-once Kafka transactions. They need at-least-once delivery plus idempotent writes, deterministic keys, and deduplication in the sink.
Exactly-once is not magic. If a consumer calls an external REST API and then crashes before committing the offset, Kafka cannot automatically undo the API side effect.
# Common idempotent sink pattern
event_id = record.headers["event_id"]
upsert into target_table(event_id, payload, processed_at)
values (:event_id, :payload, current_timestamp)
on conflict (event_id) do update
set payload = excluded.payload,
    processed_at = excluded.processed_at;

Schema Governance with Glue Schema Registry

Glue Schema Registry helps producers and consumers enforce schemas for Kafka messages. It supports schema formats such as Avro, JSON Schema, and Protobuf depending on client integration. The registry stores schema versions and compatibility rules so event contracts can evolve without breaking consumers.

For senior data engineering teams, schema governance is not paperwork. It is outage prevention. Streaming systems fail painfully when producers silently rename fields, change types, remove required attributes, or publish malformed records.

Compatibility Mode What It Protects Typical Use
Backward New consumers can read old data Common for analytics and replay.
Forward Old consumers can read new data Useful during producer-first deployments.
Full Both backward and forward compatibility Strict enterprise contracts. 
{
  "type": "record",
  "name": "MetricSample",
  "namespace": "com.sean.telemetry",
  "fields": [
    { "name": "endpoint_id", "type": "string" },
    { "name": "metric_name", "type": "string" },
    { "name": "value", "type": "double" },
    { "name": "event_time", "type": "string" }
  ]
}
Schema versioning makes replay safer. A consumer rebuilding a table from last month's events must understand older message versions.
Do not let teams publish arbitrary JSON forever. The first downstream warehouse, ML feature store, or audit replay will expose the damage.

MSK Connect and Data Engineering Patterns

MSK Connect runs Kafka Connect connectors as a managed AWS service. It is commonly used for S3 sinks, JDBC sources, JDBC sinks, Debezium CDC, OpenSearch sinks, and other connector-based integrations. This reduces custom code, but connector configuration and operational ownership still matter.

Common MSK patterns

Pattern Flow Notes
Raw event lake Producer -> MSK -> S3 sink Use partitioned paths by event date, topic, and source.
CDC lakehouse Database -> Debezium -> MSK -> Iceberg/S3 Requires delete handling, ordering, and schema evolution.
Real-time analytics MSK -> Flink/Spark Streaming -> S3/OpenSearch Use checkpoints and idempotent sinks.
Operational search MSK -> OpenSearch sink Requires stable document IDs to avoid duplicates. 
{
  "connector.class": "io.confluent.connect.s3.S3SinkConnector",
  "topics": "telemetry.metric_samples",
  "s3.bucket.name": "de-raw-events",
  "s3.region": "us-east-1",
  "flush.size": "10000",
  "format.class": "io.confluent.connect.s3.format.parquet.ParquetFormat",
  "partitioner.class": "io.confluent.connect.storage.partitioner.TimeBasedPartitioner",
  "path.format": "'year'=YYYY/'month'=MM/'day'=dd/'hour'=HH"
}
MSK Connect is best when the integration is standard. Write custom consumers only when business logic, error handling, or sink semantics exceed connector configuration.
Connectors can fail silently from poison records, schema mismatches, IAM permission errors, small-file explosions, or sink throttling. Monitor connector task state and dead letter queues.

Monitoring, Security, and Cost

MSK operations need three monitoring layers: broker health, topic throughput, and consumer behavior. CloudWatch broker metrics show CPU, memory pressure, disk usage, network throughput, request latency, under-replicated partitions, active controller count, and connection counts. Consumer lag tells you if downstream applications are keeping up.

Security checklist

  • Use TLS for encryption in transit.
  • Use IAM authentication, SASL/SCRAM, or mTLS consistently.
  • Restrict broker access to approved VPCs, subnets, and security groups.
  • Separate producer and consumer permissions by topic prefix.
  • Encrypt data at rest and rotate secrets/certificates.

Cost drivers

Driver Why It Surprises Teams Mitigation
Broker capacity Provisioned clusters run even when traffic is low. Right-size, use Serverless for bursty workloads.
Storage retention Long retention across replicated partitions grows fast. Set retention per topic and offload to S3 when possible.
Cross-AZ traffic Replication and clients across AZs add network cost. Place clients carefully and understand data transfer paths.
Small files in S3 Over-flushing from connectors increases downstream query cost. Tune flush size, rotate interval, and compaction jobs.
Alert on symptoms users feel: consumer lag age, failed connector tasks, under-replicated partitions, disk pressure, and produce/consume error rates.
Kafka retention is not a warehouse retention policy. Keeping months of replicated Kafka data can be expensive. Land durable history in S3 and use Kafka for hot replay windows.

Kafka vs Kinesis

Kafka and Kinesis both support streaming ingestion, but they fit different operating models. Kafka is portable, ecosystem-rich, and strong when teams already use Kafka clients, Kafka Connect, Flink, Spark, or multi-cloud patterns. Kinesis is AWS-native, simpler to operate, and integrates directly with Lambda, Firehose, CloudWatch, IAM, and other AWS services.

Dimension Kafka/MSK Kinesis
API ecosystem Open Kafka protocol and large connector ecosystem AWS-native APIs and integrations
Operations More tuning and Kafka knowledge Less broker thinking; shard/serverless model
Portability High Lower; AWS-specific
Ordering unit Partition Shard
Best fit Kafka ecosystem, complex streaming platform AWS-first event ingestion and simple stream fan-out
Choose MSK when Kafka compatibility and ecosystem matter. Choose Kinesis when AWS-native simplicity matters more than Kafka portability.
Do not compare only ingestion price. Include client complexity, operations, replay needs, connector maturity, downstream integrations, and team expertise.

Interview Q&A

Q: How do Kafka partitions affect ordering and scalability?
A: Kafka guarantees ordering only within a partition. More partitions increase parallelism for producers and consumer groups, but they also increase metadata, recovery overhead, rebalance cost, and operational complexity. The partition key should match the business unit that requires ordering.
Q: When would you choose MSK Serverless instead of provisioned MSK?
A: I would choose MSK Serverless for new or variable workloads where I want Kafka semantics without broker sizing. I would choose provisioned MSK for predictable high-throughput platforms where explicit control over broker type, storage, partition strategy, and cost optimization matters.
Q: What producer settings matter most for reliable ingestion?
A: The core settings are acks=all, enable.idempotence=true, retries enabled, reasonable delivery timeout, compression, batching, and a partition key that distributes load. These settings protect against data loss and improve throughput, but they must be matched with broker replication and topic min.insync.replicas.
Q: How do you design a Kafka consumer that writes reliably to S3 or a database?
A: I usually disable auto-commit, process records in controlled batches, write to the sink using idempotent keys or upserts, then commit offsets only after the sink write succeeds. For S3, I also watch file sizing, partition paths, schema evolution, and retry behavior around partial failures.
Q: What does exactly-once mean in Kafka, and when is it worth using?
A: Kafka exactly-once usually means transactional Kafka-to-Kafka processing where output records and consumed offsets are committed atomically. It is worth using for stateful stream processing where duplicates corrupt results. For many data pipelines, at-least-once plus idempotent sink writes is simpler and sufficient.
Q: How would you troubleshoot increasing consumer lag in MSK?
A: I would check whether produce rate increased, consumers are erroring, rebalances are frequent, processing time exceeds max.poll.interval.ms, sink systems are throttling, or partitions are imbalanced. Then I would inspect CloudWatch metrics, consumer group lag, connector task status, and application logs before scaling consumers or partitions.

Quick Reference

Broker
Kafka server that stores partitions and handles producer/consumer requests.
Topic
Named event stream with retention, partitions, and replication settings.
Partition
Ordered shard of a topic; the unit of parallelism and ordering.
Offset
Record position within a partition; committed by consumer groups.
Consumer group
Logical subscriber where partitions are distributed among active consumers.
acks=all
Producer waits for all required in-sync replicas before acknowledging a write.
idempotence
Producer feature that prevents duplicates caused by retrying sends.
linger.ms
Producer delay that allows more records to batch before send.
max.poll.interval
Maximum time between consumer polls before Kafka triggers group rebalance.
Consumer lag
Difference between latest offset and committed consumer group offset.
Rebalance
Partition reassignment after consumer group membership or topic changes.
MSK Connect
Managed Kafka Connect service for source and sink connectors.
Glue Registry
AWS schema registry for schema versions, compatibility, and enforcement.
Serverless MSK
MSK option that abstracts broker capacity for variable workloads.
Provisioned MSK
MSK option where you choose broker count, instance type, storage, and scaling.
Kafka vs Kinesis
Kafka favors portability and ecosystem; Kinesis favors AWS-native simplicity.
