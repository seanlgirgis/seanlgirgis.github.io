The GIL — why it matters for data engineers

The Global Interpreter Lock allows only one thread at a time to execute Python bytecode in the standard CPython runtime. That does not mean Python cannot do concurrent work; it means CPU-bound Python code does not get true parallel speedup from threads. For data engineers, the distinction matters when deciding whether a slow pipeline is waiting on I/O or burning CPU.

Threads can still help dramatically when work is blocked on network, disk, S3, APIs, databases, or remote services. While one thread waits for a response, another thread can run. But if your function is parsing JSON in pure Python, compressing files, hashing records, or applying row-level transformations, threads usually just fight over the GIL.

Decision shortcut: use threads for waiting, processes for calculating, async for many cooperative I/O calls, and Spark when the data or compute no longer fits one machine.
Many native libraries release the GIL during heavy work. NumPy, Pandas, PyArrow, and compression libraries may already parallelize internally, so adding Python-level concurrency can sometimes make performance worse.

Threading vs Multiprocessing — the decision rule

Threading runs multiple execution paths inside one process and shares memory. That makes it cheap to start and convenient for I/O-heavy tasks such as calling 500 URLs, listing S3 keys, or querying many small database partitions. Shared memory is also the danger: you must protect mutable state or avoid sharing it.

Multiprocessing starts separate Python processes with separate memory spaces. That bypasses the GIL and can use multiple CPU cores, but arguments and results must cross process boundaries. The overhead is worth it for expensive CPU-bound functions, not for tiny per-row operations where serialization costs dominate.

WorkloadBest fitReason
HTTP/API callsThreads or asyncioMost time is network waiting
S3 object metadata scansThreads or async SDKMany independent I/O calls
CPU-heavy parsingProcessesTrue parallelism across cores
Vectorized dataframe opsLibrary engine firstPandas, Polars, DuckDB, Arrow may already optimize
Large distributed joinsSparkNeeds cluster memory and shuffle management
Do not choose multiprocessing just because it sounds faster. If each task sends a large DataFrame to a worker, pickling can cost more than the computation.

concurrent.futures — ThreadPoolExecutor & ProcessPoolExecutor

concurrent.futures is the clean high-level API for Python concurrency. ThreadPoolExecutor is the usual choice for I/O-bound fan-out. ProcessPoolExecutor is the usual choice for CPU-bound fan-out when the function and data are safely picklable.

Use executor.map() when every item is independent and you want ordered results. Use executor.submit() plus as_completed() when you need per-task error handling, progress logging, retries, or different arguments per task.

from concurrent.futures import ThreadPoolExecutor, as_completed


def fetch_partition(partition_id):
    # I/O-bound: API, S3, database, etc.
    return partition_id, call_remote_service(partition_id)

partitions = range(100)
results = {}

with ThreadPoolExecutor(max_workers=16) as executor:
    futures = [executor.submit(fetch_partition, p) for p in partitions]
    for future in as_completed(futures):
        partition_id, data = future.result()
        results[partition_id] = data
submit() + as_completed() is the production pattern because it lets you log and recover task by task instead of failing blindly at the end.
max_workers is not a bragging number. Too many workers can overload APIs, saturate database connection pools, increase throttling, or make S3 calls slower through retries.

Exception Handling & Pickling

Exceptions raised inside workers are not raised at submission time. They are raised when you call future.result(). That is good: it lets a pipeline continue processing other independent tasks while collecting failures for retry, quarantine, or dead-letter handling.

Process pools have an extra constraint: arguments, return values, and worker functions must be picklable. Lambdas, nested functions, open database connections, active file handles, and many class instances fail at the process boundary. Keep process-pool worker functions top-level, pass small serializable inputs, and create external clients inside the worker if needed.

from concurrent.futures import ProcessPoolExecutor, as_completed


def score_file(path):
    # Top-level function: safe for process pools.
    return path, expensive_cpu_score(path)

with ProcessPoolExecutor(max_workers=4) as executor:
    futures = [executor.submit(score_file, p) for p in file_paths]
    for future in as_completed(futures):
        try:
            path, score = future.result()
        except Exception as exc:
            log_failure(exc)
        else:
            persist_score(path, score)
Never pass a live database connection, boto3 client, logger with handlers, or giant DataFrame into a process worker unless you have measured the serialization cost and failure behavior.

asyncio — event loop, async/await, when to use it

asyncio uses a single-threaded event loop and cooperative multitasking. A coroutine yields control when it awaits an I/O operation, allowing other coroutines to run. This is excellent for thousands of lightweight I/O tasks, but it does not make CPU-bound Python code parallel.

The async model shines when your client libraries are async-native: HTTP clients, async database drivers, queues, and cloud SDK wrappers. It is less useful when the underlying library is blocking, because one blocking call can freeze the event loop and ruin concurrency.

import asyncio


async def fetch_one(session, url):
    async with session.get(url) as resp:
        resp.raise_for_status()
        return await resp.json()

async def fetch_many(session, urls):
    tasks = [fetch_one(session, url) for url in urls]
    return await asyncio.gather(*tasks)
Async is not faster because it uses more CPU. It is faster when it keeps one thread busy while many remote operations are waiting.
Mixing blocking libraries into async code is the classic footgun. If a call has no await and performs network or disk I/O, assume it can block the whole loop.

asyncio for Data Engineering — aiohttp, aiobotocore, asyncpg

For data pipelines, async is most useful at ingestion edges: hitting REST APIs with aiohttp, talking to AWS services through aiobotocore, or querying PostgreSQL with asyncpg. These tools can keep many requests in flight without the memory and context-switch overhead of hundreds of threads.

The production concern is backpressure. Async makes it easy to create far more in-flight work than a downstream API, database, or object store can tolerate. Use semaphores, bounded queues, and connection pool limits so the pipeline controls pressure instead of discovering limits through throttling.

import asyncio

sem = asyncio.Semaphore(20)

async def bounded_fetch(session, url):
    async with sem:
        async with session.get(url) as resp:
            resp.raise_for_status()
            return await resp.text()
The best async ingestion jobs usually combine high fan-out with explicit limits: concurrency cap, timeout, retry policy, and a bounded output sink.
Async database writes can still overwhelm the database. Fast clients do not remove transaction locks, index costs, WAL pressure, or connection pool limits.

Queue-Based Producer-Consumer Pattern

The producer-consumer pattern separates fetching work from processing work. Producers discover or read tasks, push them into a queue, and consumers process them at a controlled rate. This keeps pipelines stable when one side is bursty and the other side is slow.

In one Python process, use queue.Queue for threaded workers or asyncio.Queue for coroutines. Across machines or services, use SQS, Kafka, RabbitMQ, or a database-backed job table. The pattern is the same: bounded queue, idempotent worker, retry policy, poison-message handling, and observable lag.

from queue import Queue
from threading import Thread

q = Queue(maxsize=500)


def worker():
    while True:
        item = q.get()
        try:
            process_item(item)
        finally:
            q.task_done()

for _ in range(8):
    Thread(target=worker, daemon=True).start()

for item in discover_items():
    q.put(item)
q.join()
A queue without idempotency is only half a design. Retries can duplicate work, so writes need natural keys, upserts, checkpoints, or dedupe tables.

Rate Limiting & The Embarrassingly Parallel Pattern

An embarrassingly parallel workload splits into independent tasks with little or no communication between them: process 10,000 files, call one API per account, validate one partition per date, or compute one feature bundle per entity. These are ideal for threads, processes, async, AWS Batch, Lambda fan-out, ECS tasks, or Spark depending on size and dependencies.

Rate limiting is what turns a cute concurrency demo into a reliable pipeline. External systems have quotas, retry budgets, connection limits, and fairness controls. Respecting them usually beats blindly increasing workers, especially when retries amplify traffic during incidents.

SemaphoreAsync or threaded fan-outCaps in-flight requests

Concurrency increases pressure. Rate limiting shapes pressure. Senior pipeline design needs both.

When to Move to Spark

Python concurrency is a single-machine scaling tool. It helps when the job is blocked on I/O, can use multiple CPU cores, or can split cleanly into independent tasks. It does not solve cluster-scale shuffles, terabyte joins, skewed aggregations, or memory pressure from data that cannot fit comfortably on one host.

Move to Spark when the hard part is distributed data movement, not just local parallelism. Spark brings partitioning, shuffle management, fault recovery, executor memory isolation, cluster scheduling, and integration with Parquet, S3, Glue, EMR, and Databricks. That power comes with overhead, so DuckDB, Polars, or Python multiprocessing may be better for single-machine jobs under the right size.

A good decision rule: optimize locally until the bottleneck is data volume, distributed joins, or fault-tolerant cluster execution. Then move to Spark.
Do not wrap Spark jobs in Python thread pools to make them faster. Spark already parallelizes work across executors; extra driver-side concurrency often creates scheduling noise and operational confusion.

Interview Q&A

Q: Why do Python threads not speed up CPU-bound work in CPython?
A: The GIL allows only one thread to execute Python bytecode at a time. For CPU-bound Python code, multiple threads mostly take turns instead of running in parallel. Threads can still help when work releases the GIL or waits on I/O, but process pools are the safer choice for pure Python CPU work.
Q: How would you choose between ThreadPoolExecutor and ProcessPoolExecutor in a pipeline?
A: I would start with the bottleneck. If the job waits on APIs, S3, or databases, I would use threads with bounded workers. If the job burns CPU in Python code, I would use processes, while keeping inputs and outputs small enough to avoid pickling overhead.
Q: What is the most common production bug in process-pool code?
A: Passing non-picklable or huge objects into workers. Lambdas, nested functions, open connections, and large DataFrames often fail or serialize slowly. I prefer top-level functions, small identifiers as inputs, and worker-local clients.
Q: When is asyncio better than a thread pool?
A: Asyncio is strong when there are many lightweight I/O operations and async-native libraries are available. It can handle large fan-out with fewer OS threads and lower overhead. It is not a CPU acceleration tool, and blocking calls inside the event loop can erase the benefit.
Q: How do you make a concurrent ingestion job safe to retry?
A: I design writes to be idempotent using natural keys, upserts, checkpoints, or dedupe tables. I also isolate failed tasks, track retry counts, and send poison records to a dead-letter path. Concurrency without idempotency is fragile because partial failure is normal.
Q: When would you stop using local Python concurrency and move to Spark?
A: I would move when the bottleneck becomes distributed data volume, large joins, shuffles, skew, or memory pressure beyond one machine. Spark gives partitioned execution, retryable tasks, and cluster scheduling. For smaller single-node analytics, DuckDB, Polars, or local multiprocessing may be simpler and faster.

Quick Reference

GIL
CPython lock that prevents multiple threads from executing Python bytecode at the same time.
ThreadPool
Best for I/O-bound fan-out such as APIs, S3 calls, metadata scans, and database reads.
ProcessPool
Best for CPU-bound pure Python work when inputs and outputs are picklable and not huge.
executor.map
Simple ordered parallel mapping; less flexible for per-task error handling.
submit()
Creates individual futures; useful for logging, retries, timeouts, and mixed arguments.
as_completed()
Processes futures as they finish, which is ideal for long-tail tasks and partial failures.
future.result()
Returns worker output or re-raises the worker exception in the caller.
Pickling
Serialization boundary required by process pools; avoid lambdas, nested functions, and live clients.
asyncio
Single-threaded event loop for cooperative I/O concurrency using async and await.
Semaphore
Concurrency cap that prevents async or threaded jobs from overwhelming external systems.
Queue
Producer-consumer buffer that decouples discovery from processing and enables backpressure.
Idempotency
Required for safe retries; use natural keys, upserts, checkpoints, or dedupe tables.
Rate limit
Controls request pressure with caps, token buckets, backoff, jitter, and batching.
Move to Spark
Use when distributed joins, shuffles, data volume, or fault-tolerant cluster execution dominate.
