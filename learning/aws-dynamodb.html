What DynamoDB Is

Amazon DynamoDB is a fully managed, serverless NoSQL database built for predictable low-latency access at very large scale. It is not a relational database with weaker SQL. It is a key-value and document database where the physical access path is part of the data model.

For a senior data engineer, the important mental shift is this: DynamoDB rewards knowing the exact questions your application will ask before you design the table. You do not model around entities first. You model around access patterns, cardinality, write rate, read rate, item size, and partition distribution.

Dimension DynamoDB Behavior Engineering Implication
Query model Primary key, sort key, indexes, point reads, range reads Fast when access patterns are known; awkward for ad hoc analytics
Scaling model Managed partitions and distributed storage Great for high concurrency if keys distribute load well
Schema Schemaless items with optional attributes Flexible, but requires strong application-side discipline
Transactions Supported, but not the default modeling style Useful for integrity boundaries; expensive if overused
DynamoDB is strongest when your workload is operational: known queries, high request volume, predictable key access, and strict latency goals.
The classic failure is treating DynamoDB like PostgreSQL without joins. That usually leads to scan-heavy access, index sprawl, and surprise cost.

Relational Thinking vs Single-Table Design

Relational modeling separates entities into normalized tables and lets SQL reconstruct views through joins. DynamoDB pushes the opposite direction: duplicate data intentionally, colocate related items under the same partition key, and encode item type into the key structure.

Single-table design means multiple logical entity types live in one physical table. A customer profile, order, order line, payment status, shipment, and audit marker can share one table if their access patterns benefit from colocated reads.

Example single-table pattern

PK                  SK                       Entity
CUSTOMER#123        PROFILE                  Customer profile
CUSTOMER#123        ORDER#2026-04-25#9001    Order header
CUSTOMER#123        ORDER#2026-04-25#9001#L1 Order line
CUSTOMER#123        PAYMENT#9001             Payment status
ORDER#9001          EVENT#001                Order event record

This pattern lets the application query PK = CUSTOMER#123 and retrieve a customer-centered view without a join. It also allows range filtering on the sort key, such as only orders or only recent orders.

Single-table design is not about forcing everything into one table. It is about optimizing item adjacency for your most important reads.
Do not use single-table design as a religious rule. If two domains have unrelated access patterns, separate tables can be cleaner, cheaper, and safer.

Partition Keys, Sort Keys, and Access Patterns

The partition key determines physical distribution. The sort key determines ordered retrieval inside an item collection. Together, they define what DynamoDB can retrieve efficiently without scanning.

A strong table design begins with an access-pattern inventory. For each query, write down the required key condition, expected cardinality, peak read/write rate, and whether results must be strongly consistent.

Access Pattern Good Key Shape Why It Works
Get pipeline run by ID PK=PIPELINE#id, SK=RUN#timestamp Point or bounded range lookup
List latest jobs for tenant PK=TENANT#id, SK=JOB#date#id Sorted time-based retrieval
Lookup by external request ID GSI with request_id as key Alternate unique access path
Find all failed jobs today GSI with bucketed status/date key Avoids full table scan

Common sort key tricks

RUN#2026-04-25T01:30:00Z
RUN#2026-04-25T01:30:00Z#ATTEMPT#001
STATUS#FAILED#2026-04-25#RUN#abc123
TYPE#METADATA
TYPE#CHECKPOINT#000042
Design keys so DynamoDB can answer with GetItem or Query. If your design needs frequent Scan, the model is probably wrong.
A high-cardinality partition key is not enough. It must also distribute traffic. A million keys do not help if 80 percent of traffic hits one key.

Item Modeling for Data Engineering

DynamoDB is often excellent as a metadata store for data engineering pipelines. It can track ingestion jobs, checkpoints, file manifests, idempotency keys, schema versions, workflow locks, backfill status, and compact operational state.

It is usually not the place to store large analytical facts. Put raw and curated datasets in S3, query with Athena or Spark, warehouse in Redshift or Snowflake, and keep DynamoDB for fast operational coordination.

Pipeline metadata item example

{
  "PK": "PIPELINE#daily_customer_extract",
  "SK": "RUN#2026-04-25T00:00:00Z",
  "status": "RUNNING",
  "source": "s3://landing/customer/",
  "target": "s3://curated/customer/",
  "watermark": "2026-04-24T23:59:59Z",
  "attempt": 2,
  "owner": "data-platform",
  "ttl_epoch": 1777075200
}
Use Case DynamoDB Fit Reason
Idempotency record Excellent Conditional writes prevent duplicate processing
Workflow checkpoint Excellent Fast point reads and atomic updates
Large time-series metrics Weak Usually better in Timestream, InfluxDB, OpenSearch, or S3
Ad hoc reporting Weak No joins, no SQL aggregation, scan cost risk
For data engineering, DynamoDB is often the control plane, not the data plane.
The 400 KB item limit matters. Store large payloads in S3 and keep a pointer, checksum, status, and metadata in DynamoDB.

GSIs and LSIs

Global Secondary Indexes and Local Secondary Indexes add alternate access paths. They are powerful, but every index is also another write target, another cost surface, and another operational dependency.

A GSI can use a different partition key and sort key from the base table. An LSI shares the base table partition key but uses a different sort key. LSIs must be created with the table. GSIs can be added later, but backfilling them on a large table can take time and consume capacity.

Index Type Key Behavior Best Use Tradeoff
GSI Different partition key and optional sort key Alternate query path such as status, tenant, external ID Extra write cost and eventual consistency
LSI Same partition key, different sort key Alternate ordering within the same item collection Must be planned at table creation
Sparse GSI Only items with index keys appear Queues, open tasks, failed jobs, active sessions Requires careful attribute lifecycle management
Overloaded GSI Multiple entity types share one index Single-table designs with many access patterns Harder naming discipline and testing

Sparse GSI example

{
  "PK": "JOB#abc123",
  "SK": "METADATA",
  "status": "FAILED",
  "GSI1PK": "FAILED#2026-04-25",
  "GSI1SK": "PIPELINE#customer_extract#JOB#abc123"
}
A sparse GSI is one of DynamoDB's best production patterns. Only the items you need to query appear in the index.
Every GSI has its own partitioning problem. A low-cardinality GSI key like status=FAILED can become a hot partition unless bucketed by date, tenant, or shard.

Capacity Modes and Throughput Economics

DynamoDB offers on-demand capacity and provisioned capacity. On-demand removes most capacity planning and charges per request. Provisioned capacity charges for configured read and write capacity, commonly with auto scaling for predictable workloads.

The engineering choice is not only price per request. It also includes operational overhead, traffic predictability, cold-start growth, budget guardrails, and the blast radius of accidental high-volume traffic.

Mode Use When Cost Behavior Risk
On-demand Unknown, bursty, spiky, or early-stage workloads Pay per request Cost can rise quickly if traffic or scans explode
Provisioned Predictable steady workloads Pay for configured capacity Throttling if auto scaling lags or limits are wrong
Provisioned + auto scaling Known baseline with moderate variation Balances cost and elasticity Scaling is reactive, not magical
Reserved capacity Long-running predictable provisioned workloads Discounted commitment Waste if usage drops

Simple CLI examples

aws dynamodb update-table \
  --table-name pipeline_metadata \
  --billing-mode PAY_PER_REQUEST

aws dynamodb update-table \
  --table-name pipeline_metadata \
  --provisioned-throughput ReadCapacityUnits=200,WriteCapacityUnits=100
Use on-demand when product traffic is unknown. Move to provisioned only when measurement proves a stable workload and the team can manage capacity intentionally.
Scans, large items, global tables, backups, Streams, DAX, exports, and GSIs can all show up as bill surprises. The table request rate is only one part of cost.

Hot Partitions and Scale Failure Modes

The hot partition problem happens when too many reads or writes target the same partition key or a small set of partition keys. DynamoDB can scale horizontally, but your key design must give it room to distribute traffic.

Senior engineers should ask: what is the hottest key, not just how many keys exist? A table can have millions of distinct tenants but still fail if one enterprise tenant produces most traffic under one partition key.

Bad Pattern Why It Breaks Better Pattern
PK=STATUS#OPEN All open records hit one partition PK=STATUS#OPEN#DATE#2026-04-25#SHARD#03
PK=TENANT#big_customer One tenant dominates traffic Add write shards or split by workload dimension
PK=DATE#today All current writes concentrate on today Bucket by date plus source, region, or shard
Unbounded item collection Large partition grows forever Time bucket the partition key

Write sharding pattern

PK = "TENANT#123#INGEST#SHARD#" + random_int(0, 19)
SK = "EVENT#2026-04-25T01:30:00Z#uuid"

Write sharding improves write distribution, but it complicates reads because the application must query multiple shards and merge results. That tradeoff is acceptable for high-ingest systems but annoying for simple dashboards.

Hot partitions are usually modeling bugs, not DynamoDB bugs.
Random sharding solves write heat but can hurt query simplicity. Use it only when measured traffic justifies the added read fan-out.

Streams and Event-Driven Pipelines

DynamoDB Streams capture item-level changes and make them available for downstream processing. They are commonly connected to Lambda, EventBridge Pipes, Kinesis, or custom consumers to build event-driven workflows.

For data engineering, Streams are useful for change propagation, audit capture, cache invalidation, search indexing, CDC-style fanout, and triggering downstream processing when metadata changes.

Pattern Flow Engineering Note
Metadata event DynamoDB Streams to Lambda to Step Functions Trigger orchestration when a job status changes
Search indexing DynamoDB Streams to Lambda to OpenSearch Keep operational lookup separate from search
Lake export Streams or export to S3 Use S3/Athena for analytics, not table scans
Cache invalidation Streams to Lambda to Redis or DAX strategy Invalidate derived read models after writes

Lambda trigger shape

for record in event["Records"]:
    event_name = record["eventName"]        # INSERT, MODIFY, REMOVE
    keys = record["dynamodb"]["Keys"]
    new_image = record["dynamodb"].get("NewImage")
    old_image = record["dynamodb"].get("OldImage")
Streams let DynamoDB become the source of operational truth while downstream systems build analytics, search, notifications, and workflow side effects.
Stream consumers must be idempotent. Retries, duplicate deliveries, partial batch failures, and poison records are normal production concerns.

TTL, DAX, and Read Optimization

Time to Live automatically marks expired items for deletion using an epoch timestamp attribute. TTL is excellent for sessions, locks, temporary idempotency records, short-lived pipeline state, and deduplication windows.

DAX is DynamoDB Accelerator, an in-memory cache compatible with DynamoDB API calls. It is useful for read-heavy, eventually consistent, low-latency workloads where repeated key-value reads dominate.

Feature Best Use Gotcha
TTL Automatic expiry of temporary records Deletion is asynchronous, not immediate
DAX Microsecond read latency for repeated reads Not useful for write-heavy or strongly consistent reads
ProjectionExpression Read only attributes needed Does not reduce read capacity for full item read in all cases the way people expect
BatchGetItem Many known keys Handle unprocessed keys and retries

Enable TTL

aws dynamodb update-time-to-live \
  --table-name pipeline_metadata \
  --time-to-live-specification "Enabled=true,AttributeName=ttl_epoch"
TTL is great for operational hygiene. It prevents metadata tables from becoming junk drawers full of expired locks and stale deduplication keys.
Never build correctness on the assumption that TTL deletes exactly at expiration time. Treat it as eventual cleanup, not a scheduler.

DynamoDB in the AWS Data Stack

DynamoDB fits cleanly into AWS data systems when used as the fast operational layer around slower analytical systems. It can coordinate Glue jobs, store Athena query metadata, track Step Functions state, support Lambda-driven APIs, and feed S3-based analytics through exports or streams.

The strong architecture pattern is separation of concerns: DynamoDB for current operational state, S3 for durable lake storage, Glue Data Catalog for table metadata, Athena or Spark for analysis, OpenSearch for search, and Redshift for warehouse-style serving.

AWS Service DynamoDB Interaction Typical Data Engineering Use
S3 Store object pointers, manifests, checksums Track file ingestion and curated outputs
Glue Store job run metadata and watermarks Coordinate ETL and backfills
Lambda Read/write metadata, consume Streams Serverless orchestration and event handling
Step Functions Persist workflow checkpoints Retry-safe state management
Athena Query exported data in S3 Analyze historical table snapshots
OpenSearch Build search projection from Streams Search by text, many filters, relevance
DynamoDB is a sharp tool for metadata, state, and coordination. Pair it with S3 and analytics engines instead of forcing analytics into the table.
Do not run large analytical scans against production DynamoDB tables. Export to S3 or stream changes into an analytical store.

Operations, Observability, and Recovery

Production DynamoDB ownership means watching throttles, latency, consumed capacity, hot keys, stream iterator age, conditional check failures, item size growth, replication health, and account-level quotas.

Backups and recovery should be designed before the first outage. Use point-in-time recovery where appropriate, on-demand backups for release checkpoints, and export-to-S3 patterns for analytical replay and audit retention.

Concern Control Why It Matters
Accidental deletes PITR and least-privilege IAM Fast recovery from application or operator mistakes
Runaway cost Budgets, alarms, scan controls Scans and GSIs can create surprise bills
Data corruption Conditional writes and validation Schemaless does not mean ruleless
Consumer lag Stream iterator age alarms Delayed event processing breaks downstream SLAs
The most valuable DynamoDB dashboards show access-pattern health: throttles by operation, consumed capacity by index, latency, hot keys, and stream lag.
IAM permissions should separate table reads, table writes, index access, backup actions, and destructive operations. Admin-like access from apps is asking for pain.

When DynamoDB Is the Wrong Choice

DynamoDB is excellent for specific access patterns, but it is not a universal database. If the business needs ad hoc filtering, many joins, complex reporting, heavy aggregations, relational constraints, or analyst-friendly SQL, DynamoDB will fight the team.

It can still participate in those systems, but usually as the operational state store feeding another system. Senior judgment means choosing the right persistence layer, not proving every workload can be squeezed into one service.

Requirement Better Fit Reason
Complex SQL reporting PostgreSQL, Redshift, Snowflake, Athena Joins, aggregations, flexible predicates
Full-text search OpenSearch Text analysis, scoring, search filters
Large analytical datasets S3 + Parquet + Spark/Athena Columnar scans and cheap storage
Strong relational integrity PostgreSQL or another RDBMS Foreign keys, joins, constraints, transactions
High-cardinality metrics Timestream, InfluxDB, Prometheus-style stores Time-series compression and range analytics
Choose DynamoDB when access is known and latency matters. Choose relational or analytical systems when questions are unknown and exploration matters.
The most expensive DynamoDB migration is the one caused by using it before the access patterns were understood.

Interview Q&A

Q: How would you explain single-table design to a team coming from relational databases?
A: I would explain that relational design optimizes for normalized storage and flexible joins, while DynamoDB optimizes for known access paths. In single-table design, related items are intentionally colocated by partition key and ordered by sort key so the application can answer business queries with key-based reads instead of joins.
Q: How do you choose a partition key for a high-volume DynamoDB table?
A: I start from access patterns and traffic distribution. The key must support the query, have high enough cardinality, and distribute actual read/write traffic. I also look for hot tenants, hot dates, status buckets, and write bursts. If one key can dominate traffic, I bucket or shard intentionally.
Q: When would you use a GSI instead of changing the base table key?
A: I use a GSI when the table needs an alternate access pattern that cannot be served by the primary key, such as lookup by external ID or listing failed jobs by date. I avoid adding GSIs casually because each one increases write cost, storage, backfill complexity, and operational monitoring.
Q: How would you use DynamoDB in a data pipeline architecture?
A: I would use it as the control plane: pipeline run records, watermarks, file manifests, idempotency keys, locks, and retry state. The actual large datasets would live in S3 as Parquet or another analytical format, with Glue, Athena, Spark, or Redshift doing the heavy analytical work.
Q: What are common DynamoDB cost surprises?
A: Common surprises include scans, large item sizes, too many GSIs, stream reads, global table replication, backups, exports, DAX clusters, and provisioned capacity that sits idle. Another subtle one is a GSI with a bad key design that becomes both expensive and throttled.
Q: When would you reject DynamoDB for a project?
A: I would reject it if the team needs ad hoc analytics, complex SQL, many joins, strong relational constraints, or flexible reporting as a primary requirement. DynamoDB is excellent when access patterns are known. It is a poor fit when the main requirement is exploratory querying.

Quick Reference

PK
Partition key; controls data distribution and primary lookup path.
SK
Sort key; orders related items within the same partition key.
GetItem
Fast point lookup by full primary key.
Query
Efficient lookup by partition key with optional sort key condition.
Scan
Reads across table or index; dangerous for large production workloads.
GSI
Global Secondary Index; alternate partition/sort key access path with extra write and storage cost.
LSI
Local Secondary Index; same partition key, alternate sort key, created with the table.
Sparse GSI
Index only items that contain the index key attributes; useful for queues and filtered states.
On-demand
Pay-per-request capacity mode for unknown or spiky workloads.
Provisioned
Capacity mode where read/write throughput is configured and paid hourly.
TTL
Epoch timestamp attribute used for eventual automatic item expiry.
Streams
Ordered change records for item inserts, updates, and deletes.
DAX
Managed in-memory cache for read-heavy DynamoDB workloads.
400 KB
Maximum DynamoDB item size; store large payloads in S3 and keep pointers in DynamoDB.
