What DuckDB Is & Why It's Fast

DuckDB is an in-process OLAP database. There is no server to run, no cluster to operate, and no daemon listening on a port. In Python, it feels like importing a library; in production, it behaves like a serious analytical SQL engine embedded inside your process.

Its speed comes from the right architecture for analytical scans: columnar execution, vectorized processing, parallel query execution inside one machine, and strong pushdown into files such as Parquet. Instead of looping through Python objects row by row, DuckDB processes typed chunks close to the CPU.

Key insight: DuckDB is not "SQLite for analytics" because it looks similar; it is a columnar OLAP engine that happens to be embedded like SQLite.
Production gotcha: DuckDB removes infrastructure friction, not data engineering judgment. Bad file layout, tiny files, missing partition filters, and oversized local workloads can still make it slow.

DuckDB vs SQLite vs Pandas vs Spark

DuckDB overlaps with several tools, but it does not replace all of them. SQLite is excellent for embedded transactional storage and point lookups. Pandas is flexible for DataFrame manipulation. Spark is built for distributed compute. DuckDB lives in the sweet spot where the data fits on one machine and SQL is the cleanest expression of the transformation.

Tool Best Fit Primary Tradeoff
DuckDB Single-node analytical SQL over files, DataFrames, and local datasets Not a multi-user database server or distributed engine
SQLite Embedded OLTP, metadata, app state, small lookups Row-store design is not ideal for large aggregations
Pandas Python-native exploration and custom transformations Can become memory-heavy and slow with Python-level operations
Spark Distributed jobs, very large datasets, cluster-scale joins Operational overhead and latency for smaller workloads
Rule of thumb: under roughly laptop-to-workstation scale, DuckDB often beats "local Spark" because it avoids cluster overhead entirely.
Do not use DuckDB as a drop-in replacement for a warehouse when many users need concurrent writes, governance, workload isolation, and shared serving semantics.

Reading Parquet & CSV Directly

One of DuckDB's strongest data engineering use cases is querying files directly. You can run SQL against Parquet and CSV without first loading them into a database table. For Parquet, DuckDB can prune columns, push filters, inspect metadata, and avoid reading bytes that the query does not need.

SELECT region, count(*) AS endpoint_count
FROM read_parquet('data/endpoints/*.parquet')
WHERE status = 'ACTIVE'
GROUP BY region
ORDER BY endpoint_count DESC;

SELECT *
FROM read_csv_auto('landing/events_2026_04_25.csv')
LIMIT 20;

CSV is convenient at the boundary of systems, but Parquet is the better analytical storage format. CSV forces parsing, type inference, and full row reads; Parquet gives DuckDB typed columns, compression, row-group statistics, and selective I/O.

CSV type inference is useful for exploration, but risky for repeatable pipelines. Declare types explicitly when nulls, mixed date formats, leading zeros, or identifier columns matter.

Querying S3 with httpfs

With the httpfs extension, DuckDB can read remote objects from S3-compatible storage. This is powerful for lakehouse-style inspection: query a prefix, validate a partition, sample a file, or produce a small aggregate without spinning up Spark, Glue, or EMR.

INSTALL httpfs;
LOAD httpfs;

SET s3_region='us-east-1';

SELECT event_date, count(*) AS rows
FROM read_parquet('s3://my-bucket/events/date=*/part-*.parquet')
WHERE event_date >= DATE '2026-04-01'
GROUP BY event_date
ORDER BY event_date;

The main performance question is not "Can DuckDB read S3?" It can. The better question is whether your query shape minimizes remote I/O. Partition filters, column pruning, larger files, and Parquet statistics matter more over object storage than on local disk.

Great use case: inspect and aggregate S3 lake data from Python notebooks, CI validation jobs, or lightweight data quality checks.
S3 is not a local filesystem. Many small files, broad wildcard scans, and missing filters can turn a quick query into expensive network chatter.

Python API — connect, execute, fetchdf, arrow

The Python API is intentionally small: connect, execute SQL, and fetch results as Pandas, Arrow, Python tuples, or relations. That makes DuckDB easy to embed in ETL utilities, notebooks, validation scripts, and local analytical tools.

import duckdb
import pandas as pd

con = duckdb.connect("analytics.duckdb")

df = pd.DataFrame({
    "region": ["east", "east", "west"],
    "cpu": [71.2, 63.5, 82.1],
})

result = con.execute("""
    SELECT region, avg(cpu) AS avg_cpu
    FROM df
    GROUP BY region
""").fetchdf()

arrow_table = con.execute("""
    SELECT * FROM read_parquet('data/metrics/*.parquet')
    WHERE metric_name = 'cpu'
""").arrow()

DuckDB can query Pandas DataFrames directly, which is a killer feature for data engineers who already live in Python. It lets you use SQL for joins, aggregations, windows, and filters while still handing results back to Pandas or Arrow when needed.

Pattern: use Pandas for small ergonomic transforms, DuckDB for set-based SQL, and Arrow as the high-performance interchange layer.

Window Functions

DuckDB supports mature analytical SQL, including window functions. This matters because many pipeline questions are not simple group-bys: deduplication, latest-row selection, running totals, sessionization, ranking, and change detection all need row context.

SELECT
    endpoint_id,
    metric_ts,
    cpu,
    avg(cpu) OVER (
        PARTITION BY endpoint_id
        ORDER BY metric_ts
        ROWS BETWEEN 5 PRECEDING AND CURRENT ROW
    ) AS rolling_avg_cpu,
    row_number() OVER (
        PARTITION BY endpoint_id
        ORDER BY metric_ts DESC
    ) AS latest_rank
FROM read_parquet('metrics/*.parquet');

For senior data engineering interviews, this is where DuckDB becomes more than a file reader. You can express production-grade logic locally using the same SQL patterns you would use in Snowflake, BigQuery, Redshift, Postgres, or Spark SQL.

Window functions can be memory-intensive when partitions are huge or ordering keys are poorly distributed. Watch partition cardinality and sort pressure.

Writing Results & In-Memory vs Persistent

DuckDB can run entirely in memory or persist to a .duckdb database file. In-memory mode is ideal for notebooks, tests, temporary transformations, and CI checks. Persistent mode is better when you want reusable local tables, indexes of metadata, cached intermediate results, or repeatable development datasets.

-- Write query results to Parquet
COPY (
    SELECT region, metric_name, avg(value) AS avg_value
    FROM read_parquet('raw_metrics/*.parquet')
    GROUP BY region, metric_name
) TO 'curated/metric_summary.parquet' (FORMAT PARQUET);

-- Persist a local table
CREATE TABLE metric_summary AS
SELECT * FROM 'curated/metric_summary.parquet';

Writing Parquet keeps the output portable across Python, Spark, Athena, Snowflake external tables, and other engines. Writing to a DuckDB file is useful for local acceleration and repeatability, but it is not the right artifact when the next consumer is a cloud data lake.

Choose the output based on the next reader: Parquet for interoperability, .duckdb for local analytical state.

When to Use DuckDB — and When Not To

Use DuckDB when you need fast single-node analytics over files, local extracts, Pandas DataFrames, or medium-sized pipeline artifacts. It is excellent for profiling, joining, validating, sampling, and aggregating data before deciding whether a workload deserves a warehouse or distributed engine.

Avoid DuckDB when the requirements are multi-user serving, high-concurrency writes, distributed execution, strict enterprise governance, row-level security at organization scale, or operational dashboards that many teams hit all day. That is warehouse, lakehouse, or application database territory.

DuckDB is a force multiplier for the engineer, not a universal serving platform.
The dangerous anti-pattern is building a hidden production dependency on someone's laptop-grade embedded database and calling it a platform.

Real-World Pipeline Patterns

DuckDB shines as a sharp utility inside bigger data platforms. Common patterns include local Parquet inspection, smoke tests for landing files, schema drift checks, historical backfill validation, data quality aggregates, and fast joins between CSV extracts and lake data.

Pattern DuckDB Role Why It Works
Landing zone validation Count rows, inspect schema, detect null spikes Fast file reads without loading to a database first
Local feature engineering Aggregate Parquet into model-ready tables SQL is clearer than nested DataFrame code
Backfill audit Compare source and curated partitions Cheap validation before expensive reruns
Notebook acceleration Query Pandas, Arrow, CSV, and Parquet together Reduces Python loops and memory churn

In AWS-heavy environments, DuckDB is especially useful around S3, Glue/Athena-style lake layouts, and local developer workflows. It does not replace Glue, EMR, or Athena, but it can prevent you from using those services for every small inspection or validation task.

Do not let local convenience bypass production controls. If DuckDB produces a dataset used downstream, version the SQL, log the inputs, and write portable outputs.

Interview Q&A

Q: Why is DuckDB often faster than Pandas for analytical operations?
A: DuckDB executes vectorized SQL over typed columnar data, while Pandas workflows can fall back into Python-level operations and object-heavy memory layouts. For filters, joins, aggregations, and windows, DuckDB can push work into optimized C++ execution. Pandas is still useful, but DuckDB is often cleaner and faster for relational transformations.
Q: How would you decide between DuckDB and Spark for a pipeline?
A: I would start with data size, SLA, concurrency, and operational context. If the workload fits comfortably on one strong machine and is mostly analytical SQL over files, DuckDB is simpler and often faster. If the workload needs distributed compute, large shuffles, many executors, or managed production orchestration, Spark is the safer choice.
Q: What makes DuckDB a good fit for Parquet?
A: Parquet is columnar, typed, compressed, and stores metadata such as row-group statistics. DuckDB can use that structure for column pruning and predicate pushdown, which reduces I/O. The combination is strong because both the engine and file format are designed for analytical access patterns.
Q: What are the risks of using DuckDB against S3?
A: The main risks are remote I/O, small-file overhead, broad wildcard scans, and missing partition filters. DuckDB can read S3 effectively, but object storage has different latency behavior than local disk. I would design queries to read fewer columns, fewer partitions, and appropriately sized files.
Q: Is DuckDB a replacement for SQLite?
A: No. They are both embedded databases, but SQLite is a row-store OLTP database and DuckDB is a columnar OLAP engine. SQLite is better for application state, transactional writes, and point lookups. DuckDB is better for scans, joins, aggregations, and analytical queries.
Q: How would you use DuckDB in a production data engineering workflow?
A: I would use it as a controlled utility for validation, profiling, local transforms, CI checks, and producing portable Parquet outputs. I would keep SQL versioned, make inputs explicit, and avoid hidden laptop-only dependencies. For shared serving or high-concurrency production workloads, I would promote the logic into the warehouse, lakehouse, or distributed engine.

Quick Reference

duckdb.connect()
Creates an in-memory or persistent DuckDB connection from Python.
:memory:
Temporary database mode for notebooks, tests, and short-lived jobs.
.duckdb file
Persistent local database file for reusable tables and cached analysis state.
read_parquet()
Queries Parquet directly with column pruning and predicate pushdown.
read_csv_auto()
Reads CSV with automatic dialect and type inference; useful but risky for repeatable pipelines.
COPY (...) TO
Writes query results to files such as Parquet or CSV.
INSTALL httpfs
Installs the extension needed for HTTP and S3 object access.
LOAD httpfs
Loads remote file access support into the current DuckDB session.
fetchdf()
Returns query results as a Pandas DataFrame.
arrow()
Returns query results as an Arrow table for efficient interchange.
Window functions
Supports ranking, deduplication, running totals, rolling metrics, and latest-row logic.
Predicate pushdown
Pushes filters into file scans so fewer rows or row groups are read.
Column pruning
Reads only referenced columns from columnar formats such as Parquet.
Best fit
Single-node analytical SQL over files, DataFrames, and medium-sized pipeline artifacts.
