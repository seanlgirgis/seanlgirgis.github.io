Window Functions

Window functions compute across related rows without collapsing the result set. For data engineering, the workhorse functions are ROW_NUMBER for dedupe, RANK and DENSE_RANK for ordered groups, LAG and LEAD for change detection, and FIRST_VALUE for baseline comparison.

The practical pattern is always the same: define the partition, define deterministic ordering, then filter or calculate from that window. Running totals and moving averages use explicit frames so the query says whether it means physical rows, value ranges, or all rows to the current point.

SELECT
  customer_id,
  event_ts,
  amount,
  SUM(amount) OVER (
    PARTITION BY customer_id
    ORDER BY event_ts
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_amount,
  LAG(status) OVER (
    PARTITION BY customer_id
    ORDER BY event_ts
  ) AS previous_status
FROM fact_customer_events;
Key insight: a window function is often better than a self-join because it keeps row-level detail while exposing prior, next, first, last, or ranked context.
Gotcha: if the ORDER BY is not deterministic, your rank, dedupe winner, or previous-row logic can change between runs.

CTEs vs Subqueries vs Temp Tables

CTEs make complex SQL readable by naming intermediate logic. Subqueries are fine for compact filters or scalar lookups. Temp tables are stronger when the intermediate result is reused, inspected, indexed, or shared across multiple statements in a pipeline step.

Performance depends on the engine. Some optimizers inline CTEs, while others may materialize them or treat them as optimization boundaries. In warehouse ELT, temp tables are useful when breaking one monster query into auditable stages with row counts and quality checks.

PatternBest UseTradeoff
CTEReadable single statementMay hide repeated scans
SubquerySmall nested filterCan become hard to debug
Temp tableReusable staged resultExtra writes and cleanup
ViewShared semantic layerMay push complexity downstream
Key insight: use CTEs for clarity, temp tables for operational checkpoints, and subqueries when the logic is truly local.
Gotcha: repeating the same heavy CTE multiple times can force repeated work on engines that inline it.

Recursive CTEs

Recursive CTEs model relationships where each row points to another row: org charts, product assemblies, dependency trees, category hierarchies, and lineage chains. They have an anchor query for the starting rows and a recursive query that walks from parent to child or child to parent.

For data engineering, the value is controlled expansion. You can flatten hierarchies, compute depth, build paths, and detect unreachable or cyclic records before they poison downstream dimensions.

WITH RECURSIVE org AS (
  SELECT employee_id, manager_id, name, 0 AS depth
  FROM dim_employee
  WHERE manager_id IS NULL

  UNION ALL

  SELECT e.employee_id, e.manager_id, e.name, org.depth + 1
  FROM dim_employee e
  JOIN org ON e.manager_id = org.employee_id
)
SELECT * FROM org;
Key insight: recursive SQL is excellent for bounded hierarchy expansion, not for pretending a relational database is a graph engine.
Gotcha: always design for cycle protection or max depth; one bad parent-child loop can turn a clean load into a runaway query.

Slowly Changing Dimensions

Slowly Changing Dimensions preserve how descriptive attributes change over time. Type 1 overwrites the old value, Type 2 creates a new history row with effective dates, and Type 3 stores limited previous values in additional columns.

Type 2 is the senior data engineer default when reporting must answer, "What did we know at the time?" The table usually has a surrogate key, natural business key, effective start and end timestamps, current flag, and hash of tracked attributes.

SCD TypeBehaviorUse Case
Type 1OverwriteCorrections, no history needed
Type 2New version rowHistorical reporting and audits
Type 3Current plus previousLimited change comparison
Key insight: facts should usually join to the dimension version valid at the fact event time, not just the current dimension row.
Gotcha: a broken Type 2 load often creates overlapping effective ranges, which silently double-count facts in downstream joins.

MERGE & Upsert

MERGE combines insert, update, and sometimes delete logic into one statement. It is the backbone of incremental loads, SCD processing, CDC application, and idempotent reprocessing when source batches can arrive late or be replayed.

Upsert syntax varies by engine. PostgreSQL uses INSERT ... ON CONFLICT, many warehouses support MERGE INTO, and lakehouse engines may require special table formats to make row-level changes safe and performant.

MERGE INTO dim_customer t
USING stg_customer s
ON t.customer_id = s.customer_id AND t.is_current = true
WHEN MATCHED AND t.attr_hash <> s.attr_hash THEN
  UPDATE SET is_current = false, effective_end = s.load_ts
WHEN NOT MATCHED THEN
  INSERT (customer_id, name, attr_hash, effective_start, is_current)
  VALUES (s.customer_id, s.name, s.attr_hash, s.load_ts, true);
Key insight: good upsert design starts with stable business keys, deterministic source ranking, and a clear idempotency rule.
Gotcha: if your source has duplicate keys in the same batch, MERGE can fail or update the same target row unpredictably.

Deduplication Patterns

Deduplication is not just removing identical rows. Production dedupe means choosing the right surviving record using business rules: latest event, highest source priority, non-null payload, trusted vendor, or load timestamp.

The standard pattern is ROW_NUMBER() over a business key and a deterministic sort, then keep row 1. For event streams, separate exact duplicate removal from entity-state resolution; they answer different questions.

WITH ranked AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY order_id
      ORDER BY event_ts DESC, source_priority ASC, ingest_ts DESC
    ) AS rn
  FROM stg_orders
)
SELECT *
FROM ranked
WHERE rn = 1;
Key insight: dedupe is a business rule expressed in SQL, not a cosmetic cleanup step.
Gotcha: using DISTINCT for dedupe can hide source defects while keeping the wrong version of the record.

Anti-Joins & Set Operations

Anti-joins find rows in one dataset that do not exist in another. The common forms are LEFT JOIN ... IS NULL and NOT EXISTS; both are useful for reconciliation, missing dimension detection, orphan fact checks, and incremental load filters.

Set operations compare complete result sets. UNION ALL preserves duplicates and is faster, UNION removes duplicates, INTERSECT finds overlap, and EXCEPT finds differences. These are sharp tools for data validation when schemas align.

OperationMeaningCommon DE Use
NOT EXISTSA not in BFind missing target rows
LEFT JOIN IS NULLA not matched to BOrphan detection
UNION ALLAppend all rowsCombine partitions or sources
EXCEPTRows in first onlyRegression comparison
Key insight: anti-joins are reconciliation primitives; use them before and after loads to prove what changed.
Gotcha: NOT IN behaves badly with nulls; prefer NOT EXISTS when correctness matters.

EXPLAIN Plan Reading

EXPLAIN plans show how the optimizer intends to access, join, sort, aggregate, and distribute data. A senior data engineer reads plans to spot full scans, bad join order, skewed hash joins, missing partition pruning, broadcast mistakes, and expensive sorts.

The first pass is simple: look for the largest row estimates, the most expensive operators, and mismatches between estimated and actual rows. On distributed engines, also inspect data movement; shuffling terabytes to make a join work is usually the real bill.

Plan SignalLikely MeaningAction
Sequential scanNo useful index or pruningCheck filters and partitions
Hash joinBuild/probe joinWatch memory and skew
SortOrder requiredCheck keys and spill risk
BroadcastSmall table copiedVerify it is actually small
Key insight: query tuning starts with row counts and data movement, not with rewriting syntax for style.
Gotcha: stale statistics make the optimizer confidently choose a terrible plan.

Data Quality SQL

Data quality SQL turns assumptions into executable checks. Typical checks include uniqueness, required fields, accepted values, referential integrity, freshness, row-count thresholds, duplicate business keys, and numeric range validation.

The best checks are close to the pipeline boundary and produce actionable rows, not just pass or fail flags. In modern stacks, these checks may run in dbt tests, warehouse SQL jobs, Airflow tasks, or custom validation tables before curated data is published.

SELECT 'missing_customer_id' AS check_name, COUNT(*) AS failed_rows
FROM fact_orders
WHERE customer_id IS NULL

UNION ALL

SELECT 'negative_amount', COUNT(*)
FROM fact_orders
WHERE amount < 0

UNION ALL

SELECT 'duplicate_order_id', COUNT(*)
FROM (
  SELECT order_id
  FROM fact_orders
  GROUP BY order_id
  HAVING COUNT(*) > 1
) d;
Key insight: quality checks should protect business contracts, not just satisfy technical neatness.
Gotcha: checks without thresholds, owners, and failure handling become dashboard noise instead of pipeline protection.

Interview Q&A

Q: When would you use a window function instead of a group by?
A: Use GROUP BY when you want to collapse rows into aggregates. Use a window function when you need aggregate or relative context while preserving each row. Common examples are dedupe, running totals, prior status comparison, and top-N per group.
Q: What makes an SCD Type 2 implementation production-ready?
A: It needs stable business keys, surrogate keys, effective start and end timestamps, a current flag, and deterministic change detection. It should prevent overlapping ranges for the same business key. It also needs idempotent behavior so rerunning a batch does not create duplicate history.
Q: How do you decide between a CTE and a temp table?
A: I use a CTE when the logic belongs inside one readable statement. I use a temp table when the intermediate result is reused, needs indexing, needs row-count validation, or should be inspected during a pipeline. For very large transforms, temp tables often make debugging and recovery easier.
Q: Why can NOT IN be dangerous?
A: NOT IN interacts poorly with nulls because a null in the comparison set can make the result unknown. That can unexpectedly return no rows. NOT EXISTS is usually safer for anti-join logic.
Q: What do you look for first in an EXPLAIN plan?
A: I look for row counts, scan type, join strategy, sorts, spills, and data movement. Then I compare estimated rows to actual rows when available. Big estimate errors usually point to stale stats, bad predicates, or missing distribution and partition design.
Q: What is the difference between deduping events and resolving entity state?
A: Event dedupe removes repeated copies of the same event. Entity-state resolution chooses the current or winning version of a business object across many events. Mixing the two can remove valid history or keep the wrong current record.

Quick Reference

ROW_NUMBER
Assigns a unique sequence per partition; primary dedupe tool.
RANK
Ranks rows with gaps after ties; useful for leaderboards and top-N logic.
DENSE_RANK
Ranks rows without gaps after ties; useful for grouped tiering.
LAG / LEAD
Reads previous or next row values for change detection.
ROWS frame
Physical row-based window frame; best for moving row counts.
RANGE frame
Value-based window frame; useful but can surprise with duplicate order values.
CTE
Named query block for readability and staged logic inside one statement.
Temp table
Materialized intermediate result for reuse, inspection, indexing, or checkpoints.
Recursive CTE
Anchor plus recursive member for hierarchy traversal.
SCD Type 1
Overwrite dimension attributes; no historical tracking.
SCD Type 2
Create versioned dimension rows with effective dates and current flag.
MERGE
Conditional insert, update, and delete pattern for incremental loads.
NOT EXISTS
Safe anti-join pattern for rows in one dataset missing from another.
EXCEPT
Returns rows present in the first query and absent from the second.
EXPLAIN
Shows query plan: scans, joins, sorts, estimates, and sometimes runtime metrics.
