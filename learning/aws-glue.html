What AWS Glue Is

AWS Glue is the managed data integration layer for the AWS data stack. It combines a shared metadata catalog, schema discovery, serverless ETL runtimes, visual pipeline tooling, workflow orchestration, and schema governance. For a senior data engineer, the important point is not that Glue can run Spark. The important point is that Glue often becomes the connective tissue between S3, Athena, Redshift Spectrum, EMR, Lake Formation, Kafka, and downstream analytics.

Glue is most commonly used to transform data in S3 from raw landing formats into query-optimized layouts such as Parquet, partitioned by business keys like date, region, source system, tenant, or event type. It is also used to populate the Glue Data Catalog so Athena and Redshift Spectrum can query data without each service maintaining its own separate metastore.

Glue is best understood as two products joined together: a metastore used by many AWS analytics services, and managed compute for ETL jobs.
Do not treat Glue as just a scheduler. If the hard part is dependency management, retries, SLAs, and complex branching, pair Glue jobs with Step Functions, MWAA, or Airflow instead of forcing everything into Glue workflows.

Glue Data Catalog

The Glue Data Catalog stores databases, tables, partitions, columns, storage locations, SerDe information, classification metadata, and table parameters. In a lake architecture, the Catalog is the shared metastore that lets Athena, Redshift Spectrum, EMR Spark, Glue ETL, and Lake Formation agree on what a table is.

A Glue database is a namespace. A Glue table describes the physical layout of files and columns. Partitions are metadata entries that map partition keys to S3 prefixes. For example, a table may point to s3://lake/curated/orders/ while individual partitions point to dt=2026-04-25/region=us-east-1/.

The Catalog does not store your data. It stores the map that tells query engines where data lives and how to read it.
Partition metadata can become a bottleneck. Millions of partitions can slow planning and increase crawler/catalog operations. Use partition projection in Athena or table formats like Iceberg when partition scale gets painful.
-- Athena table backed by Glue Catalog metadata
CREATE EXTERNAL TABLE curated.orders (
  order_id string,
  customer_id string,
  amount decimal(12,2),
  status string
)
PARTITIONED BY (dt string, region string)
STORED AS PARQUET
LOCATION 's3://company-lake/curated/orders/';

Catalog design rules

Use stable database names by environment and domain, such as prod_sales, dev_sales, or lake_curated. Avoid letting every pipeline create random databases. For tables, prefer names that represent business entities, not job names.

Crawlers and Schema Discovery

Glue crawlers inspect data stores, infer schema, detect partitions, and create or update Data Catalog tables. They are useful for exploration, fast onboarding, and datasets where the file structure is regular. They are less safe when production schema must be strictly controlled.

A crawler can infer CSV, JSON, Parquet, ORC, Avro, and other formats. It can also group files into tables based on folder structure and classifiers. Crawler scheduling is useful when upstream systems land new partitions periodically, but many mature teams eventually replace scheduled crawling with explicit partition registration during pipeline execution.

Crawlers are excellent for discovery and partition detection. Manual table definitions are better when schema contracts matter.
A crawler can surprise you by changing column types after seeing messy data. In production, lock down crawler update behavior or use explicit schemas.

ETL Job Runtimes

Glue supports several job styles. Spark ETL jobs are the default choice for distributed file processing, joins, aggregations, and large transformations. Python shell jobs are better for lightweight orchestration, API calls, metadata maintenance, small file operations, or invoking AWS SDK operations. Ray jobs are useful for Python-native distributed workloads that do not map naturally to Spark DataFrame operations.

The runtime choice should follow the workload shape. Spark is powerful, but it has startup overhead and requires attention to partitions, shuffles, file sizes, and executor memory. Python shell is cheaper and simpler for small work. Ray can be attractive for parallel Python tasks, ML preprocessing, or custom functions that would be awkward in Spark.

Use the smallest runtime that fits the job. Not every data pipeline deserves a Spark cluster.
A common cost leak is running Spark Glue jobs for tiny tasks that could have been a Python shell job or Lambda.

SparkLarge S3 datasets, joins, repartitioning, Parquet writesSmall control-plane tasks
Python shellSDK calls, small transforms, metadata jobsLarge distributed processing
RayPython-native parallelism, ML-style workloadsSimple SQL-like ETL
StreamingNear-real-time ingestion from Kafka or KinesisBatch-only jobs with loose latency
from awsglue.context import GlueContext
from pyspark.context import SparkContext

sc = SparkContext()
glueContext = GlueContext(sc)
spark = glueContext.spark_session

orders = spark.read.parquet("s3://company-lake/raw/orders/")
clean = orders.dropDuplicates(["order_id"])
clean.write.mode("append").partitionBy("dt").parquet("s3://company-lake/curated/orders/")

DynamicFrames vs DataFrames

Glue introduced DynamicFrames to handle semi-structured data and messy schemas more gracefully than standard Spark DataFrames. A DynamicFrame can carry ambiguous types and use operations such as resolveChoice to decide how to handle fields that appear as different types across records.

In mature pipelines, many engineers use DynamicFrames at the edges when reading from the Glue Catalog or dealing with messy JSON, then convert to Spark DataFrames for serious transformation work. Spark DataFrames are more familiar, have broader API coverage, integrate with Spark SQL, and are often easier to optimize.

DynamicFrames are useful when schema ambiguity is real. DataFrames are usually better once the schema is known and controlled.
Do not keep using DynamicFrames just because the job was generated by Glue Studio. For complex transformations, convert to DataFrames and use normal Spark patterns.
dyf = glueContext.create_dynamic_frame.from_catalog(
    database="lake_raw",
    table_name="orders_json"
)

resolved = dyf.resolveChoice(specs=[
    ("amount", "cast:double"),
    ("customer_id", "cast:string")
])

df = resolved.toDF()
df.createOrReplaceTempView("orders")

result = spark.sql("""
SELECT customer_id, SUM(amount) AS total_amount
FROM orders
GROUP BY customer_id
""")

Job Bookmarks

Job bookmarks let Glue track previously processed input so incremental jobs do not repeatedly process the same files. For S3 sources, bookmarks generally track file state based on path and modification metadata. For JDBC sources, bookmarks can use keys to track incremental progress.

Bookmarks are helpful, but they are not a complete data correctness strategy. They do not automatically solve late-arriving files, overwritten files, replay requirements, upstream corrections, or exactly-once output writes. Senior engineers treat bookmarks as one state mechanism among several, not as a replacement for idempotent pipeline design.

Bookmarks reduce repeated reads. Idempotent writes protect correctness.
If upstream overwrites files in place, bookmarks can behave differently than expected. Prefer immutable landing paths with batch IDs or event dates.
# Typical job args include bookmark behavior
--job-bookmark-option job-bookmark-enable

# Reset bookmark when you intentionally need a replay
aws glue reset-job-bookmark --job-name orders-curation-job

Bookmark-safe pattern

Land raw files immutably under source=batch_id=... or ingest_dt=..., process into a temporary output prefix, validate counts, then publish to the final curated table. Keep audit tables for batch ID, input file count, output count, and status.

Pushdown Predicates

Pushdown predicates reduce data movement by filtering at the source before data reaches the Spark executor. In Glue, this often means using partition predicates when reading from the Data Catalog, JDBC predicates when reading databases, or Spark filters that can be pushed into Parquet/ORC readers.

For S3 data lakes, the highest-value optimization is usually partition pruning. Reading one day from a table partitioned by dt is dramatically cheaper than listing and scanning the whole dataset. For JDBC sources, pushdown can prevent accidentally extracting an entire operational database table into Spark.

Push filtering as close to storage as possible. The cheapest row is the row Spark never reads.
A filter written in code is not always pushed down. Confirm with Spark explain plans, CloudWatch metrics, and S3 bytes scanned.
dyf = glueContext.create_dynamic_frame.from_catalog(
    database="lake_curated",
    table_name="orders",
    push_down_predicate="dt = '2026-04-25' and region = 'us-east-1'"
)

filtered = spark.read.parquet("s3://company-lake/curated/orders/") \
    .where("dt = '2026-04-25'")

Workflows and Triggers

Glue workflows chain crawlers and jobs into a pipeline. Triggers can be scheduled, on-demand, or conditional based on the success or failure of previous nodes. This is convenient for simple Glue-native pipelines such as crawl raw data, run transformation, crawl curated data, and notify downstream consumers.

Workflows become less attractive when orchestration requires complex branching, fan-out, external service calls, cross-account dependencies, manual approvals, or detailed SLA management. At that point, Step Functions, MWAA, Airflow, or a custom orchestrator may be a better control plane.

Glue workflows are fine for simple data integration chains. Use a stronger orchestrator when the pipeline becomes a business process.
Retries at the workflow level can rerun non-idempotent jobs. Design every job so a retry does not duplicate output or corrupt state.
aws glue create-trigger \
  --name run-orders-curation-daily \
  --type SCHEDULED \
  --schedule "cron(0 6 * * ? *)" \
  --actions JobName=orders-curation-job

Glue Studio vs Scripts

Glue Studio provides a visual editor for building ETL jobs. It is useful for prototyping, onboarding, and documenting simple flows. It can generate Spark scripts and helps teams see source, transform, and target nodes. However, production engineering usually needs version control, code review, testing, CI/CD, parameterization, and reusable libraries.

A practical pattern is to use Glue Studio for initial discovery or for simple analyst-owned pipelines, then move serious jobs into Git-backed scripts deployed through Terraform, CloudFormation, CDK, or CI/CD. Treat generated code as a starting point, not as sacred architecture.

Visual tools accelerate first draft creation. Code ownership keeps production systems maintainable.
Jobs edited manually in the console can drift from infrastructure as code. Decide which system is authoritative before production.

Workers, DPUs, and Cost

Glue capacity is priced around Data Processing Units and worker types. Spark jobs use workers such as G.1X, G.2X, and larger options for memory-intensive workloads. Smaller worker options can be useful for light jobs. Python shell jobs have their own smaller capacity model. The right sizing question is not only speed; it is cost per successful run.

At scale, tune file layout before blindly adding workers. Too many tiny files cause listing overhead and poor Spark task efficiency. Too few huge files can limit parallelism. Expensive shuffles often come from wide joins, skewed keys, and unnecessary repartitioning.

Optimize data layout and query shape before increasing DPUs. More workers can make a bad plan more expensive.
Autoscaling helps, but it does not fix skew, bad joins, or tiny-file explosions. Watch CloudWatch metrics and Spark UI evidence.

S3 Lake Patterns

A common Glue pattern is raw to processed to curated. Raw stores immutable source extracts. Processed applies cleanup, normalization, deduplication, and standard typing. Curated organizes domain-ready tables for Athena, Redshift Spectrum, SageMaker, dashboards, or downstream applications.

Glue jobs should preserve lineage between these zones. A curated table should be explainable back to raw batch IDs, input paths, source timestamps, and pipeline run IDs. This matters for audits, backfills, data quality failures, and production incidents.

Treat S3 prefixes as data contracts. Folder layout is part of your architecture, not just storage housekeeping.
Partitioning by ingestion date is operationally easy but analytically weak if users filter by event date. Choose partition keys based on dominant access patterns.
s3://company-lake/raw/orders/source_system=crm/ingest_dt=2026-04-25/batch_id=abc123/
s3://company-lake/processed/orders/event_dt=2026-04-25/
s3://company-lake/curated/orders/dt=2026-04-25/region=us-east-1/

RawImmutable source evidenceCrawl or register source metadata

Redshift Integration

Glue can read from and write to Redshift using JDBC and the Redshift connector. It is commonly used to load curated S3 data into Redshift tables, unload Redshift query results to S3, or join warehouse data with lake data during migration. For large loads, stage data in S3 and use Redshift COPY-style patterns rather than row-by-row inserts.

The main design decision is whether Redshift should own the final serving table or whether S3 remains the source of truth queried through Spectrum or Athena. For high-concurrency BI and warehouse workloads, Redshift tables may be right. For flexible lake storage and cross-engine access, S3 plus open table formats may be better.

Glue plus Redshift works best when S3 is used as the bulk transfer boundary.
JDBC writes can become slow or fragile if used like OLTP inserts. Prefer bulk staging and carefully manage temporary directories, IAM roles, and network access.
glueContext.write_dynamic_frame.from_options(
    frame=curated_dyf,
    connection_type="redshift",
    connection_options={
        "redshiftTmpDir": "s3://company-temp/glue/redshift/",
        "useConnectionProperties": "true",
        "dbtable": "analytics.orders_daily",
        "connectionName": "redshift-prod"
    }
)

Schema Registry

AWS Glue Schema Registry manages schemas for streaming and event-driven systems, especially Kafka, MSK, Kinesis, and Java/Python producers and consumers using Avro, JSON Schema, or Protobuf-style contracts depending on integration. In data engineering, schema governance prevents downstream jobs from breaking when producers change event shape.

Compatibility modes matter. Backward compatibility allows new consumers to read old data. Forward compatibility allows old consumers to read new data. Full compatibility gives stricter guarantees but can slow producer evolution. The right choice depends on ownership boundaries and deployment cadence.

Schema Registry moves schema drift detection from random consumer failure to controlled producer registration.
A registry does not fix bad event design. Optional fields, semantic meaning, and versioning rules still require governance.

Glue vs EMR vs Lambda

Glue, EMR, and Lambda overlap, but they optimize for different operating models. Glue is serverless data integration with a managed catalog and managed Spark runtime. EMR gives more cluster control, deeper Spark/Hadoop ecosystem tuning, and long-running cluster patterns. Lambda is ideal for short event-driven functions, not heavy distributed ETL.

Choose Glue when the work is primarily batch ETL on S3 and you want less infrastructure management. Choose EMR when you need custom cluster control, specialized libraries, persistent clusters, or deeper performance tuning. Choose Lambda when the work is small, event-driven, and finishes quickly.

Glue is the default AWS-native ETL choice when operational simplicity matters more than deep cluster control.
Glue is not automatically cheaper than EMR. Frequent long-running heavy Spark jobs may justify EMR, EMR Serverless, or a platform like Databricks.

Interview Q&A

Q: How would you explain the Glue Data Catalog to a senior analytics team?
A: It is the shared metastore for lake tables. It stores databases, table schemas, partition locations, and storage metadata so Athena, Glue, EMR, Redshift Spectrum, and Lake Formation can interpret S3 data consistently. The data remains in S3; the Catalog stores the metadata contract.
Q: When would you avoid Glue crawlers in production?
A: I avoid crawlers when schema changes must be controlled, reviewed, and versioned. Crawlers infer from observed files, so messy or partial data can cause unwanted type changes. For governed production tables, I prefer explicit DDL, IaC-managed tables, or pipeline-controlled partition registration.
Q: What is the practical difference between DynamicFrames and Spark DataFrames?
A: DynamicFrames are Glue-specific and useful for ambiguous semi-structured schemas, especially with resolveChoice. DataFrames are standard Spark, better for SQL, optimization, testing, and complex transformations. I usually use DynamicFrames at ingestion edges and DataFrames for core transformation.
Q: What production issue can happen with Glue job bookmarks?
A: Bookmarks can skip or reprocess data depending on file overwrite patterns, path changes, and replay behavior. They are useful for incremental reads, but not enough for correctness. I still design idempotent outputs, immutable raw paths, batch audit records, and controlled replay procedures.
Q: How do you reduce Glue job cost without breaking SLAs?
A: First reduce input size with partition pruning and pushdown predicates. Then fix file layout, compact tiny files, write Parquet, remove unnecessary shuffles, and right-size workers. Only after that do I increase DPUs. The metric is cost per successful run, not just runtime.
Q: When would you choose EMR instead of Glue?
A: I choose EMR when I need deeper Spark tuning, custom cluster configuration, specialized ecosystem components, persistent clusters, or heavy workloads where cluster economics beat Glue. I choose Glue when serverless operation, catalog integration, and simpler batch ETL matter more than cluster control.
