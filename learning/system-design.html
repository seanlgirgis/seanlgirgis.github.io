Foundations

System design for data engineers focuses on building scalable, reliable, observable, and maintainable data platforms.

Modern systems must support:

  • High-volume ingestion
  • Batch and streaming pipelines
  • Real-time analytics
  • Governance and compliance
  • Failure recovery
  • Distributed processing
  • Cost-efficient scaling
Key insight: strong engineers explain trade-offs, recovery paths, and operational reasoning — not only tools.
Gotcha: designing only the happy path creates weak system design interviews.

Core Architecture Patterns

Data Warehouse

Curated analytics systems optimized for SQL, governance, and reporting.

Data Lake

Low-cost storage for raw and semi-structured data.

Lakehouse

Combines lake flexibility with warehouse reliability using ACID transactions and schema enforcement.

Key insight: lakehouses unify scalable storage with trusted analytics.
Gotcha: flexible raw storage without governance eventually creates unreliable analytics.

Batch vs Streaming

Model Strength Challenge
Batch Simpler and cheaper Higher latency
Streaming Real-time analytics Operational complexity
Lambda Accuracy + low latency Duplicate logic
Kappa Simplified replay model Streaming dependency
Key insight: streaming introduces ordering, replay, checkpointing, and state recovery concerns.
Gotcha: low latency increases operational burden significantly.

Medallion Architecture

Bronze

Immutable raw ingestion layer used for replay and recovery.

Silver

Validation, deduplication, enrichment, schema enforcement, and trusted processing.

Gold

Business-ready analytics, KPIs, dashboards, and ML feature datasets. 

OLTP Apps
    |
CDC / Events
    |
Kafka / Kinesis
    |
Bronze Raw Storage
    |
Spark / Flink Processing
    |
Silver Trusted Tables
    |
Gold BI + ML Features
Key insight: Bronze preserves truth, Silver creates trust, Gold serves consumers.
Gotcha: corrupting raw data destroys replay and recovery capability.

Modeling and Storage

Analytics modeling starts with access patterns.

Fact Tables

Store measurable business events: orders, clicks, payments, shipments.

Dimension Tables

Provide descriptive context: customer, product, geography, calendar.

Star Schema

Fact table connected directly to dimensions for simpler analytics queries.

Key insight: grain defines what one row represents.
Gotcha: unclear grain causes duplicated metrics and inconsistent analytics.

Governance and Observability

Governance defines ownership, lineage, discoverability, compliance, and trust boundaries.

Observability validates both infrastructure health and data correctness.

  • Freshness monitoring
  • Schema drift detection
  • Volume anomaly detection
  • Completeness checks
  • SLA monitoring
  • Audit logging
Key insight: green pipelines do not guarantee trustworthy data.
Gotcha: missing lineage makes schema changes dangerous at scale.

Pipeline Reliability

Reliable pipelines are designed around failure recovery.

Concept Purpose
DLQ Quarantine failed events
Replayability Rebuild trusted datasets
Idempotency Avoid duplicate corruption
Checkpointing Recover streaming state
Backfills Repair historical partitions
Watermarks Handle late-arriving data
Key insight: recovery engineering is now a core data engineering skill.
Gotcha: retries without limits can amplify outages.

System Design Walkthrough

Scenario: design a scalable analytics platform for a global e-commerce company processing millions of daily events.

Requirements:

  • Real-time dashboards
  • Historical analytics
  • Machine learning training
  • Governance and compliance
  • Low operational cost
  • Replay and recovery support
Layer Design Choice Reason
Ingestion Kafka / CDC Reliable event capture
Storage Bronze object storage Replay source of truth
Processing Spark / Flink Batch and streaming support
Trusted Layer Silver validation Reliable analytics quality
Serving Gold BI + ML features Consumer-ready datasets
Governance IAM + lineage + contracts Security and trust
Key insight: strong designs explain recovery, replay, observability, and failure handling.
Gotcha: interviewers care more about operational reasoning than exact tool names.

Trade-Offs

Decision Trade-Off
Batch vs Streaming Simplicity vs low latency
Lake vs Warehouse Flexibility vs governance
Heavy partitioning Performance vs operational complexity
Strict governance Control vs engineering velocity
Multi-region replication Reliability vs infrastructure cost
Key insight: every scaling improvement introduces operational consequences.
Gotcha: optimizing prematurely often increases complexity without business value.

Common Mistakes

  • Designing only the happy path
  • Ignoring replay and recovery
  • Over-focusing on tools
  • Weak observability
  • No schema governance
  • Missing operational thinking
Key insight: senior engineers explain failures as clearly as successes.
Gotcha: large systems fail in small hidden ways before they fail visibly.
