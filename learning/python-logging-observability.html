The logging Module — loggers, handlers, formatters

Python's logging module separates three jobs: loggers decide what event happened, handlers decide where the event goes, and formatters decide how it looks. In production data pipelines, that separation matters because the same event may need to go to console logs, a file, CloudWatch, or a centralized log platform without rewriting pipeline logic.

Use module-level loggers with logging.getLogger(__name__) instead of printing. That keeps logs tied to the package path, allows level control by namespace, and avoids the painful pattern where every library writes unstructured text to stdout like it is 2009.

import logging

logger = logging.getLogger(__name__)
logger.setLevel(logging.INFO)

handler = logging.StreamHandler()
handler.setFormatter(logging.Formatter(
    "%(asctime)s %(levelname)s %(name)s %(message)s"
))
logger.addHandler(handler)

logger.info("pipeline stage started")
Key insight: application code should emit events; deployment configuration should decide routing, format, and retention.
Avoid configuring logging repeatedly inside reusable library modules. Duplicate handlers create duplicate log lines and make incident timelines look haunted.

Log Levels — when to use each

Log levels are not decoration; they are operational contracts. DEBUG is for deep troubleshooting, INFO is for normal lifecycle milestones, WARNING means something degraded but continued, ERROR means a unit of work failed, and CRITICAL means the system cannot safely continue.

For data engineering, the biggest mistake is logging everything as INFO. A healthy run should be readable from a small number of high-signal milestones: started, extracted count, validation result, loaded count, duration, and final status. Everything else should be debug detail or structured fields attached to those milestones.

LevelUse in pipelinesExample
DEBUGTemporary diagnosisSQL text, API page token, sample schema
INFONormal milestonesStage completed, row counts, elapsed time
WARNINGRecoverable issueLate file, partial API response, low match rate
ERRORFailed work itemBatch failed, validation failed, write rejected
CRITICALUnsafe continuationCredential failure, corrupt checkpoint, missing contract
Do not use ERROR for expected business rejects. A rejected record can be normal; a failed pipeline stage is operationally different.

Structured Logging — JSON logs with python-json-logger

Plain text logs are good for humans and bad for machines. Structured JSON logs make fields queryable: run_id, stage, dataset, rows_written, and duration_ms become dimensions you can filter, aggregate, and alarm on.

python-json-logger is a common lightweight formatter for emitting JSON to stdout. In containerized jobs, that is usually enough: Docker, ECS, Lambda, Kubernetes, or Airflow workers can collect stdout and ship it to the platform logging backend.

import logging
from pythonjsonlogger import jsonlogger

logger = logging.getLogger("pipeline")
handler = logging.StreamHandler()
handler.setFormatter(jsonlogger.JsonFormatter(
    "%(asctime)s %(levelname)s %(name)s %(message)s %(run_id)s %(stage)s"
))
logger.addHandler(handler)
logger.setLevel(logging.INFO)

logger.info(
    "stage completed",
    extra={"run_id": "20260425-001", "stage": "extract"}
)
JSON logs turn observability from grep archaeology into indexed queries. That is the difference between guessing and operating.
Never log secrets, raw tokens, full connection strings, or sensitive payloads. Structured logging makes leaks easier to search, which is great until the leaked thing is a password.

Contextual Fields — run_id, stage, source_system

Context is what lets one log line join the rest of the story. A pipeline should stamp every event with stable identifiers such as run_id, job_name, stage, source_system, dataset, and environment. Without these fields, a production incident becomes a scavenger hunt across unrelated text.

For larger codebases, use LoggerAdapter, a custom filter, or a logging wrapper to avoid passing the same extra dictionary everywhere. The goal is boring consistency: every extract, transform, load, validation, and publish event should carry the same correlation spine.

class ContextAdapter(logging.LoggerAdapter):
    def process(self, msg, kwargs):
        extra = kwargs.setdefault("extra", {})
        extra.update(self.extra)
        return msg, kwargs

base = logging.getLogger("pipeline.orders")
log = ContextAdapter(base, {
    "run_id": "20260425-001",
    "source_system": "salesforce",
    "dataset": "orders"
})

log.info("validation completed", extra={"stage": "validate"})
A good run_id behaves like a distributed trace ID for batch work: every event, metric, table row, and alert points back to one execution.

Pipeline Observability Metrics — what to log at each stage

Logging is not just about failure messages. A pipeline should emit operational facts that prove work happened correctly: input files seen, rows read, rows rejected, rows written, duplicate count, schema version, watermark, elapsed time, and output location.

The best observability pattern is stage-level accounting. Each stage logs a start event, a completion event, and a small set of counters. That makes a run auditable even when no exception occurs, which is exactly where many bad data incidents hide.

StageUseful fieldsWhy it matters
Extractsource, file_count, rows_read, watermarkConfirms input coverage
Validatebad_rows, schema_version, null_rateSeparates data quality from system failure
Transformrows_in, rows_out, join_match_rateFinds silent row loss
Loadtarget, rows_written, partitions_touchedProves output landed
Publishcheckpoint, manifest_path, consumers_notifiedTracks handoff to downstream systems
A pipeline can succeed technically and fail analytically. If row counts drop from 10 million to 10 thousand and no one alarms, the job did not really succeed.

CloudWatch Integration & Alarms

On AWS, most Python jobs can rely on stdout logging and let the runtime ship logs to CloudWatch: Lambda does this natively, ECS uses the awslogs driver, and Glue/EMR have their own log paths. Once logs are centralized, CloudWatch Logs Insights can query fields, and metric filters can convert specific events into metrics.

For alarms, prefer metrics over raw log scanning when possible. Emit counts and durations as metrics using CloudWatch Embedded Metric Format, a library, or a sidecar pattern. Alert on symptoms that matter: failed runs, zero rows written, late completion, validation failure rate, or duration above normal.

# CloudWatch Logs Insights examples
fields @timestamp, levelname, message, run_id, stage, rows_written
| filter job_name = "orders_daily" and levelname in ["ERROR", "CRITICAL"]
| sort @timestamp desc
| limit 50

fields @timestamp, run_id, stage, duration_ms
| filter message = "stage completed"
| stats max(duration_ms) by stage
CloudWatch is strongest when logs carry consistent fields. Without structure, Logs Insights becomes expensive text searching with nicer furniture.
Do not alarm on every ERROR log blindly. Alarm on failed pipeline outcomes or sustained error rates, otherwise alert fatigue will quietly murder the process.

Pipeline Run Tracking Table

Logs are event streams; a run tracking table is the durable summary. For serious data platforms, store one row per pipeline execution with status, timestamps, inputs, outputs, row counts, error category, and retry metadata. This table becomes the operational source of truth for dashboards, SLAs, and incident review.

The table should be updated at key transitions: started, stage completed, failed, retried, succeeded. Keep it small and queryable. Large detailed diagnostics belong in logs or object storage, while the tracking table answers the executive question: what ran, did it finish, and should anyone care?

CREATE TABLE pipeline_run (
    run_id          VARCHAR PRIMARY KEY,
    job_name        VARCHAR NOT NULL,
    status          VARCHAR NOT NULL,
    started_at      TIMESTAMP NOT NULL,
    finished_at     TIMESTAMP,
    rows_read       BIGINT DEFAULT 0,
    rows_written    BIGINT DEFAULT 0,
    bad_rows        BIGINT DEFAULT 0,
    error_category  VARCHAR,
    error_message   VARCHAR,
    output_path     VARCHAR
);
Logs explain the movie; the run table is the scoreboard. You need both.

Exception Logging & The Silent Success Anti-Pattern

Use logger.exception() inside an exception handler when you want the traceback included automatically. The traceback matters because production failures often depend on the exact call path, not just the final error message.

The silent success anti-pattern happens when a job catches an exception, logs a warning, and exits with success. Schedulers, dashboards, and downstream jobs then believe the pipeline completed. That is worse than a loud failure because it creates false confidence and corrupts downstream assumptions.

try:
    load_partition(df, target_path)
except ValidationError:
    logger.exception("validation failed", extra={"stage": "load"})
    mark_run_failed(run_id, "validation")
    raise
except Exception:
    logger.exception("unexpected pipeline failure", extra={"stage": "load"})
    mark_run_failed(run_id, "system")
    raise
Logging an exception is not handling it. If the job cannot safely continue, update status and re-raise so the scheduler sees failure.

Monitoring vs Logging — knowing the difference

Logging records events. Monitoring evaluates system health. A log line can say a stage wrote zero rows; monitoring decides whether zero rows is acceptable for that dataset on that date. Good platforms convert logs and run tables into metrics, alarms, dashboards, and SLA checks.

For senior engineers, the design question is not "do we have logs?" It is "can we detect bad outcomes quickly, explain root cause, and prove data completeness?" That usually requires logs for detail, metrics for alerting, traces or correlation IDs for causality, and data quality checks for correctness.

SignalBest forPipeline example
LogsDetailed event historyValidation failed for partition date
MetricsTrend and alarmRows written, runtime, failure count
Run tableExecution auditDaily job succeeded with output path
Data checksCorrectnessNull rate, duplicate keys, referential coverage
DashboardsOperational viewSLA status across pipelines
The best observability systems answer three questions fast: what happened, how bad is it, and where should I look next?

Interview Q&A

Q: Why is print() not enough for production data pipelines?
A: print() has no severity, namespace, routing, structured fields, or consistent formatting. Logging lets you attach context, control verbosity, and integrate with platforms like CloudWatch or Datadog. In production, the difference shows up during incidents when you need to filter by run, stage, and failure type.
Q: What fields should every batch pipeline log?
A: At minimum: run_id, job_name, stage, source_system, dataset, environment, status, row counts, and duration. For load stages, include target table or output path. For validation, include bad row counts and rule identifiers.
Q: How do you avoid noisy alerts from pipeline logs?
A: Alert on business-relevant outcomes, not raw log volume. Failed run count, zero-row output, SLA miss, high bad-row rate, or repeated retries are better signals than every single ERROR. Logs should support investigation; metrics and run status should drive alarms.
Q: What is the value of JSON logging in a data platform?
A: JSON logging makes operational fields queryable and aggregatable. Instead of parsing text, the platform can filter on stage="load", group by source_system, or calculate max duration_ms. It also standardizes logs across services and schedulers.
Q: How should exception logging behave in a pipeline?
A: Capture the traceback with logger.exception(), update the run tracking table to failed, classify the failure, and re-raise if the job cannot safely continue. Swallowing exceptions creates false success and can poison downstream jobs. Recovery should be explicit, not accidental.
Q: What is the difference between logging and observability?
A: Logging is one signal: detailed event records. Observability is the broader ability to understand system behavior from logs, metrics, run metadata, traces, dashboards, and data quality checks. A pipeline with many logs but no alerts, counters, or run state is still poorly observable.
