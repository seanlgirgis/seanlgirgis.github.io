1. What Redshift Actually Is

Amazon Redshift is a fully managed, petabyte-scale columnar data warehouse built on a massively parallel processing (MPP) architecture. It is designed for analytical workloads — large aggregations, multi-table joins, and full-column scans across billions of rows — rather than transactional (OLTP) workloads that require row-level point reads and writes. Every design decision in Redshift, from its columnar storage format to its distribution strategy, optimizes for throughput on analytical SQL rather than latency on individual row operations.

Positioned against alternatives: compared to Athena (serverless S3 query engine), Redshift provides faster query performance for repeated, structured workloads because data is stored in an optimized internal format with statistics, sort order, and zone maps pre-built. Athena wins for ad-hoc queries on raw or semi-structured S3 data without upfront table design. Compared to Snowflake, Redshift requires more hands-on administration (sort keys, distribution styles, VACUUM) but integrates more tightly with the AWS ecosystem and offers Spectrum for seamless S3 querying. Compared to BigQuery, the operational model is meaningfully different — Redshift has persistent compute infrastructure while BigQuery separates storage from compute entirely.

Redshift Serverless (launched 2022) removes cluster sizing and management entirely. It auto-scales based on workload and charges per RPU-second. For variable or unpredictable workloads, Serverless simplifies operations significantly. For steady, high-throughput production workloads where consistent performance and cost predictability matter, provisioned clusters remain the standard in most enterprise deployments.

Redshift is fundamentally a columnar MPP system. Every performance question — distribution, sort keys, compression, WLM — traces back to one goal: minimize the number of bytes read from disk across as many parallel slices as possible.

2. Architecture — Nodes, Slices, Leaders

A Redshift provisioned cluster consists of one leader node and one or more compute nodes. The leader node is the entry point: it receives SQL from clients, parses and optimizes the query, generates a compiled execution plan, distributes fragments to compute nodes, collects results, and returns the final result set to the client. The leader node never stores user data — it only orchestrates.

Each compute node is divided into slices. A slice is the fundamental unit of parallel processing in Redshift. Each slice owns a portion of the node's CPU, memory, and disk. Data in a table is distributed across all slices cluster-wide, and query fragments execute in parallel across all slices simultaneously. The number of slices per node depends on the node type: dc2.large has 2 slices, ra3.4xlarge has 4 slices, ra3.16xlarge has 16 slices.

Understanding slices is critical because Redshift's distribution, sort, and performance tuning all operate at the slice level. When you size a cluster, you're choosing a total slice count. A 4-node ra3.4xlarge cluster has 16 slices total — 16 parallel execution units. A table with 1 million rows distributed across 16 slices has ~62,500 rows per slice on average (for even distribution).

ra3 vs dc2 Node Types

TypeStorageBest For
dc2.large / dc2.8xlargeSSD (local, fixed)Smaller datasets (<500 GB), latency-sensitive
ra3.xlplus / ra3.4xlarge / ra3.16xlargeManaged storage (S3-backed, scalable)Large or growing datasets; pay for compute and storage separately

ra3 nodes use Redshift Managed Storage (RMS) — data is stored in S3 with a local SSD cache (hot data stays in cache, cold data spills to S3 transparently). This decouples storage scaling from compute scaling, which is the primary reason ra3 is now the standard choice for new clusters.

With ra3, you can resize compute (add/remove nodes) without waiting for data redistribution across local disks. The managed storage layer handles redistribution in the background. This makes cluster resizing much faster and less operationally risky than dc2.

3. Distribution Styles

Distribution style controls how rows of a table are spread across slices. The right distribution style eliminates or minimizes data movement during query execution — specifically, it avoids the need to broadcast or redistribute data between nodes when joining or aggregating. Data movement is the single biggest cause of slow queries in Redshift.

EVEN

Rows are distributed in round-robin order across all slices regardless of column values. Every slice gets an equal number of rows. Use EVEN when a table is not joined to other tables or when no column qualifies as a good distribution key. EVEN eliminates data skew but does not co-locate join keys — joins between EVEN tables always require redistribution.

KEY

Rows with the same value in the distribution key column are placed on the same slice. When two large tables are joined on their distribution keys, Redshift can perform the join locally within each slice — no data movement across nodes. This is the highest-performance distribution style for large fact-to-fact or fact-to-large-dimension joins. The risk: if the key has low cardinality or is heavily skewed (many rows share the same key value), some slices will be overloaded and others underutilized.

-- KEY distribution: rows with same order_id go to same slice
CREATE TABLE orders (
    order_id     BIGINT     NOT NULL,
    customer_id  INT        NOT NULL,
    order_date   DATE,
    amount       DECIMAL(12,2)
)
DISTSTYLE KEY
DISTKEY (order_id)
SORTKEY (order_date);

-- If order_items also uses order_id as DISTKEY,
-- the join below executes entirely on each slice — no redistribution
SELECT o.order_id, SUM(oi.quantity)
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.order_id;

ALL

A full copy of the table is stored on every node (not every slice, but the first slice of each node). Use ALL for small, frequently-joined dimension tables (lookup tables, date dimensions, reference data). The copy on every node means joins against this table never require data movement, regardless of the fact table's distribution. The trade-off: storage overhead and slower COPY/INSERT operations since every node must receive the full write.

AUTO

Redshift chooses between EVEN and ALL automatically based on table size. Small tables get ALL; large tables get EVEN. AUTO is appropriate when you're unsure and want Redshift to manage it, but it will never choose KEY distribution — so for large join-heavy tables, explicit KEY is still required.

Skew check: After loading data, check for slice skew with SELECT slice, COUNT(*) FROM stv_tbl_perm WHERE name='your_table' GROUP BY slice ORDER BY slice. If the max count is more than 2–3x the min, your distribution key has high cardinality skew and query performance will suffer on that table.

4. Sort Keys

Sort keys determine the physical on-disk order of rows within each slice. Redshift maintains zone maps — min/max statistics per 1 MB block — for each sort key column. When a query filters on the sort key, Redshift uses zone maps to skip entire disk blocks whose range cannot satisfy the filter. This is called block pruning and is the primary mechanism by which sort keys improve query performance.

Compound Sort Key

Specifies multiple columns in order of priority. Data is sorted by the first column, then by the second within equal first-column values, and so on. Compound sort keys are efficient when queries filter on the leading columns in order. They become progressively less useful if a query skips the leading column and filters only on a secondary column.

-- Compound sort key: most queries filter by event_date first, then event_type
CREATE TABLE events (
    event_id    BIGINT,
    event_date  DATE,
    event_type  VARCHAR(50),
    user_id     INT,
    payload     VARCHAR(MAX)
)
DISTSTYLE KEY
DISTKEY (user_id)
COMPOUND SORTKEY (event_date, event_type);

Interleaved Sort Key

Gives equal weight to all sort key columns, enabling efficient filtering on any subset of the columns regardless of order. This sounds ideal for multi-dimensional filter patterns, but it comes with significant costs: interleaved sort keys degrade over time as data is inserted (requiring frequent VACUUM REINDEX operations), and VACUUM REINDEX is substantially slower and more I/O-intensive than regular VACUUM. For most workloads, compound sort keys on the highest-frequency filter columns outperform interleaved in practice.

The most common and highest-value sort key pattern in analytical warehouses is a single date/timestamp column. Nearly all analytical queries filter by date range, and a date-sorted table gives Redshift's zone maps maximum pruning power.

Choosing a Sort Key

  • Use the column(s) most commonly in WHERE clauses and range filters
  • For time-series data, the timestamp or date column is almost always the right sort key
  • For a fact table joined to a date dimension, sorting by date and distributing by the join key is a common high-performance combination
  • Avoid sort keys on high-cardinality columns that are never filtered (e.g., UUID primary keys)
Sort key effectiveness degrades with unsorted rows: As new data is loaded, new rows land in the unsorted region of each slice. Redshift's zone maps cannot prune blocks in the unsorted region. Run VACUUM SORT ONLY periodically to merge unsorted rows into the sorted region. Monitor SVV_TABLE_INFO.unsorted — if it exceeds 5–10%, query performance on that table is degrading.

5. Loading Data — COPY Command

The COPY command is the canonical, high-performance way to load data into Redshift. It reads data from S3 (or DynamoDB, EMR, SSH) in parallel across all slices simultaneously, using the cluster's full I/O bandwidth. Never use INSERT INTO ... VALUES for bulk loading — each row is a separate round-trip and will be orders of magnitude slower.

-- Basic COPY from S3 (Parquet)
COPY schema_name.events
FROM 's3://my-bucket/processed/events/year=2026/month=04/'
IAM_ROLE 'arn:aws:iam::123456789:role/MyRedshiftRole'
FORMAT AS PARQUET;

-- COPY from JSON with explicit JSONpath
COPY schema_name.raw_events
FROM 's3://my-bucket/raw/events/'
IAM_ROLE 'arn:aws:iam::123456789:role/MyRedshiftRole'
FORMAT AS JSON 's3://my-bucket/config/events_jsonpath.json'
TIMEFORMAT 'epochmillisecs'
TRUNCATECOLUMNS
MAXERROR 100;

-- COPY from CSV with explicit options
COPY schema_name.dim_products
FROM 's3://my-bucket/dims/products.csv'
IAM_ROLE 'arn:aws:iam::123456789:role/MyRedshiftRole'
CSV QUOTE '"'
DELIMITER ','
IGNOREHEADER 1
DATEFORMAT 'YYYY-MM-DD'
EMPTYASNULL
BLANKSASNULL;

File Splitting for Parallelism

COPY reads one file per slice in parallel. For maximum throughput, split your source data into at least as many files as there are slices in your cluster, and ideally a multiple of the slice count. A 16-slice cluster loading a single 5 GB file will use only one slice — 15 slices sit idle. Splitting the same data into 16 or 32 files uses all available parallelism.

For Parquet data written by Glue or Spark, the partition structure naturally creates multiple files. If each partition has at least one file per slice count, COPY parallelism is automatically saturated. For CSV/JSON, explicitly split large files using Glue or a Lambda preprocessing step before loading.

COPY Error Handling

COPY writes errors to STL_LOAD_ERRORS. Query it immediately after a failed or partial load to diagnose issues. The MAXERROR parameter sets how many load errors are tolerated before the entire COPY is aborted. For production loads, keep MAXERROR at 0 or a very low value — silent partial loads are worse than loud failures.

-- Inspect load errors after a failed COPY
SELECT filename, line_number, colname, type, col_length, raw_line, raw_field_value, err_reason
FROM STL_LOAD_ERRORS
WHERE starttime > SYSDATE - INTERVAL '1 hour'
ORDER BY starttime DESC
LIMIT 50;

6. Columnar Storage & Compression

Redshift stores data in columns rather than rows. For analytical queries that read a few columns from millions of rows, columnar storage means only the relevant columns are read from disk — unrelated columns are never touched. This reduces I/O dramatically compared to row-oriented databases (PostgreSQL, MySQL) where every row is read in full even for single-column aggregations.

Each column is stored in 1 MB blocks. Each block has a zone map (min/max values) used for block pruning. Within a block, values are stored in the column's encoding (compression). Redshift uses per-column compression — different columns in the same table can use different encodings.

Compression Encodings

EncodingBest ForNotes
AZ64Numeric, date/timestamp columnsRedshift's proprietary algorithm; usually best for numbers
ZSTDGeneral purposeGood compression ratio with reasonable CPU cost; best default for most string columns
LZOLong strings, free-form textFast decompression; good for high-cardinality strings
BYTEDICTLow-cardinality columnsDictionary encoding; very efficient for enums (<256 distinct values)
RUNLENGTHSorted, repeated valuesBest for columns with long runs of the same value (e.g., status flags in sorted tables)
RAWNo compressionFastest read; largest storage; use for columns used in complex predicates
-- Let Redshift recommend encodings (ANALYZE COMPRESSION)
ANALYZE COMPRESSION schema_name.events;

-- Apply recommended encodings when re-creating the table
CREATE TABLE schema_name.events_optimized (
    event_id    BIGINT      ENCODE AZ64,
    event_date  DATE        ENCODE AZ64,
    event_type  VARCHAR(50) ENCODE BYTEDICT,
    user_id     INT         ENCODE AZ64,
    payload     VARCHAR(MAX) ENCODE ZSTD
)
DISTSTYLE KEY DISTKEY (user_id)
COMPOUND SORTKEY (event_date);
Encoding cannot be changed in place: Once a table is created with a specific encoding, you cannot ALTER the encoding. To change compression, you must: create a new table with the desired encoding, INSERT INTO ... SELECT from the old table (or use CREATE TABLE AS SELECT), rename tables, and drop the old. Plan your encoding choices upfront or accept the re-create cost later.

7. Redshift Spectrum

Redshift Spectrum allows you to run SQL queries against data stored in S3 without loading it into Redshift first. It extends Redshift's query engine outward to read from external tables defined in the Glue Data Catalog (or a Redshift-hosted external catalog). Spectrum queries are executed by a fleet of Spectrum nodes that are independent of your Redshift cluster — they scale automatically based on data volume.

Spectrum is ideal for: querying the raw or processed S3 zone from within Redshift SQL (without a COPY load cycle), joining Redshift internal tables with S3 external tables in a single query, long-term data archival where old partitions are moved to S3 but still need to be occasionally queryable, and federating queries across the full data lake without ETL.

-- Create an external schema pointing to Glue Data Catalog
CREATE EXTERNAL SCHEMA processed_ext
FROM DATA CATALOG
DATABASE 'processed_db'
IAM_ROLE 'arn:aws:iam::123456789:role/MyRedshiftRole'
CREATE EXTERNAL DATABASE IF NOT EXISTS;

-- Query the external S3 table directly
SELECT event_type, COUNT(*) AS event_count
FROM processed_ext.events
WHERE year = '2026' AND month = '04'
GROUP BY event_type
ORDER BY event_count DESC;

-- Join Redshift internal table with S3 external table
SELECT r.customer_name, COUNT(e.event_id) AS event_count
FROM internal_schema.customers r
JOIN processed_ext.events e ON r.customer_id = e.user_id
WHERE e.year = '2026'
GROUP BY r.customer_name;

Partition Pruning in Spectrum

Spectrum reads partition metadata from the Glue Catalog. Always include partition column filters in WHERE clauses for Spectrum queries. A full Spectrum scan over a year of hourly partitioned data with millions of files will be extremely slow and expensive — Spectrum charges per TB scanned. Partition pruning is the primary cost and performance control.

Spectrum works best when the S3 data is stored as Parquet with snappy or zstd compression. ORC is also well-supported. CSV or JSON requires Spectrum to deserialize every field in every row before filtering, dramatically increasing scan costs. If Spectrum is a planned consumer, store data in columnar format.
Spectrum vs internal table performance: Spectrum queries are slower per-row than queries against internal Redshift tables because data must be read from S3, transferred to Spectrum nodes, and partially aggregated before being sent to Redshift. For frequently-queried hot data, COPY into internal tables. Reserve Spectrum for cold/archival data or one-off historical queries.

8. Workload Management (WLM)

Workload Management controls how Redshift allocates memory and concurrency slots across different query types. Without WLM configuration, all queries compete for the same pool of memory — a single large ETL load can consume all available memory and starve interactive analyst queries, or vice versa.

WLM organizes queries into queues. Each queue has a concurrency limit (maximum simultaneous queries), a memory allocation percentage, and routing rules (which user groups or query groups are routed to this queue). When a query's slot is full, new queries wait in the queue until a slot frees up.

Automatic vs Manual WLM

Automatic WLM (the default for new clusters) lets Redshift dynamically allocate memory based on query complexity and current load. It removes the need to manually tune concurrency and memory percentages. Manual WLM gives explicit control over slots and memory, which is necessary when you have SLAs that require predictable resource allocation for specific query classes.

-- Route ETL sessions to a dedicated queue using query group
SET query_group TO 'etl';

-- Run the ETL query — it's now routed to the 'etl' WLM queue
INSERT INTO schema_name.daily_summary
SELECT event_date, event_type, COUNT(*) AS event_count
FROM schema_name.events
WHERE event_date = CURRENT_DATE - 1
GROUP BY event_date, event_type;

-- Reset to default queue
RESET query_group;

Short Query Acceleration (SQA)

SQA is a WLM feature that automatically routes short-running queries (under a configurable time threshold) to a dedicated short-query queue, bypassing wait time in longer queues. It uses machine learning to predict query execution time before routing. Enable SQA for clusters serving mixed workloads with both analyst ad-hoc queries and long-running ETL jobs — it significantly reduces p99 latency for short queries.

Concurrency Scaling

When all WLM slots are full and queries are waiting, Redshift can automatically spin up additional transient clusters (Concurrency Scaling clusters) to handle the overflow. These clusters are identical to your main cluster and the additional capacity is billed per second. Concurrency Scaling is appropriate for workloads with predictable burst patterns (e.g., morning report runs) but can generate unexpected cost if enabled without monitoring queue wait times.

Manual queuesExplicit memory + concurrency per queueStrict SLAs, ETL/analyst isolation

9. VACUUM & ANALYZE

Redshift requires periodic maintenance operations that relational databases like PostgreSQL handle automatically. Understanding when and why to run VACUUM and ANALYZE is essential for maintaining query performance over time.

VACUUM

VACUUM reclaims disk space from deleted rows and re-sorts unsorted rows. When rows are deleted or updated in Redshift, the old row versions are not immediately removed — they are marked as deleted and remain on disk until VACUUM runs. Similarly, rows inserted after the initial table load land in an "unsorted region" and are not sorted by the sort key until VACUUM merges them into the sorted blocks.

-- Full vacuum (reclaim space + re-sort)
VACUUM schema_name.events;

-- Sort only (faster — only re-sorts unsorted rows, doesn't reclaim space)
VACUUM SORT ONLY schema_name.events;

-- Delete only (reclaim space from deleted rows, faster if no sort needed)
VACUUM DELETE ONLY schema_name.events;

-- Reindex (for interleaved sort keys only — very slow, avoid on large tables)
VACUUM REINDEX schema_name.events;

-- Check what needs vacuuming
SELECT "table", unsorted, stats_off, tbl_rows, estimated_visible_rows
FROM SVV_TABLE_INFO
WHERE unsorted > 5 OR stats_off > 10
ORDER BY unsorted DESC;
VACUUM blocks writes: VACUUM acquires an exclusive lock for the delete phase. Long-running VACUUM operations on large tables can block concurrent writes. For large tables, prefer VACUUM SORT ONLY during off-peak hours, and schedule VACUUM DELETE ONLY separately. Redshift also has automatic vacuum that runs during idle periods — check if it's keeping up before scheduling manual VACUUM.

ANALYZE

ANALYZE collects column-level statistics (null count, distinct count, histogram) and writes them to the query optimizer's catalog. Redshift's cost-based query planner uses these statistics to choose optimal join orders, join types (hash vs. sort-merge), and distribution strategies. Outdated statistics after a large data load can cause the planner to choose poor plans — for example, choosing a broadcast join for a table that has grown 100x since statistics were last collected.

-- Analyze the full table
ANALYZE schema_name.events;

-- Analyze specific columns (faster for wide tables)
ANALYZE schema_name.events (event_date, user_id, event_type);

-- Check statistics staleness
SELECT "table", stats_off
FROM SVV_TABLE_INFO
WHERE stats_off > 10
ORDER BY stats_off DESC;
After every significant COPY load (loading more than 10% of a table's existing rows), run ANALYZE on the loaded table. Redshift's automatic ANALYZE will eventually run, but a manual ANALYZE immediately after large loads prevents query plan degradation in the window between load completion and auto-analyze.

10. Query Performance & EXPLAIN

Diagnosing slow Redshift queries requires reading the query execution plan and understanding which operations are expensive. The primary tool is EXPLAIN, which returns the query plan with estimated costs. For completed queries, the system tables SVL_QUERY_REPORT, STL_QUERY, and SVL_QLOG contain actual execution metrics.

-- View query plan
EXPLAIN
SELECT event_type, COUNT(*) AS cnt
FROM schema_name.events
WHERE event_date BETWEEN '2026-04-01' AND '2026-04-13'
GROUP BY event_type;

-- View recent slow queries
SELECT query, trim(querytxt) AS sql, starttime, endtime,
       DATEDIFF(seconds, starttime, endtime) AS duration_sec
FROM STL_QUERY
WHERE starttime > SYSDATE - INTERVAL '24 hours'
  AND aborted = 0
ORDER BY duration_sec DESC
LIMIT 20;

Reading the EXPLAIN Plan

Key operations to watch for in the EXPLAIN output:

  • DS_BCAST_INNER: The inner table of a join is being broadcast to all nodes. Acceptable for small tables; a warning sign if it appears for large tables.
  • DS_DIST_BOTH: Both sides of a join are being redistributed across nodes. This means neither table has a matching DISTKEY — the most expensive data movement pattern. Investigate distribution styles if this appears on large joins.
  • DS_DIST_NONE: No redistribution needed — data is already co-located on the correct slices. The ideal state for large joins.
  • Hash Join vs Merge Join: Merge join requires both inputs to be sorted on the join key. It's faster but only possible when sort keys align with join keys. Hash join is the fallback and is more memory-intensive.
-- Check for data movement in recent queries
SELECT query, step, rows, bytes, label
FROM SVL_QUERY_REPORT
WHERE query = [your_query_id]
  AND label LIKE 'DS_%'
ORDER BY step;
The most common performance fix after reading an EXPLAIN plan: change the DISTKEY on a large table so it matches the join key used in the slow query. This converts DS_DIST_BOTH to DS_DIST_NONE and eliminates the inter-node shuffle entirely.

11. Materialized Views

Redshift materialized views store the precomputed results of a query physically on disk, like a cached result set that can be queried directly. Unlike regular views (which re-execute the underlying query on every access), materialized views read from the stored result, making repeated access to complex aggregations very fast.

Materialized views are particularly useful for: pre-aggregating large fact tables into summary tables consumed by BI tools, caching expensive cross-table joins that power dashboards, and creating denormalized "wide table" representations of normalized warehouse schemas for performance.

-- Create a materialized view for daily event aggregates
CREATE MATERIALIZED VIEW schema_name.daily_event_summary
DISTSTYLE KEY DISTKEY (event_date)
SORTKEY (event_date)
AS
SELECT
    event_date,
    event_type,
    COUNT(*)            AS event_count,
    COUNT(DISTINCT user_id) AS unique_users
FROM schema_name.events
GROUP BY event_date, event_type;

-- Query the materialized view (fast — reads precomputed data)
SELECT event_date, SUM(event_count)
FROM schema_name.daily_event_summary
WHERE event_date >= '2026-04-01'
GROUP BY event_date;

-- Refresh (recompute from base tables)
REFRESH MATERIALIZED VIEW schema_name.daily_event_summary;

Auto-Refresh

Redshift can automatically refresh materialized views when the underlying base tables are updated. Enable with AUTO REFRESH YES in the CREATE statement. Auto-refresh is best-effort — it runs during idle cluster periods and may lag behind base table updates. For SLA-sensitive dashboards, explicit REFRESH MATERIALIZED VIEW after each ETL load ensures freshness.

Incremental vs full refresh: Some materialized views support incremental refresh (only recomputing changed rows) while others require a full recompute. Redshift determines eligibility automatically — aggregate views with certain SQL patterns qualify for incremental refresh. If your MV requires a full recompute, refresh cost scales with base table size. Monitor refresh duration and schedule accordingly.

12. Security & Access Control

IAM Authentication

Redshift supports both traditional database password authentication and IAM-based authentication. With IAM authentication, users or applications obtain temporary database credentials via redshift:GetClusterCredentials. This eliminates long-lived passwords and integrates Redshift access with your IAM identity lifecycle (SSO, role assumption, etc.).

# Get temporary credentials via boto3 (IAM auth)
import boto3

redshift = boto3.client('redshift', region_name='us-east-1')
creds = redshift.get_cluster_credentials(
    DbUser='glue_etl_user',
    DbName='mydb',
    ClusterIdentifier='my-cluster',
    DurationSeconds=3600,
    AutoCreate=False
)
# creds['DbUser'] and creds['DbPassword'] are temporary credentials

Database Roles and Row-Level Security

Redshift supports RBAC via database groups and roles. Grant object-level privileges (SELECT, INSERT, USAGE) to groups rather than individual users. For column-level security, use views that expose only permitted columns. For row-level security (RLS), Redshift supports CREATE RLS POLICY — policies that filter rows returned to specific users or roles, enforced transparently at query time.

-- Create a group and grant SELECT on a schema
CREATE GROUP analysts;
GRANT USAGE ON SCHEMA schema_name TO GROUP analysts;
GRANT SELECT ON ALL TABLES IN SCHEMA schema_name TO GROUP analysts;
ALTER DEFAULT PRIVILEGES IN SCHEMA schema_name
    GRANT SELECT ON TABLES TO GROUP analysts;

-- Row-level security policy
CREATE RLS POLICY filter_by_region
WITH (region VARCHAR(50))
USING (region = current_setting('app.user_region'));

ATTACH RLS POLICY filter_by_region ON schema_name.sales TO ROLE analyst_role;

Encryption

Redshift encrypts data at rest using AES-256. For new clusters, choose encryption at creation time — it cannot be enabled retroactively without migrating to a new cluster. Use AWS KMS with a CMK for full key control in regulated environments. Data in transit between client and Redshift is encrypted via SSL (enforce SSL connections with the require_ssl parameter group setting).

Parameter group: require_ssl: By default, Redshift accepts unencrypted connections. Set require_ssl=true in the cluster's parameter group for any production cluster handling sensitive data. Without this, internal network connections bypass TLS even if your client is configured to use it.

VPC and Network Isolation

Deploy Redshift in a private subnet with no public accessibility unless explicitly required. Use security groups to restrict inbound TCP 5439 to specific application subnets, Glue connection security groups, and BI tool subnets. For cross-account access patterns (e.g., sharing data with a partner team's Redshift), use Redshift Data Sharing rather than VPC peering and shared credentials.

13. Common Gotchas and Anti-Patterns

1. Using DISTKEY on a skewed column: Choosing a distribution key with low cardinality or heavy skew (e.g., a boolean flag, a status column where 90% of rows are "active") concentrates data on a few slices and serializes query execution. Always check data distribution after choosing a DISTKEY.
2. Ignoring VACUUM after large deletes: Deleted rows are not reclaimed until VACUUM runs. A table that has had 50% of its rows deleted will still occupy full original disk space and zone maps will span both live and deleted rows, reducing pruning effectiveness. Run VACUUM DELETE ONLY after large delete or update operations.
3. Using INSERT for bulk loads: Row-by-row INSERT from application code or ETL processes is the slowest possible way to load data into Redshift. Always use COPY from S3 for bulk loads. Even a single-file COPY is dramatically faster than thousands of individual INSERTs.
4. Not splitting source files for COPY: A COPY from a single large file uses only one slice regardless of cluster size. Split source data into at least N files where N equals the number of slices. This is the most commonly missed COPY optimization.
5. SELECT * on wide tables: Redshift's columnar storage means that SELECT * reads every column from disk — negating the primary performance advantage of columnar storage. Always select only the columns you need. This is especially important for wide tables with many VARCHAR(MAX) columns.
6. Running ANALYZE COMPRESSION on a production table in use: ANALYZE COMPRESSION acquires an exclusive lock and can block queries. Run it on a copy of the table in a dev environment and apply the recommendations by recreating the production table during a maintenance window.
7. Forgetting ALTER DEFAULT PRIVILEGES: Granting SELECT ON ALL TABLES IN SCHEMA covers existing tables. New tables created after the grant are not covered unless ALTER DEFAULT PRIVILEGES is also set. A common pattern where new ETL-created tables are invisibale to analyst groups until someone manually re-runs the grants.

14. 10 Key Engineering Questions

Q1. What are the four distribution styles in Redshift and when would you use each?
EVEN distributes rows round-robin — use for tables that aren't joined. KEY distributes rows by column value hash — use for large tables frequently joined on that column (co-locates matching rows on the same slice, eliminating data movement). ALL copies the full table to every node — use for small, frequently-joined dimension tables. AUTO lets Redshift decide between EVEN and ALL based on table size. KEY is the only style that eliminates data movement for large joins; AUTO never chooses KEY.
Q2. How do sort keys improve Redshift query performance?
Sort keys determine physical row order on disk. Redshift maintains zone maps — min/max statistics per 1 MB block — for each sort key column. When a query filters on the sort key, Redshift skips entire disk blocks whose range cannot contain matching values. This block pruning is most powerful for date/timestamp columns where range queries are common. Effectiveness degrades as unsorted rows accumulate; VACUUM SORT ONLY restores sort order.
Q3. What is the difference between compound and interleaved sort keys?
Compound sort keys prioritize columns in declared order — efficient when queries filter on the leading column(s), progressively less useful when leading columns are skipped. Interleaved sort keys give equal weight to all columns — efficient for any subset filter pattern but degrade over time with inserts and require expensive VACUUM REINDEX. In practice, compound sort keys on the top 1–2 filter columns outperform interleaved for most workloads without the maintenance overhead.
Q4. Why is the COPY command preferred over INSERT for bulk loading?
COPY reads data from S3 in parallel across all slices simultaneously, using the cluster's full I/O bandwidth. INSERT operations are sequential single-row transactions with per-row commit overhead. For a 16-slice cluster, COPY can run 16 parallel read streams; INSERT uses one. The performance difference is typically 10–100x in favor of COPY for bulk loads. Additionally, COPY supports format-native parsing (Parquet, JSON, CSV) without row-by-row deserialization overhead.
Q5. When would you use Redshift Spectrum instead of loading data into internal Redshift tables?
Spectrum is appropriate for: cold or archival data that's rarely queried (avoid the storage cost of internal tables), ad-hoc historical queries that don't justify a COPY load cycle, joining Redshift internal tables with S3 data lake tables in a single query, and tiered storage where hot data is internal and cold data stays in S3. Internal tables are better for frequently-queried data where sub-second query latency matters, since Spectrum adds S3 read latency per query.
Q6. What does DS_DIST_BOTH mean in a Redshift EXPLAIN plan and how do you fix it?
DS_DIST_BOTH means both sides of a join are being redistributed across nodes during query execution — neither table has a DISTKEY that matches the join column, so Redshift must shuffle data across the network to co-locate matching rows. It's the most expensive data movement pattern. The fix is to align the DISTKEY of at least one of the joining tables with the join column. If one table is small, alternatively use DISTSTYLE ALL on it to eliminate redistribution entirely.
Q7. What is WLM and why does it matter for production Redshift deployments?
WLM (Workload Management) controls how query concurrency and memory are allocated across different query types. Without WLM, a single large ETL COPY or complex aggregation can consume all available memory and concurrency slots, blocking interactive analyst queries. WLM queues isolate workloads — a dedicated ETL queue with high memory allocation, a dedicated analyst queue with higher concurrency, and SQA for sub-second interactive queries. Production deployments without WLM tuning typically suffer from unpredictable query latency under load.
Q8. When should you run VACUUM and ANALYZE, and what happens if you don't?
VACUUM should run after large DELETE or UPDATE operations (reclaims deleted row space) and after significant INSERT/COPY loads (re-sorts unsorted rows into sort order). Without VACUUM, deleted row space is never reclaimed (tables grow indefinitely) and zone maps lose pruning effectiveness as the unsorted region grows. ANALYZE should run after large loads to update column statistics. Without current statistics, the query planner makes poor decisions — choosing broadcast joins for large tables, or merge joins where hash joins are more appropriate.
Q9. How does Redshift columnar storage interact with compression encodings?
Each column is stored independently in 1 MB blocks, and each column can use a different compression encoding. Columnar storage means only queried columns are read from disk; compression reduces how many bytes those columns occupy. The right encoding per column type dramatically reduces storage and I/O: AZ64 for numerics and dates, BYTEDICT for low-cardinality enums, ZSTD for general-purpose strings, RUNLENGTH for sorted repeated values. ANALYZE COMPRESSION recommends encodings based on actual data distribution. Encoding is immutable after table creation — requires a table recreation to change.
Q10. What is Redshift Data Sharing and when is it preferable to a cross-account COPY?
Data Sharing allows one Redshift cluster (producer) to share live, read-only access to database objects with another Redshift cluster (consumer) without copying data. The consumer queries the producer's data in real time. It's preferable to cross-account COPY when: data freshness matters (no copy lag), storage duplication cost is a concern, or the sharing relationship is ongoing rather than a one-time transfer. A cross-account COPY is preferable when the consumer needs to transform or enrich the data, needs write access, or needs the data in a different format than the producer's internal storage.

15. Production Story Angles

At a large financial institution, Redshift served as the primary analytical warehouse for a multi-team data platform. The pipeline feeding it ran on AWS Glue: ETL jobs read from the S3 processed zone, applied a final transformation layer, and loaded into Redshift using COPY from S3 staging. The staging bucket was in the same region as the Redshift cluster, and the cluster's IAM role had explicit s3:GetObject permissions on the staging prefix. Each COPY job loaded a date partition, and the staging files were split into multiples of the cluster's slice count to ensure full parallel utilization.

Distribution and sort key choices were made table by table based on query access patterns. The main event fact table used DISTKEY (user_id) and SORTKEY (event_date) — the majority of production queries filtered by date range and then joined to user dimension tables, also distributed on user_id. This combination eliminated DS_DIST_BOTH from all major join paths. A dimension table with under 500K rows used DISTSTYLE ALL so it could be joined from any fact table without redistribution overhead.

WLM was configured with three queues: an ETL queue (high memory, 2 concurrency slots, routed by query group etl), an analyst queue (balanced memory, 8 concurrency slots, routed by user group), and the default queue as a catch-all. Short Query Acceleration was enabled on the analyst queue. This configuration meant that a long-running nightly aggregate job did not delay a 5-second dashboard query — the WLM routing kept them fully isolated.

Redshift Spectrum was used for historical queries against the full 3-year S3 archive, which was cost-prohibitive to store in internal Redshift tables. External tables were defined in the Glue Data Catalog and registered in Redshift via an external schema. Analysts could write a single SQL query joining the current-year internal table with the historical external table for trend analysis — without knowing or caring which storage layer each partition lived in.

VACUUM and ANALYZE were scheduled as nightly maintenance jobs. The monitoring query on SVV_TABLE_INFO ran as part of a Lambda-based health check — any table exceeding 10% unsorted or 15% stats_off triggered an alert and an on-demand VACUUM/ANALYZE run before the next morning's batch queries began.

DISTKEY
Routes matching values to same slice — eliminates data movement for large joins on that column
DISTSTYLE ALL
Full copy on every node — use for small dimension tables (<~10M rows)
SORTKEY
Physical row order; enables zone map block pruning on range filters
Zone Maps
Min/max stats per 1 MB block — used to skip blocks during filtered scans
COPY command
Parallel load from S3 across all slices — always use for bulk loads; never row-by-row INSERT
DS_DIST_BOTH
Both join sides redistributed — most expensive pattern; fix by aligning DISTKEYs
DS_DIST_NONE
No redistribution — ideal; data already co-located on correct slices
VACUUM SORT ONLY
Re-sort unsorted rows into sort order; faster than full VACUUM

Reclaim space from deleted rows; does not re-sort
ANALYZE
Update column statistics for the query planner; run after large loads

Spectrum

Per-table health: unsorted %, stats_off %, size — primary VACUUM/ANALYZE monitoring table
