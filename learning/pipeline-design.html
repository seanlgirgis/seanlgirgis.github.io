Architecture-First Thinking

The most common mistake in data pipeline design is starting with the tool. An engineer reaches for Kafka, Glue, or Spark before answering the questions that determine whether those tools are appropriate. Architecture-first thinking means you understand the problem constraints before you commit to any implementation.

Four questions define every pipeline before any technology choice:

QuestionWhy it comes first
Who consumes this data, and what SLA do they need?Determines whether you need real-time, near-real-time, or batch delivery
What is the volume and velocity of the source?Determines compute scale, partitioning strategy, and cost model
What happens when the pipeline fails?Determines durability requirements, replay strategy, and DLQ design
How often does the source schema change?Determines how much schema evolution protection you need to build in
Start from the consumer, not the source. The consumer's SLA is the constraint that drives every upstream decision about latency, durability, and compute.
Starting with a tool instead of requirements is how teams end up with a real-time Kafka pipeline serving a dashboard that is only refreshed daily, or a batch Glue job for a consumer that needs sub-minute freshness.

Architecting a New Pipeline from Scratch

When asked this question in an interview — or facing a real design session — the answer is a structured process, not a list of tools. Here is the process that separates senior engineers from those who jump straight to implementation.

Step 1 — Define the consumer contract

What does the downstream system need? Freshness (how old can the data be?), completeness (can rows arrive late?), format (Parquet, JSON, SQL table?), and access pattern (query by key, scan a range, subscribe to a stream?). Every upstream decision flows from this.

Step 2 — Characterize the source

Is the source a database, an API, a message queue, files dropped to S3, or a CDC stream? What is the volume per hour/day? Does it emit deletes and updates or only inserts? Does it have a reliable cursor for incremental reads? Can it be replayed if you miss a window?

Step 3 — Design the data model at each stage

Sketch the schema at ingestion, after transformation, and at serving. Identify where data is enriched, filtered, aggregated, or joined. Make schema contracts explicit between stages rather than allowing them to drift.

Step 4 — Design for failure before designing for the happy path

What happens at each stage if it fails? Is the failure transient or fatal? How does the pipeline retry without producing duplicates? Where does bad data go? What is the replay path if a stage needs to be rerun from a checkpoint?

Step 5 — Choose compute to fit the constraints

Only now do you choose tools. The consumer SLA, source volume, and failure model together determine whether you need streaming (Kafka + Flink), micro-batch (Spark Streaming), or batch (Glue, EMR, Lambda). Match the tool to the problem, not the other way around.

Consumer SLA: 15-minute freshness, SQL query access, daily aggregate reports
Source: operational RDS database, 50 GB/day, inserts and updates

Decision path:
  - 15 min SLA --> micro-batch is sufficient, full streaming is overkill and costly
  - Updates exist --> need CDC or MERGE strategy, not append-only
  - SQL access --> land in Redshift or Athena on S3
  - Daily aggregates --> materialized views or scheduled dbt runs on top of raw load

Architecture: DMS CDC --> S3 (Parquet, partitioned by date) --> Glue crawler
             --> Athena for ad-hoc + Redshift Spectrum for aggregate reports
             --> dbt for business-layer transformations
In interviews, walk the interviewer through your decision process out loud. Say "I'm asking about the consumer SLA first because that determines whether we need streaming." This demonstrates seniority — you're reasoning, not just listing tools.

Batch vs Streaming — The First Decision

The choice between batch and streaming is the highest-leverage architectural decision in any pipeline. Getting it wrong is expensive to fix. The decision is not about which is more modern — it is about matching the architecture to what the consumer actually needs.

DimensionBatchStreaming
LatencyMinutes to hoursMilliseconds to seconds
ComplexityLower — simpler orchestrationHigher — state, watermarks, replay
CostLower at moderate volumeHigher — always-on infrastructure
Fault toleranceSimple — re-run the jobComplex — checkpointing and offset management
Late data handlingEasy — next batch picks it upRequires watermarks and grace periods
Right forDaily reports, ETL, ML featuresFraud detection, live dashboards, CDC

The Micro-Batch Middle Ground

Most production pipelines that appear to need "real-time" actually need near-real-time — freshness of 1 to 15 minutes is acceptable. Micro-batch with Spark Structured Streaming or a short-interval Glue job achieves this at far lower operational cost than a full streaming architecture. Before committing to Kafka and Flink, ask whether micro-batch solves the problem.

The question to ask is: "What is the business impact of data being 5 minutes stale vs 15 minutes stale vs 1 hour stale?" If the answer is "no real difference," batch or micro-batch is the correct architecture. Streaming is a cost you pay for a latency requirement.
Streaming architectures are significantly harder to test, debug, reprocess, and backfill than batch. Never choose streaming for its own sake. Make the consumer justify the complexity cost.

Designing for Idempotency

Idempotency means running the same pipeline job twice produces the same result as running it once. It is not an optimization — it is a correctness constraint that must be designed in from the start. Without it, retries and reruns create duplicate data, inflated metrics, and corrupted aggregations.

Why idempotency matters

Every production pipeline will be retried. Networks fail. EC2 instances are terminated. Glue jobs time out. Lambda functions hit concurrency limits. The pipeline will run twice for the same input, and it must produce correct output in that case without manual intervention.

Idempotency patterns

PatternHow it worksWhen to use
Overwrite partitionWrite output to a deterministic S3 prefix, overwrite on rerunBatch jobs writing partitioned Parquet to S3
MERGE / UPSERTUse primary key to insert new rows and update existing onesCDC loads into Redshift, DynamoDB, or Delta Lake
Idempotency keyHash of input fields stored to detect and skip duplicatesEvent processing in Lambda or Flink
Transactional writeWrite to staging table, commit atomically to targetRelational database loads requiring consistency
CheckpointingRecord last processed offset or watermark, resume from checkpoint on restartKafka consumers, Spark Structured Streaming
# Idempotent S3 partition overwrite pattern
# Each run writes to the same deterministic prefix and overwrites it

output_prefix = f"s3://data-lake/processed/events/year={year}/month={month}/day={day}/"

# Delete existing objects at the prefix first (or use spark overwrite mode)
spark.write \
    .mode("overwrite") \
    .partitionBy("year", "month", "day") \
    .parquet(output_prefix)

# Running this twice for the same date produces the same result
Test idempotency explicitly: run the job, record the row count and a checksum of the output, run the job again with identical input, verify the row count and checksum are identical. If they differ, the pipeline is not idempotent.
At-least-once delivery from Kafka or SQS is the norm. Your consumer must be idempotent because the same message will arrive more than once under normal operating conditions — not just during failure scenarios.

Microservices Boundaries for Data Engineering

In data engineering, microservices are components with a single, well-defined responsibility and a stable interface. The question of where to draw boundaries is one of the most consequential architectural decisions, because the wrong cut creates tight coupling that makes individual components impossible to deploy, scale, or debug independently.

Principles for drawing boundaries

Separate by rate of change. If ingestion logic changes frequently but transformation logic is stable, they should be separate services. Coupling them means a change in one triggers redeployment of the other.

Separate by failure domain. If a downstream enrichment service can fail without affecting ingestion, keep them separate. A failure in one should not cascade into the other.

Separate by scale requirement. Ingestion of high-volume events and serving of low-volume query results have different scaling characteristics. They should scale independently.

Separate by team ownership. A service boundary that crosses team ownership creates coordination cost. Align service boundaries with team responsibility where possible.

ServiceResponsibilityInterface
Ingestion serviceRead from source, validate, write raw to S3 or KafkaPublishes raw events to topic or S3 prefix
Transformation serviceApply business logic, enrich, normalizeConsumes raw, publishes processed
Quality gate serviceValidate row counts, nulls, schema, freshnessPasses or fails a batch before it reaches serving
Serving layerExpose data to consumers via SQL, API, or file exportQuery interface or scheduled delivery
OrchestratorTrigger, sequence, monitor, retryDAG definition, no business logic
A service should be independently deployable. If you cannot deploy, restart, or scale one component without touching another, the boundary is in the wrong place.
Too many fine-grained services create distributed system complexity without benefit. The goal is the right granularity — not the most services. A monolithic pipeline that can be deployed as one unit is often the right answer for small teams or early-stage data products.

Sync vs Async Communication

How services communicate is as important as where the boundaries are. Synchronous communication (REST, gRPC) creates temporal coupling — the caller waits for the callee and fails if the callee is unavailable. Asynchronous communication (queues, event streams) decouples availability but introduces complexity around ordering, delivery guarantees, and error handling.

PatternLatencyCouplingBest for
Synchronous REST/gRPCImmediateHigh — caller blocksQuery APIs, real-time lookups, user-facing requests
Async queue (SQS)SecondsLow — caller continuesWork distribution, retryable tasks, fan-out
Event stream (Kafka/Kinesis)MillisecondsVery low — pub/subCDC, high-volume event pipelines, replay
S3 file dropMinutesVery low — pollingBatch handoff between teams or systems

For data pipelines, asynchronous patterns dominate because they allow each stage to run at its own pace, buffer during traffic spikes, and retry independently. The source does not need to wait for the transformation, and the transformation does not need the serving layer to be healthy before it can write results.

Use synchronous communication when you need an immediate answer (lookups, validations, user-facing APIs). Use asynchronous communication when you need durability, scale, or independence between stages.
Async patterns shift errors from immediate failures to deferred failures visible only in dead letter queues or consumer lag metrics. You must invest in observability proportional to the asynchrony you introduce.

Data Contracts and Schema Evolution

A data contract is an explicit agreement between a producer and its consumers about the structure, semantics, and quality of the data being exchanged. In most pipelines, contracts are implicit — an upstream team changes a field name and two downstream pipelines break silently on the next run. Making contracts explicit is how you prevent this.

What a data contract covers

DimensionExample
SchemaField names, types, nullability, nesting structure
SemanticsWhat does event_time mean — UTC, local, server receipt time?
Freshness SLAData will arrive within 15 minutes of the source event
CompletenessRow count will not drop more than 5% versus previous day
UniquenessNo duplicate event_id values within a partition

Schema evolution compatibility modes

Backward compatible  -- new schema can read data written with old schema
                        Safe: add optional fields, remove fields with defaults
                        Breaks: rename fields, change types, make optional fields required

Forward compatible   -- old schema can read data written with new schema
                        Safe: remove fields, add fields with defaults
                        Breaks: add required fields, change types

Full compatible      -- both backward and forward
                        Only safe change: add optional fields with defaults

Breaking change      -- requires consumer migration before producer deploys
                        Any rename, type change, or removal of a required field
Treat a schema change like a database migration. Announce it to consumers, provide a migration timeline, use expand-and-contract: add the new field first while keeping the old one, migrate consumers, then remove the old field.
Schema Registry (Confluent, AWS Glue, or Apicurio) enforces compatibility rules automatically on every produce call. Without it, a producer can publish an incompatible schema and break consumers before anyone notices.

Testing — The Full Pyramid

Testing a data pipeline is different from testing application code. A test can pass — the job completed, returned exit code 0, wrote files to S3 — while the data is wrong. The testing strategy must prove correctness of the data, not just execution of the code.

The five test layers

LayerWhat it provesWhen it runsTool
Unit testsIndividual transformation functions produce correct output for known inputEvery commit, fastpytest, unittest
Integration testsComponents work together — job reads from source, writes correct output to sinkPull request, staging deploypytest + moto, localstack
Contract testsProducer output matches the schema and semantics consumers expectBefore every deployGreat Expectations, dbt tests, custom validators
End-to-end testsThe full pipeline path produces the correct serving-layer resultStaging environmentCustom harness with known input fixtures
Data quality testsProduction data meets freshness, completeness, uniqueness, and value-range expectationsAfter every pipeline run in productiondbt tests, Great Expectations, custom SQL checks

Testing large transformations

You cannot run a 500 GB Spark job in a CI pipeline. The practical approach is to extract transformation logic into pure functions that take DataFrames and return DataFrames, then test those functions against small representative samples. The schema, edge cases, and business logic can all be validated on 1000 rows. The scale-specific behavior (shuffle correctness, partition skew) is tested separately in a staging environment with a representative data sample.

# Separate transform logic from Spark job scaffolding
# So it can be tested without a Spark cluster

def normalize_event_timestamps(df: pd.DataFrame) -> pd.DataFrame:
    """Convert all timestamp fields to UTC ISO-8601 strings."""
    df['event_time'] = pd.to_datetime(df['event_time'], utc=True).dt.strftime('%Y-%m-%dT%H:%M:%SZ')
    return df

# Test with 10 rows — no Spark cluster needed
def test_timestamp_normalization():
    input_df = pd.DataFrame({'event_time': ['2026-04-25 10:00:00-05:00']})
    result = normalize_event_timestamps(input_df)
    assert result['event_time'][0] == '2026-04-25T15:00:00Z'

Testing idempotency

# Idempotency test pattern
def test_pipeline_is_idempotent():
    run_pipeline(date='2026-04-25', input_path='s3://test/raw/2026-04-25/')
    first_run_checksum = compute_checksum('s3://test/processed/2026-04-25/')
    first_run_count = count_rows('s3://test/processed/2026-04-25/')

    run_pipeline(date='2026-04-25', input_path='s3://test/raw/2026-04-25/')  # run again
    second_run_checksum = compute_checksum('s3://test/processed/2026-04-25/')
    second_run_count = count_rows('s3://test/processed/2026-04-25/')

    assert first_run_checksum == second_run_checksum
    assert first_run_count == second_run_count
The most valuable tests for data pipelines are the data quality tests that run in production after every job. A green CI pipeline only tells you the code ran. Production data quality checks tell you the output was correct.

Data Quality Validation

Data quality is a pipeline concern, not just a consumer concern. By the time a downstream analyst notices wrong data, it has propagated through multiple pipeline stages and potentially into production reports. Quality gates embedded in the pipeline catch problems at the earliest possible point.

The five data quality dimensions

DimensionWhat to checkExample assertion
CompletenessRequired fields are not null, row counts are within expected rangeRow count today ≥ 95% of row count yesterday
UniquenessPrimary key fields have no duplicates within a partitionCOUNT(DISTINCT event_id) = COUNT(*)
FreshnessLatest record timestamp is within the SLA windowMAX(event_time) within last 30 minutes
ValidityValues are within expected range or enumerationAll status values in {active, inactive, pending}
ConsistencyRelationships between fields hold, totals reconcile with sourceSUM(line_items) = order_total for each order

Where to put quality gates

Place a quality gate between each major pipeline stage — after ingestion (validate raw data arrived correctly), after transformation (validate business logic produced correct output), and before serving (validate what consumers will query is trustworthy). A failing quality gate should halt the pipeline and alert, not silently pass bad data downstream.

# dbt test examples — run after each model build
-- schema.yml
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - not_null
          - unique
      - name: order_total
        tests:
          - not_null
          - dbt_utils.accepted_range:
              min_value: 0
      - name: status
        tests:
          - accepted_values:
              values: ['placed', 'shipped', 'delivered', 'cancelled']
A pipeline that completes successfully but produces wrong data is more dangerous than a pipeline that fails. A failure alerts immediately. Wrong data can propagate silently for days before a consumer notices.

Observability and SLAs

A pipeline without observability is a black box. You cannot tell if it is healthy, falling behind, or silently producing wrong data. Observability means you can answer three questions at any moment: is the pipeline running, is it on time, and is the output correct?

The three pillars for pipelines

PillarWhat to instrumentTool
MetricsRecords processed per minute, consumer lag, job duration, error rate, row count per partitionCloudWatch, Prometheus, Datadog
LogsJob start/end events, transformation errors, quality gate pass/fail, retry eventsCloudWatch Logs, ELK, Splunk
TracesEnd-to-end latency from source event to serving layer writeX-Ray, OpenTelemetry

Pipeline SLOs

A Service Level Objective for a data pipeline is a measurable target on data freshness, completeness, or availability. Without explicit SLOs, "the pipeline is slow" cannot be evaluated objectively. Common pipeline SLOs:

Freshness SLO:     Data in serving layer is no more than 15 minutes behind source
Completeness SLO:  Row count for any partition is within 2% of source count
Availability SLO:  Pipeline runs complete successfully 99.5% of scheduled executions
Latency SLO:       P99 processing time per event < 30 seconds (streaming pipeline)
Define SLOs before you build the pipeline, not after. SLOs drive the monitoring, alerting thresholds, and retry design. A pipeline built without SLOs in mind is usually under-instrumented and over-alerting on noise.
Consumer lag is one of the most important metrics for streaming pipelines. Rising lag means the consumer is falling behind the producer — it is a leading indicator of freshness SLO breach, not a lagging one. Alert on lag, not on output delay.

Late Data and Watermarking

Late data is data that arrives at the pipeline after the time window it belongs to has nominally closed. In batch pipelines this is usually handled by the next scheduled run picking it up. In streaming pipelines it requires explicit handling because windows are computed incrementally and results may have already been emitted.

Watermarks

A watermark is a declaration: "I believe I have seen all events with event_time up to timestamp T." Events with timestamps before T that arrive after the watermark is advanced are considered late. The watermark advances as new events arrive with later timestamps, minus a configurable lag allowance.

# Spark Structured Streaming watermark example
from pyspark.sql.functions import window

events_with_watermark = (
    events_stream
    .withWatermark("event_time", "10 minutes")   # allow 10-min late arrivals
    .groupBy(window("event_time", "5 minutes"))   # 5-min tumbling windows
    .count()
)
# Events up to 10 minutes late are included in the correct window
# Events later than 10 minutes are dropped (or routed to a late-data sink)

Handling late data in batch

For daily batch pipelines, the standard approach is to reprocess the last N days on each run using a lookback window. This catches late-arriving events without requiring watermark logic. The tradeoff is compute cost — you process N days of data instead of one day, but the pipeline stays simple and correct.

The right watermark lag is a business decision, not a technical one. Ask: how late can data realistically arrive, and what is the cost of missing it vs the cost of holding windows open longer?

Backfill Strategy

Backfilling means reprocessing historical data — because the pipeline was fixed, the business logic changed, a new derived field was added, or the historical data was corrupted. A poorly designed pipeline makes backfill slow, expensive, and risky. A well-designed one makes backfill a routine operational task.

Requirements for a backfillable pipeline

RequirementWhy it matters
Immutable raw sourceYou need the original data to still exist and be replayable
Idempotent writesReprocessing the same partition must overwrite cleanly, not duplicate
Parameterized date rangeYou must be able to run the job for any arbitrary date range, not just "today"
Independent of downstream stateBackfill should not break consumers reading current data while historical data is being reprocessed

Backfilling 2 years of data safely

# Strategy: parallel monthly batches, not a single 2-year run
# Avoids a single job failure losing all progress

for year_month in generate_months('2024-01', '2025-12'):
    submit_backfill_job(
        date_range=year_month,
        output_prefix=f"s3://data-lake/processed/backfill/{year_month}/",
        parallelism=20
    )
    wait_for_completion()
    validate_quality_gate(year_month)

# After all months pass quality gates, atomic swap:
promote_backfill_to_production()
Run the backfill to a separate output prefix first, validate it, then atomically swap it into the production path. Never backfill directly over production data in place — a failed backfill should leave production untouched.
Backfilling can consume significant compute and incur unexpected costs. Rate-limit your backfill jobs, monitor S3 request costs, and consider running during off-peak hours if the backfill competes with production workloads.

Failure Modes and Recovery

Every pipeline failure falls into one of two categories: transient or fatal. The recovery strategy must match the failure category. Retrying a fatal error wastes compute and delays alerting. Failing permanently on a transient error causes unnecessary data loss.

Failure typeExamplesCorrect response
TransientNetwork timeout, throttling, temporary service unavailabilityExponential backoff retry with jitter, up to a limit
FatalSchema mismatch, malformed record, permission denied, source data missingMove to dead letter queue, alert, do not retry
PartialSome records fail in a batch job while others succeedRoute failed records to DLQ, complete the successful batch, alert on DLQ depth
SilentJob completes but output is wrong — wrong count, wrong valuesCatch with data quality gates post-run, not retry logic

Dead Letter Queue pattern

# SQS DLQ pattern for Lambda event processor
# Records that fail after maxReceiveCount retries go to DLQ automatically

resource "aws_sqs_queue" "events_dlq" {
  name = "pipeline-events-dlq"
  message_retention_seconds = 1209600  # 14 days to investigate
}

resource "aws_sqs_queue" "events_queue" {
  name = "pipeline-events"
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.events_dlq.arn
    maxReceiveCount     = 3   # retry 3 times before DLQ
  })
}

# Alert when DLQ depth > 0 -- every DLQ message needs investigation
A dead letter queue is your safety net for partial failures. Without it, failed records either block the pipeline indefinitely or are silently dropped. Always wire up a DLQ, always alert on its depth, always have a replay mechanism.
Distributed transactions are nearly impossible to implement correctly in data pipelines. Use the saga pattern — a sequence of local transactions with compensating transactions for rollback — rather than attempting two-phase commit across services.

Build vs Buy

Every pipeline component can be built from scratch or sourced from a managed service or open-source tool. The build vs buy decision is not just about upfront development cost — it is about the total cost of ownership over the lifetime of the pipeline, including operational burden, scaling, security patching, and the engineering time consumed by maintenance.

ComponentBuildBuy / ManagedWhen to build
Message queueSelf-managed Kafka on EC2MSK, Kinesis, SQSSpecific Kafka features MSK doesn't expose, cost at extreme scale
ETLCustom PySpark on EMRAWS GlueComplex dependency management, cost sensitivity at high DPU usage
OrchestrationCustom schedulerAirflow, Step Functions, MWAAAlmost never — orchestrators are solved problems
Data qualityCustom SQL checksGreat Expectations, dbt testsVery specific domain rules not expressible in standard frameworks
Transformation logicAlways customN/AAlways — business logic is yours, no tool replaces it

The honest cost of building includes: initial development time, operational runbooks, on-call burden, security patching, scaling incidents, and the opportunity cost of not building product features. Managed services shift operational burden to the vendor at a cost premium. The right answer depends on your team size, scale, and whether the component is differentiating.

Default to managed services for undifferentiated infrastructure (queues, orchestrators, catalogs). Build custom for your actual business logic. The closer a component is to raw infrastructure, the less likely it is that building it yourself creates competitive advantage.
Technical debt from build decisions is compounded. A custom Kafka deployment that needs upgrading in year two will consume engineering time proportional to your cluster size. Factor the 3-year total cost of ownership into the build vs buy decision, not just the sprint estimate.

Interview Q&A

How do you approach architecting a new data pipeline from scratch?
I start from the consumer, not the source. The first questions are: what SLA does the downstream system need, what format does it need the data in, and what happens to their business if the pipeline is late or wrong? Those answers define the constraints — freshness requirement drives the batch vs streaming decision, format drives the transformation design, and the business impact of failure drives the durability and retry requirements. Only after I understand the consumer contract do I characterize the source — its volume, velocity, whether it emits deletes and updates, and whether it can be replayed. Then I design the schema at each stage, explicitly document the data contract between stages, and design failure handling before I design the happy path. Tool selection comes last — I choose the compute that fits the already-defined constraints, not the other way around.
How do you decide where to draw microservice boundaries in a data platform?
The three principles I use are: separate by rate of change, separate by failure domain, and separate by scale requirement. Rate of change means if ingestion logic and transformation logic evolve independently, coupling them forces joint deployments and mutual risk. Failure domain means a failure in an enrichment service should not take down the core ingestion path. Scale requirement means components with different throughput profiles should scale independently. Practically, most data platforms need at least four distinct services: ingestion (source to raw), transformation (raw to processed), quality gate (validation between stages), and serving (processed to consumers). The orchestrator is a fifth service that should contain sequencing logic only and no business logic. I resist over-splitting until there is a concrete operational reason — two services have a coordination cost that a single well-structured service does not.
How do you test a data pipeline, and how do you handle the fact that it runs on hundreds of gigabytes?
I use five test layers. Unit tests on pure transformation functions — these have no Spark dependency and run in milliseconds against small DataFrames. Integration tests using moto or localstack to mock AWS services and validate that the job reads from the source and writes correct output to the sink. Contract tests that validate the output schema and semantics match what consumers declared they need. End-to-end tests in a staging environment with a representative sample of production data. And data quality tests that run in production after every job to validate freshness, completeness, uniqueness, and value ranges. The scale problem is solved by separating logic from scaffolding — transformation functions are pure functions testable on 1000 rows in CI. Scale-specific behavior like partition skew is caught in staging. The most important insight is that a pipeline test proving the job ran is not the same as a test proving the data is correct — you need both.
A pipeline ran successfully but the output data was wrong. How does that happen and how do you prevent it?
This is one of the most dangerous categories of failure in data engineering because there is no alert — the job returned exit code 0. It happens in several ways: a source schema changed silently and a field that was parsed as one type is now parsed as another with no error, just wrong values; a transformation has a logic bug that produces plausible-looking but incorrect output; an idempotency failure doubled rows in the output; or a JOIN on the wrong key produced a cartesian product that passes row count checks but has wrong data. Prevention requires data quality gates that run after every job and test the actual data values, not just the job status — row count reconciliation against the source, uniqueness checks on primary keys, freshness checks on the latest timestamp, and range or enumeration checks on key fields. The quality gate must be a blocking step that fails the pipeline and alerts before bad data reaches consumers.
How do you handle a backfill of 2 years of historical data without disrupting the production pipeline?
The prerequisites are an immutable raw source that can be replayed, idempotent writes so reprocessing a partition overwrites cleanly, and a parameterized date range so the job can process any arbitrary window. For the backfill execution I split it into monthly batches rather than one 2-year run — this contains the blast radius if any month fails and makes progress tracking concrete. Each batch writes to a separate staging prefix, runs the standard quality gate, and only after all months pass does an atomic swap promote the backfill to the production path. During the backfill, the production pipeline continues running for new data unaffected. The key rule is never write the backfill directly over production data in place — a failed backfill mid-run should leave production in the last known good state, not in a partially overwritten state.
How do you decide between batch, micro-batch, and streaming for a new pipeline?
The decision comes from the consumer SLA and the business impact of latency, not from a preference for modern technology. I start by asking what the business consequence is of data being 5 minutes stale versus 15 minutes stale versus 1 hour stale. If the answer is "no real difference," batch or micro-batch is the right architecture — streaming is a cost and complexity premium you pay for a latency requirement that does not actually exist. Most pipelines that appear to need real-time actually need near-real-time, which micro-batch achieves at far lower operational cost. I recommend streaming only when the consumer has a hard sub-minute freshness requirement, when the source emits high-volume events that need per-event processing (fraud detection, CDC fan-out), or when stateful windowed aggregations over event-time streams are genuinely required. Streaming architectures are harder to test, debug, backfill, and replay than batch — that complexity needs to be justified by a real business requirement.

Quick Reference

Architecture rule
Start from the consumer SLA, work backwards to the source. Never start with the tool.
Batch vs stream
Choose streaming only when the consumer has a hard sub-minute freshness requirement. Micro-batch covers most "real-time" needs.
Idempotency
Running the pipeline twice on the same input produces the same output. Design this in from day one — retrofitting is painful.
Test idempotency
Run the job, checksum the output, run again, assert checksums match.
Service boundary
Separate by rate of change, failure domain, and scale requirement. A service must be independently deployable.
Sync vs async
Sync for immediate answers (lookups, APIs). Async for durability, fan-out, and independent scaling between stages.
Data contract
Explicit schema, semantics, freshness SLA, completeness, and uniqueness agreement between producer and consumers.
Schema evolution
Backward: new schema reads old data. Forward: old schema reads new data. Breaking change = consumer migration required first.
Testing pyramid
Unit → Integration → Contract → End-to-end → Data quality in production. Each layer catches different failure modes.
Silent failure
Job exits 0 but data is wrong. Only caught by post-run data quality checks — row counts, uniqueness, freshness, value ranges.
Quality gate
Blocking validation step between pipeline stages. Fail and alert rather than passing bad data downstream.
Watermark
Streaming declaration: "all events before timestamp T have arrived." Late data beyond the grace period is dropped or routed to DLQ.
Backfill rule
Write to a staging prefix, validate each partition, then atomic swap to production. Never overwrite production in place during a backfill.
Transient error
Retry with exponential backoff and jitter. Examples: network timeout, throttling, temporary service unavailability.
Fatal error
Move to DLQ, alert, do not retry. Examples: schema mismatch, permission denied, source data missing.
Dead letter queue
Sink for unprocessable records after max retries. Alert when depth > 0. Always have a replay mechanism.
Build vs buy
Default to managed services for undifferentiated infrastructure. Build custom only for business logic that is genuinely yours.
SLO
Measurable target: freshness ≤ 15 min, completeness ≥ 98%, availability ≥ 99.5%. Define before building, not after.
