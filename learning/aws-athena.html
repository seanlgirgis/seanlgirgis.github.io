1. What Athena Actually Is

Athena is a serverless interactive query service that lets you run standard SQL directly against data stored in S3 — no cluster to provision, no data to load, no infrastructure to manage. You point it at an S3 path, define a schema (or let Glue infer one), and query.

The key mental model: Athena is a query engine, not a database. It does not store your data. It does not index your data. It reads files from S3 on demand, applies your SQL, and returns results. The data lives entirely in S3 — Athena is purely the compute layer on top of it.

The one-sentence positioning: Athena = SQL on S3, serverless, pay per byte scanned. Everything else — performance, cost, design choices — flows from understanding that single sentence deeply.

Under the hood Athena is built on Presto (now Trino), a distributed SQL engine originally developed at Meta. Athena v3 (current) runs on Trino. This matters because Presto/Trino SQL has some differences from standard ANSI SQL and from Redshift SQL — knowing this saves debugging time.

What Athena is Not

  • Not a data warehouse — no columnar storage management, no sort keys, no distribution styles
  • Not a streaming engine — batch/interactive queries only, not real-time
  • Not a replacement for Redshift — for complex multi-join analytics at high concurrency, Redshift wins
  • Not free — every query scans data, and you pay per TB scanned

2. How Athena Works Under the Hood

When you run a query, Athena does the following in sequence: 

You submit SQL
    ↓
Athena parses query → generates execution plan
    ↓
Reads table metadata from Glue Data Catalog
    (schema, S3 location, partition info, file format)
    ↓
Applies partition pruning
    (eliminates S3 prefixes that don't match WHERE clause)
    ↓
Dispatches parallel read workers across matching S3 files
    ↓
Each worker reads and decompresses its file slice
    ↓
Applies column projection (reads only needed columns from Parquet)
    ↓
Aggregates and returns results
    ↓
Writes results to your designated S3 results bucket

Two optimizations in that flow are critical to understand: partition pruning and column projection. Partition pruning means Athena skips entire S3 prefixes that don't match your WHERE clause — this is why partitioning by date cuts query cost dramatically. Column projection means with Parquet files, Athena reads only the columns you SELECT — it doesn't read the whole file.

Both optimizations require the right file format. Column projection only works with columnar formats like Parquet or ORC. With CSV or JSON, Athena reads every column regardless of what you SELECT. This is the single biggest lever for reducing cost.

Query Results

Every Athena query writes its results to an S3 bucket you configure — the query results location. Results are stored as CSV files with a companion metadata file. You can point BI tools (QuickSight, Tableau) at Athena and they read from this results bucket.

3. The Cost Model — Pay Per Scan

Athena charges $5 per TB of data scanned. There is no charge for DDL statements, failed queries, or cancelled queries. The compute is serverless — you only pay for what you scan.

This makes cost optimization a first-class engineering concern. A poorly written query against an unpartitioned CSV table can scan terabytes and cost dollars. The same query against a Parquet table with partitions can scan megabytes and cost fractions of a cent.

Cost Reduction Levers — In Order of Impact

LeverMechanismTypical Reduction
Use Parquet or ORCColumn projection — only reads selected columns60–90%
Partition by query columnsPartition pruning — skips non-matching prefixes50–99%
Compress dataSnappy/GZIP reduces bytes on disk = bytes scanned30–60%
Compact small filesFewer, larger files = less metadata overhead10–40%
SELECT only needed columnsWith Parquet, fewer columns = less scanVaries
Use LIMIT carefullyLIMIT does not stop scanning — it filters afterNone
LIMIT does not reduce cost. SELECT * FROM large_table LIMIT 10 still scans the entire table. To sample cheaply, use partition filters in the WHERE clause instead.

4. File Formats and Why They Matter

FormatTypeAthena PerformanceBest For
ParquetColumnarExcellent — column pruning + compressionAnalytics, data lake curated zone
ORCColumnarExcellent — similar to ParquetHive-native workloads
JSONRowPoor — reads full rows alwaysRaw landing zone only
CSVRowPoor — reads full rows, no compression benefitSource files, never for analytics
AvroRowFair — good for schema evolutionStreaming ingestion formats
Parquet is the default answer. For any analytics use case on Athena, the data should be in Parquet with Snappy compression. The Glue ETL job that processes raw S3 data should always write Parquet to the processed/curated zones. This one decision drives the majority of Athena cost savings.

Parquet Internals Worth Knowing

Parquet organizes data in row groups (horizontal slices) and column chunks (vertical slices within a row group). Each column chunk has statistics (min, max, null count) stored in its footer. Athena uses these statistics for predicate pushdown — it can skip entire row groups if the column statistics show no matching values. 

Parquet file structure:
┌─────────────────────────────────────┐
│  Row Group 1                        │
│  ├── Column chunk: user_id          │
│  ├── Column chunk: event_date       │  ← statistics: min=2026-01-01, max=2026-01-31
│  └── Column chunk: revenue          │
├─────────────────────────────────────┤
│  Row Group 2                        │
│  ├── Column chunk: user_id          │
│  ├── Column chunk: event_date       │  ← statistics: min=2026-02-01, max=2026-02-28
│  └── Column chunk: revenue          │
├─────────────────────────────────────┤
│  File Footer (schema + statistics)  │
└─────────────────────────────────────┘

WHERE event_date = '2026-01-15'
→ Athena reads footer → skips Row Group 2 entirely

5. Athena + Glue Data Catalog

Athena does not manage its own metadata. It reads table definitions — schema, S3 location, partition information, file format — from the Glue Data Catalog. This is the central metadata store that ties together Athena, Glue ETL jobs, and Redshift Spectrum into a single coherent data platform. 

Glue Data Catalog
    ├── Database: capacity_data
    │   ├── Table: raw_telemetry      → s3://bucket/raw/      (JSON, no partitions)
    │   ├── Table: processed_metrics  → s3://bucket/processed/ (Parquet, partitioned year/month)
    │   └── Table: monthly_summary    → s3://bucket/curated/   (Parquet, partitioned year)
    └── Database: reference_data
        └── Table: server_inventory   → s3://bucket/reference/ (Parquet)

Creating Tables — Two Approaches

1. Glue Crawler (automated) — crawler scans S3, infers schema, creates/updates table in catalog automatically. Best for evolving schemas or large numbers of tables.

2. DDL in Athena (manual) — write CREATE EXTERNAL TABLE directly in Athena. Best for full control over schema definition:

CREATE EXTERNAL TABLE processed_metrics (
    server_id   STRING,
    metric_name STRING,
    value       DOUBLE,
    ts          TIMESTAMP
)
PARTITIONED BY (year STRING, month STRING)
STORED AS PARQUET
LOCATION 's3://bucket/processed/metrics/'
TBLPROPERTIES ('parquet.compress' = 'SNAPPY');

Loading Partitions

After creating or adding data to a partitioned table, Athena needs to know about the new partitions:

-- Option 1: discover all partitions automatically
MSCK REPAIR TABLE processed_metrics;

-- Option 2: add a specific partition manually (faster for large tables)
ALTER TABLE processed_metrics
ADD PARTITION (year='2026', month='04')
LOCATION 's3://bucket/processed/metrics/year=2026/month=04/';
MSCK REPAIR TABLE can be slow on tables with thousands of partitions — it scans all S3 prefixes. For production pipelines, prefer ALTER TABLE ADD PARTITION at the end of each ETL job run.

6. Partitioning for Performance and Cost

Partitioning is the single most impactful design decision for Athena. A well-partitioned table can reduce query cost by 99% compared to a flat unpartitioned table with the same data.

How Partition Pruning Works

Table: processed_metrics
Partitions: year=2026/month=04/ contains 50 GB

-- This query scans only 50 GB
SELECT * FROM processed_metrics
WHERE year = '2026' AND month = '04';

-- This query scans the entire table (no partition filter)
SELECT * FROM processed_metrics
WHERE metric_name = 'cpu_utilization';  -- metric_name is not a partition key

Partition Projection — Skip the Glue Catalog for Date Partitions

For tables with predictable date-based partitions, Athena can use Partition Projection — it generates partition paths mathematically without querying the Glue catalog. This eliminates the catalog lookup overhead and is especially fast for date ranges. 

CREATE EXTERNAL TABLE daily_metrics (...)
PARTITIONED BY (dt STRING)
STORED AS PARQUET
LOCATION 's3://bucket/metrics/'
TBLPROPERTIES (
    'projection.enabled'        = 'true',
    'projection.dt.type'        = 'date',
    'projection.dt.range'       = '2025-01-01,NOW',
    'projection.dt.format'      = 'yyyy-MM-dd',
    'projection.dt.interval'    = '1',
    'projection.dt.interval.unit' = 'DAYS',
    'storage.location.template' = 's3://bucket/metrics/dt=${dt}/'
);
Partition Projection removes the need to run MSCK REPAIR TABLE or add partitions manually. For time-series data it's the cleanest pattern — no catalog maintenance required.

7. Writing Effective Athena SQL

Athena uses Trino SQL (formerly Presto). It is mostly ANSI-compatible but has some differences worth knowing before hitting confusing errors.

Common Patterns

-- Date filtering using partition columns (always use partition keys in WHERE)
SELECT server_id, AVG(value) AS avg_cpu
FROM processed_metrics
WHERE year = '2026' AND month = '04'
  AND metric_name = 'cpu_utilization'
GROUP BY server_id
ORDER BY avg_cpu DESC
LIMIT 20;

-- Working with timestamps (Athena uses from_iso8601_timestamp, not TO_DATE)
SELECT server_id,
       from_iso8601_timestamp(ts_string) AS event_time
FROM raw_telemetry
WHERE year = '2026';

-- String functions (Trino uses || for concat, not CONCAT in older versions)
SELECT server_id || '-' || metric_name AS metric_key FROM processed_metrics;

-- Approximate COUNT DISTINCT (much faster for large datasets)
SELECT approx_distinct(server_id) AS unique_servers
FROM processed_metrics
WHERE year = '2026';

-- JSON extraction from a string column
SELECT json_extract_scalar(raw_payload, '$.hostname') AS hostname
FROM raw_telemetry
WHERE year = '2026';

Trino vs Redshift SQL Differences

8. CTAS — Create Table As Select

CTAS lets you create a new table from the results of a SELECT query. The output is written to S3 as Parquet (or another format you specify) and registered in the Glue Data Catalog. This is one of the most powerful Athena features for data engineering.

Primary Use Cases

  • Convert CSV/JSON to Parquet — run once, all future queries are faster and cheaper
  • Repartition a table — rebuild with better partition keys without writing Glue ETL code
  • Materialize aggregations — pre-compute expensive aggregations into a summary table
  • Compact small files — CTAS writes fewer, larger files than many small source files
-- Convert raw JSON to partitioned Parquet
CREATE TABLE processed_metrics
WITH (
    format           = 'PARQUET',
    parquet_compression = 'SNAPPY',
    partitioned_by   = ARRAY['year', 'month'],
    external_location = 's3://bucket/processed/metrics/'
)
AS
SELECT
    server_id,
    metric_name,
    CAST(value AS DOUBLE) AS value,
    from_iso8601_timestamp(ts) AS ts,
    DATE_FORMAT(from_iso8601_timestamp(ts), '%Y') AS year,
    DATE_FORMAT(from_iso8601_timestamp(ts), '%m') AS month
FROM raw_telemetry
WHERE year = '2026';
CTAS is Athena's ETL capability. For lightweight transformations — format conversion, repartitioning, light aggregation — CTAS can replace a Glue ETL job entirely. For complex multi-step transformations, Glue PySpark is still the right tool.

INSERT INTO — Incremental Appends

-- Append new data to an existing CTAS table
INSERT INTO processed_metrics
SELECT server_id, metric_name, value, ts, year, month
FROM raw_telemetry
WHERE year = '2026' AND month = '05';

9. Views in Athena

Athena supports logical views — stored SQL queries that behave like tables. Views do not store data; they execute the underlying query every time they are queried. They are stored in the Glue Data Catalog. 

-- Create a view that abstracts partition columns from consumers
CREATE VIEW current_month_metrics AS
SELECT server_id, metric_name, value, ts
FROM processed_metrics
WHERE year = FORMAT('%Y', current_date)
  AND month = FORMAT('%m', current_date);

-- Consumers query the view without knowing the partition structure
SELECT server_id, AVG(value)
FROM current_month_metrics
WHERE metric_name = 'memory_utilization'
GROUP BY server_id;
Views do not reduce cost. Querying a view executes the full underlying SQL including all scans. If the view has no partition filter, every query against it scans the entire table. Always ensure views push down partition predicates, or document that consumers must add their own WHERE clauses.

10. Workgroups

Workgroups let you organize queries, enforce controls, and track costs by team or use case. Every Athena query runs in a workgroup — the default workgroup if you don't specify one.

What Workgroups Control

  • Query results location — each workgroup writes to a different S3 prefix
  • Data scan limit — cancel a query if it would scan more than X bytes (cost guard)
  • Workgroup scan limit — cut off the entire workgroup if it exceeds a daily/weekly limit
  • Encryption — enforce SSE-KMS on query results
  • Cost allocation — tag queries by team, project, or cost center
-- Using the API (boto3) to run a query in a specific workgroup
import boto3

athena = boto3.client('athena', region_name='us-east-1')
response = athena.start_query_execution(
    QueryString = "SELECT * FROM processed_metrics WHERE year='2026' AND month='04'",
    QueryExecutionContext = {'Database': 'capacity_data'},
    WorkGroup = 'data-engineering-team'
)
In a financial services environment, workgroups are typically set up per team with enforced scan limits and SSE-KMS on results. This prevents runaway queries from generating unexpected cost and ensures query results are encrypted at rest.

11. Federated Queries

Athena Federated Query lets you run SQL against data sources other than S3 — including RDS, DynamoDB, Redshift, CloudWatch Logs, JDBC databases — and join them with S3 data in a single query. The mechanism is a Lambda-based connector that Athena invokes to retrieve data from the external source. 

-- Join S3-based processed data with RDS reference data in one query
SELECT m.server_id,
       m.value AS cpu_pct,
       r.data_center,
       r.owner_team
FROM processed_metrics m
JOIN "oracle-connector".dbo.server_inventory r
    ON m.server_id = r.server_id
WHERE m.year = '2026'
  AND m.month = '04'
  AND m.metric_name = 'cpu_utilization'
  AND m.value > 80;

When to Use Federated Queries

  • Enriching S3 analytics data with reference data that lives in a relational database
  • Ad-hoc cross-source analysis without an ETL pipeline to join the data first
  • Querying CloudWatch Logs with SQL — useful for operational analysis
Federated queries are slower and more expensive than pure S3 queries. The Lambda connector adds latency and the external source is queried in real time. Use for ad-hoc or low-frequency queries — not for high-concurrency dashboards. For frequent joins, ETL the reference data into S3 instead.

12. Athena vs Redshift — When to Use Which

This is one of the most common architectural questions. The answer is not one or the other — they serve different workloads and are often used together in the same data platform.

DimensionAthenaRedshift
ArchitectureServerless, no clusterProvisioned or Serverless cluster
Data locationAlways in S3In Redshift storage (or S3 via Spectrum)
Cost modelPer TB scannedPer hour (provisioned) or per RPU-hour (serverless)
ConcurrencyModerate — good for ad-hocHigh — good for dashboards, many users
Query latencySeconds to minutesMilliseconds to seconds (with sort/dist keys)
SetupZero — point at S3 and queryCluster setup, table design, data loading
Best forAd-hoc exploration, data lake queries, ETL validationBI dashboards, high-concurrency reporting, complex joins
The common pattern in production: Athena for exploration and pipeline validation; Redshift for production BI workloads. Glue processes raw S3 data into Parquet — both Athena and Redshift read from the same processed S3 data (Redshift via COPY or Spectrum, Athena directly). One pipeline, two consumers.

13. Common Gotchas and Anti-Patterns

1. Querying without partition filters

SELECT * FROM large_table WHERE metric_name = 'cpu' — if metric_name is not a partition key, this scans the entire table. Always filter on partition columns first.

2. Small files problem

Thousands of small Parquet files (under 128MB) cause Athena to spend more time on file metadata overhead than actual data reading. An S3 prefix with 10,000 × 1MB files performs far worse than 100 × 100MB files containing the same data. Fix with a periodic compaction job using CTAS or Glue.

3. Using LIMIT to reduce cost

SELECT * FROM table LIMIT 10 scans the full table and returns 10 rows. LIMIT is applied after scanning. To cheaply sample data, use a partition filter: WHERE year='2026' AND month='04' LIMIT 10

4. Schema mismatch after Glue crawler runs

If source data changes schema (new column added, type changed), the Glue crawler may update the catalog table in unexpected ways. Use crawler configuration to control schema update behaviour — specifically the SchemaChangePolicy setting. In production, prefer manual DDL for critical tables rather than relying on crawlers alone.

5. Forgetting to run MSCK REPAIR TABLE

New data written to S3 is invisible to Athena until the partition is registered. Either run MSCK REPAIR TABLE, use ALTER TABLE ADD PARTITION, or switch to Partition Projection to eliminate the problem entirely.

6. Mixing Hive-style and non-Hive partitions

Athena expects Hive-style partitions (year=2026/month=04/). If your S3 data uses plain date folders (2026/04/), you must define partitions manually with explicit LOCATION in ALTER TABLE — MSCK REPAIR TABLE will not find them.

14. Ten Key Engineering Questions and Answers

Q1 — "How does Athena reduce query cost and improve performance?"
"Two main levers: file format and partitioning. Parquet gives you column projection — Athena only reads the columns in your SELECT, not the whole row. Partitioning gives you partition pruning — Athena skips entire S3 prefixes that don't match your WHERE clause. Together they can reduce bytes scanned by 90% or more. On top of those, compression reduces file size, which directly reduces scan bytes since Athena charges per compressed byte scanned."
Q2 — "What is the Glue Data Catalog and why does Athena need it?"
"Athena doesn't store metadata — it reads it from the Glue Data Catalog. The catalog holds the table schema, the S3 location, the file format, and the partition structure. When you run a query, Athena looks up the table in the catalog first to know where the data is and how to read it. This is also why Glue, Athena, and Redshift Spectrum can all share the same metadata — one catalog, multiple query engines."
Q3 — "What is CTAS and when would you use it over Glue ETL?"
"CTAS is Create Table As Select — it runs a SELECT query and writes the results to S3 as a new table, typically in Parquet. I'd use it for lightweight transformations: converting raw JSON or CSV to Parquet, repartitioning an existing table with better partition keys, or materializing a frequently-run aggregation. For complex multi-step transformations, joins across many tables, or anything needing Python logic, Glue PySpark is the right tool. The rule of thumb: if it can be expressed in one SQL statement, CTAS is probably simpler."
Q4 — "How do you handle schema evolution in Athena tables?"
"Parquet is schema-on-read, so adding new columns to source data doesn't break existing queries — Athena just returns NULL for missing columns in older files. The risk is type changes or column renames, which can break queries silently. My approach: use Glue crawlers to detect schema changes but set the SchemaChangePolicy to LOG rather than UPDATE for critical tables. Then review changes manually and apply controlled DDL with ALTER TABLE. For append-only new columns, Parquet handles this gracefully."
Q5 — "What is Partition Projection and when is it better than standard partitioning?"
"Partition Projection tells Athena to compute partition paths mathematically from a pattern rather than looking them up in the Glue catalog. For a daily-partitioned table spanning years, that's thousands of catalog entries — every query requires a catalog lookup to find which partitions exist. With Partition Projection, Athena generates the S3 paths directly from the date range in your WHERE clause. It eliminates catalog overhead and removes the need to run MSCK REPAIR TABLE or ALTER TABLE ADD PARTITION when new data lands. I use it by default for any time-series table with predictable date-based partitioning."
Q6 — "How do you prevent a runaway Athena query from incurring large unexpected cost?"
"Workgroups with data scan limits. You configure a per-query byte limit — if a query would scan more than that amount, Athena cancels it before it completes. You can also set a workgroup-level daily scan limit so the entire team's queries stop if a threshold is crossed. Combined with IAM policies restricting which tables teams can query, this is a reasonable cost governance layer. The deeper fix is making sure every production table is properly partitioned and in Parquet, so even without limits the cost per query is low."
Q7 — "When would you choose Athena over Redshift for a query workload?"
"Athena for ad-hoc exploration, data validation, one-off analysis, and queries that run infrequently. Redshift for dashboards with many concurrent users, sub-second latency requirements, and complex analytics with lots of joins that benefit from sort keys and distribution styles. In practice they coexist: Athena is the exploration layer against the same S3 data that Redshift reads via COPY for production reporting. No need to choose — design the S3 layer well and both engines consume it."
Q8 — "Why does LIMIT not reduce query cost in Athena?"
"Because Athena scans data first, then applies LIMIT to the results. The scan cost is incurred before LIMIT is evaluated. To cheaply get a sample, use partition filters in the WHERE clause to constrain the scan, then LIMIT. For example, instead of SELECT * FROM table LIMIT 10, use SELECT * FROM table WHERE year='2026' AND month='04' LIMIT 10. The partition filter does the cost reduction work; LIMIT just reduces the result set size."
Q9 — "What is Athena Federated Query and what are its limitations?"
"Federated Query lets you join S3-based Athena tables with external data sources — RDS, DynamoDB, JDBC databases — in a single SQL statement. It works through Lambda connectors that Athena invokes to fetch data from the external source. The limitations are latency and cost: each federated source adds Lambda invocation overhead, and external databases may be slow to respond at query time. It's suited for ad-hoc enrichment queries. For high-frequency production queries that need reference data, the better pattern is to ETL that reference data into S3 so it's always in the fast path."
Q10 — "Walk me through how you'd migrate a reporting layer from querying raw CSV files to an optimised Athena setup."
"First, profile the existing queries — identify what columns are filtered on most (these become partition keys) and what columns are selected (this tells me how much column pruning is possible). Then run a CTAS to convert the CSV data to Parquet with Snappy compression, partitioned by the most-queried dimensions (typically date). Register the new table in the Glue catalog. Use Partition Projection if the partition structure is date-based and predictable. Validate query results match the original, measure cost difference (expect 60–90% reduction), then switch the reporting layer to the new table. Going forward, the ETL pipeline writes Parquet directly — the CSV table becomes read-only for historical reference."

15. Production Story Angles

These are the patterns that come up repeatedly when working with Athena at scale in a production data engineering environment.

Athena as Pipeline Validator

After a Glue ETL job writes Parquet to the processed zone, a lightweight Athena query serves as the validation step — row count check, null check on key columns, range check on values. This is fast, cheap (small scan on the just-written partition), and avoids loading bad data downstream into Redshift. 

-- Validation query run after ETL job completes
SELECT
    COUNT(*)                              AS row_count,
    SUM(CASE WHEN server_id IS NULL THEN 1 ELSE 0 END) AS null_server_ids,
    MIN(value)                            AS min_value,
    MAX(value)                            AS max_value
FROM processed_metrics
WHERE year = '2026' AND month = '04';

Ad-Hoc Exploration Before Building Pipelines

When raw data first lands in S3 — whether from a new source system or an irregular data dump — Athena is the fastest way to understand its structure and quality before committing to a schema in a data warehouse. Define an external table pointing at the raw files, run exploratory SQL, identify issues. The cost of this exploration is negligible compared to loading into Redshift and discovering problems after the fact.

Cost-Effective Historical Analysis

Historical data that is rarely queried but must be retained (compliance, audit) can live in S3 Glacier-compatible storage. When analysis is needed, Athena queries it directly without restoring to a warehouse. For data accessed a few times a year at most, this is dramatically cheaper than keeping it in Redshift.
