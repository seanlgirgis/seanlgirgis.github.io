What Flink Is For

Apache Flink is a distributed stream processing engine for low-latency, stateful computation over unbounded and bounded data. It is strongest when pipelines need event-time correctness, large keyed state, exactly-once processing, and continuous results instead of periodic batch refreshes.

In a modern data platform, Flink usually sits between ingestion systems such as Kafka or Kinesis and serving or storage systems such as Iceberg, S3, OpenSearch, Redis, or analytical warehouses. It is commonly used for enrichment, sessionization, fraud detection, CDC processing, real-time aggregates, alerting, and streaming ETL.

Flink is not just "Spark Streaming but faster." Its core abstraction is a continuously running stateful dataflow with checkpointed state, event-time timers, and restartable operators.
Do not choose Flink only because a dashboard needs fresher data. If the logic is stateless, latency tolerance is minutes, and replay cost is low, simpler batch or micro-batch systems may be cheaper to operate.

Runtime Architecture

A Flink application is compiled into a job graph of sources, transformations, shuffles, and sinks. The JobManager coordinates scheduling, checkpoints, failover, and metadata, while TaskManagers execute parallel subtasks and hold working state.

Parallelism controls how many subtasks run for each operator. Keyed streams are partitioned by key-group, which allows Flink to rescale state across different parallelism levels as long as state descriptors and serializers remain compatible.

Think in terms of operator chains and key groups. The code reads like a pipeline, but production behavior is shaped by partitions, network shuffles, state locality, and checkpoint barriers.
Changing parallelism, serializers, operator UIDs, or state names without planning can break restore from savepoints. Assign stable operator UIDs for long-lived production jobs.
env.enableCheckpointing(60000);

DataStream<Order> orders = env
    .fromSource(kafkaSource, WatermarkStrategy.noWatermarks(), "orders")
    .uid("orders-source");

orders
    .keyBy(Order::customerId)
    .process(new CustomerRiskFunction())
    .uid("customer-risk")
    .sinkTo(alertSink)
    .uid("alert-sink");

Event Time, Watermarks, and Windows

Flink separates processing time from event time. Processing time is when the job sees the record; event time is when the business event occurred. Event time is what you want for financial periods, customer sessions, IoT readings, CDC ordering, and analytics that must remain correct after retries or late arrivals.

Watermarks are Flink's estimate of event-time progress. A window can close when the watermark passes the window end, optionally allowing late records for a controlled period.

Watermarks are a correctness contract with the data. Conservative watermarks improve completeness but add latency; aggressive watermarks reduce latency but increase late-data handling.
A single idle Kafka partition can hold back watermarks for the whole downstream operator unless idleness is configured. This is a common cause of windows that appear to stop firing.

State, Checkpoints, and Savepoints

State is Flink's main differentiator. Operators can keep keyed state, operator state, timers, and accumulators that survive failures through checkpointing. Large Flink jobs often have terabytes of RocksDB-backed state and still maintain second-level processing latency when tuned carefully.

Checkpoints are automatic recovery snapshots. Savepoints are manually triggered, portable snapshots used for upgrades, migrations, and controlled rollback. Treat savepoints as part of release management, not just emergency recovery.

A reliable Flink deployment is a state management system as much as a compute system. Backup location, state backend, serializer evolution, and savepoint discipline matter as much as business code.
State TTL is not a substitute for business deletion logic unless the semantics match. TTL cleanup is lazy in many cases, so stale state may remain until touched or compacted.

Exactly-Once Semantics

Exactly-once in Flink means that after a failure and restart, the final committed result is equivalent to processing each input record once. It does not mean every external system is magically idempotent or that every downstream reader sees no intermediate state.

End-to-end exactly-once requires aligned source offsets, checkpointed operator state, and a sink that can commit transactionally or idempotently. Kafka transactions, Iceberg commits, and two-phase commit sinks are common patterns.

Exactly-once is an end-to-end property. Flink can coordinate it, but the source, sink, checkpoint storage, and deployment lifecycle must all participate.
At-least-once plus non-idempotent writes creates duplicate money, duplicate notifications, or inflated aggregates. For external side effects, design idempotency keys before writing code.

APIs and Development Model

Flink supports DataStream APIs for custom event processing, Table API and SQL for relational streaming, and connectors for common sources and sinks. Senior teams often standardize on SQL for common ETL and reserve DataStream for custom state machines, timers, or complex enrichment.

The SQL model is powerful because it makes streaming tables, changelogs, and windows declarative. The DataStream model gives more control but creates more room for lifecycle, serialization, and state compatibility mistakes.

Use the highest-level API that preserves the required semantics. SQL is easier to review and govern; DataStream is better for custom stateful behavior.
Mixing APIs is valid, but schema conversion, changelog mode, and event-time attributes must be explicit. Hidden append-versus-update assumptions cause painful sink failures.
CREATE TABLE orders (
  order_id STRING,
  customer_id STRING,
  amount DECIMAL(12,2),
  event_time TIMESTAMP(3),
  WATERMARK FOR event_time AS event_time - INTERVAL '30' SECOND
) WITH (
  'connector' = 'kafka',
  'topic' = 'orders',
  'format' = 'json'
);

Kafka and Lakehouse Integration

Kafka is the most common operational source for Flink because partitions map naturally to parallel source readers and offsets can be checkpointed. For lakehouse targets, Flink commonly writes to Apache Iceberg, Hudi, Delta Lake, or file sinks on object storage.

The main architectural decision is whether Flink owns real-time transformation and storage commits, or whether it publishes clean events for downstream warehouse ingestion. Owning commits gives lower latency and stronger control, but increases operational coupling to table format semantics.

For lakehouse pipelines, align checkpoint interval, file rolling policy, table commit frequency, and compaction strategy. Small files are a streaming tax that must be managed deliberately.
Kafka ordering is only guaranteed within a partition. If CDC or account-level ordering matters, partition by the same key used for downstream state and upsert semantics.

Operations on AWS and Kubernetes

On AWS, Flink is commonly deployed with Amazon Managed Service for Apache Flink, self-managed Kubernetes, or EMR. Managed service reduces cluster operations, while Kubernetes provides deeper control over versions, plugins, networking, autoscaling, and custom deployment workflows.

Object storage is typically used for checkpoints and savepoints, and IAM boundaries must cover source reads, sink writes, checkpoint paths, metrics, and secret access. For private networking, plan connectivity to MSK, RDS, OpenSearch, S3 endpoints, and any cross-account data targets.

The operational unit is the job, not just the cluster. Release strategy, savepoint automation, alerting, and rollback procedures should be defined per production job.
Checkpoint storage must be durable, isolated, and lifecycle-managed. Accidentally deleting checkpoint or savepoint prefixes can turn a routine restart into a full replay or data loss incident.

Performance and Backpressure

Flink performance tuning starts with backpressure. A slow sink, skewed key, undersized state backend, blocked checkpoint, or network shuffle can propagate upstream and make a healthy-looking source lag dramatically.

Important metrics include checkpoint duration, checkpoint alignment time, busy time, backpressured time, source lag, RocksDB read/write latency, garbage collection, and sink commit latency. For large state jobs, incremental checkpoints and RocksDB tuning often matter more than raw CPU.

Tuning Flink is mostly bottleneck isolation: source ingestion, network shuffle, state access, user code, serialization, checkpointing, or sink commit. Guessing usually wastes days.
Hot keys defeat parallelism. If one customer, account, device, or tenant dominates the stream, repartitioning alone will not fix the bottleneck without a salting or two-stage aggregation strategy.

Interview Q&A

Q: When would you choose Flink over Spark Structured Streaming?
A: Choose Flink when the workload is truly continuous, latency-sensitive, and heavily stateful with event-time correctness. Spark Structured Streaming is often simpler for micro-batch ETL, warehouse-centric pipelines, and teams already standardized on Spark. The deciding factors are usually state size, latency target, operational maturity, and sink semantics.
Q: What does exactly-once mean in a Flink pipeline?
A: It means the final committed output after failure recovery is equivalent to each input being processed once. Flink achieves this through checkpointed source offsets, state snapshots, and compatible sink commit protocols. It is not guaranteed if the sink performs non-idempotent side effects outside checkpoint coordination.
Q: How do watermarks affect correctness and latency?
A: Watermarks decide when Flink believes event time has advanced enough to close windows or fire timers. A conservative watermark waits longer and captures more late events, but increases output latency. An aggressive watermark lowers latency but pushes more records into late-data handling or correction paths.
Q: How would you upgrade a stateful Flink job safely?
A: Assign stable operator UIDs, trigger a savepoint, deploy the new version, and restore from that savepoint. Validate serializer compatibility, state schema changes, connector versions, and parallelism changes before rollout. Keep rollback instructions and the previous artifact available until the new job is stable.
Q: What are common causes of Flink backpressure?
A: Common causes include slow sinks, hot keys, expensive user code, slow RocksDB access, network shuffles, and checkpoint alignment delays. The right response is to identify the constrained operator from metrics, not blindly increase cluster size. Scaling helps only if the bottleneck can actually be parallelized.
Q: How do you prevent unbounded state growth?
A: Use state TTL, clear state when business sessions end, compact aggregations, and avoid storing raw event history unless required. Monitor state size per operator and per key group, not just total job memory. For regulated or customer-facing data, align cleanup logic with business retention requirements rather than relying only on lazy TTL cleanup.

Quick Reference

JobManager
Coordinates scheduling, checkpoints, failover, and job metadata.
TaskManager
Executes parallel subtasks and hosts operator state during runtime.
Parallelism
Number of subtasks for an operator; bounded by source partitions and downstream design.
Keyed state
Partitioned state scoped by key, used for counters, sessions, joins, and timers.
Checkpoint
Automatic snapshot used for failure recovery and exactly-once coordination.
Savepoint
Manual, portable state snapshot used for upgrades, migrations, and rollback.
Watermark
Event-time progress signal that controls window firing and timer execution.
Allowed lateness
Grace period for records that arrive after a window's watermark trigger.
Operator UID
Stable identifier used to map saved state back to operators during restore.
RocksDB
Common state backend for large durable keyed state with incremental checkpoints.
Backpressure
Upstream slowdown caused by a constrained downstream operator or sink.
Two-phase sink
Commit protocol that ties external writes to successful checkpoints.
Hot key
A dominant key that overloads one subtask and limits horizontal scaling.
Side output
Secondary stream for late events, errors, or records needing separate handling.
