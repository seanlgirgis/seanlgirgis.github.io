What Terraform Actually Solves

Terraform is an infrastructure as code tool that turns cloud infrastructure into versioned, reviewable, repeatable configuration. For a senior data engineer, the value is not only creating servers or buckets. The real value is making a data platform reproducible: S3 buckets, IAM roles, Glue catalogs, VPC networking, RDS databases, ECS services, EventBridge schedules, Secrets Manager entries, and monitoring policies can be described in code and promoted through environments.

Terraform is declarative. You describe the desired end state, and Terraform compares that desired state against its recorded state and the provider API. The result is an execution plan. This is different from a script that says, step by step, how to create infrastructure. Terraform works best when infrastructure ownership is clear, naming is deterministic, and state is protected like a production database.

Terraform is not just automation. It is a contract between code, state, and the cloud provider.
The fastest way to make Terraform dangerous is to treat it like a loose deployment script. If state is wrong, backend access is weak, or multiple people apply at once, the tool can delete or recreate important resources.
Use Terraform forBe careful with
Repeatable AWS environmentsOne-off manual experiments that are never imported into state
Shared platform componentsApplication deploys better handled by CI/CD or Helm
Network, IAM, storage, databasesSecrets, credentials, and generated passwords in state
Cross-cloud or vendor-neutral IaCAWS-native services where CloudFormation features arrive first

HCL Syntax and Project Structure

Terraform uses HCL, HashiCorp Configuration Language. HCL is designed to be readable configuration, not a general-purpose programming language. Blocks define things, arguments configure them, expressions compute values, and references connect resources together. A clean project usually separates provider configuration, variables, resources, outputs, and backend configuration.

terraform {
  required_version = ">= 1.6.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = var.aws_region
}

variable "aws_region" {
  type        = string
  description = "AWS region for the workload."
  default     = "us-east-1"
}

resource "aws_s3_bucket" "raw" {
  bucket = "sean-data-platform-raw-${var.environment}"

  tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

output "raw_bucket_name" {
  value = aws_s3_bucket.raw.bucket
}
Good Terraform structure makes ownership obvious: who owns the module, what variables are required, what resources are created, and what outputs downstream stacks can safely consume.
Do not overuse clever HCL. Deep nested expressions, heavy dynamic blocks, and magic naming conventions make plans hard to review and failures hard to debug.

Common file layout

FilePurpose
main.tfCore resources or module calls
providers.tfProvider versions and provider configuration
variables.tfInput variables and validation rules
outputs.tfValues exposed to humans, CI/CD, or other Terraform stacks
backend.tfRemote backend configuration
terraform.tfvarsEnvironment-specific values, never secrets

Providers, Resources, Data Sources, and Outputs

Providers are plugins that know how to talk to APIs such as AWS, GitHub, Datadog, Snowflake, or Kubernetes. Resources create and manage infrastructure. Data sources read existing infrastructure without owning it. Outputs expose selected values after apply. These four concepts are enough to model most production stacks.

data "aws_caller_identity" "current" {}

data "aws_vpc" "shared" {
  tags = {
    Name = "shared-data-vpc"
  }
}

resource "aws_security_group" "glue_jobs" {
  name        = "glue-jobs-${var.environment}"
  description = "Security group for Glue jobs"
  vpc_id      = data.aws_vpc.shared.id
}

output "account_id" {
  value = data.aws_caller_identity.current.account_id
}
Use data sources when Terraform needs to reference shared infrastructure owned somewhere else. Use resources only when this state file is responsible for the lifecycle.
If two Terraform states manage the same AWS resource, you have an ownership conflict. The result is drift, surprise changes, or destructive replacements.
ConceptCreates?Typical use
ProviderNoDefines API client and credentials
ResourceYesOwns lifecycle of infrastructure
Data sourceNoReads existing infrastructure
OutputNoPublishes selected values from the state

State: The Real Source of Truth

Terraform state maps configuration addresses to real provider objects. For example, aws_s3_bucket.raw might map to an actual S3 bucket. State contains resource IDs, dependency metadata, many attribute values, and sometimes sensitive values. Terraform uses state to decide whether a plan should create, update, replace, or delete infrastructure.

Configuration says what you want. The cloud provider says what exists. State says what Terraform believes it owns. A plan is the reconciliation between those three views.

For production Terraform, state is operational data. Back it up, lock it, restrict it, encrypt it, and treat edits as a break-glass operation.
Deleting a local terraform.tfstate file does not delete AWS resources. It deletes Terraform's memory of them, which can cause duplicate creation or destructive imports later.
# Inspect state addresses
terraform state list

# Show one tracked object
terraform state show aws_s3_bucket.raw

# Move an object after refactoring resource names
terraform state mv aws_s3_bucket.raw aws_s3_bucket.data_raw

# Remove from state without deleting the cloud resource
terraform state rm aws_s3_bucket.legacy

Remote State with S3 and DynamoDB Locking

Local state is acceptable for a solo lab. Production teams should use remote state. On AWS, the classic backend is an encrypted S3 bucket with versioning enabled, plus a DynamoDB table for state locking. S3 stores the state file. DynamoDB prevents two applies from mutating the same state at the same time.

terraform {
  backend "s3" {
    bucket         = "company-terraform-state-prod"
    key            = "data-platform/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-locks"
    encrypt        = true
  }
}
Remote state gives the team one shared memory of infrastructure. Versioned S3 gives recovery. DynamoDB locking gives concurrency control.
Do not put Terraform state in the same AWS account or bucket policy blast radius as the workload without thinking. If the workload account is compromised, state exposure can reveal infrastructure topology and sensitive attributes.
Backend optionBest forTradeoff
Local statePersonal demos and throwaway labsNo collaboration, easy to lose
S3 backendAWS teams wanting simple remote stateYou manage bucket, encryption, versioning, and lock table
Terraform CloudPolicy checks, hosted state, run historyVendor platform and pricing considerations
Consul backendHashiCorp-heavy environmentsMore operational overhead

Bootstrap pattern

The backend bucket and lock table cannot be created by the same backend they configure on the first run. Most teams use a small bootstrap stack, a separate admin script, or a manually approved foundation module.

Plan, Apply, Destroy, and State Mutation

The Terraform workflow has three core actions. terraform plan calculates proposed changes. terraform apply executes those changes and updates state. terraform destroy plans and applies deletion for resources owned by the current state. In production, the plan is the review artifact. The apply is the mutation event.

terraform init
terraform fmt -recursive
terraform validate
terraform plan -out=tfplan
terraform apply tfplan

# Dangerous: destroys resources tracked by this state
terraform destroy
The plan should be reviewed like code. For data infrastructure, look closely for replacements of stateful resources such as RDS, buckets, KMS keys, Glue catalogs, and IAM roles used by running pipelines.
A clean terraform plan does not mean the change is safe. It means Terraform can calculate the change. Provider bugs, AWS quotas, naming collisions, and runtime dependencies can still break the apply.
CommandChanges cloud?Changes state?Notes
terraform planNoNoReads state and provider APIs
terraform applyYesYesState is updated after successful operations
terraform destroyYesYesDeletes tracked resources unless protected by policy or lifecycle
terraform refreshNoYesUpdates state view from provider; use carefully

Modules for Reusable Infrastructure

Modules package resources into reusable units. A module can represent an S3 data lake bucket, an ECS service, a Glue job pattern, an RDS instance, or an entire environment slice. Good modules expose stable inputs and outputs while hiding repetitive implementation details. Bad modules hide too much, become giant abstraction walls, and make simple changes painful.

module "raw_bucket" {
  source = "./modules/s3-data-bucket"

  name        = "raw"
  environment = var.environment
  kms_key_id  = module.kms.key_id
  tags        = local.common_tags
}

module "glue_job" {
  source = "./modules/glue-python-job"

  job_name         = "ingest-customer-events"
  script_s3_path   = "s3://company-artifacts/glue/ingest.py"
  role_arn         = module.iam.glue_role_arn
  worker_type      = "G.1X"
  number_of_workers = 5
}
The best modules encode platform standards: encryption, tags, logging, network rules, naming, and least-privilege IAM.
Avoid making one universal mega-module for every workload. Large modules create tight coupling and make blast radius hard to reason about.
Module styleGood fitRisk
Small resource moduleReusable S3 bucket, IAM role, Glue jobToo many tiny wrappers with little value
Service moduleECS service, RDS cluster, data pipeline unitInputs can become huge
Environment moduleFull dev/test/prod compositionHarder to promote changes independently

Workspaces vs Separate State Files

Terraform workspaces allow one configuration directory to maintain multiple state files. They are useful for small variations, ephemeral environments, or preview stacks. For serious environment promotion, many teams prefer separate state keys, separate folders, or separate root modules per environment. Separate state files make blast radius clearer and permissions easier to control.

For data platforms, separate state files usually win for dev, test, and prod because access control and blast radius are easier to explain.
Workspaces are not a strong environment boundary. A bad variable, provider alias, or backend misconfiguration can still point a workspace at the wrong account or resource names.
ApproachProsCons
WorkspacesSimple for similar stacks and temporary environmentsWeak boundary; easy to confuse current workspace
Separate backend keysClear state split while sharing codeRequires disciplined backend config
Separate root foldersVery explicit environment ownershipCan duplicate code if modules are weak
Separate accountsStrongest AWS isolationRequires account vending and cross-account access design
# Workspace commands
terraform workspace list
terraform workspace new dev
terraform workspace select prod

# Many teams prefer explicit backend keys instead:
# dev/data-platform/terraform.tfstate
# prod/data-platform/terraform.tfstate

Importing Existing AWS Resources

Import brings existing infrastructure under Terraform state. This is common when a team has manually created S3 buckets, IAM roles, VPCs, RDS instances, or Glue resources and wants to standardize management. Import does not automatically write perfect Terraform code. You must create matching resource blocks, import the real object, run a plan, and reconcile differences until the plan is safe.

# Terraform 1.5+ import block style
import {
  to = aws_s3_bucket.raw
  id = "existing-raw-data-bucket"
}

resource "aws_s3_bucket" "raw" {
  bucket = "existing-raw-data-bucket"
}

# Then run:
terraform plan
terraform apply
Import is a migration process, not a magic scanner. The goal is to reach a no-op plan where Terraform code, state, and AWS reality agree.
Importing a production resource with incomplete configuration can cause Terraform to plan destructive changes on the next apply. Always review the first post-import plan carefully.

Practical import flow

terraform import aws_iam_role.glue_role DataPlatformGlueRole
terraform state show aws_iam_role.glue_role
# Copy important attributes into configuration
terraform plan
# Repeat until the plan is no-op or intentionally controlled

Terraform for Data Engineering Infrastructure

Terraform is especially useful for provisioning the durable infrastructure around data pipelines. In AWS, that usually includes S3 buckets for raw, curated, and artifact zones; IAM roles for Glue, ECS, Lambda, and Airflow; VPC networking for private jobs; RDS or Aurora for metadata stores; ECS services for workers; EventBridge schedules; and CloudWatch alarms.

resource "aws_glue_catalog_database" "curated" {
  name = "curated_${var.environment}"
}

resource "aws_iam_role" "glue" {
  name = "data-platform-glue-${var.environment}"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = { Service = "glue.amazonaws.com" }
      Action = "sts:AssumeRole"
    }]
  })
}

resource "aws_db_instance" "metadata" {
  identifier        = "metadata-${var.environment}"
  engine            = "postgres"
  instance_class    = "db.t4g.medium"
  allocated_storage = 100
  storage_encrypted = true
  skip_final_snapshot = false
}
Terraform should create the platform skeleton. Pipeline code, SQL transformations, and job artifacts should usually be deployed by application CI/CD, not buried inside infrastructure state.
Do not let Terraform upload large scripts, data files, or changing artifacts into S3 on every apply. That mixes infrastructure lifecycle with application release lifecycle and makes plans noisy.
Data componentTerraform should manageUsually not Terraform
S3 data lakeBuckets, encryption, lifecycle, access policiesData files and daily partitions
GlueCatalog DBs, roles, job definitions, connectionsRapid script iteration and package builds
RDSInstance, subnet group, security group, parametersSchema migrations and seed data
ECSCluster, service, task definition baseline, IAMFrequent container image promotion logic

Secrets, Sensitive Values, and State Exposure

Terraform state can contain sensitive values even when variables are marked sensitive = true. The sensitive flag hides values from CLI output, but it does not remove them from state. For production, secrets should live in AWS Secrets Manager, SSM Parameter Store, Vault, or a CI/CD secret store. Terraform can create secret containers and access policies, but it should not be the place where secret values are casually stored.

resource "aws_secretsmanager_secret" "db_password" {
  name = "data-platform/${var.environment}/metadata-db-password"
}

# Better: create the secret container and let a secure rotation process set the value.
# Avoid hardcoding secret_string in Terraform unless there is a strict reason.
Terraform can manage where secrets live and who can access them. It should rarely manage the secret payload itself.
A secret passed into Terraform can end up in state, logs, crash files, plan files, or CI artifacts. Treat plan files and state files as sensitive.
PatternRiskRecommendation
Plain variable passwordHighAvoid
sensitive = trueStill in stateUseful for output masking only
Secrets Manager container onlyLowPreferred for many teams
External rotationLowBest for production databases

Drift Detection and Remediation

Drift happens when real infrastructure changes outside Terraform. Someone edits an IAM policy in the console, changes an RDS parameter manually, deletes a security group rule, or modifies bucket encryption. Terraform detects drift during plan by reading provider APIs and comparing reality against state and configuration.

# Detect drift without applying
terraform plan -detailed-exitcode

# Exit codes:
# 0 = no changes
# 1 = error
# 2 = changes present
Drift is not always bad. Emergency fixes happen. The discipline is to reconcile the change back into code or revert it intentionally.
Blindly applying after drift detection can undo an emergency production change. Review whether the drift represents a bug, a hotfix, or an unauthorized mutation.
Drift typeExampleTypical response
Manual hotfixTemporary security group ruleConvert to code or remove after incident
Console accidentBucket policy edited incorrectlyApply Terraform to restore desired state
Provider default changeAWS default attribute differsPin provider or add explicit config
External controllerKubernetes or autoscaler changes countUse lifecycle ignore carefully

CI/CD with GitHub Actions and OIDC

Terraform should run through a controlled pipeline for shared environments. GitHub Actions can authenticate to AWS using OIDC, which avoids long-lived AWS access keys. A common pattern is: pull request runs format, validate, and plan; main branch approval runs apply. Production applies should require environment protection, code review, and sometimes a manual approval gate.

name: terraform

on:
  pull_request:
  push:
    branches: [ main ]

permissions:
  id-token: write
  contents: read

jobs:
  terraform:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-terraform-role
          aws-region: us-east-1

      - uses: hashicorp/setup-terraform@v3

      - run: terraform init
      - run: terraform fmt -check -recursive
      - run: terraform validate
      - run: terraform plan -out=tfplan

      - name: Apply
        if: github.ref == 'refs/heads/main' && github.event_name == 'push'
        run: terraform apply -auto-approve tfplan
OIDC lets GitHub request short-lived AWS credentials. That is much safer than storing an AWS access key as a repository secret.
Never run automatic production apply from every branch. Plans from untrusted pull requests can expose values through logs or abuse provider credentials if the workflow is not locked down.

Pipeline controls worth having

ControlWhy it matters
Provider lock fileKeeps provider versions reproducible
Plan artifact retention limitsPlan files can contain sensitive values
Environment approvalPrevents accidental prod mutation
Policy checksBlocks public buckets, weak IAM, missing encryption

Terraform vs CloudFormation

Terraform and CloudFormation both manage infrastructure as code, but they optimize for different realities. CloudFormation is AWS-native and often supports AWS features early. Terraform is provider-neutral, widely adopted across platforms, and has a mature module ecosystem. In AWS-only enterprises, the choice often comes down to governance, skill set, service coverage, and whether the platform needs to manage non-AWS systems in the same workflow.

Choose Terraform when the platform spans AWS plus external services, or when module reuse and cross-provider workflow matter. Choose CloudFormation when AWS-native integration, StackSets, or first-class AWS support matter more.
Do not split ownership of the same resource between Terraform and CloudFormation. One resource should have one infrastructure authority.
AreaTerraformCloudFormation
ScopeMulti-cloud and third-party providersAWS-native
LanguageHCLYAML or JSON
StateManaged by backendManaged by AWS service
Feature freshnessDepends on provider updatesOften earlier for AWS features
EcosystemStrong module registryStrong AWS-native governance

Interview Q&A

Q: What is Terraform state, and why is it risky in production?
A: State maps Terraform resource addresses to real cloud resources and stores many resource attributes. It is risky because losing it breaks ownership, corrupting it causes wrong plans, and exposing it can leak sensitive infrastructure details or secret values.
Q: How would you design Terraform state for dev, test, and prod data platform environments?
A: I would usually use separate state files, separate backend keys, and ideally separate AWS accounts. Shared modules can keep the code reusable, but state isolation keeps blast radius, IAM permissions, and promotion boundaries clear.
Q: Why use S3 plus DynamoDB for Terraform backend storage?
A: S3 provides durable, versioned, encrypted state storage. DynamoDB provides state locking so two applies do not mutate the same state at the same time. Together they solve collaboration and recovery better than local state.
Q: What should Terraform manage in a data engineering platform?
A: Terraform should manage durable infrastructure: S3 buckets, IAM roles, VPC networking, Glue resources, RDS instances, ECS services, EventBridge rules, KMS keys, and monitoring. It should not usually manage daily data files, database schema migrations, or fast-changing application artifacts.
Q: How do you handle secrets with Terraform?
A: I avoid putting secret values directly in Terraform. I let Terraform create secret containers and IAM permissions, then use Secrets Manager, SSM, Vault, or a rotation process to set the actual value. Marking a variable sensitive hides output but does not remove the value from state.
Q: When would you choose CloudFormation over Terraform?
A: I would choose CloudFormation when the organization is AWS-only, needs native AWS governance, wants StackSets, or requires immediate support for new AWS features. I would choose Terraform when cross-provider infrastructure, reusable modules, and a wider ecosystem matter more.

Quick Reference

Initializes providers, modules, and backend configuration.
terraform fmt
Formats HCL files consistently; use -recursive for modules.

Checks syntax and internal configuration validity.
terraform plan
Shows proposed changes before mutating infrastructure or state.
terraform apply
Executes the plan and updates Terraform state.
terraform destroy
Deletes resources tracked by the current state; dangerous in shared environments.
resource
A managed object Terraform creates, updates, or deletes.
data
A read-only lookup of existing infrastructure not owned by this state.
module
Reusable Terraform package with inputs, resources, and outputs.
backend
Where Terraform stores state, such as S3 or Terraform Cloud.
state lock
Concurrency guard that prevents simultaneous applies against one state file.
terraform import
Associates an existing cloud resource with a Terraform address.
state mv
Moves tracked objects when refactoring resource names or module paths.
sensitive
Masks CLI display, but values can still exist in state.
OIDC
Preferred GitHub Actions to AWS authentication pattern using short-lived credentials.
drift
Difference between Terraform configuration, state, and real infrastructure.
