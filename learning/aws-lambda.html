Lambda's Place in the AWS Data Stack

AWS Lambda is a managed, event-driven compute service. For a senior data engineer, the important idea is not simply "serverless functions." Lambda is the glue between events and action: S3 object created, SQS message available, DynamoDB stream record emitted, API Gateway request received, EventBridge schedule fired, or Kinesis shard records ready to process.

Lambda is strongest when the unit of work is short, isolated, horizontally scalable, and triggered by an event. It is weak when the workload needs long-lived compute, huge local disk, predictable low-latency startup, complex distributed processing, or heavy dependency initialization.

Key insight: Lambda is excellent for control-plane automation and lightweight data-plane processing. It should orchestrate or transform small units, not replace Spark, Flink, or a durable worker platform for every workload.
Production gotcha: teams often start with Lambda because it is easy, then accidentally build a distributed system with hidden queues, retries, partial failures, and duplicate processing. Treat Lambda pipelines as distributed systems from day one.

Event reactionS3 file arrival validates metadata and starts GlueLambda is a good fit
Light transformNormalize small JSON payload and write to SQSLambda is a good fit
Heavy ETLJoin hundreds of GB of ParquetGlue, EMR, Spark, Athena CTAS
Long workerPoll API for hoursECS Fargate, EC2, Step Functions
Low-latency APIStrict p99 under 50 msECS service, provisioned Lambda, or regional cache

Execution Model: Init, Invoke, Shutdown

A Lambda execution environment is the isolated runtime environment where your function code runs. The lifecycle has three practical phases: init, invoke, and shutdown. Understanding this lifecycle is the difference between writing toy functions and production functions that reuse resources safely.

Init phase

During init, Lambda prepares the runtime, loads extensions, imports your code, and runs top-level initialization. In Python this means module-level code executes before the handler is called. This is where you should create reusable clients such as S3, DynamoDB, Secrets Manager cache clients, database pools, or compiled regex objects.

import boto3

s3 = boto3.client("s3")
dynamodb = boto3.resource("dynamodb")
table = dynamodb.Table("etl_control")

def handler(event, context):
    # Reuses clients across warm invocations.
    return {"status": "ok", "request_id": context.aws_request_id}

Invoke phase

During invoke, Lambda passes the event and context to your handler. The same execution environment may process many invocations sequentially. Memory, temporary files in /tmp, and global variables can persist across warm invocations, but you must never rely on persistence for correctness.

Shutdown phase

Shutdown happens when AWS retires the environment because of scale-down, deployment, idle timeout, runtime update, or infrastructure maintenance. Your code usually does not control this moment. Extensions may receive shutdown signals, but application logic should assume the environment can disappear after any invocation.

Key insight: initialize expensive clients outside the handler, but keep request-specific state inside the handler. Warm reuse is a performance optimization, not a data consistency mechanism.
Production gotcha: global variables can leak data between invocations. This is especially dangerous for per-user authorization state, batch accumulators, or cached secrets with rotation requirements.

Cold Starts and Mitigation

A cold start occurs when Lambda must create a new execution environment before invoking your handler. Cold starts are caused by scale-out, new versions, idle environments being retired, runtime updates, VPC networking setup, large packages, slow dependency imports, and heavy initialization code.

Cold start time varies widely. Small Python or Node.js zip functions can start very quickly. JVM and .NET workloads, large container images, many layers, and heavy framework bootstraps can take longer. The real performance question is p95 and p99 latency under bursty traffic, not the average.

CauseImpactMitigation
Large deployment packageMore load and unpack workTrim dependencies, use smaller base images, avoid unused SDKs
Heavy init codeLonger first invocationLazy-load rarely used dependencies, cache only critical clients
JVM runtimeSlower startup but strong steady-stateUse SnapStart where supported, tune framework startup
Traffic burstMany new environments at onceProvisioned concurrency, queue buffering, reserved concurrency
VPC accessAdditional networking path complexityUse VPC only when private resources are required

Provisioned concurrency

Provisioned concurrency keeps execution environments initialized and ready. It is useful for latency-sensitive APIs, predictable traffic windows, and workloads where cold start outliers violate SLOs. The tradeoff is cost: you pay to keep capacity warm whether invocations arrive or not.

SnapStart

SnapStart reduces startup for supported runtimes by snapshotting initialized execution state and restoring it for new environments. It is valuable for Java-heavy applications, but you must design initialization carefully: anything that must be unique per environment or invocation should be generated after restore, not frozen into the snapshot.

Key insight: cold starts are not one problem. They are a blend of runtime startup, package loading, dependency initialization, VPC path, and burst scaling. Measure each before buying provisioned concurrency.
Production gotcha: provisioned concurrency reduces cold starts, but it does not fix slow handler code, downstream database latency, bad connection pooling, or overloaded dependencies.
aws lambda put-provisioned-concurrency-config \
  --function-name ingest-api \
  --qualifier prod \
  --provisioned-concurrent-executions 25

Invocation Types and Error Behavior

Lambda has three broad invocation patterns: synchronous, asynchronous, and stream or queue based. They differ most in who waits, who retries, and where failures go.

Invocation TypeExamplesRetry OwnerFailure Path
SynchronousAPI Gateway, ALB, direct SDK invokeCallerCaller receives error immediately
AsynchronousS3, SNS, EventBridgeLambda serviceRetries, then destination or DLQ
Poll basedSQS, Kinesis, DynamoDB StreamsEvent source mappingBatch retry, partial batch response, DLQ/redrive depending source

Synchronous invocation

The caller waits for the function response. If Lambda times out or throws an error, the caller sees the failure. This fits APIs, validation services, and request-response workflows. The caller must implement retry policy, timeout policy, and idempotency controls.

Asynchronous invocation

The event is accepted by Lambda and processed later. Lambda retries failed events and can route final success or failure to destinations. This fits S3 notifications, SNS fanout, and EventBridge automation.

Stream and queue invocation

Lambda polls the source, reads records in batches, and invokes your function with a batch. Failure behavior is batch-oriented unless you enable partial batch responses. For streams, ordering and shard progress matter. A poison record can block progress on a shard until handled.

Key insight: the same handler code can behave very differently depending on invocation type. Error handling belongs to the event contract, not just the try/except block.
Production gotcha: with batch sources, one bad record can cause an entire batch to retry repeatedly. Use partial batch responses and poison-pill isolation where supported.

  "FunctionName": "process-orders",
  "InvocationType": "Event",
  "Payload": "{\"order_id\":\"123\"}"

Event Sources: Push vs Pull

Lambda integrations are either push-based or pull-based. In push-based models, the source service invokes Lambda. In pull-based models, Lambda's event source mapping polls the source and invokes your function. This distinction matters for throughput, permissions, retries, and failure isolation.

SourceModelCommon Data Engineering UseMain Risk
S3PushStart ETL when a file landsDuplicate events, missing idempotency
SQSPullBuffer work and smooth spikesVisibility timeout mismatch
SNSPushFanout event notificationSubscriber failure isolation
EventBridgePushSchedules and domain eventsLoose schemas without governance
KinesisPullOrdered stream processingShard hot spots and iterator age
DynamoDB StreamsPullCDC from DynamoDB tablesPoison records blocking progress
API GatewayPushData product APIsTimeout and cold-start latency

For high-scale data systems, SQS is often the safest front door. It absorbs bursts, gives you redrive policies, supports visibility timeout control, and lets Lambda scale consumers based on backlog. S3 directly invoking Lambda is elegant, but S3 to SQS to Lambda is usually more resilient for production ETL.

Key insight: direct triggers are simple; buffered triggers are controllable. When correctness matters, insert SQS between noisy producers and Lambda consumers.
Production gotcha: S3 event notifications are at-least-once. Design object processing to be idempotent using object key, version ID, ETag, or a control table.

Concurrency, Throttling, and Backpressure

Concurrency is the number of Lambda execution environments handling requests at the same time. AWS enforces account-level concurrency limits, and each function can also have reserved concurrency and provisioned concurrency. Concurrency is the primary scaling control and also the easiest way to accidentally overload downstream systems.

Reserved concurrency

Reserved concurrency guarantees capacity for a function and caps its maximum concurrency. This is both a protection and a throttle. For example, you can cap a database-writing Lambda at 20 concurrent invocations to avoid exhausting database connections.

Provisioned concurrency

Provisioned concurrency pre-initializes environments for latency-sensitive workloads. It addresses startup latency, not downstream capacity.

Throttling behavior

When concurrency is exhausted, synchronous callers receive throttling errors. Asynchronous events are retried by Lambda. SQS events remain in the queue and are retried after visibility timeout. Stream consumers may fall behind, increasing iterator age.

ControlWhat It DoesBest Use
Account limitMaximum regional concurrency poolGlobal safety boundary
Reserved concurrencyGuarantees and caps one functionProtect critical functions or fragile databases
Provisioned concurrencyKeeps environments warmLatency-sensitive APIs
SQS max concurrencyLimits event source mapping scaleBackpressure for queue consumers
Key insight: concurrency is not just Lambda scaling. It is also downstream load generation. A Lambda function can scale faster than your RDS database, vendor API, or OpenSearch cluster can tolerate.
Production gotcha: increasing memory or timeout does not fix throttling. Throttling is usually a concurrency quota, reserved concurrency, event source mapping, or downstream protection issue.
aws lambda put-function-concurrency \
  --function-name write-to-rds \
  --reserved-concurrent-executions 20

Memory, CPU, Timeout, and Cost Math

Lambda charges are driven by requests and duration multiplied by allocated memory. Memory also controls CPU share and network throughput. This coupling is important: increasing memory can make a function faster enough that total cost stays flat or even drops.

The practical tuning method is to test memory sizes against real events and compare duration, p95 latency, and cost per invocation. For CPU-bound transforms, more memory often reduces runtime. For IO-bound functions waiting on S3, DynamoDB, or APIs, memory may not help much.

SettingTradeoffData Engineering Angle
MemoryHigher cost per ms, more CPU/networkUseful for compression, JSON parsing, Parquet metadata, encryption
TimeoutLonger max runtime, slower failure detectionMust align with SQS visibility timeout and API Gateway limits
Ephemeral storageMore local scratch spaceUseful for temp files, decompression, small file staging
Batch sizeMore throughput, bigger retry blast radiusCritical for SQS, Kinesis, DynamoDB Streams
# Rough cost intuition:
# cost ~= invocations * duration_seconds * memory_GB * price_per_GB_second
# plus request charges and any provisioned concurrency charges.
Key insight: right-sizing Lambda is empirical. Benchmark with production-like payloads, not synthetic hello-world events.
Production gotcha: for SQS, the visibility timeout should be longer than the Lambda timeout. Otherwise the same message can become visible and be processed twice while the first invocation is still running.

Packaging: Zip, Layers, and Container Images

Lambda supports zip deployments, layers, and container images. The packaging choice affects startup time, dependency management, deployment size, security scanning, and developer workflow.

PackagingBest ForTradeoff
ZipSmall functions, fast deploys, simple dependenciesPackage size discipline required
LayersShared libraries, common utilities, agentsVersion pinning and dependency drift
Container imageLarge dependencies, custom runtimes, ML librariesImage hygiene, slower build/deploy loop, ECR management

Layers are useful for shared libraries, observability agents, or organization-wide helper packages. Pin layer versions explicitly. A layer update does not automatically mean all functions are safely compatible. Treat layers like shared production libraries with semantic versioning and release notes.

Container images can be up to 10 GB and are useful when the dependency tree is awkward for zip deployment. They do not turn Lambda into ECS. The same Lambda lifecycle, timeout, event model, and concurrency behavior still apply.

Key insight: choose container images for dependency complexity, not because the workload is container-shaped. If you need long-running workers or daemon processes, use ECS or EC2.
Production gotcha: using the latest image tag for Lambda deployments makes rollbacks and audits painful. Use immutable tags or image digests.
FROM public.ecr.aws/lambda/python:3.12

COPY requirements.txt .
RUN pip install -r requirements.txt --target "${LAMBDA_TASK_ROOT}"

COPY app.py ${LAMBDA_TASK_ROOT}

CMD ["app.handler"]

VPC Networking and Private Access

Lambda does not need a VPC to access public AWS service endpoints such as S3, DynamoDB, or public APIs. Lambda needs VPC access when it must reach private resources: RDS in private subnets, ElastiCache, internal NLBs, private OpenSearch domains, or services reachable only through private networking.

When attached to a VPC, Lambda uses elastic network interfaces behind the scenes to connect to selected subnets and security groups. Modern Lambda networking is much better than the old painful ENI cold-start days, but VPC design still affects routing, NAT cost, DNS, and security.

NeedRecommended PatternWhy
Access S3 privatelyS3 Gateway EndpointAvoid NAT data charges and keep traffic on AWS network
Access Secrets ManagerInterface EndpointPrivate API access from VPC subnets
Access RDSLambda in private subnetsSecurity group to database security group
Access internet APIPublic Lambda or private subnet plus NATVPC Lambda in private subnet needs outbound route
Key insight: do not put Lambda in a VPC by default. Put it in a VPC only when it needs private network reachability, then design endpoints and NAT deliberately.
Production gotcha: a Lambda in a private subnet without NAT or VPC endpoints cannot reach public AWS APIs or the public internet. This often breaks calls to Secrets Manager, STS, or third-party APIs.
{
  "Effect": "Allow",
  "Action": [
    "ec2:CreateNetworkInterface",
    "ec2:DescribeNetworkInterfaces",
    "ec2:DeleteNetworkInterface"
  ],
  "Resource": "*"
}

Destinations, DLQs, and Failure Routing

Failure handling in Lambda should be explicit. Asynchronous invocations can use destinations to route successful or failed events to SQS, SNS, EventBridge, or another Lambda. Older DLQ patterns route failed async events to SQS or SNS. For SQS event sources, the queue's redrive policy controls movement to a dead-letter queue after receive attempts are exhausted.

Destinations are richer than DLQs because they include execution context, response information, and failure details. DLQs are still simple and valuable where a queue-based replay workflow is preferred.

MechanismApplies ToBest Use
Lambda destinationAsync invokeRoute success/failure to EventBridge or SQS
Lambda DLQAsync invokeSimple failure capture
SQS redrive policySQS source queuePoison messages after max receives
Partial batch responseSQS and some streamsRetry only failed records
Key insight: design a replay path before production. A DLQ without an operator workflow is just a graveyard with better branding.
Production gotcha: sending failures to another Lambda can create recursive failure loops if the failure handler itself throws errors or writes back to the same source.
aws lambda update-function-event-invoke-config \
  --function-name enrich-file-event \
  --maximum-retry-attempts 2 \
  --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:us-east-1:123456789012:lambda-failures"}}'

Lambda and S3 Event-Driven ETL

A common pattern is S3 event notification to Lambda: a file lands in raw storage, Lambda validates the object, records metadata, and starts the next step. This is powerful for low-latency ingestion, but it needs guardrails.

For production data platforms, the robust version is often S3 to EventBridge or S3 to SQS to Lambda. The queue provides buffering, retry visibility, redrive, and controlled concurrency. Lambda should not perform a huge transformation directly if the file is large. It should trigger Glue, Step Functions, ECS run-task, Athena CTAS, or a streaming workflow.

def handler(event, context):
    for record in event["Records"]:
        bucket = record["s3"]["bucket"]["name"]
        key = record["s3"]["object"]["key"]
        etag = record["s3"]["object"].get("eTag")

        # Idempotency key example:
        # bucket + key + etag or bucket + key + version_id
        start_glue_job(bucket, key, etag)
StepLambda ResponsibilityWhat Not To Do
ValidateCheck prefix, size, extension, manifestRead a 20 GB object into memory
RegisterWrite control row to DynamoDB or RDSAssume S3 event is unique
TriggerStart Glue, Step Functions, or ECS taskRun a full Spark-like ETL inside Lambda
NotifyPublish status eventHide failure without DLQ or destination
Key insight: Lambda is often the event router in S3 ETL, not the ETL engine. Keep it small, idempotent, and observable.
Production gotcha: S3 multipart uploads, object overwrites, retries, and duplicate notifications can all create repeated events. Use idempotency keys and control tables.

Lambda for Data Engineering Workloads

Lambda is useful in data engineering when the work is small and event-driven: CDC fanout, schema validation, metadata enrichment, API backends for data products, scheduled control tasks, and file-arrival orchestration.

Trigger-based CDC

DynamoDB Streams to Lambda can publish change events to EventBridge, SQS, OpenSearch, or downstream services. This is not a free lunch: ordering, retries, poison records, and idempotency must be designed. For relational CDC, Lambda is often downstream of DMS, Kinesis, MSK, or SQS rather than reading database logs directly.

Lightweight transformation

Lambda can normalize JSON, validate schemas, enrich events with small reference data, write compact records to Firehose, or call a model endpoint. It should not do unbounded joins, repartitioning, or memory-heavy analytics.

Data product APIs

API Gateway plus Lambda is a strong pattern for internal metadata APIs, ML inference wrappers, feature lookup endpoints, and pipeline trigger APIs. Add caching, authentication, throttling, and downstream timeouts deliberately.

Key insight: Lambda is great at edges: event edge, API edge, orchestration edge, validation edge. The closer you get to heavy stateful compute, the more you should consider another service.
Production gotcha: database-backed Lambda APIs can create connection storms. Use RDS Proxy, reserved concurrency, pooling discipline, or move to ECS for high steady traffic.
# Example: return partial batch failures for SQS
def handler(event, context):
    failures = []
    for record in event["Records"]:
        try:
            process_message(record)
        except Exception:
            failures.append({"itemIdentifier": record["messageId"]})
    return {"batchItemFailures": failures}

Lambda vs Fargate, Glue, and EC2

Choosing Lambda is an architectural decision. Compare it against ECS Fargate, AWS Glue, and EC2 based on runtime duration, dependency complexity, scaling profile, operational control, and cost shape.

ServiceBest ForWhen Lambda Loses
LambdaShort event-driven tasks, APIs, orchestrationLong jobs, heavy state, large local processing
ECS FargateContainers, workers, APIs, batch tasksWhen event volume is tiny and sporadic
GlueSpark ETL, catalog-aware data lake processingSmall instant reactions and simple routing
EC2Maximum control, custom runtimes, high steady usageWhen operations overhead outweighs control
Step FunctionsWorkflow orchestration and retriesSingle small task with no workflow state

A strong pattern is to combine services: Lambda receives the event, Step Functions manages state, Glue performs distributed ETL, ECS handles custom containers, and EventBridge publishes domain events. Lambda is not the entire platform; it is one compute primitive in a larger design.

Key insight: senior architecture is not "Lambda or Glue." It is often "Lambda triggers Step Functions, Step Functions starts Glue, and failures route to EventBridge and SQS."
Production gotcha: forcing Lambda to handle long-running data jobs usually creates timeout workarounds, recursive invocations, fragile checkpoints, and painful replay logic.

Observability, Security, and Production Design

Production Lambda functions need structured logs, metrics, tracing, alarms, deployment safety, least-privilege IAM, and repeatable infrastructure. CloudWatch Logs alone is not enough. Track invocations, errors, duration, throttles, concurrent executions, iterator age, DLQ depth, async event age, and downstream dependency errors.

Structured logging

Log JSON with request IDs, correlation IDs, event source, object key, message ID, retry attempt, and business identifiers. Do not log secrets or full payloads blindly.

Security

Use least-privilege IAM roles, encrypt environment variables, prefer Secrets Manager or Parameter Store for sensitive values, pin runtime versions, scan dependencies, and isolate functions by responsibility. The execution role should grant exactly what the function needs, not broad administrator access.

Deployment safety

Use versions and aliases for production. Shift traffic gradually with CodeDeploy when downtime or error spikes matter. Keep infrastructure in Terraform, CloudFormation, CDK, or SAM so event sources and permissions are reproducible.

{
  "level": "INFO",
  "service": "s3-file-router",
  "correlation_id": "01HVZ...",
  "bucket": "raw-zone",
  "key": "orders/date=2026-04-25/file.json",
  "action": "start_glue_job",
  "status": "submitted"
}
Key insight: the operational unit is not just the function. It is function plus trigger plus permissions plus retries plus DLQ plus alarms plus replay process.
Production gotcha: Lambda permissions are split across execution role permissions and resource-based invoke permissions. A function can have S3 permissions but still not be invokable by S3 unless the resource policy allows it.

Interview Q&A

Q: Explain the Lambda execution lifecycle and how it affects performance.
A: Lambda creates an execution environment, runs init code, invokes the handler, and eventually shuts the environment down. Expensive clients should be initialized outside the handler for warm reuse, but request-specific state must stay inside the handler. Cold starts happen when a new environment is needed, so package size, runtime choice, VPC setup, and init logic all affect latency.
Q: How would you design an S3-triggered ETL pipeline with Lambda safely?
A: I would avoid doing heavy ETL inside Lambda. S3 events should route to SQS or EventBridge, Lambda should validate and register the object, then start Glue, Step Functions, ECS, or Athena. I would add idempotency using bucket, key, version or ETag, and route failures to a DLQ or destination with a replay process.
Q: What is the difference between reserved concurrency and provisioned concurrency?
A: Reserved concurrency guarantees and caps the concurrency for a function, which protects both the function and downstream dependencies. Provisioned concurrency keeps environments initialized to reduce cold-start latency. Reserved concurrency is mainly a capacity and safety control; provisioned concurrency is mainly a latency control.
Q: Why can Lambda be dangerous in front of a relational database?
A: Lambda can scale very quickly, and each execution environment may open database connections. Without reserved concurrency, RDS Proxy, pooling discipline, and timeout controls, a traffic spike can exhaust database connections. The application may look serverless, but the database is not infinitely scalable.
Q: How do error semantics differ between API Gateway, S3, SQS, and Kinesis triggers?
A: API Gateway is synchronous, so the caller receives the error and owns retries. S3 invokes asynchronously, so Lambda retries and can use destinations or DLQ. SQS is poll-based; messages return to the queue after visibility timeout and can redrive to a DLQ. Kinesis is stream-based, so failed batches can block shard progress and increase iterator age unless failure handling is designed carefully.
Q: When would you choose ECS Fargate or Glue instead of Lambda?
A: I would choose ECS Fargate for long-running workers, container-native services, steady APIs, or custom runtimes. I would choose Glue for distributed Spark ETL, data lake transformations, catalog integration, and large file processing. Lambda is best for short event-driven orchestration, validation, and lightweight transforms.
