1. What Lambda Actually Is

AWS Lambda is a serverless compute service that runs your code in response to events without requiring you to provision or manage servers. You upload a function — a single handler in Python, Node.js, Java, Go, Ruby, or a custom runtime — and AWS handles everything else: execution environment provisioning, scaling, patching, and billing. You pay only for the compute time consumed, measured in 1ms increments.

Lambda's value is not raw compute performance — it's operational simplicity combined with infinite auto-scaling. A Lambda function that handles 1 invocation per day and one that handles 100,000 concurrent invocations require the same operational effort to deploy and maintain. For data engineers, Lambda fills a specific niche: short-lived, event-driven operations that sit between storage events and processing pipelines. Triggering a Glue job when a file lands in S3, registering new Athena partitions after an ETL run completes, sending a Slack notification on pipeline failure, or validating an incoming schema before it reaches a database — these are Lambda's natural domain.

Positioning Lambda against alternatives: compared to ECS/Fargate tasks, Lambda has a 15-minute execution limit and 10 GB ephemeral storage ceiling but zero cluster management overhead. For tasks that complete in under 15 minutes and don't need persistent state, Lambda wins on simplicity. Compared to Glue Python Shell jobs, Lambda has lower startup latency but no native Spark or DynamicFrame support. Compared to Step Functions tasks, Lambda is the execution unit — Step Functions orchestrates Lambda invocations rather than replacing them. In event-driven data pipelines, Lambda and Step Functions are complementary, not competing.

Lambda is not a general-purpose compute platform. It excels at: short, stateless, event-triggered operations. When a task needs more than 15 minutes, persistent network connections, large local disk, or GPU compute — choose ECS, Fargate, EMR, or Glue instead.

2. Execution Model & Lifecycle

Understanding Lambda's execution model is essential for writing correct, performant functions and avoiding subtle bugs around state, connections, and initialization.

Execution Environment

When Lambda receives an invocation, it provisions an execution environment — an isolated micro-VM (using AWS Firecracker) with your function code, runtime, and configured memory. The environment has a fixed amount of memory (128 MB to 10 GB, configurable), a proportional CPU allocation (CPU scales linearly with memory — 1,769 MB gets you one full vCPU), and up to 10 GB of ephemeral local storage at /tmp.

Init, Invoke, Shutdown Phases

The execution environment lifecycle has three phases:

  • Init phase: Lambda downloads your code, starts the runtime, and runs code outside the handler function — module-level imports, SDK client initialization, database connection setup. This runs once per environment creation, not once per invocation.
  • Invoke phase: Lambda calls your handler function with the event and context objects. This is the billable compute time.
  • Shutdown phase: After a period of inactivity, Lambda freezes and eventually terminates the execution environment. Any state stored in memory is lost.
import boto3
import json

# INIT phase — runs once when the environment is created
# Expensive initialization here: SDK clients, DB connections, loaded config
s3_client = boto3.client('s3')
BUCKET_NAME = 'my-processed-bucket'

def lambda_handler(event, context):
    # INVOKE phase — runs on every invocation
    # s3_client is already initialized — no re-initialization cost
    records = event.get('Records', [])

    for record in records:
        key = record['s3']['object']['key']
        process_object(key)

    return {'statusCode': 200, 'body': json.dumps('OK')}

def process_object(key):
    obj = s3_client.get_object(Bucket=BUCKET_NAME, Key=key)
    # ... process ...

Environment Reuse

After a successful invocation, Lambda keeps the execution environment warm for a period (typically minutes to tens of minutes — exact duration is not guaranteed or published). Subsequent invocations reuse the same environment: module-level code is not re-executed, the /tmp directory retains files from previous invocations, and SDK clients remain initialized. This reuse is a performance optimization (eliminates init cost) but is also a source of subtle bugs when functions assume a clean state on every invocation.

Never assume a clean environment between invocations: Global variables mutated in one invocation persist into the next on the same environment. Temporary files written to /tmp survive across invocations. If your function writes to /tmp and assumes the directory is empty at startup, a warm invocation will see files from the previous run. Always check for and clean up state that must not persist.
import os, glob

def lambda_handler(event, context):
    # Clean up /tmp from potential previous warm invocations
    for f in glob.glob('/tmp/*.csv'):
        os.remove(f)

    # Now safe to write fresh files
    output_path = '/tmp/output.csv'
    # ...

3. Cold Starts — Causes & Mitigations

A cold start occurs when Lambda must create a new execution environment before invoking your function. The cold start duration is the time to: provision the micro-VM, download and unpack the deployment package (or pull the container image), initialize the runtime, and run your init-phase code. Cold start latency ranges from ~100ms for lightweight Python functions with minimal dependencies, to several seconds for Java functions with large JARs or container images with heavy dependencies.

What Causes Cold Starts

  • First invocation ever — no environment exists yet
  • Scaling out — concurrent invocations exceed the number of warm environments; new environments are created for the excess
  • Code or configuration deployment — new deployments invalidate all existing environments
  • Inactivity — environments not invoked for ~15–20 minutes (varies) are frozen and eventually terminated
  • VPC attachment changes — historically a major cold start source; significantly improved since 2019 with the Hyperplane ENI model, but VPC functions still have slightly higher cold starts

Mitigation Strategies

1. Minimize deployment package size. Lambda downloads your package before initialization. A 10 MB zip cold-starts faster than a 250 MB zip. Remove unused dependencies, use Lambda Layers to cache shared libraries, and avoid bundling test frameworks into production packages.

2. Move expensive init out of the handler. SDK client initialization, loading config from SSM Parameter Store, and establishing DB connections should all happen at module level (init phase), not inside the handler. Each cold start pays the init cost once; each warm invocation reuses the result.

3. Provisioned Concurrency. Pre-warms a configurable number of execution environments and keeps them perpetually initialized. Invocations hitting provisioned environments never experience cold starts. Billed continuously (not per-invocation), so only cost-effective for latency-sensitive functions with predictable concurrency patterns.

# Enable Provisioned Concurrency on a function version/alias via boto3
lambda_client = boto3.client('lambda')

lambda_client.put_provisioned_concurrency_config(
    FunctionName='my-api-function',
    Qualifier='prod',           # alias or version
    ProvisionedConcurrentExecutions=10
)

4. Use Python or Node.js for latency-sensitive functions. Java and .NET have JVM/CLR startup overhead that adds hundreds of milliseconds to cold start time regardless of function logic. Python and Node.js cold starts are typically under 300ms for reasonably-sized packages. For Java/JVM workloads where Lambda is still needed, GraalVM native image (via custom runtime) can eliminate JVM startup overhead.

For data pipeline event triggers (start a Glue job, register a partition, send a notification), cold start latency usually doesn't matter — a 1-second cold start on a function that then triggers a 10-minute Glue job is irrelevant. Provisioned Concurrency makes sense for customer-facing synchronous APIs, not internal pipeline orchestration.

5. Invocation Types — Sync vs Async

Lambda functions can be invoked in two fundamental modes: synchronous and asynchronous. The invocation type determines error handling behavior, retry logic, and how the caller interacts with the result.

Synchronous Invocation

The caller waits for the function to complete and receives the response directly. API Gateway, ALB, and direct SDK invocations with InvocationType='RequestResponse' are synchronous. Error handling is the caller's responsibility — if the function returns an error, the caller must decide whether to retry.

import boto3, json

lambda_client = boto3.client('lambda')

# Synchronous invocation — waits for result
response = lambda_client.invoke(
    FunctionName='my-validator-function',
    InvocationType='RequestResponse',
    Payload=json.dumps({'key': 'value'})
)

result = json.loads(response['Payload'].read())
print(result)

Asynchronous Invocation

The caller hands the event to Lambda's internal event queue and returns immediately (HTTP 202). Lambda processes the event from the queue, independent of the caller. If the function fails, Lambda automatically retries up to 2 times (3 total attempts) with delays between retries. After exhausting retries, the event is sent to a Dead Letter Queue (DLQ) or an EventBridge failure destination if configured. S3, SNS, and EventBridge all use asynchronous invocation.

# Asynchronous invocation — returns immediately
response = lambda_client.invoke(
    FunctionName='my-pipeline-trigger',
    InvocationType='Event',             # async
    Payload=json.dumps({'date': '2026-04-13'})
)
# response['StatusCode'] == 202 means Lambda accepted the event
# Function executes independently; no result returned to caller
For async invocations, always configure a DLQ (SQS queue) or an on-failure EventBridge destination. Without a DLQ, events that fail all retry attempts are silently dropped — there is no record of the failure beyond CloudWatch logs. A DLQ gives you a durable record of failed events and the ability to replay them.

Event Source Mapping (Streaming)

For SQS, Kinesis, and DynamoDB Streams, Lambda manages an internal poller (the Event Source Mapping). Lambda reads batches from the source and invokes your function with a batch of records. For streaming sources (Kinesis, DynamoDB Streams), a function failure blocks further processing of that shard until the batch succeeds or expires — records are processed in order. For SQS, failed batches return to the queue and are retried according to the queue's visibility timeout and redrive policy.

6. Concurrency — Reserved, Provisioned, Burst

Lambda concurrency is the number of function instances executing simultaneously. Understanding how concurrency is allocated, limited, and burst-scaled is essential for designing reliable event-driven systems.

Account-Level Concurrency

Every AWS account has a regional concurrency limit (default 1,000 concurrent executions, can be raised via support). All Lambda functions in the region share this pool. A single function that scales to 1,000 concurrent executions can starve all other functions in the account. This is the primary reason to set reserved concurrency on critical functions.

Reserved Concurrency

Reserving concurrency on a function guarantees that function a dedicated slice of the account pool, and simultaneously caps it at that level. A function with reserved_concurrency=50 will always have 50 available slots and can never exceed 50 simultaneous invocations. Requests exceeding the cap are throttled (synchronous) or queued (asynchronous). Use reserved concurrency to: protect downstream systems from Lambda-driven overload, isolate critical functions from noisy neighbors, and cap cost for functions with unpredictable invocation patterns.

# Set reserved concurrency via boto3
lambda_client.put_function_concurrency(
    FunctionName='my-db-writer',
    ReservedConcurrentExecutions=20   # cap at 20 simultaneous executions
)

# Remove reserved concurrency (function shares account pool)
lambda_client.delete_function_concurrency(
    FunctionName='my-db-writer'
)

Provisioned Concurrency

Provisioned concurrency pre-initializes a set number of execution environments and keeps them perpetually warm. Unlike reserved concurrency (which caps), provisioned concurrency is a floor guarantee on warm environments. Provisioned instances are always available with zero cold start, billing continuously at a separate (lower) rate for the initialized capacity. Suitable for user-facing functions with strict latency SLAs.

Burst Concurrency

When traffic scales rapidly, Lambda can burst beyond initial concurrency limits at a defined rate: initially 500–3,000 concurrent executions immediately (varies by region), then adding 500 per minute until the account limit is reached. Burst limits exist to prevent runaway scaling from consuming all account concurrency in seconds. For predictably high-concurrency workloads, request a concurrency limit increase in advance rather than discovering the burst ceiling under load.

Concurrency TypePurposeCost
Unreserved (default)Shared account pool; no guaranteePer-invocation only

7. Handler Patterns & Best Practices

Writing maintainable, testable Lambda functions requires deliberate handler design. The handler function should be thin — a routing and coordination layer — with the actual logic extracted into separately testable modules.

Thin Handler Pattern

# handler.py — thin entry point
import json
from processor import process_s3_event
from utils import setup_logging

logger = setup_logging()

def lambda_handler(event, context):
    logger.info("Invocation started", extra={"event_source": event.get("source")})

    try:
        result = process_s3_event(event)
        return {"statusCode": 200, "body": json.dumps(result)}
    except ValueError as e:
        logger.error("Validation error", extra={"error": str(e)})
        return {"statusCode": 400, "body": json.dumps({"error": str(e)})}
    except Exception as e:
        logger.exception("Unexpected error")
        raise   # re-raise for async retry / DLQ routing

Context Object

The context object provides runtime metadata about the invocation: context.function_name, context.aws_request_id (unique per invocation — include in logs for traceability), context.get_remaining_time_in_millis() (useful for graceful shutdown before timeout), and context.memory_limit_in_mb.

def lambda_handler(event, context):
    request_id = context.aws_request_id
    remaining_ms = context.get_remaining_time_in_millis()

    if remaining_ms < 5000:
        # Less than 5 seconds remaining — abort gracefully
        logger.warning("Insufficient time remaining", extra={
            "request_id": request_id,
            "remaining_ms": remaining_ms
        })
        return {"statusCode": 408, "body": "Timeout imminent"}

    # ... normal processing ...

Environment Variables

Use environment variables for configuration that varies between environments (dev/staging/prod): bucket names, table names, API endpoints, feature flags. Never hardcode ARNs or resource names in function code. For secrets (passwords, API keys), retrieve from AWS Secrets Manager or SSM Parameter Store at init time and cache in a module-level variable — do not pass secrets as plain environment variables where they appear in CloudWatch logs and console.

import os, boto3, json
from functools import lru_cache

@lru_cache(maxsize=1)
def get_db_password():
    """Fetch secret once per execution environment, cache thereafter."""
    client = boto3.client('secretsmanager')
    secret = client.get_secret_value(SecretId=os.environ['DB_SECRET_ARN'])
    return json.loads(secret['SecretString'])['password']

# Called at init time — cached on warm reuse
DB_PASSWORD = get_db_password()

8. Layers, Packages & Container Images

Lambda supports three deployment models: zip packages, Lambda Layers, and container images. Choosing the right model depends on dependency size, sharing requirements, and team workflow.

Zip Deployment Packages

The default and simplest model. You bundle your function code and dependencies into a zip file (up to 50 MB compressed / 250 MB uncompressed). For Python, this means running pip install -r requirements.txt -t ./package, copying your code in, and zipping. Simple, fast to iterate on, but the 250 MB limit is hit quickly by data science or ML libraries.

# Package a Python Lambda function
mkdir -p package
pip install -r requirements.txt -t package/
cp handler.py processor.py utils.py package/
cd package && zip -r ../function.zip . && cd ..

# Deploy
aws lambda update-function-code \
  --function-name my-function \
  --zip-file fileb://function.zip

Lambda Layers

Layers are versioned archives of shared code or dependencies that can be attached to multiple Lambda functions. A function can have up to 5 layers. Layer contents are extracted to /opt/ in the execution environment. Common use: shared utility libraries used across many functions, large third-party packages (pandas, numpy) stored once as a layer rather than bundled into every function zip.

# Create a layer containing pandas + pyarrow
mkdir python
pip install pandas pyarrow -t python/
zip -r pandas_layer.zip python/

aws lambda publish-layer-version \
  --layer-name pandas-pyarrow \
  --zip-file fileb://pandas_layer.zip \
  --compatible-runtimes python3.12

Container Images

Container images (up to 10 GB) are the right choice for functions with large dependencies (ML models, heavy data processing libraries), functions that need custom system packages, or teams that want a unified container-based deployment workflow. Lambda pulls the image from ECR. Cold start is higher for large images — minimize image size with multi-stage builds and slim base images.

# Dockerfile for a Lambda container image
FROM public.ecr.aws/lambda/python:3.12

COPY requirements.txt .
RUN pip install -r requirements.txt --no-cache-dir

COPY handler.py processor.py ./

CMD ["handler.lambda_handler"]
Container image cold starts: Lambda caches container images at the infrastructure level, so cold starts for previously-invoked images are faster than the first pull. However, a 2 GB container image will always have a noticeably higher cold start than a 5 MB zip package. Use Provisioned Concurrency if deploying large container images in latency-sensitive contexts.

9. Lambda + S3 Event Pipelines

The Lambda + S3 combination is one of the most common patterns in data engineering: a file lands in an S3 bucket, an S3 event notification triggers a Lambda function, and the function either processes the file directly or orchestrates downstream processing (Glue job, Step Functions, SNS notification). This pattern enables event-driven pipelines that respond to data arrival without polling.

# S3 trigger Lambda — triggers a Glue job when a new file lands
import boto3, os, urllib.parse, logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)

glue = boto3.client('glue')
GLUE_JOB_NAME = os.environ['GLUE_JOB_NAME']

def lambda_handler(event, context):
    for record in event['Records']:
        bucket = record['s3']['bucket']['name']
        key = urllib.parse.unquote_plus(record['s3']['object']['key'])

        logger.info(f"New file detected: s3://{bucket}/{key}")

        # Derive processing date from key path (year=2026/month=04/day=13/...)
        parts = {p.split('=')[0]: p.split('=')[1]
                 for p in key.split('/') if '=' in p}

        response = glue.start_job_run(
            JobName=GLUE_JOB_NAME,
            Arguments={
                '--input_path': f's3://{bucket}/{key}',
                '--processing_date': f"{parts.get('year','')}-{parts.get('month','')}-{parts.get('day','')}",
            }
        )
        logger.info(f"Started Glue job run: {response['JobRunId']}")

    return {'statusCode': 200}

S3 Event Notification Configuration

S3 event notifications can be configured to filter by prefix and suffix, ensuring Lambda is only triggered for relevant files. This is important — without prefix filtering, every object created in a bucket (including temp files, .crc files, or output from the Lambda itself) triggers an invocation, potentially causing runaway recursive invocations.

Recursive invocation trap: If your Lambda function writes output back to the same S3 bucket it's triggered from, and you don't use prefix/suffix filtering to distinguish input from output paths, each Lambda output file triggers a new Lambda invocation — creating an infinite recursive loop that runs until the concurrency limit is hit and generates significant unexpected cost. Always use prefix filters to ensure triggers only fire on input paths.
# EventBridge rule as an alternative to S3 notifications
# (More flexible filtering, better audit trail)
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": { "name": ["my-raw-bucket"] },
    "object": { "key": [{ "prefix": "raw/events/" }] }
  }
}

10. Lambda + SQS / SNS / EventBridge

SQS, SNS, and EventBridge are the three core messaging services that integrate with Lambda for decoupled, resilient event-driven architectures. Each has a distinct delivery model and failure behavior.

Lambda + SQS

Lambda polls the SQS queue via an Event Source Mapping. Lambda reads batches of messages (configurable batch size 1–10,000 for Standard queues) and invokes your function with the batch. If processing succeeds, Lambda deletes the messages from the queue. If processing fails (function throws an exception), the messages return to the queue after the visibility timeout and are retried. A Dead Letter Queue (DLQ) on the SQS queue captures messages that exhaust their retry count.

def lambda_handler(event, context):
    failed_message_ids = []

    for record in event['Records']:
        message_id = record['messageId']
        body = json.loads(record['body'])

        try:
            process_message(body)
        except Exception as e:
            logger.error(f"Failed to process {message_id}: {e}")
            failed_message_ids.append(message_id)

    # Partial batch response — only failed messages return to queue
    # Requires: FunctionResponseTypes=['ReportBatchItemFailures'] on ESM
    if failed_message_ids:
        return {
            "batchItemFailures": [
                {"itemIdentifier": mid} for mid in failed_message_ids
            ]
        }
Use partial batch responses (ReportBatchItemFailures) for SQS event source mappings. Without it, a single failed message in a batch of 100 causes all 100 messages to return to the queue and be retried — most of them successfully processed but now re-processed again. Partial batch responses mark only the failed messages for retry.

Lambda + SNS

SNS pushes notifications directly to Lambda asynchronously. SNS fan-out (one topic, multiple Lambda subscriptions) is useful for broadcasting an event to multiple independent processors in parallel — e.g., an order event triggers both an inventory-update Lambda and an analytics-write Lambda simultaneously without either knowing about the other.

Lambda + EventBridge

EventBridge is the most flexible routing layer. Rules match events by source, detail-type, and field-level patterns and route to one or more Lambda targets. Scheduled rules (cron or rate expressions) replace CloudWatch Events for time-based Lambda invocations. EventBridge Pipes connect a source (SQS, Kinesis, DynamoDB Streams) to a Lambda target with optional filtering and enrichment steps, reducing boilerplate polling code.

11. VPC, Networking & RDS Access

By default, Lambda functions run outside any VPC — they have access to the internet and all public AWS endpoints but cannot reach resources in a private VPC subnet (RDS instances, ElastiCache clusters, internal services). To reach VPC-private resources, you attach the Lambda function to a VPC by specifying subnets and security groups.

VPC Attachment Model (Hyperplane)

Since 2019, Lambda uses the Hyperplane ENI model for VPC connectivity. Instead of creating a new ENI per execution environment (which caused 30–90 second cold starts), Lambda creates shared ENIs per unique (VPC, subnet, security group) combination at function creation time. Cold starts for VPC-attached functions are now typically under 1 second, matching non-VPC functions.

# Lambda function in VPC (CDK/CloudFormation-style config)
# The function gets an ENI in each specified subnet
{
  "VpcConfig": {
    "SubnetIds": [
      "subnet-0a1b2c3d",   // private subnet AZ-a
      "subnet-0e5f6g7h"    // private subnet AZ-b
    ],
    "SecurityGroupIds": ["sg-0123456789abcdef0"]
  }
}

Accessing RDS from Lambda

The recommended pattern for Lambda-to-RDS connectivity is RDS Proxy. Lambda functions can create thousands of concurrent database connections — each execution environment opens its own connection, and at high concurrency this exhausts the RDS connection pool (typically capped at a few hundred connections). RDS Proxy pools and multiplexes connections between Lambda and RDS, presenting a single connection endpoint to Lambda while managing a smaller connection pool to the actual database.

import psycopg2, os, boto3

# Connect via RDS Proxy endpoint (not directly to RDS)
# RDS Proxy handles connection pooling behind the scenes
conn = psycopg2.connect(
    host=os.environ['RDS_PROXY_ENDPOINT'],
    port=5432,
    database=os.environ['DB_NAME'],
    user=os.environ['DB_USER'],
    password=get_db_password(),   # from Secrets Manager
    sslmode='require'
)
Lambda in VPC requires internet access via NAT: A VPC-attached Lambda function loses its default internet access. To call external APIs, reach public AWS endpoints (S3, DynamoDB, SSM — unless using VPC endpoints), or pull packages, the subnets must have a NAT Gateway route. A common failure mode: Lambda is attached to a private subnet, tries to call boto3.client('s3'), and times out because there's no NAT and no S3 VPC endpoint.

12. Observability — Logs, Metrics, Traces

Lambda emits logs to CloudWatch Logs, metrics to CloudWatch Metrics, and traces to X-Ray automatically. Understanding each layer is important for diagnosing production issues.

CloudWatch Logs

Each function has a log group (/aws/lambda/function-name). Each execution environment produces a log stream. Lambda automatically logs the START, END, and REPORT lines for every invocation — REPORT includes: duration, billed duration, memory configured, max memory used, and init duration (for cold starts). Your function's print() or logging output goes to the same log stream.

import logging, json

# Structured logging — makes CloudWatch Insights queries effective
logger = logging.getLogger()
logger.setLevel(logging.INFO)

def lambda_handler(event, context):
    logger.info(json.dumps({
        "request_id": context.aws_request_id,
        "event_source": event.get("source", "unknown"),
        "record_count": len(event.get("Records", []))
    }))

CloudWatch Metrics

Lambda publishes key metrics per function: Invocations, Errors, Throttles, Duration (p50/p90/p99), ConcurrentExecutions, and IteratorAge (for streaming sources — how far behind the stream the function is). Build dashboards and alarms on Errors, Throttles, and for streaming sources, IteratorAge — high iterator age means the function is falling behind the stream.

# CloudWatch alarm on Lambda errors (boto3)
cloudwatch = boto3.client('cloudwatch')

cloudwatch.put_metric_alarm(
    AlarmName='LambdaErrorRate-my-function',
    MetricName='Errors',
    Namespace='AWS/Lambda',
    Dimensions=[{'Name': 'FunctionName', 'Value': 'my-function'}],
    Statistic='Sum',
    Period=300,         # 5-minute window
    EvaluationPeriods=1,
    Threshold=5,
    ComparisonOperator='GreaterThanOrEqualToThreshold',
    AlarmActions=['arn:aws:sns:us-east-1:123456789:ops-alerts']
)

X-Ray Tracing

Enable active tracing on your Lambda function to get distributed traces across Lambda invocations, SDK calls, and downstream services. X-Ray traces show time spent in each segment (function init, handler, AWS SDK calls), making it easy to identify whether latency is in your function code, in S3 calls, in downstream Lambda invocations, or in DynamoDB. For event-driven pipelines with multiple Lambda functions, X-Ray's service map shows the full call graph.

13. Security & IAM

Execution Role

Every Lambda function runs under an IAM execution role. The function assumes this role at invocation time and all AWS SDK calls use the role's permissions. Follow least-privilege: give the role only the permissions the function actually needs. Avoid attaching broad managed policies like AmazonS3FullAccess — scope to specific resource ARNs and specific actions.

# Minimal execution role policy for an S3-triggered Glue-launching function
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::my-raw-bucket/raw/*"
    },
    {
      "Effect": "Allow",
      "Action": ["glue:StartJobRun", "glue:GetJobRun"],
      "Resource": "arn:aws:glue:us-east-1:123456789:job/my-etl-job"
    },
    {
      "Effect": "Allow",
      "Action": ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents"],
      "Resource": "arn:aws:logs:us-east-1:123456789:log-group:/aws/lambda/my-function:*"
    }
  ]
}

Resource-Based Policy

In addition to the execution role (which grants the function permission to call AWS services), Lambda functions have a resource-based policy that grants other services permission to invoke the function. When you add an S3 trigger in the console, AWS automatically adds a resource-based policy statement allowing S3 to invoke the function. Review these policies — an overly permissive resource-based policy can allow unintended services or accounts to invoke your function.

Environment Variable Encryption

Lambda encrypts environment variables at rest using a Lambda-managed KMS key by default. For sensitive values, use a CMK and enable in-transit encryption (encrypt values before they reach the Lambda service). Better still, avoid storing secrets in environment variables entirely — retrieve them from Secrets Manager at init time.

Execution role scope creep: Lambda roles accumulate permissions over time as developers add new integrations without removing old ones. Periodically audit Lambda execution roles with IAM Access Analyzer or AWS CloudTrail to identify unused permissions and remove them. An over-privileged Lambda function is a significant blast radius in the event of a code injection vulnerability.

14. Common Gotchas and Anti-Patterns

1. Mutable global state across invocations: Execution environment reuse means global variables, cached objects, and /tmp files persist between warm invocations. A counter incremented in a global variable will have an unpredictable value on warm invocations. Always initialize per-invocation state inside the handler, not at module level.
2. Missing DLQ on async invocations: Async Lambda invocations retry up to 2 times on failure and then silently drop the event. Without a DLQ or on-failure destination, failed events disappear with no recovery path. Always configure an SQS DLQ or EventBridge on-failure destination for any async Lambda function processing important events.
3. Opening DB connections inside the handler: Opening a new database connection on every invocation (inside the handler) is expensive and exhausts DB connection limits at high concurrency. Initialize connections at module level so they are reused across warm invocations. Use RDS Proxy to absorb connection churn from cold starts and scale-out events.
4. Ignoring SQS partial batch failures: Without partial batch response support, a single failed message in a large SQS batch causes all messages to retry. Successfully processed messages are processed again unnecessarily. Enable ReportBatchItemFailures and return the batch item failure response structure from your handler.
5. Recursive S3 trigger loops: A Lambda function triggered by S3 writes output to the same bucket prefix it's triggered from. Each output file triggers a new invocation. The function scales to maximum concurrency, generates unexpected cost, and may corrupt or duplicate data. Always use prefix filters on S3 event notifications and validate that output paths are outside the trigger prefix.
6. Exceeding the 15-minute timeout for long operations: Lambda has a hard 15-minute execution limit. Designing a Lambda function to process a large batch of work in a single invocation is fragile — any unexpected slowdown or data volume increase pushes it over the limit. For work that might approach the limit, break it into smaller units using SQS, Step Functions, or fan-out patterns.
7. Over-allocating memory without measuring: Lambda CPU scales proportionally with memory. Doubling memory from 512 MB to 1 GB doubles CPU and roughly halves execution time for CPU-bound functions — often at lower total cost since billed duration drops. Under-allocating memory for compute-intensive functions wastes money. Use Lambda Power Tuning (open-source tool) to find the optimal memory setting for your function's cost/performance profile.

15. 10 Key Engineering Questions

Q1. What is a Lambda cold start and what factors affect its duration?
A cold start occurs when Lambda must create a new execution environment before invoking the function. Duration is affected by: deployment package size (larger zip = longer download), runtime choice (Python/Node cold-start in ~100–300ms; Java in 1–3s), dependency count and complexity, VPC attachment (slightly higher due to ENI setup), and amount of init-phase code. Mitigations: minimize package size, initialize SDK clients at module level, use Provisioned Concurrency for latency-sensitive functions, and prefer lighter runtimes when cold start matters.
Q2. What is the difference between reserved concurrency and provisioned concurrency?
Reserved concurrency is both a guarantee and a cap: it dedicates a slice of the account concurrency pool to a function and prevents it from exceeding that limit. Requests beyond the limit are throttled. Provisioned concurrency pre-warms a set number of execution environments, eliminating cold starts for those instances. Reserved concurrency costs nothing extra; provisioned concurrency bills continuously for the initialized capacity. Reserved concurrency is for isolation and caps; provisioned concurrency is for eliminating cold start latency.
Q3. How does Lambda handle failures differently for synchronous vs asynchronous invocations?
For synchronous invocations, errors are returned directly to the caller — no automatic retry; the caller handles retries. For asynchronous invocations, Lambda automatically retries up to 2 times (3 total attempts) with increasing delays. After all retries are exhausted, the event is sent to a configured DLQ or on-failure EventBridge destination, or silently dropped if none is configured. For SQS Event Source Mappings, failed batches return to the queue and are retried according to the queue's visibility timeout and redrive policy.
Q4. Why is execution environment reuse both a performance feature and a source of bugs?
Environment reuse amortizes cold start cost across multiple invocations — module-level initialization runs once and SDK clients are reused. However, it means global variables, /tmp files, and cached state persist between invocations on the same environment. A function that assumes a clean state (empty /tmp, zero counters, fresh connection) will behave incorrectly on warm invocations if that state was mutated by a previous invocation. Always initialize per-invocation state inside the handler, not at module level, and explicitly clean up /tmp if needed.
Q5. How would you prevent Lambda from exhausting RDS connection limits at high concurrency?
Use RDS Proxy. At high Lambda concurrency, each execution environment opens its own database connection — 500 concurrent Lambda invocations can attempt 500 simultaneous connections, overwhelming an RDS instance (typically capped at a few hundred). RDS Proxy pools connections between Lambda and RDS: Lambda connects to the Proxy, the Proxy multiplexes those into a smaller pool of real connections to RDS. Additionally, initialize the connection at module level (not inside the handler) so it's reused across warm invocations on the same environment.
Q6. What is a partial batch response in SQS + Lambda and why is it important?
Without partial batch responses, if a Lambda function fails while processing an SQS batch (even due to one bad message), all messages in the batch return to the queue for retry — including ones that were successfully processed, causing duplicate processing. With partial batch responses (ReportBatchItemFailures on the Event Source Mapping), the function returns a list of only the failed message IDs. Lambda deletes the successful messages and returns only the failures to the queue, preventing duplicate processing of good messages.
Q7. How does Lambda VPC networking work and what is required for a VPC-attached function to reach S3?
Lambda uses the Hyperplane ENI model — shared ENIs are created per (VPC, subnet, security group) combination rather than per execution environment, eliminating the old 30-90 second cold start penalty. A VPC-attached function loses default internet access. To reach S3, the function's subnet needs either: a NAT Gateway (for internet-routed S3 traffic), or an S3 VPC Endpoint (Gateway type, free, routes S3 traffic within AWS network). Without one of these, boto3 S3 calls time out silently.
Q8. When would you use a Lambda Layer vs a container image deployment?
Use Lambda Layers when: multiple functions share the same dependencies (layer is attached to all of them, avoiding duplicate packaging), dependencies are under the 250 MB uncompressed limit, and you want fast zip-based deployments. Use container images when: dependencies exceed 250 MB (container limit is 10 GB), you need custom system packages (OS libraries, binaries), the team already uses containers for other services and wants a unified workflow, or you need ML models bundled with the function. Container images have higher cold starts and require ECR management.
Q9. What Lambda metrics should you alarm on for a production event-driven pipeline?
Core alarms: Errors (absolute count or error rate) — signals function failures; Throttles — signals concurrency limits being hit, causing dropped or delayed processing; for SQS/Kinesis sources, IteratorAge — measures how far behind the stream the function is, indicating processing backlog. Secondary: Duration p99 — if approaching the 15-minute limit; ConcurrentExecutions — to detect unexpected traffic spikes. For async functions, monitor the DLQ depth separately to catch events accumulating after exhausting retries.
Q10. How does Lambda CPU allocation work and how can you use this to optimize cost?
Lambda CPU scales linearly with configured memory — at 1,769 MB you get one full vCPU; at 3,538 MB you get two full vCPUs. For CPU-bound functions, doubling memory halves execution time, and since Lambda bills duration × memory, the cost impact is neutral or better — you pay the same or less for faster execution. Use the open-source Lambda Power Tuning tool to benchmark your function across memory settings and find the optimal cost/performance point. Memory-bound functions benefit directly from more memory; I/O-bound functions (waiting on S3, RDS) see less benefit from additional CPU/memory.

16. Production Story Angles

At a large financial institution, Lambda served as the event-driven coordination layer in a multi-stage data pipeline. Raw data arrived in an S3 landing zone via partner file drops and internal system exports throughout the day — arrival times were irregular, not on a fixed schedule. Rather than polling for new files or running a scheduled Glue job every 15 minutes (which would either over-scan or introduce lag), an S3 event notification triggered a Lambda function within seconds of each file landing.

The Lambda function's role was intentionally narrow: validate that the file matched expected naming conventions and size thresholds, extract partition metadata from the S3 key path, and trigger a Glue ETL job with the file path and processing date as arguments. The function itself did no data transformation — it was an orchestration router, not a processor. This design kept the function fast (under 500ms per invocation), well within Lambda's timeout ceiling, and easy to test in isolation.

Concurrency management was critical. The downstream Glue cluster had a finite number of concurrent job slots. Without concurrency controls on the Lambda function, a burst of 50 files landing simultaneously would trigger 50 parallel Glue job starts — more than the cluster could handle. The Lambda function was configured with reserved concurrency of 5, effectively serializing Glue job launches. Excess S3 events queued in Lambda's async queue and were processed as Glue job slots freed up, with the full event backlog draining cleanly over time.

Failure handling used an SQS DLQ on the Lambda async invocation. If a file failed validation or the Glue job launch failed three times, the event landed in the DLQ. A separate Lambda function processed the DLQ on a schedule, extracted the failed file details, and posted a structured alert to the operations channel. The DLQ also served as the replay mechanism — once the root cause was resolved, messages in the DLQ could be re-driven to the main function without re-dropping the original files.

Observability was structured from day one. Every Lambda invocation logged a JSON structure including the request ID, S3 key, triggered Glue job run ID, and processing duration. CloudWatch Insights queries over this structured log data made it trivial to answer "what Glue job corresponds to this S3 file?" or "how many files arrived between 9am and 10am yesterday?" within seconds — without needing to cross-reference multiple systems.
