What Streamlit Is & The Execution Model

Streamlit turns a Python script into an interactive internal data app without requiring HTML, JavaScript, or a frontend framework. For data engineers, that makes it useful for operational dashboards, pipeline monitors, data quality consoles, forecast review screens, and lightweight tools that would otherwise become spreadsheet chaos.

The most important mental model is rerun behavior: every widget interaction reruns the script from top to bottom. That is simple and productive, but it changes how you think about side effects, expensive queries, API calls, and mutable state.

Key insight: a Streamlit app is not an event-driven web app in the React sense. It is a Python script that repeatedly re-executes and rebuilds the page.
Production gotcha: never put database writes, emails, job launches, or expensive refresh logic at top level unless guarded by a button, form, cache, or state check.
import streamlit as st

st.title("Pipeline Health")
region = st.selectbox("Region", ["ALL", "US", "EU", "APAC"])

if st.button("Run validation"):
    st.write(f"Running validation for {region}")

st.caption("Changing the selectbox reruns this script.")

Core Display Elements

The core Streamlit display functions cover most internal data tools. st.write() is the universal renderer for text, DataFrames, objects, and charts; st.dataframe() is best for interactive tables; st.metric() gives executive-style KPI cards; and st.json() is excellent for nested API responses, configuration payloads, and debug output.

For senior data engineering work, the question is not whether Streamlit can display something. The better question is whether the display makes operational state obvious: counts, freshness, null rates, failed partitions, late files, retry status, and SLA risk should be visible without scrolling through raw logs.

ElementBest useWatch for
st.write()Fast mixed outputCan become vague in production apps
st.dataframe()Read-only interactive tablesLarge data needs filtering first
st.metric()KPI cards and deltasNeeds clear units and time window
st.json()Nested configs and API responsesAvoid exposing secrets
Key insight: Streamlit is strongest when the app reduces operational ambiguity, not when it simply dumps a DataFrame onto a page.

Input Widgets & The Standard Filtering Pattern

Input widgets such as st.selectbox, st.multiselect, st.slider, st.text_input, and st.date_input become normal Python variables after each rerun. The standard pattern is simple: collect filter values at the top, apply them to a DataFrame or SQL query, then render the filtered result.

For small and medium datasets, filtering in pandas is fine. At scale, push filters into SQL, DuckDB, Athena, Snowflake, or the warehouse layer; otherwise the app quietly becomes a memory-heavy extract job pretending to be a dashboard.

import streamlit as st
import pandas as pd

df = pd.DataFrame({
    "region": ["US", "EU", "US"],
    "status": ["OK", "FAILED", "OK"],
    "records": [1000, 80, 1200]
})

regions = st.multiselect("Region", sorted(df["region"].unique()))
status = st.selectbox("Status", ["ALL", "OK", "FAILED"])

filtered = df.copy()
if regions:
    filtered = filtered[filtered["region"].isin(regions)]
if status != "ALL":
    filtered = filtered[filtered["status"] == status]

st.dataframe(filtered)
Production gotcha: do not pull 50 million rows into pandas just because Streamlit makes the UI easy. Filter close to the data.

Charts — st.line_chart vs Plotly

st.line_chart and st.bar_chart are excellent for quick trend visibility: row counts over time, latency by hour, error counts by pipeline, or forecast vs actual at a basic level. They keep the app short and readable, which matters for internal tools that should be maintained by data engineers, not frontend specialists.

Use st.plotly_chart when the chart needs precision: custom hover text, annotations, dual axes, confidence bands, thresholds, color control, or multiple traces. Plotly is the better choice for executive dashboards and model review screens where misreading a chart can trigger the wrong operational decision.

ChoiceUse whenTradeoff
st.line_chartFast time-series viewLimited formatting control
st.bar_chartSimple category comparisonNot ideal for dense labels
st.plotly_chartProduction-grade interactive chartMore code and chart config
import plotly.express as px
import streamlit as st

fig = px.line(
    df,
    x="run_date",
    y="records_out",
    color="pipeline_name",
    title="Pipeline Output Trend"
)
st.plotly_chart(fig, use_container_width=True)
Key insight: quick charts are for exploration; Plotly charts are for decisions.

st.cache_data & st.cache_resource

st.cache_data caches data-returning functions such as file reads, SQL result sets, API responses, and expensive transformations. It is ideal when the same inputs should return the same data, and the result can be safely copied between reruns. The ttl parameter controls staleness for dashboards where freshness matters.

st.cache_resource is for shared long-lived objects such as database connections, ML models, embedding clients, or API SDK clients. Treat it as the resource singleton layer; use it carefully because the object can be reused across sessions and reruns.

import streamlit as st
import pandas as pd
from sqlalchemy import create_engine

@st.cache_resource
def get_engine():
    return create_engine(st.secrets["warehouse_url"])

@st.cache_data(ttl=300)
def load_runs(region: str) -> pd.DataFrame:
    sql = "select * from pipeline_runs where region = %(region)s"
    return pd.read_sql(sql, get_engine(), params={"region": region})

runs = load_runs("US")
st.dataframe(runs)
Production gotcha: caching stale operational data can hide failures. Put freshness timestamps on the page and set TTL intentionally.

Layout — sidebar, columns, tabs, expander

Streamlit layout primitives are simple but powerful. Use st.sidebar for persistent filters, st.columns for KPI rows, st.tabs for separating views, and st.expander for details that matter during debugging but should not dominate the default screen.

A strong data engineering layout usually has filters on the left, KPIs at the top, status tables in the middle, and raw diagnostics tucked away. The goal is not visual flash; it is fast triage when a pipeline, SLA, or data product is unhealthy.

import streamlit as st

with st.sidebar:
    region = st.selectbox("Region", ["US", "EU", "APAC"])
    days = st.slider("Lookback days", 1, 30, 7)

c1, c2, c3 = st.columns(3)
c1.metric("Failed runs", 3, "+1")
c2.metric("Freshness lag", "12 min", "-4 min")
c3.metric("Rows loaded", "8.2M", "+6%")

tab1, tab2 = st.tabs(["Runs", "Diagnostics"])
Key insight: layout should mirror the operational workflow: detect, narrow, inspect, then act.

st.session_state — persisting state across reruns

st.session_state stores values across reruns for a single user session. It is the right place for multi-step workflows, selected row IDs, temporary form inputs, confirmation flags, and values that should survive widget interactions without being written to a database.

Use session state deliberately. It is not a durable store, not shared state across all users, and not a substitute for an audit table. For production tools that approve data changes or trigger jobs, persist the final action to a database with user, timestamp, input, and result.

import streamlit as st

if "approved_ids" not in st.session_state:
    st.session_state.approved_ids = set()

candidate_id = st.text_input("Candidate run ID")
if st.button("Approve") and candidate_id:
    st.session_state.approved_ids.add(candidate_id)

st.write("Approved this session:", sorted(st.session_state.approved_ids))
Production gotcha: session state disappears when the session resets. Anything audit-worthy belongs in a real persistence layer.

st.data_editor — editable DataFrames

st.data_editor allows users to edit tabular data directly in the app. For data engineers, this is useful for mapping tables, exception queues, manual overrides, threshold tuning, reference data, and small control tables that business users should manage without touching SQL.

The dangerous part is treating edited grid data as automatically trustworthy. Validate schema, allowed values, uniqueness, numeric ranges, referential integrity, and authorization before writing changes back to a database.

import streamlit as st
import pandas as pd

rules = pd.DataFrame({
    "source_system": ["billing", "crm"],
    "max_null_rate": [0.01, 0.03],
    "enabled": [True, True]
})

edited = st.data_editor(rules, num_rows="dynamic")

if st.button("Save rules"):
    if edited["source_system"].duplicated().any():
        st.error("source_system must be unique")
    else:
        st.success("Validated; ready to persist")
Key insight: editable DataFrames turn Streamlit from dashboard into control plane. That means validation and audit become mandatory.

Deployment & Security

Streamlit apps can run locally, in containers, on internal servers, behind a reverse proxy, or on managed platforms. For enterprise data engineering, the safest pattern is usually containerized deployment behind SSO, network controls, secrets management, and read-only default permissions.

Security deserves real attention because Streamlit apps often connect directly to warehouses, object stores, APIs, and operational databases. Use st.secrets or platform secret injection, avoid hardcoded credentials, limit database roles, and log user actions for anything that changes data or triggers jobs.

ConcernGood defaultWhy it matters
SecretsSecret manager or st.secretsPrevents credential leaks in Git
Database accessLeast-privilege service roleLimits blast radius
AuthenticationSSO or reverse proxy authStreamlit alone is not enterprise IAM
NetworkPrivate subnets or allowlistsKeeps internal tools internal
AuditWrite action log tableSupports incident review
Production gotcha: an internal app can still be a production system. If it writes data or triggers jobs, treat it like one.

Interview Q&A

Q: Why does Streamlit rerun the whole script, and why does that matter?
A: Streamlit uses a top-to-bottom script execution model, so every widget interaction rebuilds the app state from Python code. This keeps development simple, but it means expensive queries and side effects must be controlled. In production, I use caching, forms, buttons, and session state to avoid accidental repeated work.
Q: When would you use Streamlit instead of a BI tool?
A: I use Streamlit when the tool needs Python logic, model outputs, custom validation, operational controls, or workflow-specific interaction. BI tools are better for governed reporting and broad dashboard consumption. Streamlit is strongest for internal data apps that sit close to engineering workflows.
Q: How do st.cache_data and st.cache_resource differ?
A: st.cache_data caches returned data values like query results or transformed DataFrames. st.cache_resource caches shared objects like database engines, ML models, or API clients. The distinction matters because data should usually be copied safely, while resources are long-lived shared objects.
Q: How would you prevent a Streamlit app from overloading a warehouse?
A: I would push filters into SQL, use caching with a sensible TTL, limit default date ranges, and avoid loading large raw tables into pandas. I would also add query timeouts, warehouse resource limits, and clear freshness indicators. For high-traffic apps, I would pre-aggregate data upstream.
Q: What are the risks of using st.data_editor in a production workflow?
A: The grid makes edits easy, but the edited data is still user input and must be validated. I would check schema, ranges, uniqueness, allowed values, and authorization before persisting. Any write-back should also produce an audit record with user, timestamp, old value, and new value.
Q: How would you deploy Streamlit securely in an enterprise environment?
A: I would containerize the app, place it behind SSO or a reverse proxy, inject secrets through the platform, and use least-privilege database credentials. Network access should be restricted to internal users or private subnets. If the app can modify data or trigger pipelines, I would add audit logging and approval controls.
