Why Columnar Storage - the I/O argument

Parquet is built for analytical reads, where queries usually touch a small set of columns across many rows. A row-based file format forces the engine to read every field in every record even when the query only needs customer_id and amount. Parquet flips that layout: values from the same column are stored together, so the engine can read only the column chunks needed by the projection.

The benefit compounds at data lake scale. On S3, every unnecessary byte read is latency, network transfer, scan cost, and pressure on the execution engine. In Athena, Spark, Trino, Glue, and Databricks, Parquet is not just a storage format; it is part of the physical query plan.

Key insight: Parquet saves money and time because most analytical queries are narrow reads over wide datasets.
Gotcha: Parquet does not make bad data modeling disappear. If every query needs every column and most rows, the columnar advantage shrinks.

File Structure - row groups, column chunks, pages

A Parquet file is divided into row groups, which are horizontal slices of the dataset. Inside each row group, each column is stored as a column chunk. Each column chunk is then split into pages, which are the smaller encoded and compressed units the reader actually scans.

This three-level layout is why Parquet can combine row-level filtering with column-level projection. Row groups carry metadata such as row counts and column statistics; column chunks let readers skip unneeded columns; pages keep encoding and compression efficient without forcing the engine to decompress the entire file.

LayerWhat it meansWhy it matters
Row groupBatch of rows inside one fileUnit of predicate skipping
Column chunkOne column within one row groupUnit of column pruning
PageEncoded, compressed blockUnit of low-level reading
Key insight: row groups control how much data can be skipped; column chunks control how little data must be read.
Gotcha: extremely tiny row groups weaken scan efficiency, while extremely huge row groups reduce skip precision and memory friendliness.

Compression - Snappy vs Gzip vs Zstd

Parquet compression is applied per column chunk, not blindly across the entire file. That matters because values in the same column usually repeat, cluster, or follow similar patterns, which makes compression more effective than compressing mixed rows.

Snappy is the common default because it is fast and splittable in practice for analytical engines. Gzip usually compresses smaller but costs more CPU. Zstd is often the best modern balance for colder lake storage because it gives strong compression with better decompression behavior than Gzip in many workloads.

CodecStrengthTradeoff
SnappyFast read/write, widely supportedModerate compression ratio
GzipHigh compression ratioSlower CPU-heavy reads
ZstdStrong ratio with good speedCheck engine compatibility and defaults
Key insight: choose compression based on access pattern. Hot data often favors Snappy; cold analytical data often favors Zstd.
Gotcha: the smallest file is not always the cheapest query. CPU-heavy decompression can erase storage savings on frequent scans.

Encoding Schemes - dictionary, RLE, delta

Encoding is different from compression. Encoding changes how values are represented before compression happens. Parquet can use dictionary encoding for repeated strings or categories, run-length encoding for repeated values, and delta encoding for sequential integers or timestamps.

The engine usually chooses encodings automatically based on column type and observed data. A low-cardinality column such as region may become tiny through dictionary encoding. A sorted timestamp or increasing ID column may benefit from delta encoding because the differences between neighboring values are smaller than the original values.

-- Conceptual shape, not actual Parquet syntax
region values:  US, US, EU, US, APAC

dictionary:     0=US, 1=EU, 2=APAC
encoded values: 0, 0, 1, 0, 2

The repeated string payload is replaced by compact integer IDs.
Key insight: Parquet performs best when similar values sit together; sorting or clustering can improve encoding, compression, and skipping.
Gotcha: high-cardinality random strings rarely benefit from dictionary encoding and can bloat metadata or fall back to plain encoding.

Predicate Pushdown & Column Pruning

Column pruning means a query like SELECT id, amount reads only the column chunks for id and amount, not the full row. Predicate pushdown means filters such as WHERE region = 'US' are evaluated as close to the file scan as possible, using Parquet metadata before reading full values.

Parquet stores statistics such as min, max, and null counts per column per row group. If the row group metadata proves a filter cannot match, the engine can skip that row group entirely. This is why sorted data, good row group sizing, and selective predicates can produce dramatic speedups.

SELECT customer_id, amount
FROM lake.sales_parquet
WHERE order_date >= DATE '2026-01-01'
  AND region = 'US';

-- Reads only selected columns.
-- Skips row groups outside date/region statistics when possible.
Key insight: Parquet performance is metadata-driven. The fastest data is the data the engine never reads.
Gotcha: functions on filtered columns, poor stats, encryption layers, or unsupported reader settings can prevent pushdown.

Schema Evolution - what's safe, what breaks

Parquet stores schema metadata in the file footer, so every file carries its own view of the dataset shape. Adding a nullable column is usually safe because older files simply do not contain that column and readers can return null. Adding fields to nested structures can also be safe when engines agree on name-based resolution.

Breaking changes include renaming columns without table metadata support, changing incompatible types, altering nested structures carelessly, or mixing files written by engines with different timestamp or decimal conventions. In a lakehouse table, the table format layer such as Delta, Iceberg, or Hudi often manages schema evolution more safely than raw Parquet paths alone.

Key insight: raw Parquet files have schemas, but a table format gives you governance over many Parquet files as one logical table.
Gotcha: a folder full of Parquet files can contain incompatible schemas. The failure may only appear when a reader touches the wrong partition.

Parquet vs CSV vs Avro vs ORC

CSV is portable but weak for production analytics: no real types, no nested schema, no column pruning, and expensive parsing. Avro is row-oriented and strong for event streams, Kafka payloads, and schema-registry workflows. Parquet and ORC are columnar formats designed for analytical scans.

In most AWS and Spark data lake work, Parquet is the default practical choice because it is widely supported by Glue, Athena, EMR, Spark, Redshift Spectrum, Databricks, DuckDB, and pandas tooling. ORC can be excellent in Hive-heavy ecosystems, but Parquet usually wins on cross-platform interoperability.

FormatBest fitWeak spot
CSVHuman exchange, simple exportsNo schema or pruning
AvroStreaming records, schema evolutionRow scans for analytics
ParquetLake analytics, Spark, AthenaSmall files and schema drift
ORCHive-style columnar workloadsLess universal than Parquet
Key insight: use Avro for moving records, Parquet for querying datasets, and CSV only when interoperability beats performance.
Gotcha: converting CSV to Parquet without fixing types, nulls, timestamps, and partition layout only moves bad data into a better container.

Partitioning Strategy on S3

S3 partitioning is directory layout, not a database index. A common pattern is Hive-style paths such as s3://bucket/table/dt=2026-04-25/region=us/. Query engines can prune partitions before listing and reading files, which is powerful when filters align with partition keys.

Good partition keys are common filters with controlled cardinality. Dates, regions, source systems, and business domains can work well. High-cardinality keys such as user ID usually create too many directories and too many small files. Partitioning should reduce scans without exploding metadata and file counts.

s3://lake/sales/
  dt=2026-04-25/region=us/part-0001.parquet
  dt=2026-04-25/region=eu/part-0002.parquet
  dt=2026-04-26/region=us/part-0003.parquet

-- Best when queries filter on dt and region.
Key insight: partitioning eliminates whole directory branches; Parquet statistics eliminate row groups inside selected files.
Gotcha: over-partitioning creates metadata drag, slow listings, expensive planning, and tiny files that hurt every downstream engine.

Small Files & Parquet in Python

Parquet likes reasonably sized files. Thousands of tiny files create excessive S3 requests, scheduler overhead, metadata reads, and task startup cost. For Spark and Athena, a smaller number of medium-to-large files is usually better than one file per event, per user, or per micro-batch.

Python can write Parquet through pandas, PyArrow, Polars, DuckDB, and Spark. For small local work, pandas with PyArrow is convenient. For production lake writes, control file size, compression, partitioning, schema, and append behavior explicitly; do not let every job emit whatever shape happens to fall out of a DataFrame.

import pandas as pd

# Small local write; production jobs should control layout upstream.
df.to_parquet(
    "sales.parquet",
    engine="pyarrow",
    compression="zstd",
    index=False
)

# Read only selected columns when possible.
cols = ["customer_id", "amount", "order_date"]
df2 = pd.read_parquet("sales.parquet", columns=cols)
Key insight: Parquet is a file format, not a compaction strategy. Your pipeline must still manage file size and layout.
Gotcha: appending many small Parquet files from Python feels harmless in dev, then becomes a query-planning tax in production.

Interview Q&A

Q: Why is Parquet usually better than CSV for analytical workloads?
A: Parquet stores typed data in a columnar layout, so engines can read only required columns and use statistics to skip row groups. CSV requires parsing text and usually scanning every field. The practical difference is lower I/O, lower scan cost, and better CPU efficiency on wide datasets.
Q: What are row groups, and why do they matter?
A: Row groups are horizontal chunks of rows inside a Parquet file. Each row group contains column chunks plus statistics such as min and max values. Good row group sizing helps readers skip data while keeping reads large enough to be efficient.
Q: How do predicate pushdown and partition pruning differ?
A: Partition pruning skips directory paths before files are read, usually from S3 layout such as dt=.... Predicate pushdown works inside selected files by using Parquet metadata and statistics. Strong lake design uses both: partitions narrow the file set, Parquet stats narrow the row groups.
Q: When would you choose Snappy, Gzip, or Zstd?
A: Snappy is a safe default for hot data because it is fast and broadly supported. Gzip is useful when storage reduction matters more than CPU. Zstd is often preferred for colder analytical data because it offers a strong compression ratio with better performance characteristics than Gzip in many systems.
Q: What causes Parquet schema evolution problems in a data lake?
A: Problems appear when files in the same logical table carry incompatible schemas, renamed columns, conflicting types, or inconsistent timestamp and decimal handling. Adding nullable columns is usually safe, but changing meaning or type is risky. A table format such as Iceberg or Delta helps enforce schema rules across files.
Q: Why are small Parquet files bad on S3?
A: Each file adds object listing, footer reads, metadata handling, and task scheduling overhead. A query over 20,000 tiny files may spend more time planning and opening objects than scanning data. Compaction is often as important as compression for lake performance.
