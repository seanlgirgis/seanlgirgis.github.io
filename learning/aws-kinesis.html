Kinesis Data Streams — shards, partition keys, retention

Kinesis Data Streams is the low-latency stream service in the Kinesis family. Producers write records into a stream, each record has a partition key, and Kinesis hashes that key to decide which shard receives the record. Within a shard, records receive sequence numbers and preserve ordering for that shard.

Shards are both the ordering boundary and the capacity boundary. A user, device, account, sensor, or tenant ID may be a good partition key when you need per-entity ordering, but the same choice can create hot shards if a few entities dominate traffic.

Key insight: Kinesis gives strong ordering only within a shard. If two records land in different shards, the service is not promising global ordering.
Production gotcha: default retention is commonly treated as short replay storage, not archival storage. Extend retention when downstream consumers may lag, but send durable history to S3 when replay windows matter.

Shard Sizing & Capacity Math

Shard sizing starts with throughput, not record count. A provisioned shard supports roughly 1 MB/sec or 1,000 records/sec for writes, and 2 MB/sec for reads with standard consumers. Required shard count is the max of the write-throughput calculation, write-record-rate calculation, and read-throughput calculation.

For senior-level design, the math must include headroom. Real streams have uneven keys, retry bursts, producer batching behavior, and consumer lag. A stream sized to exactly average traffic is already undersized.

required_write_shards = max(
  ceil(write_mb_per_sec / 1),
  ceil(write_records_per_sec / 1000)
)

required_read_shards = ceil(total_read_mb_per_sec / 2)

required_shards = max(required_write_shards, required_read_shards)
# Add headroom for burst, skew, and replay load.
A clean sizing estimate uses peak sustained rate, not daily average. Daily average hides traffic spikes and hot partitions.
If one partition key exceeds one shard of write capacity, adding more shards may not help until you change or fan out the partition key strategy.

Enhanced Fan-Out vs Standard Polling

Standard consumers poll shards using shared read throughput. This is simple and cost-friendly for one or two consumers, but multiple independent consumers compete for the same 2 MB/sec per shard read pool and can increase read latency.

Enhanced Fan-Out registers consumers and gives each registered consumer dedicated read throughput per shard. It is useful when multiple downstream systems need low-latency reads from the same stream, such as fraud detection, real-time dashboards, lake ingestion, and alerting.

ModeBest fitTradeoff
Standard pollingFew consumers, moderate latency toleranceShared read capacity per shard
Enhanced Fan-OutMany consumers or low-latency fan-outHigher cost and consumer registration
Lambda event sourceServerless processingBatch tuning and retry behavior matter
Enhanced Fan-Out is a latency isolation tool. It prevents one consumer from starving another when both read the same shard set.
Do not pay for Enhanced Fan-Out by default. Use it when shared polling is causing measurable contention, lag, or latency problems.

Kinesis Firehose — delivery, buffering, format conversion

Kinesis Data Firehose is the managed delivery service. Instead of writing consumer code, you configure delivery to targets such as S3, Redshift, OpenSearch, or partner destinations. It is a strong fit for data lake ingestion, log delivery, and analytics pipelines where transformation needs are light.

Firehose buffers records by size and time before delivery. Buffering improves throughput and file sizes, but it also introduces latency. For lakehouse ingestion, Firehose can convert JSON-style input into Parquet and apply compression such as Snappy to reduce storage and scan cost.

Firehose is not a general-purpose stream processor. It is a managed delivery pipe with buffering, transformation hooks, compression, and destination handling.
Small buffer settings create tiny files in S3. Tiny files punish Athena, Glue, Spark, and downstream compaction jobs.

Kinesis Analytics & Managed Flink

Kinesis Data Analytics evolved into Amazon Managed Service for Apache Flink for serious stream processing. This is where windowing, joins, stateful operators, late events, watermarks, and exactly-once-style processing concerns become central design topics.

Use Managed Flink when the logic is more than delivery: aggregating metrics per sliding window, joining event streams to reference state, detecting patterns, or maintaining keyed state over time. Compared with Lambda, it is heavier operationally but better for continuous stateful computation.

Kinesis Streams moves events. Firehose delivers events. Managed Flink computes over events.
Stateful streaming failures are rarely just code failures. Check checkpointing, state backend size, watermark strategy, parallelism, and downstream sink idempotency.

Kinesis vs Kafka vs SQS — decision guide

Kinesis and Kafka are stream platforms. SQS is a queue. That distinction matters: streams retain ordered records for replay by multiple consumers, while queues distribute messages for work processing and remove them after successful consumption.

Kinesis is attractive when AWS-native operations and managed scaling are more important than Kafka ecosystem depth. Kafka or MSK becomes more compelling when you need Kafka protocol compatibility, mature ecosystem tooling, long-standing platform patterns, or portability beyond AWS.

ChoiceUse whenAvoid when
KinesisAWS-native stream ingestion and replayYou need Kafka protocol/tooling compatibility
Kafka/MSKBroad ecosystem, many topics, portable stream platformYou want the simplest managed AWS ingestion path
SQSDecoupled work queue and task distributionYou need replay by multiple independent consumers
The interview shortcut: Kinesis is for ordered replayable event streams; SQS is for distributing work; Kafka is the larger open stream ecosystem.
Choosing SQS because it is simpler can backfire when the real requirement is replay, fan-out, or ordered event history.

Lambda as Consumer — patterns and gotchas

Lambda can consume Kinesis records through an event source mapping. AWS polls the stream, batches records, invokes the function, and checkpoints progress when batches succeed. This is powerful for lightweight enrichment, validation, routing, alerting, and small ETL steps.

The operational edge is failure handling. A single bad record can block progress for its shard if the batch keeps failing. Tune batch size, maximum batching window, retry behavior, bisect-on-error, partial batch response, and destinations based on the cost of duplication versus delay.

{
  "batchSize": 100,
  "maximumBatchingWindowInSeconds": 5,
  "bisectBatchOnFunctionError": true,
  "maximumRetryAttempts": 3,
  "parallelizationFactor": 2
}
Lambda plus Kinesis is excellent when processing is stateless or lightly stateful and each event can be handled idempotently.
Never assume exactly-once side effects. Design writes to S3, DynamoDB, databases, and APIs to tolerate retries and duplicate records.

Ordering, Resharding & Hot Shards

Ordering depends on partition-key placement. All records with the same partition key go to the same shard at a point in time, which preserves per-key order but concentrates load. Resharding changes shard topology and capacity, but it does not magically fix a single key that overwhelms one shard.

Hot shards usually show up as throttled writes, increasing iterator age, uneven consumer lag, or one shard carrying much more traffic than the others. Common remedies include partition-key salting, key redesign, aggregation, producer-side batching, or splitting very large tenants across logical keys.

Shard count solves aggregate capacity. Partition-key design solves distribution.
Salting improves distribution but weakens simple per-entity ordering. Only salt keys when the downstream design can tolerate or reconstruct order.

Monitoring & Cost Model

Production Kinesis monitoring should focus on throughput pressure, throttling, consumer lag, and delivery failures. Watch write throttles, read throttles, iterator age, incoming bytes, incoming records, failed put records, Firehose delivery errors, and downstream sink latency.

The cost model depends on mode and shape: provisioned shards or on-demand streams, PUT payload units, Enhanced Fan-Out consumers, extended retention, Firehose ingest and conversion, and Managed Flink compute. The cheapest design is usually the one that avoids over-fanning, tiny files, unnecessary retention, and runaway downstream retries.

SignalWhat it suggestsCommon action
Write throttlesShard write capacity or hot key issueAdd shards or redesign partition key
Iterator age risingConsumer falling behindScale consumer, tune batch, inspect failures
Firehose delivery failuresDestination or transform issueCheck IAM, schema, target health, error prefix
Tiny S3 filesBuffering too aggressiveIncrease buffer size/time or compact later
Iterator age is the senior-engineer smoke alarm. It tells you when the stream is becoming a backlog, not just a pipe.
Cost surprises often come from fan-out, retries, retained data, and downstream inefficiency rather than the base stream alone.

Interview Q&A

Q: How would you choose a partition key for a high-volume Kinesis stream?
A: I would start from the ordering requirement, then test distribution. If per-customer order matters, customer ID may be right, but I would inspect whether a few customers dominate traffic. If skew is high, I would consider composite keys, salting, or separating high-volume tenants while being explicit about the ordering tradeoff.
Q: A Kinesis consumer is falling behind. What do you check first?
A: I check iterator age, read throttles, Lambda or consumer errors, batch duration, and downstream sink latency. If the stream is healthy but the consumer is slow, I tune batch size, parallelization, and downstream writes. If one shard is worse than others, I suspect hot partition keys.
Q: When is Enhanced Fan-Out worth the cost?
A: It is worth it when multiple consumers need independent low-latency reads from the same stream and standard polling causes contention. I would justify it with observed read throttling, lag, or latency SLO pressure. For one low-volume consumer, standard polling is usually enough.
Q: Why might Firehose be better than Data Streams for lake ingestion?
A: Firehose removes consumer-code ownership for simple delivery pipelines. It handles buffering, retries, S3 delivery, optional transformation, compression, and format conversion. If the requirement is mostly landing data into S3 or Redshift, Firehose is often cleaner than building and operating custom consumers.
Q: How do you handle bad records in a Lambda Kinesis consumer?
A: The function should validate records, isolate poison messages, and write failures to a durable error location. I would use bisect-on-error or partial batch response where appropriate, cap retries, and make downstream writes idempotent. The key is avoiding one bad record blocking a shard indefinitely.
Q: How would you explain Kinesis vs SQS to a stakeholder?
A: Kinesis is an event stream: records can be replayed and multiple consumers can read the same history. SQS is a work queue: messages are distributed to workers and removed after processing. If they need replay, ordering by key, or independent consumers, I lean Kinesis; if they need task decoupling, I lean SQS.

2 MB/s out
