Metrics — namespaces, dimensions, standard vs high-resolution

CloudWatch Metrics are time-series measurements organized by namespace, metric name, dimensions, timestamp, and unit. AWS services publish metrics into namespaces like AWS/Lambda, AWS/Glue, AWS/ECS, and AWS/States; your applications can publish custom metrics into your own namespace using PutMetricData or Embedded Metric Format.

Dimensions are the identity of the metric. JobName, FunctionName, ClusterName, ServiceName, and StateMachineArn let you slice the same metric by resource. Standard metrics usually have one-minute resolution. High-resolution custom metrics can be stored at one-second granularity, useful for bursty workloads, but they increase cardinality and cost pressure quickly.

aws cloudwatch put-metric-data \
  --namespace "DataPlatform/Pipelines" \
  --metric-name "RowsProcessed" \
  --dimensions Pipeline=orders_daily,Stage=transform \
  --value 1842000 \
  --unit Count
Key insight: a metric without useful dimensions is almost a dead metric. Design dimensions around how engineers debug incidents: pipeline, stage, environment, region, and workload owner.
Gotcha: high-cardinality dimensions such as request ID, file name, user ID, or batch ID can explode custom metric cost and make dashboards noisy. Put those in logs, not metric dimensions.

Alarms — static, anomaly detection, composite

CloudWatch Alarms evaluate metric data against a condition and move between OK, ALARM, and INSUFFICIENT_DATA. Static threshold alarms are best for hard limits: disk full, DLQ depth above zero, Glue job failure count, Lambda errors, or Kinesis iterator age. Anomaly detection alarms learn normal ranges and alert when the metric breaks its expected pattern.

Composite alarms combine multiple alarms with boolean logic. They are excellent for reducing noise: alert only when error rate is high and request volume is meaningful, or when a data pipeline is late and the upstream source has already delivered files. Alarm actions can notify SNS, trigger Auto Scaling, stop or recover EC2 instances, or connect into incident tooling.

Alarm typeBest useWeak spot
Static thresholdKnown operational boundaryBad for seasonal traffic
Anomaly detectionMetrics with patternsNeeds stable history
CompositeNoise reductionCan hide root cause if over-nested
Senior pattern: alert on symptoms users and pipelines care about, then dashboard the causes. Page on missed SLA, failed partition publish, growing DLQ, or stale data; investigate CPU and memory afterward.
Gotcha: INSUFFICIENT_DATA is not always harmless. For heartbeat metrics, missing data may be the actual failure. Treat missing data as breaching when absence means silence from a pipeline.

CloudWatch Logs — groups, streams, retention

CloudWatch Logs stores application and service logs in log groups, with log streams representing producers such as Lambda instances, ECS tasks, Glue job runs, Step Functions executions, or EC2 agents. A log group is the operational boundary where you set retention, permissions, metric filters, subscription filters, and export behavior.

Retention matters. The default behavior can keep logs indefinitely unless changed, which is dangerous for verbose ETL workloads. Keep hot troubleshooting logs in CloudWatch for a practical window, then ship long-term audit or analytical logs to S3 where lifecycle policies and Athena are cheaper.

{
  "timestamp": "2026-04-25T14:02:31Z",
  "level": "ERROR",
  "pipeline": "orders_daily",
  "stage": "transform",
  "batch_id": "2026-04-25",
  "error_type": "SchemaDrift",
  "message": "column customer_tier missing"
}
Structured JSON logs are worth the discipline. They turn text search into reliable fields, filters, aggregations, and metric extraction.
Gotcha: logs are not free storage. Debug-level Spark, Glue, or container logs can become a tax on every pipeline run unless retention and sampling are intentional.

Logs Insights — query syntax and pipeline debugging patterns

CloudWatch Logs Insights is the fast operational query layer for CloudWatch Logs. The core syntax is pipe-based: choose fields, filter events, aggregate with stats, sort, and limit. For data engineers, it is especially useful for finding failing stages, slow batches, schema drift, retry storms, and partial loads across many log streams.

The trick is to log stable fields consistently. A pipeline that emits pipeline, stage, batch_id, duration_ms, rows_read, rows_written, and error_type becomes debuggable without cracking open every service console.

fields @timestamp, pipeline, stage, batch_id, error_type, message
| filter level = "ERROR"
| stats count(*) as errors by pipeline, stage, error_type
| sort errors desc
| limit 20
Good pipeline logs answer three questions quickly: what failed, which data slice was affected, and whether the failure is isolated or systemic.
Gotcha: unbounded Logs Insights queries can scan a lot of data. Narrow the time range first, then filter by log group, pipeline, environment, and severity.

Dashboards & Metric Math

CloudWatch Dashboards combine metrics, alarms, text, and Logs Insights widgets into operational views. For data platforms, the best dashboards are not vanity boards. They show freshness, throughput, failure rate, queue depth, backlog age, retry count, cost-sensitive volume, and the health of dependencies such as Glue, Lambda, ECS, Step Functions, Kinesis, SQS, and S3.

Metric Math lets you derive useful signals without publishing another metric. Common examples include error rate, success percentage, average rows per second, backlog drain time, or cost proxy metrics such as bytes processed per successful batch.

# Example metric math expression
# errors / invocations * 100
m1 = AWS/Lambda Errors
m2 = AWS/Lambda Invocations
e1 = 100 * m1 / MAX([m2, 1])
Dashboard by decision, not by service. A senior operations dashboard should tell you whether to wait, rollback, rerun, scale, or escalate.
Gotcha: averages lie during incidents. Pair averages with p95/p99, max, backlog age, and count-based widgets so spikes do not disappear into smooth lines.

EMF & Container Insights

Embedded Metric Format lets applications write structured JSON logs that CloudWatch extracts into metrics. This is cleaner than scattering PutMetricData calls across Lambda, ECS, and batch code. For data engineering workloads, EMF is a strong fit when every job run needs to emit rows processed, files processed, validation failures, batch duration, and stage-level counters.

Container Insights collects task, pod, node, CPU, memory, disk, and network telemetry for ECS, EKS, and Kubernetes-style workloads. It helps answer whether a pipeline container is compute-bound, memory-bound, network-bound, or simply stuck waiting on an external dependency.

CapabilityUse it forWatch out for
EMFApp-level business metrics from logsDimension cardinality
Container InsightsTask and cluster healthAdditional metrics cost
Metric filtersCount specific log patternsBrittle with plain text logs
EMF is a bridge between logs and metrics: keep rich event context in the log line, while extracting the small set of counters worth alarming on.
Gotcha: Container Insights is not a substitute for application instrumentation. CPU and memory can look fine while the pipeline writes corrupt data or silently skips a partition.

Data Pipeline Monitoring Patterns

Data pipelines need monitoring beyond infrastructure health. A server can be green while the business table is stale, missing a partition, double-loaded, or loaded with zero rows. Monitor freshness, completeness, volume, latency, error rate, retry count, schema drift, and downstream publish status.

For batch pipelines, emit one run-level event and stage-level metrics. For streaming pipelines, track lag, iterator age, watermark delay, DLQ depth, consumer errors, and output throughput. For warehouse pipelines, track source-to-target row counts, rejected records, merge counts, and late-arriving records.

SignalQuestion answeredExample alarm
FreshnessIs data late?No success heartbeat by SLA time
CompletenessDid all expected slices arrive?Missing partition or file count
VolumeIs today plausible?Rows outside historical band
QualityCan consumers trust it?Validation failure rate above threshold
BacklogAre we falling behind?Queue age or iterator age rising
The best data alarms are business-facing: stale customer table, missing billing partition, abnormal order volume, or failed quality gate. Service alarms are supporting evidence.
Gotcha: alerting on every failed retry creates noise. Alert when retries are exhausted, SLA is threatened, data is stale, or the failure affects published outputs.

CloudTrail — API audit trail and compliance

CloudTrail records AWS account activity: who called what API, from where, against which resource, and whether it succeeded. CloudWatch tells you how systems behave; CloudTrail tells you who changed the system. That distinction matters during incident response, compliance review, access investigation, and root-cause analysis after a production change.

Management events capture control-plane activity such as creating roles, changing policies, updating security groups, deleting buckets, or modifying Glue jobs. Data events capture high-volume object-level or resource-level activity such as S3 object access and Lambda invocations, and they must be enabled carefully because they can generate significant volume.

{
  "eventSource": "iam.amazonaws.com",
  "eventName": "AttachRolePolicy",
  "userIdentity": { "type": "AssumedRole" },
  "sourceIPAddress": "203.0.113.10",
  "requestParameters": {
    "roleName": "glue-prod-role",
    "policyArn": "arn:aws:iam::aws:policy/AdministratorAccess"
  }
}
CloudTrail is your audit backbone. In a serious incident, the key question is often not only what broke, but who or what changed the environment before it broke.
Gotcha: CloudTrail is regional unless configured as an organization-wide, multi-region trail. Single-account trails leave blind spots in mature AWS environments.

Querying CloudTrail with Athena & Cost Control

CloudTrail logs are commonly delivered to S3, which makes Athena a natural query layer for investigations and audits. Partition by account, region, and date when possible. Without partitioning and compression awareness, a simple investigation can scan far more data than expected.

Athena is strong for questions like: who changed this IAM role, who deleted this S3 object, which access key called this API, what changed before the Glue pipeline started failing, or which accounts used a deprecated service. For repeated security analysis, consider curated CloudTrail tables, partition projection, lifecycle policies, and narrower event selectors.

SELECT eventtime, eventsource, eventname,
       useridentity.arn AS actor,
       sourceipaddress
FROM cloudtrail_logs
WHERE region = 'us-east-1'
  AND eventsource = 'iam.amazonaws.com'
  AND eventname IN ('CreateRole', 'AttachRolePolicy')
  AND eventtime >= '2026-04-25T00:00:00Z'
ORDER BY eventtime DESC
LIMIT 50;
Cost control pattern: keep raw CloudTrail immutable in S3, query recent partitions for investigations, and build smaller curated tables for common audit questions.
Gotcha: enabling all data events everywhere can create a firehose of audit logs. Scope data events to sensitive buckets, critical Lambda functions, and compliance-relevant resources.

Interview Q&A

Q: How do CloudWatch and CloudTrail differ in a production AWS environment?
A: CloudWatch is observability: metrics, logs, alarms, dashboards, and operational signals. CloudTrail is audit: API activity, identity, source IP, request parameters, and control-plane history. In an incident, CloudWatch shows the symptom timeline, while CloudTrail helps identify the change or actor that triggered it.
Q: What dimensions would you use for custom data pipeline metrics?
A: I would use stable operational dimensions such as environment, pipeline, stage, dataset, region, and owner. I would avoid high-cardinality values like file name, request ID, row key, or batch UUID. Those belong in structured logs so they remain searchable without exploding metric cost.
Q: When would you use anomaly detection instead of a static threshold alarm?
A: I would use anomaly detection when the metric has a stable pattern but the acceptable value changes by time of day, weekday, or workload cycle. Examples include request volume, rows processed, or normal batch duration. I would still use static thresholds for hard limits such as DLQ depth, missing heartbeat, or disk saturation.
Q: What does good logging look like for an ETL or ELT pipeline?
A: Good pipeline logs are structured JSON and include pipeline, stage, run ID or batch date, input count, output count, duration, severity, and error type. They make Logs Insights queries predictable and allow metrics to be extracted reliably. Plain text logs are acceptable for humans, but weak for scalable operations.
Q: How would you monitor whether a data product is healthy?
A: I would start with user-visible signals: freshness, completeness, volume reasonableness, quality checks, and publish success. Then I would connect those to service-level causes such as Glue failures, Lambda errors, Step Functions failures, Kinesis lag, SQS backlog, and warehouse load errors. The goal is to page on broken data, not just busy infrastructure.
Q: How do you keep CloudTrail analysis cost under control?
A: Store CloudTrail in S3 with lifecycle rules, query it through Athena using partitions and narrow time ranges, and avoid broad scans across all accounts and regions. Enable high-volume data events selectively. For frequent audit questions, build curated tables or views that reduce repeated scanning of raw logs.

Custom metric stored below one-minute resolution; useful for bursts, risky for cost and cardinality.
Static alarm
Best for hard boundaries: DLQ depth, error count, missed heartbeat, iterator age, or failed jobs.
Anomaly alarm
Learns normal metric bands; useful for seasonal pipeline volume or latency patterns.
Composite alarm
Combines alarms with logic to reduce noise and page only on meaningful conditions.
Log group
CloudWatch Logs boundary for retention, permissions, filters, exports, and subscriptions.

Individual producer stream, commonly a Lambda instance, ECS task, Glue run, or EC2 agent.

Operational query layer using fields, filter, stats, sort, and limit over CloudWatch Logs.

Structured log format that CloudWatch extracts into custom metrics.

ECS, EKS, and Kubernetes workload telemetry for CPU, memory, network, disk, and task health.
CloudTrail
